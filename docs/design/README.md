# Telegram 多租户内容监控平台 — 文档集

这份文档集按**读者与用途**编排，不按写作顺序编排。
每一层回答一个不同的问题，稳定性不同，因此更新节奏也不同。

| 层 | 回答什么 | 稳定性 | 谁读 |
|---|---|---|---|
| [`spec/`](spec/) | 现在是什么 | 高 | 所有人。单一事实源，不留历史 |
| [`eng/`](eng/) | 怎么被强制 | 中 | 动工的人。卡口优先于散文 |
| [`ops/`](ops/) | 怎么跑起来 | 中 | 部署与值班的人 |
| [`decisions/`](decisions/) | 为什么 | 冻结 | 想推翻某个决定的人 |
| [`plan/`](plan/) | 接下来做什么 | 低 | 排期与验收。**会过期** |

---

## 三条硬规则

```text
1 spec/ 是单一事实源。数字（工期、配额、容量）只在一处定义
2 decisions/ 只追加。推翻旧决策的方式是新写一份并在旧的标 已被取代
3 plan/ 的任何数字都不得被 spec/ 引用（反向可以）—— 否则计划过期会污染规格
```

第 3 条是这次重编排的主要动机。上一版文档集里工期基数出现过三套并存的值，
根因就是规格文档引用了计划文档的数字，而计划改了规格没跟着改。

## 四条阅读路径

**第一次接手这个项目** —— 按序读四份，约 1 小时：

```text
spec/00 → spec/01 → spec/02 → spec/05
范围      能力      结构      为什么安全设计是这个样子
```

**要动工** —— 读 `eng/` 全部五份，再读 `spec/03` 与 `spec/07`。
`eng/04` 的九条卡口是验收基线，写代码前先知道什么会被 CI 挡住。

**要改一个决策** —— 先在 `decisions/` 找到对应的 ADR。
如果它还没有被取代，那就是当前生效的理由。
推翻它要写一份新 ADR，不要改旧的，也不要只改 `spec/`。

**要上线** —— `ops/01` 是就绪清单。
其中「一次真实恢复演练」不可省，也无法自动化。

## 当前局限

- **还没有一行代码。** 这是一份可执行规格，不是对已有系统的描述
- **`eng/04` 描述的卡口目前全部是文本，可执行的有 0 条。**
  文档到代码的转化率是这个项目最大的风险，不是文档完整性
- `spec/` 里带日期的实测结论均在本地容器复现过，测完即销毁，
  没有留下可重跑的脚本。重新验证需要重搭环境
- 云成本、定价、中转比例三项依赖上线后的实测，当前值是估算
