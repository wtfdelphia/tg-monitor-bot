# 工程约定

本文是**工程纪律的唯一定义处**：crate 划分、依赖版本、错误类型、
日志脱敏、仓库约定，以及汇总在 §八 的代码评审清单。
它是写第一行代码之前的施工图。

架构上的 7 个组件见 `../spec/02-总体架构.md` §一，
隔离机制的原理与实测证据见 `../spec/05-安全与租户隔离.md`，
CI 卡口的完整清单见 `04-CI门禁.md`。本文只写「代码怎么组织、怎么写」。

## 零、动工前的环境事实（2026-09-20 实测，2026-09-21 复核）

```text
rustc 1.98.1 (2026-09-01)   ✓
cargo 1.98.1                ✓
docker 29.1.3               ✓
psql 17.11                  ✓ 已装（2026-09-21）。用户级安装，非系统包：
                              ~/opt/pgdg17/，env.sh 已挂进 ~/.bashrc
仓库工程文件                  零。无 Cargo.toml / 无 .rs / 无 .sql / 无 compose
.gitignore                  Python 模板（见 §七，必须换）
```

> **`psql` 这一项从 ✗ 转 ✓，但装法有一处要知道**：它是把 PGDG 的 deb
> 解包到 `$HOME`，没有系统级注册。真实二进制在
> `usr/lib/postgresql/17/bin`，而 `usr/bin` 下是 Debian 的 `pg_wrapper`
> perl 包装脚本 —— 那个包装要读集群配置，用户级安装下读不到。
> 所以 `env.sh` 里 lib 目录必须排在 `usr/bin` 之前，
> 否则 `psql` 能找到却跑不起来。
>
> 对 CI 的含义：**CI 里不能假设 `psql` 存在**。本机的可用性来自
> `~/.bashrc`，CI runner 没有这一步 —— `04-CI门禁.md` 里凡是用
> `psql` 的断言都要自带安装步骤或走容器内 `psql`。

这份清单有一个直接后果：CI 的编译期 SQL 校验
（`04-CI门禁.md` 的 `cargo sqlx prepare --check`）
要求**第一行业务代码之前就有一个可连、且 RLS 已配好的库**。
所以「工程骨架」与「数据库迁移」两件事必须交错进行，
不是可以并列排期的两个独立任务 —— 排期见 `../plan/00-里程碑与工期.md`。

## 一、workspace 与 crate 划分

`../spec/02-总体架构.md` §一 划了 7 个组件。**不要做成 7 个 crate**，
1 人全职下那是净负担。

```text
tg-monitor/
├── Cargo.toml              # workspace root，统一依赖版本
├── crates/
│   ├── core/               # 领域类型：newtype、错误、配置、AuthContext
│   ├── db/                 # sqlx、tenant_tx、Repo trait 与实现、migrations
│   ├── tg/                 # grammers + teloxide 封装，raw invoke 收敛在此
│   └── app/                # 全部业务逻辑：fanout / rule / delivery / control
└── bins/
    └── tgm/                # 单二进制 + subcommand
```

**单二进制多 subcommand**，而不是 7 个 bin：

```bash
tgm serve --role control-plane     # axum
tgm serve --role bot-gateway
tgm serve --role mtproto-worker
tgm serve --role fanout|rule|delivery
tgm migrate                        # 迁移
tgm audit-rls                      # 跑 RLS 静态审计（见 04-CI门禁.md）
tgm openapi [--check]              # 导出/校验 OpenAPI 契约（见 04-CI门禁.md）
```

三个理由：首发锁定的部署形态就是单机跑多进程
（`../ops/00-部署与运行时.md`），subcommand 天然支持；
共享编译产物，CI 时间减半；关键路径不可压缩，
少一个 crate 边界就少一轮类型搬运。

> **`tg/` 单独成 crate 的理由不是整洁**，是依赖退出路径：
> grammers 是 0.x + bus factor 低（`../spec/08-账号接入.md` §1.1），
> 把 raw invoke 收敛在一个 crate 里，将来 fork 或替换时改动面可控。
> 这是唯一一个「为将来」而设的边界。

### 2.1 两处必须避开的选型陷阱

**① `fred` 不要用。** 最后提交 2025-02-26，停更约 1.5 年。
改用 `redis-rs`（★4256，2026-09-18 活跃）。

**② grammers 在 Codeberg，不在 GitHub。**

```text
GitHub Lonami/grammers  → archived（2026-02-10），最后 commit 即 "Migrate off GitHub"
Codeberg Lonami/grammers → 活跃，1356 commits，最后提交 2026-09-19
crates.io grammers-client 0.10.0，repository 字段已指向 codeberg.org
```

只搜 GitHub 会误判此库已死。CI 配置、依赖镜像、issue 求助都需按 Codeberg 处理。

**顺带一个有利信号**：grammers 与 Telethon 同为作者 Lonami 所维护，
而 Telethon 最后推送 2026-02-21、grammers 是 2026-09-19。
上游活跃度目前 Rust 侧高于 Python 侧。

### 2.2 对象存储客户端：`aws-sdk-s3`，不用 `rust-s3`

```text
aws-sdk-s3  1.148.0  2026-09-16  下载 8.8 千万  AWS 官方维护
rust-s3     0.37.2   2026-05-04  下载 1.0 千万  社区维护，仍是 0.x
```

选官方 SDK 的理由不是下载量，是**它与 MinIO 的兼容路径是被测过的**：
MinIO 自己的文档就以 AWS SDK 为基准客户端。代价是编译期变长、
依赖树比 `rust-s3` 大一圈 —— 接受，因为「依赖退出路径」在这里不适用
（S3 协议本身是稳定契约，换客户端不影响数据）。

用法边界：**只用到 `put_object` / `get_object` / `delete_object` 与预签名 URL**。
`media_archive.object_expires_at` 的清理走 `delete_object`，
不依赖 bucket lifecycle —— 本地 compose 里的 MinIO 版本不一定支持，
而清理逻辑不该依赖只在某一端存在的能力。

### 2.3 可观测性：一处必须手工钉住的版本错配

```text
日志   tracing + tracing-subscriber（EnvFilter + JSON layer）
指标   metrics + metrics-exporter-prometheus，暴露 /metrics
       （axum-prometheus 0.10 可选，它只是 HTTP 中间件层的封装，
         值不值得多一个依赖留到实现时定，指标门面先钉 metrics）
链路   opentelemetry + tracing-opentelemetry，OTLP 导出
```

> **版本错配（2026-09-19 核实 crates.io，不要盲取最新）**：
>
> ```text
> opentelemetry         最新 0.33.0（2026-09-18）
> tracing-opentelemetry 最新 0.33.0（2026-05-18）→ 依赖 opentelemetry ^0.32
> ```
>
> 两个 crate 的版本号撞成一样，但**桥接层比核心库落后一个大版本**。
> 若按「都取最新」写 `opentelemetry = "0.33"`，cargo 会同时链入
> 0.32 与 0.33 两份 —— 类型不互通，span 上下文串不起来，
> 且**编译能过**，表现为「trace 里父子关系莫名丢失」。
>
> 定案：**`opentelemetry` 锁 `0.32`**，跟随 `tracing-opentelemetry` 的要求，
> 待桥接层跟进 0.33 后一起升。升级前用
> `cargo tree -d -p opentelemetry` 确认只有一份。

指标与链路的实现排在上线阶段，但**选型必须现在定**：
§5.1 的 subscriber 形态首发就要落地，选错要返工。

### 2.4 API 契约从代码生成，不手写 yaml

`../spec/07-接口契约.md` §三 用表格枚举了 64 个端点，
那份表格是**设计意图**；机器可读的契约由 `utoipa` + `utoipa-axum`
在 handler 上标注、编译期生成 OpenAPI 3.1。

选生成而非手写的理由：手写 yaml 与代码是两份事实源，64 个端点必然漂移。
漂移的检出方式是 `tgm openapi --check`（`04-CI门禁.md`）。

## 三、错误类型与错误码映射

`../spec/07-接口契约.md` §2.1 定了 11 个错误码。本节定它们怎么从内部错误产生。

```rust
// crates/core/src/error.rs
#[derive(Debug, thiserror::Error)]
pub enum AppError {
    #[error("unauthenticated")]              Unauthenticated,
    #[error("forbidden")]                     Forbidden,
    #[error("csrf invalid")]                  CsrfInvalid,
    #[error("not found")]                      NotFound,
    #[error("rule conflict")]                  RuleConflict { existing_id: i64 },
    #[error("condition invalid: {0}")]         ConditionInvalid(String),
    #[error("regex invalid: {0}")]             RegexInvalid(String),
    #[error("quota exceeded")]                 QuotaExceeded,
    #[error("rate limited")]                   RateLimited,
    #[error("credential via web only")]        CredentialViaWebOnly,
    #[error("not invited")]                    NotInvited,
    // 以下不对外暴露细节，统一 500
    #[error(transparent)]                      Db(#[from] sqlx::Error),
    #[error(transparent)]                      Other(#[from] anyhow::Error),
}
```

**三条纪律**：

1. **`thiserror` 用于 `core`/`db`/`tg`（库层），`anyhow` 只用于 `bins`（顶层）。**
   库层返回具体错误，顶层才允许擦除类型。
2. **`AppError` → HTTP 的映射只有一处**（`axum::response::IntoResponse` 的单个 impl）。
   `../spec/07-接口契约.md` §2.1 那句「跨租户返回 404 不是 403」靠这一处保证 ——
   分散写就一定会有人按直觉写 403。
3. **`sqlx::Error` 绝不直接透给客户端。** 它的 message 含表名、列名、约束名，
   而约束名本身就是侧信道 —— `../spec/05-安全与租户隔离.md` §3.5 已实测
   `users_g_email_key` 这类名字可被用来探测别的租户是否存在某条记录。
   `Db(_)` 一律映射成 500 + 一个 `request_id`，细节只进日志。

> **唯一的例外要显式处理**：`RuleConflict` 需要
> `../spec/03-数据模型.md` 的 `uq_rule_conflict` 命中信息，
> 这要求在 Repo 层把 `sqlx::Error::Database` 的 `constraint()` 匹配成
> `AppError::RuleConflict`，而不是让它落进 `Db(_)`。
> **匹配约束名的代码必须集中在 `db/` 一处** —— 一旦散开，
> 第 3 条纪律就会被逐点侵蚀。

## 四、租户上下文的代码形态

`../spec/05-安全与租户隔离.md` §二/§3.2 定了 newtype 与 `tenant_tx` 的签名与安全不变量。
本节补的是**调用点**：调用点才是决定这个封装能不能用的部分 ——
`for<'a> FnOnce(&'a mut PgConnection) -> BoxFuture<'a, ...>` 这种
HRTB + 借用组合在 Rust 里很容易写不出来。

已实测（rustc 1.98.1 + sqlx 0.9，`cargo build` 通过）：

```rust
pub async fn count_rules(pool: &PgPool, t: TenantId) -> Result<i64> {
    tenant_tx(pool, t, |conn| Box::pin(async move {
        let row: (i64,) = sqlx::query_as(
            "SELECT count(*) FROM rules WHERE tenant_id = $1")   // 显式带 tenant_id
            .bind(t.get())
            .fetch_one(conn)
            .await?;
        Ok(row.0)
    })).await
}
```

注意 `Box::pin(async move { ... })` 是必需的样板。**每个查询都要写这一层**，
这是这个签名的隐含代价。SQL 里仍然显式写 `WHERE tenant_id = $1`，
不因为有 RLS 就省掉 —— RLS 是第二道防线，不是唯一防线。

> **如果这层样板在 27 张表上变得难以忍受**，替代方案是给 `tenant_tx` 配一个
> `macro_rules!` 包装。但**不要为此改成「把 conn 存进 struct」的写法** ——
> 那会让「事务边界 = `set_config` 作用域」这个安全不变量变得不可见，
> 而 `set_config` 在事务外**静默失效且无 WARNING**（已实测，
> 见 `../spec/05-安全与租户隔离.md` §3.2）。

### 4.1 `TenantId` 只有两条构造路径

「禁止裸 `i64`」是意图，下面是强制方式：

```text
Repo 层每个方法的第一个参数必须是 TenantId，且不得提供 impl From<i64> for TenantId。
构造 TenantId 只有两条路径：
  1 从 AuthContext 取（../spec/05-安全与租户隔离.md §八 的收敛点）
  2 sqlx 从数据库解码（#[sqlx(transparent)] 提供）
禁止 TenantId(x) 这种直接构造 —— 字段保持私有，不加 pub fn new(i64)。
```

这条比「代码评审时注意」有效，因为它是类型系统强制的：
没有 `From<i64>`、没有 `new`、字段私有，
于是「凭一个来路不明的整数造出租户身份」在编译期就不可表达。

### 4.2 平台级操作走 `admin_tx`，不复用 `tenant_tx`

`../spec/05-安全与租户隔离.md` §3.3 纪律 1 的结论是：
带 `tenant_id` 的表上**一律不用 `SECURITY DEFINER`**，
因为 `FORCE` 之后那条路径会退化成静默零行。提权需求因此收敛到应用层：

```text
tenant_tx(pool, tenant, f)   业务唯一入口。set_config('app.tenant_id') 后执行
admin_tx(pool, f)            平台级入口。用 platform_ops 的独立连接池，
                             不设 app.tenant_id，只查 tenant_id IS NULL 的行

两者的连接池是两个，不是同一个池换角色 —— 换角色要 SET ROLE，
那是会话级动作，与连接复用相冲。
```

`admin_tx` 的使用面必须小且可枚举：平台日志查询
（`system_logs` / `audit_logs` 的 `tenant_id IS NULL` 行）、
管理端点（`../spec/07-接口契约.md` §3.11）。
**业务代码里出现 `admin_tx` 就是评审阻塞项**，
因为它意味着某段业务逻辑绕过了租户谓词。

## 五、日志与脱敏

**不得进日志的对象，集中列在这一处。** 分散的禁令等于没有禁令：

| 对象 | 为什么 |
|---|---|
| `console_login_challenges.nonce` | 泄漏即可冒领一次登录 |
| `web_sessions.id` | 它就是会话凭证本身 |
| `bot_console_sessions` 的会话标识 | 同上 |
| MTProto session 字节 | 等价于账号的完整控制权 |
| 明文凭据（Bot token / `api_hash`） | 租户自带凭据，泄漏是对租户的违约 |
| 扫码登录的 `login_token` | 有效期内可被直接用来完成登录 |

**统一约定**：这些值一律用专门的 newtype 包裹，且**手工实现 `Debug`**：

```rust
// crates/core/src/secret.rs
pub struct Secret<T>(T);

impl<T> std::fmt::Debug for Secret<T> {
    fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
        f.write_str("[REDACTED]")
    }
}
```

理由：`tracing` 的 `?value` 和 `#[instrument]` 都走 `Debug`。
只要 `Debug` 是 `[REDACTED]`，误写 `tracing::info!(?token)` 也不会泄漏。
**靠人记住「不要打印」是不可靠的，靠类型是可靠的。**

配套三条：

```text
1 #[instrument] 默认会记录全部参数 —— 凡函数签名含 Secret<_> 或 TenantId 之外的
  敏感参数，必须显式写 #[instrument(skip(secret))]
2 tracing span 必须带 tenant_id 与 request_id，这是事故排查的最小上下文
3 生产环境日志级别 info，且 sqlx 的 query log 必须关到 warn ——
  sqlx 默认会打完整 SQL 含绑定参数
```

第 3 条值得强调：sqlx 把绑定参数打进日志，
而 `identity_secrets` 的写入语句绑定的就是密文与 nonce。
`Secret<T>` 管不到这条路径 —— 参数是在 sqlx 内部被格式化的，
不经过你的 `Debug` 实现。所以这里必须靠日志级别，不能靠类型。

### 5.1 subscriber 形态（首发就要定）

初始化形态属于工程约定，写在这里。首发只上日志，指标与链路后接。

```rust
// crates/core/src/telemetry.rs —— 首发形态，不含 OTel
pub fn init() {
    use tracing_subscriber::{fmt, EnvFilter, prelude::*};
    let filter = EnvFilter::try_from_default_env()
        // 默认值必须含 sqlx=warn，见上方第 3 条
        .unwrap_or_else(|_| EnvFilter::new("info,sqlx=warn"));
    tracing_subscriber::registry()
        .with(filter)
        .with(fmt::layer().json().with_current_span(true))
        .init();
}
```

```text
生产    JSON 单行，stdout，由容器运行时收走（不自己写文件、不自己轮转）
本地    RUST_LOG=debug,sqlx=warn，人读格式（fmt::layer().pretty()）
```

**为什么首发就要定**：`registry()` + `layer` 这个结构是后面接 OTel 的前提 ——
接链路时只是多挂一层 `tracing_opentelemetry::layer()`。
若首发图省事写成 `fmt::init()`（单 subscriber，无 registry），
接链路时就得把所有初始化代码重写一遍。这是个零成本的决定，
省掉的是后面的返工。

> **不自己做日志轮转**（不引 `tracing-appender`）：首发形态是
> docker compose（`../ops/00-部署与运行时.md`），日志归运行时管。
> 部署方若要落文件，配 Docker 的 log driver，不是应用的职责。

## 六、仓库约定

### 6.1 `.sqlx/` 必须提交

`cargo sqlx prepare --check`（`04-CI门禁.md`）依赖 `.sqlx/` 目录。
它**必须进 git**，否则 CI 里没有数据库就跑不了编译期 SQL 校验。

### 6.2 `.gitignore` 当前是 Python 模板，必须换

已核实全文是 Python 模板（`__pycache__`、`.venv`、`*.egg-info`……）。
Rust 项目需要的条目：

```gitignore
/target
**/*.rs.bk
.env
# 注意：Cargo.lock 对 bin 项目必须提交，不要 ignore
# 注意：.sqlx/ 必须提交（见 6.1），不要 ignore
```

保留 `.env`（已有）。**`target/` 当前虽然被模板里 PyBuilder 那节的
`target/` 巧合覆盖了，但依赖巧合不是约定** —— 应显式写 `/target`。

### 6.3 依赖版本统一在 workspace root

`Cargo.toml` 的 `[workspace.dependencies]` 是版本号的唯一落点，
各 crate 写 `tokio = { workspace = true }`。
理由是 §2.3 那个版本错配：两份不同版本同时链入且编译通过，
这种问题只有在版本声明集中时才能靠读一个文件排除。

CR6、CR9、CR10、CR17 值得单独说，因为它们最容易被「顺手优化」破坏：

- **CR6**：把某张表的 `tenant_id` 改成 TEXT，会静默拆掉
  fail-loud 特性 —— `''::bigint` 报错，而 `tenant_id = ''` 恒不成立、静默零行。
  这是一次「支持字符串租户标识」的需求就能触发的事故。
- **CR9 / CR10**：根因同一个 —— `lower()` 与 `LIKE` 的底层函数不是 leakproof，
  在 RLS 表上索引会失效、退化成先按租户全捞再过滤。
  已实测 `LIKE` 那条造成 150× 的 heap block 读取。
  这两条不是性能建议，是**一次「加个模糊搜索」就会撞上的坑**。
- **CR17**：它是合规约束落到代码的唯一形式。做不到静态检查的原因是
  raw invoke 的构造方式多样，但因为 raw invoke 已按 §一 收敛在 `tg/` 一个 crate 里，
  评审面是可枚举的。
