# CI 门禁

本文是**机器卡口的唯一定义处**。`00-工程约定.md` §七 的评审清单里标注「CI」的
那几条、`03-测试策略.md` §三 的 `A1`~`A9`，实现都在这里。

主查询与断言 1~9 全部在 PG 17.11 上实测过 ——
每一条都对应一种**已复现的静默失效**（配错了不报错，只是不再起作用）。

---

## 零、判据是「表里有没有 `tenant_id` 列」

不是人工维护的表清单。人工清单会随新表漏更新，列存在性不会。

`spec/03-数据模型.md` §1.3 的甲类 19 张表正是这样推导出来的
（最初凭记忆分类，错了三处，靠这个查询纠正）。
第 27 张表 `tenant_consents` 无需改查询就被自动纳入 —— 这正是要的效果。

## 一、主查询：RLS 三件套缺一即失败

```sql
-- tgm audit-rls 的主查询。返回任何行即 CI 失败
SELECT c.relname,
       c.relrowsecurity      AS rls_on,
       c.relforcerowsecurity AS forced,
       (SELECT count(*) FROM pg_policy p WHERE p.polrelid = c.oid) AS policies
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public'
  AND c.relkind IN ('r','p')            -- 含分区父表
  AND EXISTS (SELECT 1 FROM pg_attribute a
              WHERE a.attrelid = c.oid AND a.attname = 'tenant_id'
                AND a.attnum > 0 AND NOT a.attisdropped)
  AND NOT (c.relrowsecurity                 -- 已 ENABLE
           AND c.relforcerowsecurity        -- 已 FORCE（漏这个，owner 全见）
           AND (SELECT count(*) FROM pg_policy p WHERE p.polrelid = c.oid) > 0)
ORDER BY 1;
```

三个条件缺一不可。已实测能分别抓出三种失效，**每种都会被只查其一的脚本漏掉**：

| 造的错 | `rls_on` | `forced` | `policies` |
|---|---|---|---|
| 有 `tenant_id` 但没开 RLS | f | f | 0 |
| 开了 RLS 但忘了 `FORCE` | t | **f** | 1 |
| 有策略但 RLS 被 DISABLE | **f** | f | 1 |

中间那行是最危险的一类：`rls_on = t` 看起来是开着的，
只有 `forced` 这一列暴露问题
（后果见 `../spec/05-安全与租户隔离.md` §3.3 纪律 1 的实测表）。

> **乙类两张子表不在此查询覆盖内** —— `rule_conditions` 与 `delivery_logs`
> 没有 `tenant_id` 列，靠 EXISTS 策略兜。需单独断言，见 §三-1。
> 这是本查询的已知边界，不是遗漏。

## 二、九条断言

编号与 `03-测试策略.md` §三 的 `A1`~`A9` 一致。

### A1 运行时角色不得持有 `TRUNCATE`

```sql
SELECT c.relname FROM pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE n.nspname='public' AND c.relkind='r'
  AND has_table_privilege('app_user', c.oid, 'TRUNCATE');
```

理由：**`TRUNCATE` 不受 RLS 约束**。有这个权限就能清空他租户的数据，
策略写得再对也拦不住（`../spec/05-安全与租户隔离.md` §六）。

### A2 运行时角色不得是超级用户 / `BYPASSRLS` / 任何表的 owner

```sql
SELECT rolname FROM pg_roles WHERE rolname='app_user' AND (rolsuper OR rolbypassrls);
SELECT relname FROM pg_class WHERE relowner='app_user'::regrole;
```

这三项任一成立，整个 RLS 机制被旁路且**不报错**。
`01-配置与Secret.md` §4.3 在启动期查的是同一件事 ——
两处都要，因为 CI 管的是迁移产物，启动期管的是实际连上的库。

### A3 不得存在引用 `current_setting` 的 `CHECK` 约束

```sql
SELECT conrelid::regclass, conname FROM pg_constraint
WHERE contype='c' AND pg_get_constraintdef(oid) LIKE '%current_setting%';
```

**这条最值得自动化**：`CHECK (tenant_id = current_setting(...))`
建的时候不报错、日常用着也正常，**只在恢复备份时才炸** ——
`pg_restore` 的会话里没有 `app.tenant_id`，每一行都过不了约束。
这种「建表时接受、恢复时失败」的定时炸弹靠人工评审拦不住
（方案本身为何被否掉见 `../spec/05-安全与租户隔离.md` §4.1）。

### A4 有 `tenant_id` 的表上，唯一约束必须含 `tenant_id`

```sql
SELECT c.relname AS tbl, i.relname AS idx
FROM pg_index x
JOIN pg_class c ON c.oid = x.indrelid
JOIN pg_class i ON i.oid = x.indexrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname='public' AND x.indisunique
  -- 排除单列代理键唯一索引（GENERATED ALWAYS，attidentity='a'）：
  -- 值由库分配，攻击者填不进去，duplicate key 探测不出东西。
  -- 判据是「攻击者能不能构造这个值」，不是「是不是主键」——
  -- 所以 bot_console_sessions 的自然键主键仍会被命中（实测，且命中是对的）
  AND NOT (x.indnatts = 1 AND EXISTS (
        SELECT 1 FROM pg_attribute a WHERE a.attrelid=c.oid
        AND a.attnum = x.indkey[0] AND a.attidentity = 'a'))
  -- 白名单三项，都是已论证 + 已由 GRANT 层补偿的破例：
  --   bot_console_sessions_pkey  鉴权前不知 tenant_id
  --   uq_web_session_id          随机 32 字节 id 需全局唯一
  --   uq_task_idem               五元组哈希，tenant_id 已在哈希输入内
  AND i.relname NOT IN ('bot_console_sessions_pkey',
                        'uq_web_session_id',
                        'uq_task_idem')
  AND EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid=c.oid
              AND a.attname='tenant_id' AND a.attnum>0 AND NOT a.attisdropped)
  AND NOT EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid=c.oid
                  AND a.attname='tenant_id'
                  AND a.attnum = ANY(x.indkey::smallint[]));
```

漏了会开**一条 RLS 补不了的侧信道**：插入撞唯一约束时返回 duplicate key，
攻击者据此判断他租户是否存在某个值 —— 行读不到，存在性泄漏了。

> **不要为新表扩那个白名单。** 三项破例各有独立论证
> （`../spec/03-数据模型.md` §7.1 / §7.3 / §5.2），并且都由 GRANT 层补偿，
> 补偿在位与否由 A7 独立校验。扩列表就是把论证换成了默认放行。

### A5 `tenant_id` 必须 `NOT NULL`

```sql
SELECT c.relname FROM pg_attribute a
JOIN pg_class c ON c.oid=a.attrelid
JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE n.nspname='public' AND c.relkind IN ('r','p')
  AND c.relname NOT IN ('identities', 'system_logs', 'audit_logs')
  AND a.attname='tenant_id' AND a.attnum>0 AND NOT a.attisdropped
  AND NOT a.attnotnull;
```

可空会让复合外键被 NULL 绕过（NULL 参与的 FK 不做检查）。
三张排除表是铁律 5 的有意破例（`../spec/03-数据模型.md` §1.2）：
它们都不做复合 FK 的父表，破例不会传导成跨租户边 —— 这一点由 A9 独立校验。

### A6 多策略表上不得有未限定角色的 PERMISSIVE 策略

```sql
SELECT c.relname AS tbl, count(*) AS policies,
       count(*) FILTER (WHERE p.polroles = '{0}') AS public_policies
FROM pg_policy p
JOIN pg_class c ON c.oid = p.polrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname='public' AND p.polpermissive
GROUP BY c.relname
HAVING count(*) > 1 AND count(*) FILTER (WHERE p.polroles = '{0}') > 0;
```

**PERMISSIVE 之间是 OR** —— 一条 PUBLIC 策略就作废了旁边的租户策略。
这条断言是 Bot 鉴权反查引入的（`../spec/05-安全与租户隔离.md` §3.7
给 `tenant_members` 加了第二条策略），误写的后果已实测。

已实测：`polroles = '{0}'` 即 PUBLIC，`{16385}` 之类是具体角色 OID。
造一张两条策略都不限角色的表 → 命中；`tenant_members` 那种
一条 `TO app_user` 一条 `TO auth_lookup` 的正确写法 → 不误报。
单策略表（绝大多数）不进这个查询，`HAVING count(*) > 1` 已排除。

### A7 A4 白名单表的 GRANT 补偿必须在位

```sql
SELECT 'bot_console_sessions' AS tbl
WHERE has_table_privilege('app_user', 'bot_console_sessions', 'SELECT')
   OR has_table_privilege('app_user', 'bot_console_sessions', 'INSERT');
```

白名单是**靠 GRANT 换 RLS** 的：`app_user` 完全碰不到这张表，
只有 `auth_lookup` 能读写（`02-本地环境与迁移.md` §二 的权限矩阵）。
补偿一撤销，A4 放过的侧信道立刻回来。A4 与 A7 必须成对存在。

### A8 `tenant_id` 表上不得有普通视图与 `SECURITY DEFINER` 函数

```sql
WITH tenant_tbl AS (
  SELECT c.oid FROM pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace
  WHERE n.nspname='public' AND c.relkind IN ('r','p')
    AND EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid=c.oid
                AND a.attname='tenant_id' AND a.attnum>0 AND NOT a.attisdropped)
)
SELECT v.relname AS obj, 'view' AS kind FROM pg_class v
JOIN pg_namespace n ON n.oid=v.relnamespace
WHERE n.nspname='public' AND v.relkind='v'
  -- 用 pg_options_to_table 取值再转 bool，不要拿 reloptions 做数组包含判断：
  -- 实测 security_invoker = on 会原样存成 {security_invoker=on}，
  -- 而 = true 与裸写都存成 =true，按数组匹配会把合规视图当违规报出来
  AND NOT coalesce((SELECT o.option_value::bool
                    FROM pg_options_to_table(v.reloptions) o
                    WHERE o.option_name='security_invoker'), false)
  -- 视图对基表的依赖挂在 pg_rewrite 上，不是视图 oid 上。实测直接用
  -- pg_depend.objid = v.oid 查不到任何行，断言会静默全绿
  AND EXISTS (SELECT 1 FROM pg_rewrite rw
              JOIN pg_depend d ON d.classid='pg_rewrite'::regclass AND d.objid=rw.oid
              WHERE rw.ev_class=v.oid AND d.refclassid='pg_class'::regclass
                AND d.refobjid IN (SELECT oid FROM tenant_tbl))
UNION ALL
-- 函数不按表过滤：pg_depend 不记录函数体引用的表（实测 0 行），
-- 所以无法判断一个 SECURITY DEFINER 函数碰不碰带 tenant_id 的表。
-- 定案是「全面禁用」，按全库报出反而是正确形状
SELECT p.proname, 'security_definer_function' FROM pg_proc p
JOIN pg_namespace n ON n.oid=p.pronamespace
WHERE n.nspname='public' AND p.prosecdef;
```

这条拦的不是泄漏，是**功能坏掉**：`FORCE` 后这两条路径以 owner 身份执行，
无策略匹配 owner → 静默 0 行（`03-测试策略.md` §五 的实测表）。
在功能测试里表现为「查不到数据」，极易误诊成数据没写进去。
所以它是静态断言而不是动态测试 —— 静态的更可靠。

**两处实测踩到的写法陷阱**，都属于「写错了不报错、只是永远全绿」那一类：

```text
1 视图对基表的依赖记在 pg_rewrite 上，不在视图 oid 上
  直接查 pg_depend.objid = v.oid 返回 0 行 → 断言静默全绿
2 security_invoker = on 与 = true 在 reloptions 里存的字面量不同
  {security_invoker=on} vs {security_invoker=true}
  按数组包含判断会把合规视图误报成违规
```

函数侧按全库报是有意的，与 `00-工程约定.md` §七 CR8「全面禁用」一致，
不是过度报警 —— 提权路径只有 `admin_tx` 一条。

### A9 双方都有 `tenant_id NOT NULL` 时外键必须含 `tenant_id`

```sql
SELECT ct.conrelid::regclass AS child, ct.confrelid::regclass AS parent, ct.conname
FROM pg_constraint ct
JOIN pg_class c ON c.oid = ct.conrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE ct.contype='f' AND n.nspname='public'
  AND EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid=ct.conrelid
              AND a.attname='tenant_id' AND a.attnum>0 AND NOT a.attisdropped)
  -- 父表侧要求 tenant_id NOT NULL。这一条让 identities 自动落选 ——
  -- 铁律 4 的例外由断言形状承载，不靠硬编码表名
  AND EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid=ct.confrelid
              AND a.attname='tenant_id' AND a.attnum>0 AND NOT a.attisdropped
              AND a.attnotnull)
  AND NOT EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid=ct.conrelid
                  AND a.attname='tenant_id' AND a.attnum = ANY(ct.conkey));
```

单列 FK 会让**跨租户边在库层可表达**：RLS 不拦建边、规则静默失效、
FK 报错成为 id 枚举侧信道、且可 DoS 他租户的 DELETE。四项均已实测。

**断言形状承载了铁律 4 的例外**：父表侧要求 `tenant_id NOT NULL`，
`identities` 的 `tenant_id` 有意可空 → 自动落选，不需要硬编码表名。
例外的代价在应用层付：租户指定一个 NULL-tenant 身份要返回 403
（反向测试 R19，`03-测试策略.md` §三）。

A4 与 A9 互补不重复：**A4 管唯一约束（探测存在性），A9 管外键（建跨租户边）。**
两者都按真实表形状实测过 —— 造一张单列 FK 的违规子表精确命中，
`rules` 那种复合 FK 与指向 `identities` 的单列 FK（例外）均不误报。

## 三、三条补充断言

它们不在 `A1`~`A9` 的编号里，因为各自只管一处，但同属 `tgm audit-rls`。

**1）乙类两张子表的 RLS 白名单断言**

```sql
-- rule_conditions / delivery_logs 没有 tenant_id 列，主查询覆盖不到
SELECT relname, relrowsecurity, relforcerowsecurity FROM pg_class
WHERE relname IN ('rule_conditions','delivery_logs')
  AND NOT (relrowsecurity AND relforcerowsecurity);
```

这是**唯一一处用白名单表名的断言**，因为判据不可能从列结构推出来 ——
这两张表恰恰是以「没有 `tenant_id`」为特征的。

**2）`identities.tenant_id` 写入即不可变**

`../spec/06-合规与凭据责任.md` §2.5 要求「不提供把身份转给别的租户的端点」。
库层没有「列不可 UPDATE」这种约束，所以断言只能做到检查
`app_user` 对 `identities` 的 UPDATE 权限是否被收窄到不含 `tenant_id` 列：

```sql
SELECT 'identities' WHERE has_column_privilege(
    'app_user', 'identities', 'tenant_id', 'UPDATE');
```

> 这条断言弱于它想保证的性质：列级 GRANT 能拦住 `app_user` 改这一列，
> 但拦不住「先删后建」这种等效操作。真正的保证靠 §2.5 的
> 「写入路径只有一条」，这条断言只是把最直接的那条路堵上。

**3）`openapi.json` 与代码一致**

```bash
tgm openapi --check      # 重新生成并与仓库内的 openapi.json 比对，不一致即失败
```

与 `.sqlx/` 必须提交是同一个模式（`00-工程约定.md` §6.1）：
**把「代码与契约一致」变成机器能判的事**，而不是评审时靠眼睛看。
契约形态与两份文件拆分的理由见 `../spec/07-接口契约.md` §2.2。

## 四、卡口命令清单

```bash
cargo fmt --check                  # 格式
cargo clippy -- -D warnings        # lint，警告即失败
cargo test --all                   # L1 + L2 + L3（03-测试策略.md §七）
cargo sqlx prepare --check         # .sqlx/ 与 SQL 一致（00 §6.1）
cargo deny check                   # 许可证 + advisory
tgm audit-rls                      # 主查询 + A1~A9 + §三 三条
tgm openapi --check                # 契约漂移
```

前五条不需要数据库之外的东西。`tgm audit-rls` 需要一个跑完全部迁移的库，
在 CI 里复用 L2/L3 那套服务（`02-本地环境与迁移.md` §一 的同一份 compose）。

## 五、审计通过 ≠ 隔离正确

这一整套只验证「配置存在」，不验证「策略写对」。

已实测：一张 `USING (true)` 的表 —— ENABLE、FORCE、策略齐全 ——
主查询返回 0 行（全绿），而 `app_user` 用 `app.tenant_id = 1`
能看到两个租户共 2 行。**静态审计对这种写法完全无感。**

业界有现成的反面教材：某低代码平台的 RLS 扫描器只检查「是否存在任何策略」
而不检查策略正确性，作者自己称之为 "false sense of security"。

所以 `03-测试策略.md` §三 的反向测试是这项审计的**必要补充**，
两者都不能省 —— 尤其 R5（关掉 RLS 后应用层是否仍不泄漏），
它是唯一能证明第一道防线存在的测试。

## 六、本文的局限

- **本文描述的卡口目前可执行的有 0 条。** `tgm audit-rls` 子命令未实现，
  CI 配置文件不存在，`openapi.json` 不存在。SQL 本身在 PG 17.11 上实测过，
  但「SQL 正确」与「卡口在跑」是两件事
- A2 只查 `app_user` 一个角色名。四个角色里 `auth_lookup` 与 `platform_ops`
  同样不该有超级用户位，但断言没覆盖 —— 硬编码角色名本身就是个弱点
- A7 只查 `bot_console_sessions` 一张表。A4 白名单有三项，
  另两项（`uq_web_session_id` / `uq_task_idem`）的补偿形式不是 GRANT，
  目前**没有任何断言**校验它们的论证前提还成立
- §三-2 的断言弱于它要保证的性质，已在该条下写明
- 分区表一旦启用，主查询的 `relkind IN ('r','p')` 会命中分区父表，
  但**分区子表不继承 RLS**（`relrowsecurity = f`），需要补一条单独断言。
  分区目前推迟，这个缺口随之推迟（`../spec/04-数据生命周期与容量.md`）
- 全部 SQL 是在**造出来的小表**上验的，不是在真实的 27 张表上 ——
  迁移第一次跑通那天必然会冒出误报，届时要改的是断言而不是表
