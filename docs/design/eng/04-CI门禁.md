## 一、主查询：RLS 三件套缺一即失败

```sql
-- tgm audit-rls 的主查询。返回任何行即 CI 失败
SELECT c.relname,
       c.relrowsecurity      AS rls_on,
       c.relforcerowsecurity AS forced,
       (SELECT count(*) FROM pg_policy p WHERE p.polrelid = c.oid) AS policies
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public'
  AND c.relkind IN ('r','p')            -- 含分区父表
  AND EXISTS (SELECT 1 FROM pg_attribute a
              WHERE a.attrelid = c.oid AND a.attname = 'tenant_id'
                AND a.attnum > 0 AND NOT a.attisdropped)
  AND NOT (c.relrowsecurity                 -- 已 ENABLE
           AND c.relforcerowsecurity        -- 已 FORCE（漏这个，owner 全见）
           AND (SELECT count(*) FROM pg_policy p WHERE p.polrelid = c.oid) > 0)
ORDER BY 1;
```

三个条件缺一不可。已实测能分别抓出三种失效，**每种都会被只查其一的脚本漏掉**：

| 造的错 | `rls_on` | `forced` | `policies` |
|---|---|---|---|
| 有 `tenant_id` 但没开 RLS | f | f | 0 |
| 开了 RLS 但忘了 `FORCE` | t | **f** | 1 |
| 有策略但 RLS 被 DISABLE | **f** | f | 1 |

中间那行是最危险的一类：`rls_on = t` 看起来是开着的，
只有 `forced` 这一列暴露问题
（后果见 `../spec/05-安全与租户隔离.md` §3.3 纪律 1 的实测表）。

> **乙类两张子表不在此查询覆盖内** —— `rule_conditions` 与 `delivery_logs`
> 没有 `tenant_id` 列，靠 EXISTS 策略兜。需单独断言，见 §三-1。
> 这是本查询的已知边界，不是遗漏。

## 二、断言

编号与 `03-测试策略.md` §三 的 `A1`~`A9` 一致。本节现有 11 条：
`A0`、`A1`、`A2` 拆成 `A2a`/`A2b`、`A3`~`A9`。
`A0` 与 `A2` 的拆分是实现时补的，理由各写在条目里。

> **不要把本节的条数写成一个字。** 编号稳定、数量不稳定，
> 引用时一律用编号。`../../pre-do/README.md` 第 1 条纪律说的是同一件事。

### A0 运行时角色派生必须非空（元断言）

`A1`/`A2a`/`A2b`/`C2` 四条都不硬编码角色名，而是从目录派生「运行时角色集合」：

```sql
-- 判据：登录角色，且在 public 的表上持有任何直授权限或被任何策略点名。
-- 三处都要查 —— relacl（表级）、pg_attribute.attacl（列级）、pg_policy.polroles。
-- 漏掉 attacl 的后果已实测：CREATE ROLE probe_col LOGIN 之后
-- GRANT UPDATE (tenant_id) ON identities TO probe_col，relacl 命中 0、
-- pg_policy 命中 0、attacl 命中 1 —— 整个角色从派生落选，那四条断言一条都不查它，
-- 而它 has_column_privilege(identities, tenant_id, UPDATE) = true，正是 C2 要拦的事
SELECT '派生为空：A1/A2/C2 将全部空转，不是通过'
WHERE NOT EXISTS (<上述派生>);
```

派生若因 GRANT 写法变化算出空集，那四条断言会**全部静默通过**。
所以先断言派生本身有结果。当前实测得到 `app_user` / `auth_lookup` / `platform_ops` 三个。

它只管「空集」，管不了「不为空却缺人」。后者的一种已实测形状由 `C5` 兜（见 §三-4）。

**为什么不硬编码角色名**：本文 §六 原先把「A2 只查 `app_user`」列为局限。
派生取代硬编码之后这条局限消失，代价是多了 `A0` 这道哨兵。

### A1 运行时角色不得持有 `TRUNCATE`

```sql
SELECT rr.rolname, c.relname FROM <runtime_role> rr
CROSS JOIN pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE n.nspname='public' AND c.relkind IN ('r','p')
  AND has_table_privilege(rr.oid, c.oid, 'TRUNCATE');
```

理由：**`TRUNCATE` 不受 RLS 约束**。有这个权限就能清空他租户的数据，
策略写得再对也拦不住（`../spec/05-安全与租户隔离.md` §六）。

`relkind` 收 `('r','p')` 而不是只收 `'r'`：分区父表上的 `TRUNCATE` 同样能清数据。

### A2a 运行时角色不得是超级用户或 `BYPASSRLS`

```sql
SELECT r.rolname, r.rolsuper, r.rolbypassrls FROM pg_roles r
WHERE <r 属于 runtime_role 派生> AND (r.rolsuper OR r.rolbypassrls);
```

### A2b 运行时角色不得是任何表的 owner

```sql
SELECT rr.rolname, c.relname FROM <runtime_role> rr
JOIN pg_class c ON c.relowner = rr.oid
JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE n.nspname='public' AND c.relkind IN ('r','p');
```

拆成两条的理由：**两种坏法的判据不同，混成一条时报红只说明「二者之一」**。
超级用户/`BYPASSRLS` 是整机制旁路；owner 身份在 `FORCE` 之前绕过策略、
`FORCE` 之后变成另一种坏法（无策略匹配 owner → 静默 0 行）。
修法也不同：前者 `ALTER ROLE`，后者改 owner 且**必须补回受赠权限**
（实测 `ALTER TABLE ... OWNER TO X` 会吞掉 X 原有的 grantee ACL 条目，见 §三 末尾）。

这几项任一成立，整个 RLS 机制被旁路且**不报错**。
`01-配置与Secret.md` §4.3 在启动期查的是同一件事 ——
两处都要，因为 CI 管的是迁移产物，启动期管的是实际连上的库。

`A2b` 报红时 `A1` 必然连带报红（owner 隐含全部权限，含 `TRUNCATE`）。
这是两条断言从不同角度抓同一个事实，是冗余不是耦合 ——
双遍脚本把这一对登记为预期连带。

### A3 不得存在引用 `current_setting` 的 `CHECK` 约束

```sql
SELECT conrelid::regclass, conname FROM pg_constraint
WHERE contype='c' AND pg_get_constraintdef(oid) LIKE '%current_setting%';
```

**这条最值得自动化**：`CHECK (tenant_id = current_setting(...))`
建的时候不报错、日常用着也正常，**只在恢复备份时才炸** ——
`pg_restore` 的会话里没有 `app.tenant_id`，每一行都过不了约束。
这种「建表时接受、恢复时失败」的定时炸弹靠人工评审拦不住
（方案本身为何被否掉见 `../spec/05-安全与租户隔离.md` §4.1）。

### A4 有 `tenant_id` 的表上，唯一约束必须含 `tenant_id`

```sql
SELECT c.relname AS tbl, i.relname AS idx
FROM pg_index x
JOIN pg_class c ON c.oid = x.indrelid
JOIN pg_class i ON i.oid = x.indexrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname='public' AND x.indisunique
  -- 排除单列代理键唯一索引（GENERATED ALWAYS，attidentity='a'）：
  -- 值由库分配，攻击者填不进去，duplicate key 探测不出东西。
  -- 判据是「攻击者能不能构造这个值」，不是「是不是主键」——
  -- 所以 bot_console_sessions 的自然键主键仍会被命中（实测，且命中是对的）
  -- 用 indnkeyatts 不是 indnatts：前者是参与唯一性的键列数，后者含 INCLUDE 列
  AND NOT (x.indnkeyatts = 1 AND EXISTS (
        SELECT 1 FROM pg_attribute a WHERE a.attrelid=c.oid
        AND a.attnum = x.indkey[0] AND a.attidentity = 'a'))
  -- 白名单两项，都是已论证 + 已由 GRANT 层补偿的破例：
  --   bot_console_sessions_pkey  鉴权前不知 tenant_id（../spec/03 §7.1）
  --   uq_web_session_id          随机 32 字节 id 需全局唯一（同 §7.3）
  AND i.relname NOT IN ('bot_console_sessions_pkey',
                        'uq_web_session_id')
  AND EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid=c.oid
              AND a.attname='tenant_id' AND a.attnum>0 AND NOT a.attisdropped)
  -- 成员测试只看前 indnkeyatts 个键列，不是整个 indkey。int2vector 转数组后
  -- 下界是 0（实测 [0:1]={3,2}），所以切片写 [0:indnkeyatts-1]
  AND NOT EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid=c.oid
                  AND a.attname='tenant_id'
                  AND a.attnum = ANY((x.indkey::smallint[])[0:x.indnkeyatts-1]));
```

漏了会开**一条 RLS 补不了的侧信道**：插入撞唯一约束时返回 duplicate key，
攻击者据此判断他租户是否存在某个值 —— 行读不到，存在性泄漏了。
本项目已在 `rule_versions` 上实测命中过一次并改了主键（`migrations/0004`）。

**白名单从三项减到两项。** 第三项 `uq_task_idem`（五元组哈希，原论证是
「`tenant_id` 已在哈希输入内」）在动工第 5 步实测确认为**真实漏洞**：
哈希泄漏的是存在性不是值，批量 `ON CONFLICT DO NOTHING` 探测 5000 个候选
只需 0.58 秒。已改掉（`migrations/0006`），破例随之取消，
`A7` 的白名单相应也是两项。论证过程记在 `../../pre-do/03-文档待更正.md` 十。

> **不要为新表扩那个白名单。** 剩下两项破例各有独立论证
> （`../spec/03-数据模型.md` §7.1 / §7.3），并且都由 GRANT 层补偿，
> 补偿在位与否由 A7 独立校验。扩列表就是把论证换成了默认放行。
> `uq_task_idem` 那一项的下场说明「已论证」也可能是错的论证。

**两处实测的写法陷阱**，都属于「写错了不报错、只是永远全绿」：

```text
1 用 indnatts 而不是 indnkeyatts
  CREATE UNIQUE INDEX ... ON keywords (word) INCLUDE (tenant_id)
  → indkey = "3 2"、indnatts = 2、indnkeyatts = 1。
  INCLUDE 列在 indkey 里但不参与唯一性判定 —— 拿整个 indkey 做成员测试
  会把「tenant_id 塞进 INCLUDE」当成合规放过，而换租户插同一个 word
  照样报 duplicate key，侧信道原样开着

2 表达式唯一索引的 indkey 里是 0
  含 tenant_id 的表达式索引（如 ((tenant_id::text || word)））会被报红。
  这是**已知误报，方向保守，接受**：没有任何列的 attnum 是 0，
  所以判据无法确认表达式里有没有 tenant_id，报出来让人来看
```

### A5 `tenant_id` 必须 `NOT NULL`

```sql
SELECT c.relname FROM pg_attribute a
JOIN pg_class c ON c.oid=a.attrelid
JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE n.nspname='public' AND c.relkind IN ('r','p')
  AND c.relname NOT IN ('identities', 'system_logs', 'audit_logs')
  AND a.attname='tenant_id' AND a.attnum>0 AND NOT a.attisdropped
  AND NOT a.attnotnull;
```

可空会让复合外键被 NULL 绕过（NULL 参与的 FK 不做检查）。
三张排除表是铁律 5 的有意破例（`../spec/03-数据模型.md` §1.2）。

**本文这里原来写着一句错话，实现时被证伪，现按实现改。** 原句是
「它们都不做复合 FK 的父表，破例不会传导成跨租户边 —— 这一点由 A9 独立校验」。
前半句字面成立（指向 `identities` 的 FK 确实都是单列的），但推论反了 ——
**单列正是跨租户边能建起来的原因**，不是它建不起来的理由。后半句是空的：

```text
identities 是七张子表的 FK 父表，七条全是单列 FK
  identity_secrets / source_subscriptions / target_channels /
  canonical_events / delivery_tasks / account_leases / bot_console_updates

A9 的父表侧要求 tenant_id NOT NULL，而 identities 的 tenant_id 恰好可空
  → 这七条全部自动落选，「由 A9 独立校验」兜的是空的
```

**本段自己又订正过一次。** 上一版写「那条边是共享身份池的设计后果，
池里的身份本就跨租户可见，不是漏洞」—— 也是错的。实测那条边指向的是
**他租户的私有身份**，不是池里 `tenant_id IS NULL` 的共享身份：

```text
tenant 21 上下文、app_user 身份，目标是 tenant 20 的私有身份 900

SELECT ... FROM identities WHERE id=900        → 0 行     RLS 挡住了读
INSERT target_channels (21, -1, 900)           → INSERT 0 1   边建成了
```

**读不到却能引用** —— FK 检查不过 RLS。另外两个后果一并实测：

```text
枚举   填存在的他租户 id 900 → INSERT 0 1
       填不存在的 id 901     → ERROR: violates foreign key constraint
       两者可区分 = 一个跨租户 id 枚举 oracle

钉住   建边之后，tenant 20 删自己的身份 900
       → ERROR: violates foreign key constraint ... Key is still referenced
       攻击者可单方面阻止他租户删自己的数据
```

这三条与 `A9` 在复合 FK 下关掉的后果同形（见该条），
区别只是这里**没有断言可依**。缺口只能靠应用层的身份归属校验兜
（`../spec/06-合规与凭据责任.md` §2.5 第 1 条），
不靠库层的 FK 形状。**这里不该声称有一道自动校验。**

> 那道兜目前也没有反向测试覆盖这个形状：`03-测试策略.md` §三 的 `R19`
> 测的是「指定 `tenant_id IS NULL` 的**共享**身份 → 403」，
> 而上面实测用的是他租户的**私有**身份。这条现已登记为
> `03-测试策略.md` §3.3 的 `R23`（→ 404，不是 403），**仍未实现**：
> 它的层是 L4，应用层代码还没有。原产地在 `../../pre-do/03-文档待更正.md` 十九。

### A6 多策略表上不得有恒真或未限定角色的 PERMISSIVE 策略

```sql
SELECT c.relname AS tbl, p.polname, p.polroles::text AS roles,
       CASE WHEN p.polroles = '{0}' THEN 'PUBLIC 策略'
            ELSE 'qual 恒真' END AS why
FROM pg_policy p
JOIN pg_class c ON c.oid = p.polrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname='public' AND p.polpermissive
  AND (SELECT count(*) FROM pg_policy p2
       WHERE p2.polrelid = p.polrelid AND p2.polpermissive) > 1
  AND (p.polroles = '{0}'
       OR pg_get_expr(p.polqual, p.polrelid) = 'true'
       OR pg_get_expr(p.polwithcheck, p.polrelid) = 'true')
ORDER BY 1, 2;
```

**PERMISSIVE 之间是 OR** —— 一条恒真策略就作废了旁边的租户策略。
这条断言是 Bot 鉴权反查引入的（`../spec/05-安全与租户隔离.md` §3.7
给 `tenant_members` 加了第二条策略），误写的后果已实测。

已实测：`polroles = '{0}'` 即 PUBLIC，`{16385}` 之类是具体角色 OID。
造一张两条策略都不限角色的表 → 命中；`tenant_members` 那种
一条 `TO app_user` 一条 `TO auth_lookup` 的正确写法 → 不误报。
单策略表（绝大多数）不进这个查询，`count(*) > 1` 那个子查询已排除。

**判据订正过一次。** 原判据只查 `polroles = '{0}'`，漏掉**角色限定的恒真策略**：

```text
CREATE POLICY ... ON tenant_members FOR SELECT TO app_user USING (true)
  polroles 是 {16386} 而不是 {0} → 旧断言一声不响
  实测危害与 PUBLIC 等同：attacker 身份读 tenant_members 从 0 行变成 1 行
```

所以判据是「PUBLIC 策略 **或** 表达式恒真」，两者都要查。
报的是策略名而不是按表聚合 —— 多策略表上报出具体哪条恒真，修的时候能直接定位。

**覆盖边界（PG 不规范化恒真表达式，实测）**：

```text
USING (true)                        → polqual 存成 'true'，抓得到
USING (1=1)                          → 存成 '(1 = 1)'，抓不到
USING (x IS NULL OR x IS NOT NULL)   → 原样保留，抓不到
```

字面量匹配只拦最直白的那种。绕开它需要刻意写成等价的复杂式子 ——
那已不是「顺手写错」而是「刻意规避审计」，后者靠评审不靠这条断言。

**还有一种绕开方式，它不需要恒真也不需要 PUBLIC**（写 R12 时实测出来的，
见 `03-测试策略.md` §3.8）：

```text
把自查策略的 TO 写成两个角色
  CREATE POLICY member_self_lookup ON tenant_members
    FOR SELECT TO app_user, auth_lookup
    USING (user_id = current_setting('app.auth_user_id')::bigint)

  实测：app_user 在单一租户上下文里从 2 行变成 3 行（横跨两个租户）
  A6 不报红 —— polroles 非 {0}，qual 也不恒真，两个条件都不满足
  16 条断言全绿
```

危害与 `USING (true)` 同级（业务角色读到跨租户行），成因却不同：
**不是策略写错，是策略授给了多一个角色。** 判据要抓它得换个方向 ——
「同一张表上同一个角色不得被两条 PERMISSIVE 策略覆盖」，
而本项目的 `identities` 正是那个形状且是有意的
（`tenant_isolation` + `shared_identity_read` 都给 `app_user`，
出处 `../spec/03-数据模型.md` §1.3），所以这条判据得带白名单。
**目前不加**：白名单一带，它就退化成「除了已知的那一个之外」，
而下一个有意的多策略角色也会被加进白名单 —— 那时它拦的东西就没了。
这个洞现在由 `03-测试策略.md` §三 的 R12 第四条断言守着，
是反向测试而不是静态断言。

### A7 A4 白名单表的 GRANT 补偿必须在位

```sql
WITH whitelist(idx) AS (
  VALUES ('bot_console_sessions_pkey'), ('uq_web_session_id')
),
-- 由索引名反查表名。反查必须限定 nspname='public' AND relkind='i'，
-- 且往下传 oid 而不是 relname（三处陷阱见下方）
wl_tbl AS (
  SELECT w.idx, c.oid AS tbl_oid, c.relname AS tbl
  FROM whitelist w
  LEFT JOIN pg_class i ON i.relname = w.idx AND i.relkind='i'
                     AND i.relnamespace = 'public'::regnamespace
  LEFT JOIN pg_class c ON c.oid = (SELECT x.indrelid FROM pg_index x
                                   WHERE x.indexrelid = i.oid)
)
-- 找不到索引也要报红：索引被改名而白名单没跟上，等于 A4 的白名单
-- 指向了一个不存在的东西，而 A4 那边只会静默少排除一项
SELECT idx, '<索引不存在>', '白名单索引查不到所属表' FROM wl_tbl WHERE tbl IS NULL
UNION ALL
-- 有列级形式的四项权限用 has_any_column_privilege
SELECT w.idx, w.tbl, 'app_user 仍持有 ' || pv || '（含列级）'
FROM wl_tbl w CROSS JOIN unnest(ARRAY['SELECT','INSERT','UPDATE','REFERENCES']) pv
WHERE w.tbl_oid IS NOT NULL AND has_any_column_privilege('app_user', w.tbl_oid, pv)
UNION ALL
-- DELETE / TRUNCATE 没有列级形式，只能问表级
SELECT w.idx, w.tbl, 'app_user 仍持有 ' || pv
FROM wl_tbl w CROSS JOIN unnest(ARRAY['DELETE','TRUNCATE']) pv
WHERE w.tbl_oid IS NOT NULL AND has_table_privilege('app_user', w.tbl_oid, pv);
```

白名单是**靠 GRANT 换 RLS** 的：`app_user` 完全碰不到那些表，
只有 `auth_lookup` 能读写（`02-本地环境与迁移.md` §二 的权限矩阵）。
补偿一撤销，A4 放过的侧信道立刻回来。A4 与 A7 必须成对存在。

**白名单写成由索引名反查所属表**，而不是另列一份表名清单 ——
这样 A4 的白名单与 A7 的补偿清单不可能各自漂移，表名是从索引名算出来的。

**四处实测的写法陷阱**：

```text
1 全用 has_table_privilege 会漏报列级授权
  GRANT SELECT (id) ON web_sessions TO app_user
  → has_table_privilege = false、has_any_column_privilege = true
  而 app_user 的 SELECT id FROM web_sessions 真的执行成功。
  补偿被列级授权掏空，只问表级的断言察觉不到

2 DELETE / TRUNCATE 不能问 has_any_column_privilege
  ERROR: unrecognized privilege type: "DELETE"
  —— 这两项没有列级形式，必须单独一支问表级

3 传 relname 而不是 oid
  裸名字走 search_path 解析。实测 has_any_column_privilege('app_user',
  'probe_nonexistent_t','SELECT') → ERROR: relation ... does not exist。
  别的 schema 里有同名索引时，反查拿到它的基表名而该表不在搜索路径里 →
  A7 整条崩掉。传 oid（regclass 重载）完全绕开这件事

4 反查不限定 relkind='i'
  同名的表/视图让 indrelid 子查询返回 NULL，这一条被当成「索引不存在」
  报红 —— 误报，方向安全但指错地方
```

本库目前只有 `public` 一个 schema，所以 3、4 两条是「以后会炸」而不是「现在是坏的」。

### A8 `tenant_id` 表上不得有普通视图与 `SECURITY DEFINER` 函数

```sql
WITH tenant_tbl AS (
  SELECT c.oid FROM pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace
  WHERE n.nspname='public' AND c.relkind IN ('r','p')
    AND EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid=c.oid
                AND a.attname='tenant_id' AND a.attnum>0 AND NOT a.attisdropped)
)
-- 视图侧与函数侧**不限定 schema**，只有上面 tenant_tbl（基表侧）限定 public：
-- 别的 schema 里的视图照样能读 public 的表，SECURITY DEFINER 更是与所在 schema 无关。
-- 排除 pg_* / information_schema 用 nspname 前缀过滤而不是 oid 白名单，
-- 因为 pg_toast / pg_temp_N 也要排除
SELECT n.nspname||'.'||v.relname AS obj, 'view' AS kind FROM pg_class v
JOIN pg_namespace n ON n.oid=v.relnamespace
WHERE n.nspname NOT LIKE 'pg\_%' AND n.nspname <> 'information_schema'
  AND v.relkind='v'
  -- 用 pg_options_to_table 取值再转 bool，不要拿 reloptions 做数组包含判断：
  -- 实测 security_invoker = on 会原样存成 {security_invoker=on}，
  -- 而 = true 与裸写都存成 =true，按数组匹配会把合规视图当违规报出来
  AND NOT coalesce((SELECT o.option_value::bool
                    FROM pg_options_to_table(v.reloptions) o
                    WHERE o.option_name='security_invoker'), false)
  -- 视图对基表的依赖挂在 pg_rewrite 上，不是视图 oid 上。实测直接用
  -- pg_depend.objid = v.oid 查不到任何行，断言会静默全绿
  AND EXISTS (SELECT 1 FROM pg_rewrite rw
              JOIN pg_depend d ON d.classid='pg_rewrite'::regclass AND d.objid=rw.oid
              WHERE rw.ev_class=v.oid AND d.refclassid='pg_class'::regclass
                AND d.refobjid IN (SELECT oid FROM tenant_tbl))
UNION ALL
-- 函数不按表过滤：pg_depend 不记录函数体引用的表（实测 0 行），
-- 所以无法判断一个 SECURITY DEFINER 函数碰不碰带 tenant_id 的表。
-- 定案是「全面禁用」，按全库报出反而是正确形状
SELECT n.nspname||'.'||p.proname, 'security_definer_function' FROM pg_proc p
JOIN pg_namespace n ON n.oid=p.pronamespace
WHERE n.nspname NOT LIKE 'pg\_%' AND n.nspname <> 'information_schema'
  AND p.prosecdef;
```

这条拦的不是泄漏，是**功能坏掉**：`FORCE` 后这两条路径以 owner 身份执行，
无策略匹配 owner → 静默 0 行（`03-测试策略.md` §五 的实测表）。
在功能测试里表现为「查不到数据」，极易误诊成数据没写进去。
所以它是静态断言而不是动态测试 —— 静态的更可靠。

> **物化视图不在本条覆盖内**，它的 `relkind` 是 `'m'` 而不是 `'v'`。
> 而物化视图**根本不支持 RLS**，所以它不是「配置不对」而是「这类对象本身不能有」——
> 判据性质不同，单独立为 §三-3。主查询的 `('r','p')` 与本条的 `'v'` 都不含 `'m'`，
> 这个缺口是实现时造破坏用例才发现的。

**三处实测踩到的写法陷阱**，都属于「写错了不报错、只是永远全绿」那一类：

```text
1 视图对基表的依赖记在 pg_rewrite 上，不在视图 oid 上
  直接查 pg_depend.objid = v.oid 返回 0 行 → 断言静默全绿
2 security_invoker = on 与 = true 在 reloptions 里存的字面量不同
  {security_invoker=on} vs {security_invoker=true}
  按数组包含判断会把合规视图误报成违规
3 视图侧与函数侧限定 nspname='public' 等于「换个 schema 就绕过」
  SECURITY DEFINER 与函数所在 schema 无关，别的 schema 里的视图
  也照样能读 public 的表。只有基表侧该限定 public
```

函数侧按全库报是有意的，与 `00-工程约定.md` §七 CR8「全面禁用」一致，
不是过度报警 —— 提权路径只有 `admin_tx` 一条。

### A9 双方都有 `tenant_id NOT NULL` 时外键必须含 `tenant_id`

```sql
SELECT ct.conrelid::regclass AS child, ct.confrelid::regclass AS parent, ct.conname
FROM pg_constraint ct
JOIN pg_class c ON c.oid = ct.conrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE ct.contype='f' AND n.nspname='public'
  AND EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid=ct.conrelid
              AND a.attname='tenant_id' AND a.attnum>0 AND NOT a.attisdropped)
  -- 父表侧要求 tenant_id NOT NULL。这一条让 identities 自动落选 ——
  -- 铁律 4 的例外由断言形状承载，不靠硬编码表名
  AND EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid=ct.confrelid
              AND a.attname='tenant_id' AND a.attnum>0 AND NOT a.attisdropped
              AND a.attnotnull)
  -- 判据是「列序对齐」，不是「conkey 里含 tenant_id」。
  -- conkey[i] 与 confkey[i] 按下标一一对应，所以要同一个 i 上两边都是 tenant_id
  AND NOT EXISTS (
        SELECT 1 FROM generate_subscripts(ct.conkey, 1) i
        WHERE ct.conkey[i] = (SELECT a.attnum FROM pg_attribute a
                              WHERE a.attrelid=ct.conrelid AND a.attname='tenant_id')
          AND ct.confkey[i] = (SELECT a.attnum FROM pg_attribute a
                               WHERE a.attrelid=ct.confrelid AND a.attname='tenant_id'));
```

单列 FK 会让**跨租户边在库层可表达**：RLS 不拦建边、规则静默失效、
FK 报错成为 id 枚举侧信道、且可 DoS 他租户的 DELETE。四项均已实测。

**判据从「含不含」改成了「对齐不对齐」。** 原写法只问 `tenant_id` 在不在 `conkey` 里，
放得过错位形状：

```text
FOREIGN KEY (tenant_id, keyword_id) REFERENCES keywords (id, tenant_id)
  conkey={2,3}、confkey={1,2} —— 子表 tenant_id 在位置 1，
  而该位置父表侧对到的是 id。形式合规，实质仍可建跨租户边
```

实测现有 10 条复合 FK 在新判据下全部对齐（新旧判据在当前库同为绿），
所以这是**补覆盖缺口，不是修现存违规**。
单列形状仍被覆盖：它连 `tenant_id` 都不在 `conkey` 里。

> 顺带一条 PG 行为，造这个破坏用例时撞到的：**被引用列按集合匹配，不按顺序。**
> 所以上面那个错位 FK 直接复用了现有的 `uq_keywords_tenant_id (tenant_id, id)`，
> 不需要另建索引 —— 也就是说错位写法在实践中毫无阻力。

**断言形状承载了铁律 4 的例外**：父表侧要求 `tenant_id NOT NULL`，
`identities` 的 `tenant_id` 有意可空 → 自动落选，不需要硬编码表名。
例外的代价在应用层付：租户指定一个 NULL-tenant 身份要返回 403
（反向测试 R19，`03-测试策略.md` §三）。

A4 与 A9 互补不重复：**A4 管唯一约束（探测存在性），A9 管外键（建跨租户边）。**
两者都按真实表形状实测过 —— 造一张单列 FK 的违规子表精确命中，
`rules` 那种复合 FK 与指向 `identities` 的单列 FK（例外）均不误报。

## 三、补充断言

它们不在 `A1`~`A9` 的编号里，因为各自只管一处。除 `C3` 外都属 `tgm audit-rls`。
`C4`/`C5` 是实现时补的，理由各写在条目里。

**1）`C1` 乙类两张子表的 RLS 白名单断言**

```sql
-- rule_conditions / delivery_logs 没有 tenant_id 列，主查询覆盖不到。
-- 白名单断言必须从白名单那一侧出发（VALUES LEFT JOIN），不能从目录出发
SELECT w.tbl,
       CASE WHEN c.oid IS NULL THEN '表不存在于 public —— 被删或被改名'
            WHEN NOT c.relrowsecurity THEN 'RLS 未 ENABLE'
            WHEN NOT c.relforcerowsecurity THEN 'RLS 未 FORCE'
            ELSE '零条策略 —— FORCE 下等于默认拒绝，业务读不到任何行'
       END AS why
FROM (VALUES ('rule_conditions'), ('delivery_logs')) w(tbl)
LEFT JOIN pg_class c ON c.relname = w.tbl AND c.relkind IN ('r','p')
                    AND c.relnamespace = 'public'::regnamespace
WHERE c.oid IS NULL
   OR NOT (c.relrowsecurity AND c.relforcerowsecurity
           AND (SELECT count(*) FROM pg_policy p WHERE p.polrelid = c.oid) > 0);
```

这是**唯一一处用白名单表名的断言**，因为判据不可能从列结构推出来 ——
这两张表恰恰是以「没有 `tenant_id`」为特征的。

原写法（`WHERE relname IN (...)`）有三处漏报，都是实现时造破坏用例撞出来的：

```text
表被删或改名  匹配不到就是零行，而零行即通过 —— 「要查的东西不存在」
              和「查过了没问题」在结果里长得一样
策略数为 0    主查询按「有 tenant_id 列」筛表，而这两张表的特征恰恰是没有
              tenant_id → 谁都没在看它们的策略。FORCE + 零策略是默认拒绝，
              是故障不是泄漏，但比泄漏更容易被误诊成「数据没写进去」
没有 schema   别的 schema 里的同名表会混进来，与 A7 反查那处同一个形状
过滤
```

**2）`C2` `identities.tenant_id` 写入即不可变**

`../spec/06-合规与凭据责任.md` §2.5 要求「不提供把身份转给别的租户的端点」。
库层没有「列不可 UPDATE」这种约束，所以断言只能做到检查运行时角色
对 `identities` 的 UPDATE 权限是否被收窄到不含 `tenant_id` 列：

```sql
SELECT rr.rolname, 'identities.tenant_id UPDATE' FROM <runtime_role> rr
WHERE has_column_privilege(rr.oid, 'identities'::regclass, 'tenant_id', 'UPDATE');
```

角色从 `A0` 的派生来，不再只查 `app_user` 一个名字 ——
`auth_lookup` / `platform_ops` 同样不该能改这一列。

> 这条断言弱于它想保证的性质：列级 GRANT 能拦住运行时角色改这一列，
> 但拦不住「先删后建」这种等效操作。真正的保证靠 §2.5 的
> 「写入路径只有一条」，这条断言只是把最直接的那条路堵上。

**写法陷阱（本条存在的理由，已实测）：列级 `REVOKE` 减不掉表级 `GRANT`。**

```text
GRANT UPDATE ON identities TO app_user     → 表级，每一列都为 t
REVOKE UPDATE (tenant_id) ON identities    → 仍然是 t，且不报错
正确顺序：先 REVOKE 表级 UPDATE，再逐列 GRANT（见 migrations/0011）
```

改法写反了不报错、权限照旧 —— 所以需要一条断言来判，而不是靠迁移写对。

**3）`C4` 不得存在物化视图**

```sql
-- 物化视图侧不限定 schema，同 A8。relkind = 'm'
SELECT n.nspname||'.'||m.relname,
       CASE WHEN <该物化视图引用了带 tenant_id 的表>
            THEN '读了带 tenant_id 的表' ELSE '未引用 tenant_id 表，仍禁止' END
FROM pg_class m JOIN pg_namespace n ON n.oid = m.relnamespace
WHERE n.nspname NOT LIKE 'pg\_%' AND n.nspname <> 'information_schema'
  AND m.relkind = 'm';
```

它与 `A8` 的差别在**判据的性质**：`A8` 禁的是「配置不对的普通视图」
（加 `security_invoker` 就合规），这条禁的是「这类对象本身」——
物化视图根本不支持 RLS，没有「配齐三件套」这条出路：

```text
ALTER TABLE probe_mv ENABLE ROW LEVEL SECURITY
→ ERROR: ALTER action ENABLE ROW SECURITY cannot be performed on relation
  DETAIL: This operation is not supported for materialized views.
```

危害实测：victim 租户写入 `keywords` 一行，以 owner 建物化视图固化其内容，
attacker 租户从基表读到 0 行、从物化视图读到 1 行 `victim-secret`。
原文漏了它，是因为两处 `relkind` 都不含 `'m'`：主查询查 `('r','p')`、`A8` 查 `'v'`。

**不引用租户表也报。** 判据不该依赖 `pg_depend` 的准确性 ——
物化视图可以后续 `REFRESH`、可以被 `ALTER`，「当前定义没碰租户表」
不保证下一版不碰。一律禁掉，需要破例时走评审加白名单。

**4）`C5` 登录角色不得持有组成员身份**

```sql
SELECT m.rolname AS login_role, g.rolname AS grp, <why>, <inherit/set 标志>
FROM pg_auth_members am
JOIN pg_roles m ON m.oid = am.member
JOIN pg_roles g ON g.oid = am.roleid
WHERE m.rolcanlogin
  AND NOT (m.rolname = 'postgres' AND g.rolname = 'tgm_owner');
```

补的是 `A0` 那条派生的盲区。派生认的是 `a.grantee = r.oid`，即**直授**给该角色的
ACL 条目。权限若经一个组角色继承而来，被授的是组的 oid，
登录角色本人在 `relacl` / `attacl` / `polroles` 三处都查不到 ——
整个角色从派生落选，`A1`/`A2a`/`A2b`/`C2` 一条都不查它，而 `A0` 照样绿（派生非空，只是缺人）。

**为什么不去修派生**（实测过，两种改法都更坏）：

```text
把 a.grantee = r.oid 换成 pg_has_role(r.oid, a.grantee, 'USAGE')
  → 把 postgres 拉进派生集（它经 GRANT tgm_owner TO postgres 继承），
    而 postgres 是 rolsuper + rolbypassrls → A2a 在健康库上当场报红，是误报
再加一句 AND NOT r.rolsuper 排掉超级用户？方向更坏
  → A2a 的全部职责就是「运行时角色被提成超级用户时报红」，
    把超级用户排掉它就永不可能触发 —— 从「误报」换成「绿得毫无意义」
```

所以换个方向：不追认继承来的权限，而是**禁掉「登录角色持有组成员身份」这件事本身**。
派生的前提（权限都是直授的）从此由断言维持，而不是靠假设。

> **豁免写成 `postgres → tgm_owner` 这一对，而不是豁免 `postgres` 整个角色。**
> 这一对是 `scripts/init/01-roles.sql` 故意建的：`tgm_owner` 是 NOLOGIN，
> 审计与迁移都靠 `postgres` 继承它才能跑。写成「一对」，
> 是为了让别人以后给 `postgres` 加第二个组时这条断言会红。

判据不看 `inherit_option` / `set_option` 这两个标志，只看关系存在不存在 ——
`inherit` 自动生效、`set` 要 `SET ROLE` 才生效，但**都能拿到权限**。
两个标志一并打出来只是为了给人看。

**5）`C3` `openapi.json` 与代码一致**

```bash
tgm openapi --check      # 重新生成并与仓库内的 openapi.json 比对，不一致即失败
```

它比对的是文件而不是数据库状态，所以不在 `tgm audit-rls` 里，是独立子命令。
与 `.sqlx/` 必须提交是同一个模式（`00-工程约定.md` §6.1）：
**把「代码与契约一致」变成机器能判的事**，而不是评审时靠眼睛看。
契约形态与两份文件拆分的理由见 `../spec/07-接口契约.md` §2.2。

后两条是补录的：它们本来只在 ci.yml 里，而本节自称定义处 ——
于是「清单少一条」这个失败方向对它们不成立（谁照清单核对 CI 都发现不了
它们被删掉）。补录时机器比对过一次，现在两边条目一一对应。

> **但「机器比对过一次」不等于比对是对的。**2026-09-23 重比一次，
> 第一版脚本把清单项截取成命令首词，于是 `tgm openapi --check` 匹配到
> 「`tgm`」而判成 OK —— **而它恰好是唯一一条刻意不在 ci.yml 里的**。
> 只跑那一版就会以为两边对齐验过了。修正后它才落到「仅注释」，
> 同时 `tgm audit-rls` 转为误报（ci.yml 里写作
> `cargo run --bin tgm -- audit-rls`，字面不同）。
> 判据：比对脚本要先在**已知答案的那一条**上验 —— 这份清单里的已知答案
> 就是 `tgm openapi --check` 必须报「不在 ci.yml」。它报 OK 就是脚本坏了。

前五条不需要数据库之外的东西。`tgm audit-rls` 需要一个跑完全部迁移的库，
在 CI 里复用 L2/L3 那套服务（`02-本地环境与迁移.md` §一 的同一份 compose）。
`scripts/check-newtype.sh` 是 grep 级检查，也不需要库
（「不实现某 trait」在 Rust 里断不了言，理由见该脚本开头）。

落地形式是 `.github/workflows/ci.yml`，**本清单仍是定义处**，两边必须同步 ——
少一条就是那条卡口不存在，而流水线照样全绿。分两个 job（`static` / `database`）
不是为了提速：不连库那几条红是代码问题，连库那几条红可能是库没起来，
混在一个 job 里，一次 compose 启动失败会长得像审计断言报红。

另有一条**在清单里而刻意不在 ci.yml 里**：`tgm openapi --check`。
契约导出随 WP-5 落地，该命令现在 `exit 1`（见 §六），放进 CI 会让每次 PR 都红。
它在 yml 末尾以注释形式列出而不是静默省掉 —— 一条漏掉的卡口和一条
不存在的卡口在 yml 里长得一样，而前者是事故。

两处实测得到的必要参数：

```text
--workspace       没有它，cargo sqlx prepare --check 只看当前 crate。
                  这是个多 crate workspace，漏掉等于卡口只管一个 crate
DATABASE_URL      sqlx-cli 只认这个环境变量名，不认本仓库用的 TGM_DB_URL_OWNER。
                  且 tgm_owner 是 NOLOGIN，所以这里要用 postgres 连
SQLX_OFFLINE=true CI 的 static job 里没有库，靠已提交的 .sqlx/ 做编译期校验
                  （`00-工程约定.md` §6.1）。不设它 sqlx 会去连 DATABASE_URL
```

> **实测记一笔：这条卡口的反证本身会被增量编译骗过。**
> 删掉 `.sqlx/` 后跑 `cargo build --workspace`（离线）返回 0 ——
> 因为 cargo 判定 `tgm-db` 无需重编译，宏压根没展开。
> 必须 `cargo build -p tgm-db` 强制重编译才看到
> `SQLX_OFFLINE=true but there is no cached data for this query`（rc=101）。
> CI 是冷缓存所以不受影响，但**在本地验这条卡口时那个绿是假的**。

`scripts/audit-double-pass.sh` 是 ADR-0022「断言替代第二人复核」的可执行形式。
它不是「再跑一遍 `audit-rls`」：判据是**逐条**破坏后恰好那一条红
（而不是「至少有一条红」），并在撤销后比对一份库状态快照必须逐字节相同 ——
后者管的是破坏用例自己有没有留下残留。理由见 `../../pre-do/03-文档待更正.md` 十二。

## 五、审计通过 ≠ 隔离正确

这一整套只验证「配置存在」，不验证「策略写对」。

已实测：一张 `USING (true)` 的表 —— ENABLE、FORCE、策略齐全 ——
主查询返回 0 行（全绿），而 `app_user` 用 `app.tenant_id = 1`
能看到两个租户共 2 行。**静态审计对这种写法完全无感。**

业界有现成的反面教材：某低代码平台的 RLS 扫描器只检查「是否存在任何策略」
而不检查策略正确性，作者自己称之为 "false sense of security"。

所以 `03-测试策略.md` §三 的反向测试是这项审计的**必要补充**，
两者都不能省 —— 尤其 R5（关掉 RLS 后应用层是否仍不泄漏），
它是唯一能证明第一道防线存在的测试。

## 六、本文的局限

- **CI 配置已落地**（`.github/workflows/ci.yml`），§四 十条里有九条在里面
  （缺的那条是 `tgm openapi --check`，有意的，见下）。
  `cargo sqlx prepare --check` 从此不再是空绿灯：`crates/db/src/repo.rs` 的
  `count_keywords` 改用 `query_scalar!` 宏，`.sqlx/` 有了内容，
  实测改 SQL 不重跑 prepare 会红（rc=1）。审计模块仍是有意的例外
  （它必须用运行时 SQL 才能按 `-- name:` 切分并粘进 psql 复现）
- **`cargo sqlx prepare --check` 有两个实测出来的边界，都是「绿得不可信」那一类。**
  ① **无库时它报 error 但 rc=0** —— 所以它只能待在 `database` job；
  放进 static job（那里没有库）会让它每次都绿而什么都没检。
  ② **对 `.sqlx/` 里的多余条目只给 warning，rc 仍是 0** ——
  ~~「SQL 删了但缓存条目没删」这件事目前没有任何卡口管。~~
  **已补（2026-09-23）**：ci.yml 那一步不再只看 rc，改成把输出 `tee` 到
  文件再 `grep "unused queries found"`，命中就 `exit 1`。
  `set -o pipefail` 保证 `prepare` 自己的失败不被 `tee` 吃掉。

  为什么值得补而不是记成局限：`.sqlx/` 是 static job 里 `SQLX_OFFLINE`
  编译的**唯一事实来源**。留一条指向已删列的缓存，下一个改这块的人会拿到
  一份编译期通过、运行时报 `column does not exist` 的代码 ——
  而那次失败发生在离这里很远的地方。

  验法（两个方向，从 ci.yml 里把那段 `run` 提取出来实跑，不是另写一遍）：
  干净时 rc=0；往 `.sqlx/` 塞一个改了 `query` 字段的条目，
  输出 `potentially unused queries found in .sqlx`、新卡口 rc=1
  —— 而 `--check` 自己在同一状态下 rc 是 0。
  与 static job 的 `SQLX_OFFLINE=true cargo build` 也不重复：两条在
  「改了 SQL 没重跑 prepare」这个方向上都红（实测 rc 分别是 101 与 1），
  但前者给的是编译错误，后者给的是 `.sqlx is missing one or more queries`
  —— 后一句能直接告诉人下一步做什么
- **`tgm openapi --check` 仍未实现，但它现在 `exit 1` 而不是 `exit 0`。**
  一条恒 0 的卡口与一条通过的卡口在 CI 里完全同形，而
  `not_implemented()` 那行 stderr「机器看不见」。代价是它在 WP-5 前进不了 CI
  —— ci.yml 末尾以注释列明这一条及其原因
- **「跑迁移」这一步改走 `tgm migrate`，不再是 `sqlx migrate run`。**
  生产路径是 `tgm migrate`（`../ops/00-部署与运行时.md` §2.1 第 1 步），
  它用 `sqlx::migrate!` **在编译期嵌入** `migrations/`；只跑 CLI 的话，
  「嵌入的那份能不能跑」在 CI 里永远没验过，而两者不一致的方式是存在的
  （改了文件没重新编译，或 include 路径写错却恰好编过）。
  sqlx-cli 仍要装，但降级成单独一步且只服务于 `migrate-idempotent.sh`
  —— 那个脚本内部要 `sqlx migrate run` 来强制重跑。
  实测过从零建库跑完四步（migrate → 可重入 → audit-rls → 双遍）全绿。
  `tgm migrate` 也实测了拒绝被改过的已应用文件：报错文本与 CLI 一字不差、
  rc=1（校验和不区分注释与 DDL，见 `02-本地环境与迁移.md` §3.2）
- ~~**ci.yml 本身没有在 GitHub 上跑过。**~~ **已销账（2026-09-23）**：
  在 `ci/verify-wp1` 上开 PR 跑了两次，第二次两个 job 全绿
  （`static` 29s、`database` 2m49s）。runner 上核实到的实测值：
  `tgm migrate` 报「12 个版本已应用」、`migrate-idempotent.sh` 12 文件重跑
  逐字节相同、`audit-rls` 16 条、双遍 16 条逐条打红且收尾快照 554 行
  与本地同一个数、`cargo test --workspace` 59 passed 0 failed。

  **首跑是红的，而且红对了。** `pg_dump` 挑成了 16.15：
  `apt-get install postgresql-client-17` 成功装了 17.11，但 runner 镜像
  自带的 client-16 占住 `/usr/bin/pg_dump`，装 17 只往
  `/usr/lib/postgresql/17/bin/` 放文件。本节原先那句「pg_wrapper 会选
  已装的最高版本，所以不需要改 PATH」**在 runner 上不成立** ——
  这正是「本地全绿不等于 CI 会绿」的一个实例，而它只能靠真跑一次发现。

  修法两处：ci.yml 把 17 的 bin 写进 `$GITHUB_PATH`，并把版本从「打印」
  改成「断言」（只打印的话版本不对也绿到下一步，报错指向 `backup.rs`
  而不是装机那一步）；`crates/db/tests/backup.rs` 的 `pg_dump()` 从
  「能起就用」改成「必须 17.x」。

  **后一处是防误绿，不只是提前报红。** 版本不匹配时 `pg_dump` 也失败，
  而 R7 正向那条的判据是「退出码非 0 且 stdout 没有业务数据」——
  版本不匹配恰好同时满足，那条会**因为错误的原因变绿**。
  首跑只红了反证那条，正向那条当时是绿的，而它的绿是假的。
  验法：造一个只报 16.15 的假 `pg_dump` 放 PATH 最前、`HOME` 指向不存在
  的目录，改后两条都红 —— 改前正向那条绿
- §三-2（`C2`）的断言弱于它要保证的性质，已在该条下写明

  把自查策略的 `TO` 写成两个角色（不恒真、非 PUBLIC），业务角色就读到
  跨租户行，16 条全绿 —— 详情与不加断言的理由写在 `A6` 那条下。
