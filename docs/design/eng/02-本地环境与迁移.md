# 本地环境与迁移

本文是**本地环境编排与迁移序列的唯一定义处**。没有它，
`cargo sqlx prepare --check`（`04-CI门禁.md`）跑不起来，
即第一行业务代码都提交不了。

角色的职责划分见 `../spec/05-安全与租户隔离.md` §六，本文给它的可执行形式；
表结构见 `../spec/03-数据模型.md`，本文只管**顺序**。

**实测环境**：docker 29.1.3 · `postgres:17-alpine` = **PostgreSQL 17.11**
（正好满足安全下限）。

---

## 零、三个会让第一天卡住的坑（已实测）

在真实 PG 17.11 上跑通角色初始化与 RLS 配置，过程中撞到三个坑。
它们的共同点是**报错信息完全指不到真正的原因**：

```text
坑 1  PG 15+ 起 public schema 默认不对非 owner 开放
      → CREATE TABLE 直接 "permission denied for schema public"
      报错看着像权限没给够，实际要改的是 schema 的 owner
坑 2  FORCE ROW LEVEL SECURITY 之后，owner 自己的 INSERT 也被策略拦
      → "new row violates row-level security policy"
      报错里没有任何线索指向「种子数据的执行顺序」
坑 3  容器 pg_isready 返回就绪后仍可能拒连（初始化期会重启一次）
      → 等待必须用真实 SELECT 1 探测，不能用 pg_isready
```

坑 2 是三个里最贵的：它在迁移脚本写好之后才出现，
且「换个顺序就好了」这个结论几乎不可能从报错文本推出来。

## 一、compose 编排

```yaml
# compose.yaml
services:
  postgres:
    image: postgres:17-alpine          # 实测 = 17.11，满足 CVE-2026-14666 下限
    environment:
      POSTGRES_PASSWORD: pw
      POSTGRES_DB: tgm
    ports: ["55432:5432"]
    volumes:
      - ./scripts/init:/docker-entrypoint-initdb.d:ro
    healthcheck:
      # 必须用真实查询，不能用 pg_isready —— 见 §零 坑 3
      test: ["CMD-SHELL", "psql -U postgres -d tgm -c 'SELECT 1' || exit 1"]
      interval: 2s
      retries: 30

  pgbouncer:
    image: edoburu/pgbouncer:v1.25.2-p0   # ≥1.25.1（CVE-2025-12819），实测该 tag 存在
    environment:
      DB_HOST: postgres
      DB_NAME: tgm
      POOL_MODE: transaction              # 硬要求
      SERVER_RESET_QUERY_ALWAYS: 1        # 硬要求，是安全配置不是调优
      MAX_PREPARED_STATEMENTS: 200        # ≥1.21 才支持预编译语句
    ports: ["56432:5432"]
    depends_on: { postgres: { condition: service_healthy } }

  redis:
    image: redis:8-alpine
    ports: ["56379:6379"]

  minio:                                  # 媒体中转目标
    image: minio/minio
    command: server /data
    ports: ["59000:9000"]
```

> **PgBouncer 不是可选项。** transaction 模式下裸 `SET` 跨进程泄漏是
> **实测**出来的（`../spec/05-安全与租户隔离.md` §3.3 纪律 2）。
> 本地不带 PgBouncer 就测不到真实行为 —— 而那正是隔离测试要验的东西。
>
> **但日常开发连 55432（直连 PG）**，只在跑隔离测试时连 56432（经 PgBouncer）。
> 理由：sqlx 的编译期校验与迁移走直连更省事，
> 而 PgBouncer 的价值只在验证隔离行为时才体现。

## 二、角色与初始化脚本（实测可跑通）

```sql
-- scripts/init/01-roles.sql
CREATE ROLE tgm_owner   NOLOGIN;                                -- 建表与迁移
CREATE ROLE app_user    LOGIN PASSWORD 'apw' NOBYPASSRLS;       -- 业务运行时
CREATE ROLE auth_lookup LOGIN PASSWORD 'lpw' NOBYPASSRLS;       -- 鉴权反查专用
CREATE ROLE platform_ops LOGIN PASSWORD 'ppw' NOSUPERUSER NOBYPASSRLS; -- 平台日志只读
GRANT tgm_owner TO postgres;

-- 坑 1：PG 15+ 起 public schema 默认不对非 owner 开放。
-- 漏这一行，迁移第一条 CREATE TABLE 就 "permission denied for schema public"
ALTER SCHEMA public OWNER TO tgm_owner;

GRANT USAGE ON SCHEMA public TO app_user, auth_lookup, platform_ops;
```

**四个角色的权限矩阵**（逐权限列举，不写 `GRANT ALL`）：

| | tgm_owner | app_user | auth_lookup | platform_ops |
|---|---|---|---|---|
| 建表 / 迁移 / 建策略 | ✓ | ✗ | ✗ | ✗ |
| 甲类 19 张（带 `tenant_id`） | owner | SELECT/INSERT/UPDATE/DELETE | ✗ | ✗ |
| `tenant_consents` | owner | **SELECT/INSERT only**（凭证不可改） | ✗ | ✗ |
| `tenant_members` | owner | SELECT/INSERT/UPDATE/DELETE | **SELECT only** | ✗ |
| `bot_console_sessions` | owner | **全部 REVOKE**（补偿侧信道） | SELECT/INSERT/UPDATE/DELETE | ✗ |
| `web_sessions` | owner | **全部 REVOKE**（同一修法） | SELECT/INSERT/UPDATE/DELETE | ✗ |
| `console_login_challenges` | owner | **全部 REVOKE**（本表不启用 RLS） | SELECT/INSERT/UPDATE/DELETE | ✗ |
| `system_logs` / `audit_logs` | owner | SELECT/INSERT/UPDATE/DELETE | ✗ | **SELECT only**，策略限 `tenant_id IS NULL` |
| **TRUNCATE（任何表）** | ✓ | **永不授予** | ✗ | ✗ |
| `pg_dump` / 备份 | ✓ | ✗（实测必然失败） | ✗ | ✗ |

`TRUNCATE` 那一行是安全要求：**`TRUNCATE` 不受 RLS 约束**
（`../spec/05-安全与租户隔离.md` §3.5）。默认的 `GRANT ALL` 会把它带上，
所以必须逐权限列举 —— 这是「不写 `GRANT ALL`」的全部理由。

## 三、迁移序列

`../spec/03-数据模型.md` 的 DDL 是**最终态视图，不是迁移序列**。切法：

```text
migrations/
  0001_roles_and_schema.sql        角色 + schema owner（§二）
  0002_tables.sql                  27 张表 DDL + 索引
  0003_seed.sql                    种子数据（必须在 0004 之前）
  0004_rls_enable_force.sql        ENABLE + FORCE
  0005_rls_policies.sql            策略（含三分类的分别处理）
  0006_grants.sql                  §二 的权限矩阵，逐权限列举
  0007_event_trigger.sql           分区用的 rls_auto_enable()
```

**这个顺序是安全要求，不是风格偏好。** 两处具体理由：

`0003` 在 `0004` 之前 —— 即坑 2。实测报错：

```text
ERROR: new row violates row-level security policy for table "rules"
```

执行者是 **owner**、策略写的是 `TO app_user`（跟 owner 无关），照样被拦。
原因是 `FORCE` 让 owner 也受策略约束，而没有任何策略匹配 owner，默认拒绝。
若种子数据必须在 FORCE 之后灌，唯一的办法是临时 `DISABLE` 再恢复 ——
那等于在迁移里开一个窗口，宁可调整顺序。

`0004` 与 `0005` 分开 —— 因为**策略可以存在于一张 RLS 已关闭的表上，
此时策略被完全忽略**（已实测：`DISABLE` 后 `relrowsecurity=f`，
但 `pg_policy` 仍有记录）。分成两个文件，审计能分别验证「开了」和「有策略」两件事。

### 3.1 建表的两个静默陷阱

```text
1 CREATE TABLE cp (LIKE orig INCLUDING ALL)  →  relrowsecurity = f，零策略
  INCLUDING ALL 的清单里没有 RLS 这一项。用 LIKE 造表 = RLS 静默丢失。
2 策略存在 ≠ RLS 启用（见上）。
  → 只查 pg_policy 有无记录的审计脚本会漏掉这种表
```

第 1 条在迁移里最容易出现的形态是「改列类型要重建表」——
那是个日常操作，而它会静默摘掉一张表的 RLS。

### 3.2 迁移失败的处置

**不写 down 迁移。** 理由：这个库里的迁移有一半是安全配置
（`0004`~`0007`），而「回退安全配置」这个动作本身就是事故 ——
一个能把 FORCE 撤掉的脚本存在于仓库里，被误跑一次的代价远大于它的便利。

于是失败处置分三种情形：

```text
本地      docker compose down -v，从零重建。成本几十秒，不值得做 down
上线前    同上。首发阶段的租户是手工开通的，重建库的数据代价可控
上线后    只能前滚：写一个新的迁移修正它，不回退
```

上线后前滚的前提是**迁移必须可重入**：
`CREATE TABLE IF NOT EXISTS` 这类写法要用在 DDL 上，
`0003_seed.sql` 要用 `ON CONFLICT DO NOTHING`。
理由是失败的迁移可能已经部分提交 —— PG 的 DDL 虽然事务安全，
但 sqlx 的迁移器是**按文件**记录版本的，一个文件里多条语句时
部分成功的状态是真实存在的。

**每个迁移文件尽量只做一件事**，就是为了让部分成功的窗口最小。

> **不得在迁移里做数据回填的长事务**：27 张表都带 RLS，
> 回填走的是 owner 身份 + `FORCE`，会撞上坑 2 的同一个机制。
> 需要回填时单独写一个 `tgm` subcommand，用 `app_user` 按租户分批做。

## 四、审计查询已实测能抓错

`tgm audit-rls`（`04-CI门禁.md`）的主查询实测确认能抓错、也不误报：

```text
干净库（1 张表配置正确）        → 返回 0 行            ✓ 通过
注入「有 tenant_id 但没开 RLS」  → bad1|f|f|0          ✓ 抓到
注入「开了 RLS 但漏 FORCE」      → bad2|t|f|1          ✓ 抓到
```

第二种是最危险的那类：`rls_on=t` 看起来是开着的，
只有 `forced=f` 这一列暴露问题，而「只查 `relrowsecurity`」的脚本会漏掉它。
漏 `FORCE` 时 owner 的 `SECURITY DEFINER` 函数和普通视图都泄漏
（`../spec/05-安全与租户隔离.md` §3.3 纪律 1）。

## 五、隔离行为的五项快速实测（结果与设计一致）

在上面的环境里实测过五项，**全部符合预期**：

| 测试项 | 实测结果 | 判定 |
|---|---|---|
| 不设 `app.tenant_id` 直接查 | `ERROR: unrecognized configuration parameter "app.tenant_id"` | ✓ 报错而非 0 行 |
| 租户 1 写 `tenant_id=2` | `ERROR: new row violates row-level security policy` | ✓ `WITH CHECK` 拦住 |
| 正常路径（租户 1） | 返回 `2`（库里租户 1 有 2 行、租户 2 有 1 行） | ✓ 只见本租户 |
| 唯一约束探测 | 租户 1 插入租户 2 已有的 `name='c'` → **成功** | ✓ 无 duplicate key 侧信道 |
| `TRUNCATE` 权限 | `ERROR: permission denied for table rules` | ✓ 未授予 |

第四项的关键是唯一索引建成 `(tenant_id, name)` 而非 `(name)`。
建成后者就会报 `duplicate key`，那是 **RLS 原理上补不了**的侧信道。

> **这五项能在 15 分钟内跑完**，说明配 27 张表的工作量主要花在
> 「把每张表都配对」而非「验证机制」。机制本身已经清楚了。
> 完整清单与更复杂的三项（经 PgBouncer 的预编译语句复用、
> owner 的 `SECURITY DEFINER` 函数与视图、受限角色 `pg_dump`）
> 见 `03-测试策略.md`。

### 6.1 测试 Bot 与测试频道（2026-09-21 实测）

**token 不在本文，也不在仓库任何文件里。** 本节只记不敏感的标识与
**实测到的行为**。

token 的去处有一处容易搞错：**数据 Bot 的 token 是租户凭据，
归 `identity_secrets.secret_ciphertext`（密文），不是环境变量。**
`01-配置与Secret.md` 的清单里只有 `TGM_CONTROL_BOT_TOKEN` 那一个
走环境变量，因为控制 Bot 是平台自己的。

所以本地开发要用这两个测试 Bot，路径是「灌一条加密的 `identity_secrets`」，
不是「往 `.env` 里加两行」—— 也就是说**在 KEK 与信封加密可用之前，
这两个 Bot 一行代码都用不上**。这是个排期约束，不是配置问题。
临时验证 Telegram API 行为（如本节这些 `getMe` / `getChat`）
直接用 `curl` 加环境变量即可，别为此在配置清单里开口子。

```text
控制 Bot     @tg_monitor_contr_bot  id 8983228141   平台自有，走环境变量
数据 Bot 1   @tg_monitor_1_bot   id 8869608883
数据 Bot 2   @tg_monitor_2_bot   id 8826916765

演示频道     @tg_monitor_demo    chat_id -1004431202271  公开，type=channel
                                 title=TGMdemo，平台自有自运营（ADR-0027）
频道 1       @tg_monitor_test1   chat_id -1003845201743   公开，type=channel
频道 2       @tg_monitor_test2   chat_id -1004379287008   公开，type=channel

管理员关系   bot1 → 频道 1（administrator）
             bot2 → 频道 2（administrator）
             控制 Bot → 演示频道（administrator，can_post_messages=true）
             前两条实测为 can_post_messages / can_delete_messages 为 true，
             can_promote_members 为 false
```

> **控制 Bot 与演示频道是平台侧素材，和上面两个数据 Bot 不是一类东西。**
> 三处差别都会影响代码走哪条路：
>
> ```text
> token 去处    控制 Bot 走 TGM_CONTROL_BOT_TOKEN 环境变量
>               数据 Bot 走 identity_secrets 密文列
> 隐私模式      控制 Bot 保持开启（can_read_all_group_messages=false），
>               与 spec/08-账号接入.md 的对照表一致。中途手工关过一次、
>               已改回，那次往返本身有结论，记在本节末尾
> 身份归属      演示频道对应的是 tenant_id IS NULL 的共享演示身份
>               （铁律 4 的唯一例外），不是某个租户的源
> ```
>
> 演示频道的存在让 **R19 这条承重测试有了真机对照**：
> 「租户指定 `tenant_id IS NULL` 的演示身份建源 → 403」
> （`03-测试策略.md`）。在此之前它只能靠桩，
> 因为没有真实的共享演示身份可指。
>
> **演示频道已有内容（2026-09-22 复测，4 条 post）**，
> 不再是空频道。但要注意这 4 条里**只有 2 条是真内容**：
>
> ```text
> post 1  Channel created                    服务消息
> post 2  Channel name was changed to «TGMdemo»  服务消息
> post 3  hi                                 text
> post 4  test                               text
> ```
>
> 前两条是建频道自动产生的服务消息，它们**也会作为 `channel_post` 下发**
> （下面那条 `getUpdates` 实测里没有它们，只是因为它们早于 Bot 入频道）。
> 服务消息没有 `text` 也没有 `caption`，只有 `new_chat_title` 之类的字段。
> **这不是演示源特有的**：任何源频道改名、改头像、置顶消息都会推同形状的 update。
>
> 它们照样要落 `canonical_events` —— `../spec/02-总体架构.md` §2.3
> 的「先落库再处理」不允许在接入层丢 update。落进去之后
> `text` / `caption` 都是 NULL、`matched_any` 保持 FALSE、24h 被清理
> （`../spec/04-数据生命周期与容量.md`），所以**不是脏数据问题**。
> 要防的是规则匹配侧：拿 NULL 去做关键词匹配必须明确定义为「不命中」，
> 而不是 panic，也不是当空串去命中某条宽松规则。
>
> ADR-0027 的「自运营」要求的是**持续**内容，这 4 条只够证明通路。
> 演示效果要看的是有没有稳定更新，那仍是产品侧待办。

这个拓扑恰好能验三件事，都是别的办法验不了的：

```text
跨租户边界（只在写侧成立，见下方更正）
                     bot1 对频道 2 发起写动作得 403，查成员得 400，
                     但 getChat 得 ok —— 可以当「两个租户」的替身，
                     前提是断言写在写侧，不是写在读元数据侧
username 刷新        两个频道都是公开且有 username，
                     ADR-0023 的 probe 回写路径可端到端验
-100 前缀            两个 chat_id 都是 -100 开头的 13 位，
                     正是 03-数据模型.md §6.2 那条链接构造规则的输入
```

> **更正（2026-09-21 复测）：上面第一条原先写的是
> 「bot1 查频道 2 得 `400 chat not found`」，那个结论是错的。**
>
> 复测发现 `getChat` 对**公开频道无需成员身份**，任何 Bot 拿 username
> 或数字 `chat_id` 都能读到 `id` / `title` / `username`：
>
> ```text
> bot1 → 频道 2  getChat         ok:true，拿到 id/title/username
> bot1 → 频道 2  getChatMember   400 Bad Request: member list is inaccessible
> bot1 → 频道 2  sendChatAction  403 Forbidden: bot is not a member of the channel chat
> ```
>
> 当初那次 `chat not found` 是**测试脚本自己的 bug** —— Bot token 含 `:`，
> 而脚本用 `:` 做字段分隔，请求里的 `chat_id` 被拼成了
> token 尾段加频道名，Telegram 当然找不到。
> 也就是说那次根本没测到隔离，测到的是一个畸形请求。
>
> **两条后果：**
>
> 1. **跨租户断言必须写在写侧或成员查询侧，不能写在 `getChat` 上。**
>    三个动作给出三种不同结果，其中只有 403 与 400 是真边界。
>    ADR-0023 的 `probe` 要判「还是不是成员」，就**不能只调 `getChat`**：
>    它对已被踢出的公开频道照样返回 ok，`still_member` 会恒为真。
> 2. **公开频道的元数据本来就是公开的**，这不是 Telegram 的漏洞。
>    但它意味着「能读到频道信息」不能作为任何权限的证据 ——
>    `probe` 回写 `title` / `username` 是对的，
>    用同一次调用推断权限是错的。

> **隐私模式：实测确认了它的默认值与可读性两件事。**
>
> ```text
> 首次 getMe（关闭前）          can_read_all_group_messages: false
> 手工在 BotFather 关闭后再查    can_read_all_group_messages: true
> 改回开启后再查（2026-09-22）   can_read_all_group_messages: false
> ```
>
> 三条结论：
>
> 1. **默认值是错的那一侧。** 隐私模式默认开着，不是「需要时去关」——
>    每个新建的数据 Bot 都要去 BotFather 关一次，没有 API 可调。
>    对**频道**没影响（`channel_post` 不受隐私模式约束，
>    且数据 Bot 在频道里是管理员）；对**群组**有影响，
>    不关就是「频道好使、群组静默无消息、零报错」。
>    所以它必须进租户的接入文档。
> 2. **但这个状态是可读的，于是它能做成机器判据。** `getMe` 的
>    `can_read_all_group_messages` 直接反映当前值 ——
>    数据 Bot 接入时校验这一项，为 `false` 就在控制台明确提示，
>    而不是等租户发现群组没消息。这比写进文档可靠，
>    见 `../spec/08-账号接入.md` §2.1。
> 3. **双向都验过了，所以那条启动自检不是单向的。** 控制 Bot 关过又改回，
>    `getMe` 两次都如实反映 —— 也就是说这个字段读的是当前值，
>    不是注册时的快照，自检每次启动都能重新判。
>    改回本身也是必要的：控制 Bot 只处理私聊与命令，
>    开着隐私模式才是它该有的状态。

两个数据 Bot 当前 `getWebhookInfo` 都是 `url: ""`、`pending_update_count: 0`，
即没有任何 webhook 占用，也没有积压的 update。**首次 `setWebhook` 之前
这个状态要复查一次** —— 若 `pending_update_count` 不为 0，
设 webhook 会立刻灌进来一批历史 update，而那时候幂等键还没来得及验。

> **这条警告在控制 Bot 上已经实现了（2026-09-22 实测）。**
> 往演示频道发两条消息后：
>
> ```text
> 控制 Bot  getWebhookInfo  url:""，pending_update_count: 2
> 控制 Bot  getUpdates      两条都是 channel_post（演示频道的 hi / test）
> ```
>
> **积压不是「等 webhook 设好才开始」的，从 Bot 被拉进频道那刻就在攒。**
> 上面那句复查因此不是形式主义 —— 首发时控制 Bot 已经管了演示频道一段时间，
> `setWebhook` 会立刻把这期间的全部 update 灌进来。
>
> 更值得记的是**它为什么收到了 `channel_post`**：
> `../spec/08-账号接入.md` 明确写了控制 Bot 不订阅 `channel_post`，
> 而它照样收到了 —— 因为 `allowed_updates` 还没设过，
> **Telegram 的默认是「除 `chat_member` 外全给」，不是「按文档给」**。
> 所以那条「不要订阅」必须落成 `setWebhook` 的显式 `allowed_updates` 参数；
> 不设就等于订阅了全部，而这种「白拿流量」是静默的：
> 功能全对，只是控制 Bot 在替采集链路收消息。

### 6.2 MTProto 凭据（2026-09-21 实测有效）

**`api_hash` 是 secret，不在本文、不在仓库。** 生产侧的落位是
`identity_secrets`（`api_id` 明文列、`api_hash_ciphertext` 密文列，
见 `../spec/03-数据模型.md`），本地验证时从环境变量读。

> **这一对凭据是开发凭据，不是平台凭据。** 按
> `../decisions/ADR-0013-租户自带api_id.md`，平台不代持 `api_id`，
> 每个租户自己去 my.telegram.org 申请。
> 这里注册的一对只用于 spike 与本地联调 ——
> 它不能出现在任何生产配置路径上，否则就是把 ADR-0013 悄悄推翻了。

验法是 `help.getConfig` —— **不登录、不建 session、不触发短信**。
它是少数不需要授权的 MTProto 方法，握手完成即可调；
`api_id` 与 `api_hash` 不匹配时服务端直接回 `API_ID_INVALID`。
所以「凭据有效」这件事可以和「账号登录」完全解耦地验证，
不必为了验凭据就去走一遍 QR 或验证码。

实测结果里有两项对设计有用：

```text
this_dc = 2        本次连接落在 DC 2
nearest_dc = 5     服务端建议的就近 DC（country=JP）
```

> **这对「注册在非默认 DC 的账号」那条前置条件是个便利，但别当成保证。**
> `../spec/08-账号接入.md` §3.5 那六条里最难凑的是
> 「触发 `MigrateTo` 分支」，它要的是**账号注册的 DC 与客户端连接的 DC 不同** ——
> 决定因素是账号，不是 `nearest_dc`。
> 本机就近 DC 是 5 而 telethon 起手连的是 DC 2，
> 说明在这台机器上注册的账号大概率落在 DC 5，
> 拿它去扫码就有机会命中 `MigrateTo`。
> **但这取决于 grammers 起手连哪个 DC** ——
> 若它遵从 `nearest_dc` 直连 DC 5，两侧就又一致了，分支照样触发不到。
> 所以这条只是「素材可能现成」，不是「条件已满足」，
> 仍需在 spike 里实测确认，不能在清单上直接打勾。

服务端下发的几个限制值也一并记下，因为它们是**服务端的事实**，
比文档里流传的数字可靠：

```text
message_length_max          4096
caption_length_max          1024
forwarded_count_max         100
edit_time_limit             172800   秒 = 48h
revoke_time_limit           2147483647（i32 上限，即不限）
channels_read_media_period  604800   秒 = 7d
```

> **`caption_length_max` 只有 `message_length_max` 的四分之一**，
> 这一条对来源头模板有直接后果：模板拼在正文前面
> （`../spec/03-数据模型.md` §6.2），纯文本消息下 4096 很宽裕，
> 但**带媒体的消息走 caption，上限骤降到 1024** ——
> 一个略长的来源头加上原文 caption 就可能越界。
> 越界的表现是 `sendPhoto` 直接报错、整条投递进重试，
> 而重试必然重复失败（同一条内容长度不会变），白占三次退避直到 DEAD ——
> 与 §6.2 那条 HTML 转义失败的失败模式完全一样。
>
> **首发只转文本（媒体挪演进期，见 `../plan/00-里程碑与工期.md`），
> 所以这不是首发问题**，但它是媒体投递上线时必须先解决的一条，
> 且解法不是「截断原文」那么简单 —— 截断会改变内容，
> 而平台的定位是转发工具。记在这里，以免届时当成新发现。

## 七、本文的局限

- `pgbouncer` 只核实了镜像 tag `v1.25.2-p0` 存在，**本文未实测它与 RLS 的交互**。
  那部分的实测结论在 `../spec/05-安全与租户隔离.md` §3.3 纪律 2
  （裸 `SET` 的跨连接泄漏、`DISCARD ALL` 后的空串残留、
  `server_reset_query_always` 必开）
- MinIO / Redis 的 compose 片段**未实测启动** —— 这是本文最大的未验证项
- §二 的权限矩阵覆盖了甲类与四张特例表，**乙类两张**
  （`rule_conditions` / `delivery_logs`，EXISTS 策略）**未展开**
- §五 的实测都在单表玩具 schema 上做的，**不是 27 张表的真实迁移**
- §3.2 的「不写 down 迁移」是决策，但**上线后前滚的具体流程没写**
  （谁批准、怎么验证、失败了怎么办），那属于 `../ops/01-上线就绪与运维.md`
- 迁移的**可重入性没有测试**。§3.2 要求它可重入，但没有「跑两遍应当等价」
  这样的机器断言
- §6.1 实测的基本都是 Telegram 的**读侧**（`getMe` / `getChat` /
  `getChatMember` / `getWebhookInfo` / `getUpdates`）。
  收到 update 这一步有了（控制 Bot 的两条 `channel_post`），
  但**消息是人在客户端里发的，不是平台发的** ——
  **没有调过一次 `sendMessage`、没有设过一次 `setWebhook`**。
  也就是说投递链路一个字节都还没验证过，采集链路只验到「update 会到」，
  没验到「收下来能落库」。§6.1 的结论只支持
  「拓扑与权限是对的、update 确实会推」，不支持「链路能跑」
- §6.2 只验到**握手层**：`help.getConfig` 证明 `api_id`/`api_hash` 配对有效，
  仅此而已。**没有登录过一次、没有 grammers 参与、没有 session 落过盘** ——
  用的还是 telethon（Python），而首发要用的是 grammers（Rust）。
  「凭据有效」不等于「grammers 能连通」，后者仍是
  `../plan/00-里程碑与工期.md` 里那 4 项 spike 之一，一项都没减少
