# 测试策略

本文是**反向测试清单的唯一归口处**：分层、测试库的正确起法、
42 条反向测试的完整清单。设计文档里凡是说「需要一条反向测试」的地方，
那条测试都在本文 §三 有编号。

**实测环境**：PostgreSQL 17.11 + PgBouncer 1.25.2（transaction 模式）。
环境编排见 `02-本地环境与迁移.md`，CI 怎么跑见 `04-CI门禁.md`。

## 零、两个实测发现直接决定选型

在真实库上验了一遍，撞到两件事，它们**否掉了最省事的默认做法**：

```text
发现 1  #[sqlx::test] 需要超级用户 DATABASE_URL 来建测试库。
        实测：超级用户 postgres 即使在 FORCE ROW LEVEL SECURITY 的表上、
        且完全不设 app.tenant_id，也能看到全部 3 行（跨租户）。
        → 用 #[sqlx::test] 的默认连接跑隔离测试，会「全绿但什么都没测到」

发现 2  静态审计抓不到「策略写成 USING (true)」。
        实测：造一张 bad3 表，有 tenant_id、RLS on、FORCE on、1 条策略，
        审计返回 0 行（判定通过）；而 app_user 在 tenant_id=1 上下文里
        看到了两个租户的全部 2 行。
        → 静态审计与动态反向测试是两件事，
          「审计通过 ≠ 隔离正确」有了本项目自己的实证
```

发现 1 是最危险的一个：它让测试**看起来**在跑，实际上把被测机制整个旁路了。
所以 §二 的第一条纪律是「隔离测试必须以受限角色连接」。

## 一、分层与选型

| 层 | 跑什么 | 依赖 | 工具 | 单次时长目标 |
|---|---|---|---|---|
| L0 静态 | `fmt` / `clippy -D warnings` / `cargo deny` / `sqlx prepare --check` / `tgm openapi --check` | 无 | cargo | < 60s |
| L1 单元 | 规则匹配、去重键、退避算法、状态机迁移 | 无 | `#[test]` + `rstest` 0.27 | < 10s |
| L2 DB 集成 | RLS 反向测试、Repo、迁移、审计 SQL | 真实 PG | `#[sqlx::test]` + **受限角色**（§二） | < 90s |
| L3 隔离专项 | 跨租户读写、唯一约束探测、owner 路径 | PG + PgBouncer | 同 L2，另起一组 | < 60s |
| L4 外部桩 | Telegram Bot API、OIDC 回调 | 无网络 | `wiremock` 0.6 | < 30s |
| L5 混沌 | 租约脑裂五项 | 多进程 + PG | shell + docker | 手动，上线前 |

**选型理由，只说非显然的两条：**

- **L2 用 `#[sqlx::test]` 而不是 testcontainers 0.28**。sqlx 的方案是每个测试一个独立库
  （自动建、自动跑 `migrations/`、失败时保留库便于排查），
  正好匹配「27 张表 × 每表验一遍策略」这种需要干净起点的场景。
  testcontainers 的价值是起整套依赖，那是 L5 的活，用 compose 更直接
- **L4 必须有桩**。「跨租户访问返回 404 不是 403」这条测试不能依赖真实 Telegram。
  而 `my_chat_member` 拉群授权链路没有桩就只能手工拉群，无法进 CI

> **真机素材已就位，但它不改上面那条结论。** 两个测试 Bot 加两个测试频道
> （`02-本地环境与迁移.md`）可以手工走通拉群授权与 `probe` 回写。
> 跨租户边界也能在真机上看到，**但只在写侧**：
> bot1 对频道 2 写动作得 403、查成员得 400，而 `getChat` 得 ok
> —— 公开频道的元数据无需成员身份，详见 `02` 的那条更正。
> **但真机跑的不能进 CI**：token 是 secret，CI 不该持有；
> Telegram 侧有速率限制，也不该被 CI 反复打。
> 真机素材的用途是**验证桩写对了**，不是替代桩。
>
> **而这次更正本身就是「真机验桩」的一个实例**：原先写在这里的
> `400 chat not found` 是测试脚本 token 解析 bug 造成的假结论，
> 一个写错的桩会把它固化成「隔离已验证」。
> 桩要照着**三种不同的错误**写（403 / 400 / ok），不是照着一种。

不引入的：`insta` 快照（本项目没有大块结构化输出值得快照）、
`proptest`（规则匹配是 `aho-corasick` + 正则，边界用 `rstest` 表驱动更直白）、
`criterion`（性能目标用一次性压测脚本验，不需要长期基准）。

## 二、测试数据库：三条纪律

### 2.1 隔离测试必须以受限角色连接

`#[sqlx::test]` 注入给测试函数的 `PgPool` 走的是 `DATABASE_URL`，
而它要建库，所以那个账号必然有 `CREATEDB` —— 实测 `app_user` 建库直接
`ERROR: permission denied to create database`，说明两者不能是同一个角色。

```rust
// tests/support/mod.rs
/// sqlx::test 注入的 pool 是超级用户的，只用来跑 DDL 与断言前置。
/// 任何验证隔离的查询都必须走这个函数换到受限角色。
pub async fn app_pool(admin: &PgPool) -> PgPool {
    let db: String = sqlx::query_scalar("SELECT current_database()")
        .fetch_one(admin).await.unwrap();
    PgPoolOptions::new().max_connections(2)
        .connect(&format!("postgres://app_user:apw@127.0.0.1:55432/{db}"))
        .await.unwrap()
}
```

上面这段是当初的草图。**落地后的真实形态**是把注入池包成
`AdminOnlyPool` newtype（`tests/support/mod.rs`），取用要显式写 `.raw()`，
受限角色池由 `pools()` 一并开出、返回顺序刻意是 `(受限, 管理)`。

配套纪律：**测试代码里禁止用 `sqlx::test` 的 pool 做跨租户断言**。
这条靠评审拦不住（两个 pool 类型一样）。原先这里写的是
「newtype 比 grep 级检查更可靠，因为它让误用不可编译」——
**实测证明这句话只对了一半，两者都要有**：

newtype 让*直接*误用不可编译，但「`AdminOnlyPool` 不实现 `Deref`」
这个命题本身在稳定 Rust 里写不成断言。试过两条路都失败，
且第一条**失败方式是全绿**（autoref 特化探针恒返回同一个值，
加上 `impl Deref` 后测试照样过）。所以那条命题交给
`scripts/check-newtype.sh` 在源码层面 grep，并给它配了自检
（造三个坏副本，必须都被抓到 —— 否则一个正则写错的版本会永远全绿）。
Rust 侧只留正向对偶 `newtype_guard.rs`：保证 `admin_tx` 这条唯一入口是通的，
否则「唯一入口」可能是一个谁都用不了的入口。

第三个坏副本钉的是**白名单的作用域**，它补的是一个真出现过的漏检：
`.raw()` 是 `AdminOnlyPool` 获批的取池路径，而放行规则原先写死在
检查函数内部、对两个被检文件同样生效 —— 于是给生产侧的 `AdminPool`
加一个同签名的 `raw` 会被静默放行（实测 `fail=0`），
而 `AdminPool` 恰恰是 `../plan/00-里程碑与工期.md` §4.3 第 3 条
要求「不得开出取池路径」的那个。现在放行规则按被检目标传参，
`AdminPool` 传空。**「一个白名单是给谁开的」本身需要一条断言** ——
否则它会顺着共用的代码路径扩散到不该放行的目标上。

那条 grep 检查的局限写在它自己的输出里（只查两个文件、只查两种形状、
是文本匹配而非类型检查）—— 不要把它当成完整保证。

### 2.2 迁移顺序即测试前置

`FORCE` 之后 owner 自己也被策略拦（`02-本地环境与迁移.md` §零 坑 2），
所以 fixtures 里的种子数据**不能**在 RLS 启用后插入。
`#[sqlx::test(fixtures(...))]` 的 fixture 是以 `DATABASE_URL` 角色（超级用户）跑的，
**恰好绕过这个限制** —— 但这是偶然安全，不是设计安全。
明确约定：**fixture 只灌数据，不改 RLS 配置**。

### 2.3 每个测试断言自己的角色

```rust
// 每个 L3 测试开头都该有这一句，防止 2.1 的错误静默发生
assert_eq!(
    sqlx::query_scalar::<_, String>("SELECT current_user").fetch_one(&app).await?,
    "app_user"
);
```

**R5 是这份清单里最有价值的一条，也最容易被跳过。** 它测的是
「关掉 RLS 后应用层是否仍然不泄漏」 —— 即
`00-工程约定.md` §四 那条「SQL 里显式写 `WHERE tenant_id`」的纪律
是否真的被执行了。其余所有测试在 RLS 开着时都会绿，
**唯有 R5 能证明第一道防线存在**。

落地形态与原先设想的「CI 跑两遍 L3」不同，**一条测试内跑两遍**：
第一遍 RLS 开着，然后 `ALTER TABLE keywords DISABLE ROW LEVEL SECURITY`，
第二遍再查同一个 Repo 函数。选这个形态是因为「跑两遍」在 CI 编排层面要靠外部状态，
而 `#[sqlx::test]` 每条测试一个临时库，关 RLS 关在自己的库里、不影响别的测试。

**第二遍前必须先裸查一次并断言看到了两个租户的行**（实测 2 行）。
少了这一句，RLS 没真关掉时第二遍与第一遍无异，测试照样绿却什么都没测到 ——
与 `scripts/audit-double-pass.sh` 的判据同形。

### 3.1 分区上线时要补的一条

分区推迟做（`../spec/04-数据生命周期与容量.md` §三），但届时必须补：
**直接指名分区查询，应当不泄漏**。分区不继承父表的 RLS 配置
（实测 `relrowsecurity` 在分区上一律为 `f`），
经父表查是安全的、直接查子表会跨租户返回行。
这条不进当前的 42，它随分区工作包一起进来。

### 3.2 R19 实测：DB 层不拦，403 只能由应用层出

写 R19 时实测发现**数据库不会拦这条，而且必须不拦**：
`shared_identity_read` 策略让 `app_user` 看得见 `tenant_id IS NULL` 的演示身份，
而 `source_subscriptions.receiver_identity_id` 是普通单列外键
（不含 `tenant_id`，因为对侧那一列可以是 NULL，复合外键在这里立不住）
—— 于是租户拿演示身份的 id 去 INSERT，**会成功**。

所以 R19 在 L3 的形态是「记录下 DB 不拦」，403 归应用层。
现有测试 `r19_db_does_not_block_demo_identity` 断言的正是 INSERT 成功，
并附带断言演示身份对租户可见（否则「INSERT 成功」可能只是因为拿不到 id 而没测到）。

**这不是把测试写松。** 反过来写成「DB 会拦」才是假绿：
DB 确实不拦（那条测试即证据），而那样一条绿会让应用层那道检查看起来可以省。
L4 那半条仍然欠着，它随控制台建源接口一起做。

### 3.3 R19 的孪生条：他租户**私有**身份，清单里原先没有

`R19` 覆盖的形状是「租户引用 `tenant_id IS NULL` 的**共享**身份」。
更早的一轮实测（`../../pre-do/03-文档待更正.md` 十九）发现还有一条
**它不覆盖**的边：

```text
tenant 21 上下文、app_user，目标是 tenant 20 的私有身份 900
SELECT ... FROM identities WHERE id = 900   → 0 行        RLS 挡住了读
INSERT target_channels (21, -1, 900)        → INSERT 0 1  边建成了
```

**读不到却能引用** —— FK 检查不过 RLS。`identities` 是七条单列 FK 的父表
（`identity_secrets` / `source_subscriptions` / `target_channels` /
`canonical_events` / `delivery_tasks` / `account_leases` / `bot_console_updates`，
都不能改复合键，因为 `identities.tenant_id` 有意可空），
所以这七条边全都有这个形状。
另外两个后果也复现了：填存在的他租户 id 成功、填不存在的报 FK violation
（两者可区分 = 枚举 oracle）；建边之后 tenant 20 删自己的身份 900
报 `still referenced`（攻击者单方面钉住他租户的数据）。

校验要求是有的（`../spec/06-合规与凭据责任.md` §2.5 第 1 条：
`api_id` 的写入路径只有一条，身份接入端点必须校验
`identities.tenant_id = 当前租户`），但它落在凭据那一节，
**从来没有进过本文 §三 的清单** —— 准确状态是「要求写了、测试没有」。现在登记：

| # | 测试 | 层 | 出处 | 实测状态 |
|---|---|---|---|---|
| R23 | **租户引用他租户私有身份建源 → 404** | L4 | `../spec/06-合规与凭据责任.md` §2.5 第 1 条 | 未登记过，**未验** |

返回 404 不是 403，按 `../spec/07-接口契约.md` §五 的 `NOT_FOUND` 一行
（「含『存在但不属于本租户』—— **不返回 403**」）：403 会确认那个 id 存在，
把上面那条枚举 oracle 从 DB 层搬到 HTTP 层。

**这条不进上面的 42**，与 §3.1 同一个处理：它随身份接入端点的工作包进来，
届时把 42 一并改掉。原产地记录在 `../../pre-do/03-文档待更正.md` 十九，
那条的教训是**同一句话订正了三遍，前两次都没起容器、靠读代码推的**。

## 四、PgBouncer 实测：R3 与 R4 的真实形态

**R3（会话变量跨客户端泄漏）—— 独立复现：**

```text
配置：transaction 模式，server_reset_query_always = 0，default_pool_size = 1
客户端 A：SELECT set_config('app.tenant_id','2',false)   -- 注意是 false（session 级）
客户端 B：全新连接，什么都不设
        SELECT current_setting('app.tenant_id',true)  →  "2"   ← 泄漏
        SELECT count(*) FROM rules                    →  1 行（租户 2 的数据）

改成 server_reset_query_always = 1 + DISCARD ALL：
客户端 B  →  ERROR: invalid input syntax for type bigint: ""
```

两个可操作结论：

1. `02-本地环境与迁移.md` §一 那两个 PgBouncer 环境变量
   **是安全配置，不是性能调优**。漏了就是真实的跨租户泄漏，
   而且泄漏方向不可预测（取决于连接复用顺序）
2. **`DISCARD ALL` 把参数重置为空串，不是 NULL。** 实测：
   `set_config('app.tenant_id','7',false)` → `DISCARD ALL` →
   `current_setting('app.tenant_id', true)` 返回 `[]`（空串），
   而全新连接返回 `[NULL]`。
   所以 **R1（全新连接）与 R3（复用连接）的报错信息不同**：
   前者 `unrecognized configuration parameter`，
   后者 `invalid input syntax for bigint: ""`。
   两者都 fail-loud，但**断言不能写成匹配同一条错误文本** ——
   这是写这两条测试时最容易踩的点

第 2 条同时再次说明 `nullif(current_setting(...), '')` 那类「容错」写法
方向是反的：它会把空串变成 NULL、把报错变成静默 0 行
（`../spec/05-安全与租户隔离.md` §3.3 纪律 4）。

**R4（prepared statement 跨租户复用）—— 测法已按实测改写：**

实测 transaction 模式下，客户端 A `PREPARE q` 后，
同一客户端的下一条 `EXECUTE q` 就已经 `prepared statement "q" does not exist`
（语句停在了另一条 server 连接上）。所以**用 SQL 层 `PREPARE` 根本测不到这个场景**。

R4 必须在 sqlx 层测：sqlx 默认开启语句缓存，走的是协议级预编译语句，
配合 PgBouncer ≥1.21 的 `max_prepared_statements` 才有意义
（`compose.yaml` 配的是 `MAX_PREPARED_STATEMENTS: 200`）。
改写后的 R4：同一 `PgPool` 上连续跑两个不同租户的 `tenant_tx`，
断言第二次返回第二个租户的数据。这条属 L3，
但**必须连 56432（经 PgBouncer）而不是 55432**。

**结论：不泄漏。** RLS 策略里的 `current_setting` 在执行期求值，不在计划期，
所以缓存下来的执行计划不会把第一个租户的 `app.tenant_id` 一起记住。
那句话本来是推理，现在有了证据；这条测试同时是回归网 ——
日后若有人把租户条件搬进计划期能固化的位置，它会红。

落地时踩到的三件事，都属于「不做就什么也没测到」：

```text
1  PgBouncer 确实在 server 连接上跨事务保留协议级预编译语句。
   实测同一条 server 连接上反复看到同名的 PGBOUNCER_66 / PGBOUNCER_69，
   而且第一轮取样时 pg_prepared_statements 就已经有 4 条。
   → 于是测试断言「第二轮那条连接上 count(*) > 0」，把这个前提固化下来

2  客户端池必须 max_connections(1)。
   两条连接时第二次查询可能走一条全新的、没有语句缓存的连接 —— 什么都没测到

3  必须断言两轮的 pg_backend_pid() 相同。
   反证时先试「第二轮换另一个客户端池」，测试仍然绿：
   查 pg_stat_activity 只有 2 条 app_user 连接，
   说明两个客户端池顺序跑仍然落在同一条 server 连接上。
   要 tokio::join! 并发才打得破（实测 pid 131663 vs 131512，测试恰好红）
   → 所以「换池」不是有效反证，而 pid 自检不是摆设
```

第 3 条的普遍形态：**经 PgBouncer 的测试必须自己确认命中了复用的 server 连接。**
没命中时看到的是全新连接的形状（那是 R1 管的事），R3 与 R4 都会白绿一遍。

## 五、R6 的实测结论比预想更严格

| 路径（`app_user` 调用，`app.tenant_id=1`，租户 1 应见 2 行） | 实测 |
|---|---|
| 直接 `SELECT` 基表 | **2 行** ✓ |
| owner 的普通视图 | **0 行** |
| owner 的 `SECURITY DEFINER` 函数 | **0 行** |
| owner 的 `security_invoker = true` 视图 | **2 行** ✓ |
| owner 的普通（`SECURITY INVOKER`）函数 | **2 行** ✓ |

原因：策略写的是 `TO app_user`，而那两条路径以 `tgm_owner` 身份执行，
`FORCE` 让 owner 也受策略约束，却没有任何策略匹配 owner → 默认拒绝 → 0 行。
补一条 `CREATE POLICY ... TO tgm_owner USING (...)` 后，两条路径都回到 2 行。

**方向与设计一致（`FORCE` 确实关掉了泄漏），但后果不同**：
不是「安全且可用」，而是**「安全但功能坏掉」** ——
视图和 `SECURITY DEFINER` 函数会静默返回空集。
这类 bug 在功能测试里表现为「查不到数据」，很容易被误诊成数据没写进去。

**这直接改变了 R6 的断言形状**：不是断言「返回本租户」，而是断言
**「普通视图 / `SECURITY DEFINER` 函数不存在于带 `tenant_id` 的表上」** ——
一条**静态**断言比动态测试更可靠，它就是审计断言 A8（`04-CI门禁.md`）。
动态部分保留一条，用来防止有人加了 owner 策略把 A8 绕开
（补了 owner 策略之后 A8 仍绿 —— 它只查对象存不存在 —— 而泄漏是真的）。

**把动态那一条落成测试时补到一件事：视图必须以 `tgm_owner` 身份建。**
上表没写视图是谁建的 —— 而用超级用户建出来的视图 owner 是 `postgres`，
超级用户旁路 RLS，于是断言以「FORCE 没生效」失败，真因只是视图 owner 错了。
与「表的 owner 决定 FORCE 是真的还是装饰」同形，只是对象换成了视图。
所以测试里那三句 DDL 前面的 `SET ROLE tgm_owner` 不是样板；
又因为 `SET ROLE` 是会话级动作，`SET ROLE` / `CREATE VIEW` / `GRANT` / `RESET ROLE`
必须落在**同一条连接**上，不能分别走池。
