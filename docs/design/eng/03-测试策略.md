# 测试策略

本文是**反向测试清单的唯一归口处**：分层、测试库的正确起法、
42 条反向测试的完整清单。设计文档里凡是说「需要一条反向测试」的地方，
那条测试都在本文 §三 有编号。

**实测环境**：PostgreSQL 17.11 + PgBouncer 1.25.2（transaction 模式）。
环境编排见 `02-本地环境与迁移.md`，CI 怎么跑见 `04-CI门禁.md`。

## 零、两个实测发现直接决定选型

在真实库上验了一遍，撞到两件事，它们**否掉了最省事的默认做法**：

```text
发现 1  #[sqlx::test] 需要超级用户 DATABASE_URL 来建测试库。
        实测：超级用户 postgres 即使在 FORCE ROW LEVEL SECURITY 的表上、
        且完全不设 app.tenant_id，也能看到全部 3 行（跨租户）。
        → 用 #[sqlx::test] 的默认连接跑隔离测试，会「全绿但什么都没测到」

发现 2  静态审计抓不到「策略写成 USING (true)」。
        实测：造一张 bad3 表，有 tenant_id、RLS on、FORCE on、1 条策略，
        审计返回 0 行（判定通过）；而 app_user 在 tenant_id=1 上下文里
        看到了两个租户的全部 2 行。
        → 静态审计与动态反向测试是两件事，
          「审计通过 ≠ 隔离正确」有了本项目自己的实证
```

发现 1 是最危险的一个：它让测试**看起来**在跑，实际上把被测机制整个旁路了。
所以 §二 的第一条纪律是「隔离测试必须以受限角色连接」。

## 一、分层与选型

| 层 | 跑什么 | 依赖 | 工具 | 单次时长目标 |
|---|---|---|---|---|
| L0 静态 | `fmt` / `clippy -D warnings` / `cargo deny` / `sqlx prepare --check` / `tgm openapi --check` | 无 | cargo | < 60s |
| L1 单元 | 规则匹配、去重键、退避算法、状态机迁移 | 无 | `#[test]` + `rstest` 0.27 | < 10s |
| L2 DB 集成 | RLS 反向测试、Repo、迁移、审计 SQL | 真实 PG | `#[sqlx::test]` + **受限角色**（§二） | < 90s |
| L3 隔离专项 | 跨租户读写、唯一约束探测、owner 路径 | PG + PgBouncer | 同 L2，另起一组 | < 60s |
| L4 外部桩 | Telegram Bot API、OIDC 回调 | 无网络 | `wiremock` 0.6 | < 30s |
| L5 混沌 | 租约脑裂五项 | 多进程 + PG | shell + docker | 手动，上线前 |

**选型理由，只说非显然的两条：**

- **L2 用 `#[sqlx::test]` 而不是 testcontainers 0.28**。sqlx 的方案是每个测试一个独立库
  （自动建、自动跑 `migrations/`、失败时保留库便于排查），
  正好匹配「27 张表 × 每表验一遍策略」这种需要干净起点的场景。
  testcontainers 的价值是起整套依赖，那是 L5 的活，用 compose 更直接
- **L4 必须有桩**。「跨租户访问返回 404 不是 403」这条测试不能依赖真实 Telegram。
  而 `my_chat_member` 拉群授权链路没有桩就只能手工拉群，无法进 CI

> **真机素材已就位，但它不改上面那条结论。** 两个测试 Bot 加两个测试频道
> （`02-本地环境与迁移.md`）可以手工走通拉群授权与 `probe` 回写。
> 跨租户边界也能在真机上看到，**但只在写侧**：
> bot1 对频道 2 写动作得 403、查成员得 400，而 `getChat` 得 ok
> —— 公开频道的元数据无需成员身份，详见 `02` 的那条更正。
> **但真机跑的不能进 CI**：token 是 secret，CI 不该持有；
> Telegram 侧有速率限制，也不该被 CI 反复打。
> 真机素材的用途是**验证桩写对了**，不是替代桩。
>
> **而这次更正本身就是「真机验桩」的一个实例**：原先写在这里的
> `400 chat not found` 是测试脚本 token 解析 bug 造成的假结论，
> 一个写错的桩会把它固化成「隔离已验证」。
> 桩要照着**三种不同的错误**写（403 / 400 / ok），不是照着一种。

不引入的：`insta` 快照（本项目没有大块结构化输出值得快照）、
`proptest`（规则匹配是 `aho-corasick` + 正则，边界用 `rstest` 表驱动更直白）、
`criterion`（性能目标用一次性压测脚本验，不需要长期基准）。

## 二、测试数据库：三条纪律

### 2.1 隔离测试必须以受限角色连接

`#[sqlx::test]` 注入给测试函数的 `PgPool` 走的是 `DATABASE_URL`，
而它要建库，所以那个账号必然有 `CREATEDB` —— 实测 `app_user` 建库直接
`ERROR: permission denied to create database`，说明两者不能是同一个角色。

```rust
// tests/support/mod.rs
/// sqlx::test 注入的 pool 是超级用户的，只用来跑 DDL 与断言前置。
/// 任何验证隔离的查询都必须走这个函数换到受限角色。
pub async fn app_pool(admin: &PgPool) -> PgPool {
    let db: String = sqlx::query_scalar("SELECT current_database()")
        .fetch_one(admin).await.unwrap();
    PgPoolOptions::new().max_connections(2)
        .connect(&format!("postgres://app_user:apw@127.0.0.1:55432/{db}"))
        .await.unwrap()
}
```

配套纪律：**测试代码里禁止用 `sqlx::test` 的 pool 做跨租户断言**。
这条靠评审拦不住（两个 pool 类型一样），需要一条 grep 级 CI 检查，
或把 admin pool 在 support 层包成一个不实现 `Deref` 的 newtype ——
后者更可靠，因为它让误用不可编译。

### 2.2 迁移顺序即测试前置

`FORCE` 之后 owner 自己也被策略拦（`02-本地环境与迁移.md` §零 坑 2），
所以 fixtures 里的种子数据**不能**在 RLS 启用后插入。
`#[sqlx::test(fixtures(...))]` 的 fixture 是以 `DATABASE_URL` 角色（超级用户）跑的，
**恰好绕过这个限制** —— 但这是偶然安全，不是设计安全。
明确约定：**fixture 只灌数据，不改 RLS 配置**。

### 2.3 每个测试断言自己的角色

```rust
// 每个 L3 测试开头都该有这一句，防止 2.1 的错误静默发生
assert_eq!(
    sqlx::query_scalar::<_, String>("SELECT current_user").fetch_one(&app).await?,
    "app_user"
);
```

### 3.1 分区上线时要补的一条

分区推迟做（`../spec/04-数据生命周期与容量.md` §三），但届时必须补：
**直接指名分区查询，应当不泄漏**。分区不继承父表的 RLS 配置
（实测 `relrowsecurity` 在分区上一律为 `f`），
经父表查是安全的、直接查子表会跨租户返回行。
这条不进当前的 42，它随分区工作包一起进来。

## 四、PgBouncer 实测：R3 与 R4 的真实形态

**R3（会话变量跨客户端泄漏）—— 独立复现：**

```text
配置：transaction 模式，server_reset_query_always = 0，default_pool_size = 1
客户端 A：SELECT set_config('app.tenant_id','2',false)   -- 注意是 false（session 级）
客户端 B：全新连接，什么都不设
        SELECT current_setting('app.tenant_id',true)  →  "2"   ← 泄漏
        SELECT count(*) FROM rules                    →  1 行（租户 2 的数据）

改成 server_reset_query_always = 1 + DISCARD ALL：
客户端 B  →  ERROR: invalid input syntax for type bigint: ""
```

两个可操作结论：

1. `02-本地环境与迁移.md` §一 那两个 PgBouncer 环境变量
   **是安全配置，不是性能调优**。漏了就是真实的跨租户泄漏，
   而且泄漏方向不可预测（取决于连接复用顺序）
2. **`DISCARD ALL` 把参数重置为空串，不是 NULL。** 实测：
   `set_config('app.tenant_id','7',false)` → `DISCARD ALL` →
   `current_setting('app.tenant_id', true)` 返回 `[]`（空串），
   而全新连接返回 `[NULL]`。
   所以 **R1（全新连接）与 R3（复用连接）的报错信息不同**：
   前者 `unrecognized configuration parameter`，
   后者 `invalid input syntax for bigint: ""`。
   两者都 fail-loud，但**断言不能写成匹配同一条错误文本** ——
   这是写这两条测试时最容易踩的点

第 2 条同时再次说明 `nullif(current_setting(...), '')` 那类「容错」写法
方向是反的：它会把空串变成 NULL、把报错变成静默 0 行
（`../spec/05-安全与租户隔离.md` §3.3 纪律 4）。

**R4（prepared statement 跨租户复用）—— 测法要改：**

实测 transaction 模式下，客户端 A `PREPARE q` 后，
同一客户端的下一条 `EXECUTE q` 就已经 `prepared statement "q" does not exist`
（语句停在了另一条 server 连接上）。所以**用 SQL 层 `PREPARE` 根本测不到这个场景**。

R4 必须在 sqlx 层测：sqlx 默认开启语句缓存，走的是协议级预编译语句，
配合 PgBouncer ≥1.21 的 `max_prepared_statements` 才有意义。
改写后的 R4：同一 `PgPool` 上连续跑两个不同租户的 `tenant_tx`，
断言第二次返回第二个租户的数据。这条属 L3，
但**必须连 56432（经 PgBouncer）而不是 55432**。

## 五、R6 的实测结论比预想更严格

| 路径（`app_user` 调用，`app.tenant_id=1`，租户 1 应见 2 行） | 实测 |
|---|---|
| 直接 `SELECT` 基表 | **2 行** ✓ |
| owner 的普通视图 | **0 行** |
| owner 的 `SECURITY DEFINER` 函数 | **0 行** |
| owner 的 `security_invoker = true` 视图 | **2 行** ✓ |
| owner 的普通（`SECURITY INVOKER`）函数 | **2 行** ✓ |

原因：策略写的是 `TO app_user`，而那两条路径以 `tgm_owner` 身份执行，
`FORCE` 让 owner 也受策略约束，却没有任何策略匹配 owner → 默认拒绝 → 0 行。
补一条 `CREATE POLICY ... TO tgm_owner USING (...)` 后，两条路径都回到 2 行。

**方向与设计一致（`FORCE` 确实关掉了泄漏），但后果不同**：
不是「安全且可用」，而是**「安全但功能坏掉」** ——
视图和 `SECURITY DEFINER` 函数会静默返回空集。
这类 bug 在功能测试里表现为「查不到数据」，很容易被误诊成数据没写进去。

**这直接改变了 R6 的断言形状**：不是断言「返回本租户」，而是断言
**「普通视图 / `SECURITY DEFINER` 函数不存在于带 `tenant_id` 的表上」** ——
一条**静态**断言比动态测试更可靠，它就是审计断言 A8（`04-CI门禁.md`）。
动态部分保留一条，用来防止有人加了 owner 策略把 A8 绕开。

## 六、明确不测的

```text
✗ grammers / teloxide 本身的行为        不是我们的代码
✗ Telegram 服务端的限流数字            会变，只测我们的退避逻辑（L1）
✗ 覆盖率百分比目标                     单人项目里它会变成刷数字。
                                       用 §三 的清单当验收口径，比百分比有意义
✗ 端到端 UI 测试                       首发只有最小界面，不值一套 harness
```

覆盖率那条值得多说一句：它不是「覆盖率没用」，
而是**这个项目的风险集中在几十条明确的负向断言上**，
而覆盖率工具恰好不衡量这个 —— 一段 `if cross_tenant { return 404 }`
被覆盖，不代表有人验过它返回的是 404 而不是 403。

## 七、CI 编排

```text
每次 PR：      L0 → L1 → L2 → L3（含 R5 的 RLS-off 第二遍）      目标 < 5 分钟
每日：         + L4 + tgm audit-rls 全量 + cargo deny 的 advisory 刷新
上线前手动：   L5 混沌五项 + Q1~Q6 真实账号验证
```

L3 需要 PG 与 PgBouncer 两个服务，用 `02-本地环境与迁移.md` §一 的同一份 compose。
`sqlx::test` 的失败库会保留 —— CI 里要在 job 结束时销毁整个容器，否则磁盘会涨。

- §三 的「出处」列指向设计文档的章节，但**没有反向的机器校验** ——
  设计文档改了、对应测试没改，这件事没有任何东西会报警
