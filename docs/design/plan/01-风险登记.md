# 风险登记

编号规则：风险用 `RK-nn`，反向测试用 `Rn`（`eng/03-测试策略.md`）。
两套编号不混用 —— 风险是「可能发生的事」，反向测试是「必须为假的断言」。

「监控关口」列指这条风险在哪个关口复查一次。没有监控关口的风险
等于没人看，所以每条都必须有。关口定义见
[00-里程碑与工期.md](00-里程碑与工期.md)。

> **这份表会过期。** 概率与影响是当前判断，不是测量值。

## 二、三条需要多说几句的

### RK-08 · 隔离有洞但一切看起来正常

概率标**中**不是低。理由：这类缺陷的表现形式是「功能测试全绿、
日志无异常」—— 它不会自己暴露。已经实测过的几种形态：

- 策略写成 `USING (true)` 能骗过全部静态审计
- 测试框架注入的池是超级用户池，用它跑隔离测试得到假绿
- 视图未加 `security_invoker` 时，在 FORCE 下返回 0 行而非报错

第三条尤其麻烦：它的表现是功能坏掉而不是数据泄漏 ——
这正是 ADR-0004 想要的方向，但它意味着「没报错」不能证明隔离正确。

应对的核心不是「写更多测试」，是**断言必须能失败**：
CI 跑两遍，第二遍在 `ALTER TABLE ... DISABLE ROW LEVEL SECURITY` 之后，
第二遍必须红。

### RK-12 · 24 周无外部反馈

这是本表里概率最高的一条，也是唯一一条**没有应对措施**的。

瀑布形态要求需求先冻结再实现，实现期 24 周。这期间没有任何机制
能发现「需求当初就错了」。ADR-0015 把产品定位为转发工具而非聚合器，
缩小了错的范围，但没有消除它。

写在这里的作用是：G4 通过后不要把接入种子客户当成「顺便的事」。
它是这条风险唯一的检验时机，且观察窗最晚 W39 就要开始
（G6 判据要求 ≥2 周真实流量，而 P5 只有 1 周，装不下）。

### RK-10 · 单人中断

没有应对。增加人手在实现期内不可行（知识全在一个人头上），
备份方案也不存在。

能做的只有降低「中断后无人能接手」的程度：
`decisions/` 记录每个决策的理由与代价，`eng/03` 记录每条测试为什么存在。
这两样东西在正常情况下是文档，在 RK-10 发生时是唯一的交接物。

## 三、局限

**1. 概率与影响都是主观判断。** 没有历史项目数据支撑，
也没有第二个人独立评过。RK-07 标「低概率极高影响」和
RK-08 标「中概率极高影响」，两者的相对顺序是本文的判断，可能是错的。

**2. 没有量化的风险敞口。** 本表不折算成人日或金额，
所以无法回答「为这条风险预留多少缓冲」。
[00-里程碑与工期.md](00-里程碑与工期.md) 的 20% 是整体缓冲，
不按风险分摊。

**3. 触发条件多数不可自动检测。** 只有 RK-04、RK-13 能靠指标发现，
其余依赖人在关口上主动复查。而 ADR-0024 已经记过同一个弱点：
「挂在阈值上」要求真的有人看那个阈值。

**4. 缺一整类风险：外部环境。** Telegram 的服务条款变更、
API 政策调整、目标市场的合规要求变化 —— 这些都不在表内，
因为它们既不可预测也无可应对措施，列出来只是噪声。
但「不在表内」不等于「不会发生」。
