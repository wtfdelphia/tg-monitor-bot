# ADR-0011：凭据用 KEK/DEK 信封加密，不用单一对称密钥

状态：已定案

## 决定

每租户一个 DEK（AES-256-GCM 加密凭据），DEK 本身被 KMS 里的 KEK 加密后存库。
`credential_keys.kek_id` 是一列，不是常量。

## 背景

被替换掉的方案是「一个进程级密钥直接加密所有凭据」
（Python 生态里典型形式是 Fernet + 一个环境变量里的 key）。
它的问题是爆炸半径：那一个密钥泄漏 = 全部租户的 Telegram 凭据泄漏，
而且轮换必须一次性重新加密全库。

信封加密换来三件事：

- **DBA 仅凭库内容无法解密。** DEK 密文要 KMS 里的 KEK 才能解开，
  而 KEK 明文永不出 KMS。这是「平台自己也不能随便看租户凭据」的技术基础，
  而 [[ADR-0013]] 让平台必须存租户的 `api_hash`，这条保证就是必需的。
- 轮换可以增量做：新 DEK 用新 KEK 包，旧行按自己的 `kek_id` 找对应 KEK 解开，
  不需要停机重刷全库。
- 解密权可以按组件收：`control-plane` 根本拿不到 KEK 相关配置，
  于是它**不可能**解密租户凭据 —— 这不是靠代码自觉，是靠配置缺失。

## 代价

- 每次解密多一次 KMS 往返。缓解是解密结果可缓存，
  成本量级可忽略（< $1/月），但增加了一个外部依赖 ——
  KMS 不可用时采集与投递全停。
- 本地开发不能连 KMS，于是需要 `EnvKek` 后端（[[ADR-0012]]）。
  **它的安全属性比 `KmsKek` 差一个量级**（KEK 明文在进程环境里），
  所以 `production` 环境下必须拒绝启动。
- 多一张 `credential_keys` 表与一层间接，取凭据的代码路径变长。
- 加密只挡「库被读」，不挡「有解密权的组件被攻破」。
  被封号排查流程里那一步「检查 `identity_secrets.api_id` 是否跨租户复用」
  就要求平台运维能看到明文 —— 这条能力必须落审计日志。
