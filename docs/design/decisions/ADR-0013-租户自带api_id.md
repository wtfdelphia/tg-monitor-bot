# ADR-0013：`api_id` 由租户自带，平台不代持

状态：已定案

## 决定

每个租户在 my.telegram.org 自己申请 `api_id` / `api_hash`，填进平台。
平台不用自己的 `api_id` 替租户跑采集。

## 背景

两个选项：

- **平台代持**：平台申请一个 `api_id`，所有租户的采集都走它。租户接入体验最好，
  填个手机号就完事。
- **租户自带**：租户自己去申请，平台只存加密后的凭据。

代持看起来省事，但它把所有租户的行为绑在一个 `api_id` 上：
任何一个租户的滥用触发 Telegram 限流或封禁，全平台一起停。
这不是可以靠「我们会监控滥用」缓解的风险 —— 判定权在 Telegram 手里，
我们既看不到判定依据也无法申诉。

另一层：代持等于平台在用自己的身份代替用户访问内容。
这条和 [[ADR-0015]] 的定位是一致的 —— 我们是转发工具，
读取动作的主体必须是租户自己。

## 代价

- 接入门槛显著变高。my.telegram.org 的申请流程对非技术用户不友好，
  而且申请页本身偶发不可用。这会直接损失一部分潜在租户。
- 平台要存 `api_id` / `api_hash` 明文可解密的副本（见 [[ADR-0011]]），
  凭据泄漏的后果由租户承担 —— 这件事必须在接入页明写，不能只写在服务条款里。
- 无法提供「零配置试用」。补偿方案是 [[ADR-0014]] 的平台自营演示源，
  让人在不填凭据的前提下先看到产品长什么样。
