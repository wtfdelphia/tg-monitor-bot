# ADR-0012：KEK 从第一天起就是 trait，不等到需要时再抽

状态：已定案

## 决定

在密钥相关代码落地的第一个工作包里就把 KEK 抽成 trait
（`wrap_dek` / `unwrap_dek`），两个实现并存：`KmsKek`（生产）与 `EnvKek`（本地）。
不先写死 KMS 调用、以后再重构。

## 背景

「先写死，需要时再抽」通常是对的 —— 过早抽象是本项目明确反对的事情之一。
这里例外，因为**不抽的话本地开发根本跑不起来**：
`KmsKek` 需要真实的 KMS 凭据，而本地环境与 CI 都没有。

也就是说第二个实现不是假想的未来需求，它从第一天就必须存在。
既然要两个实现，trait 就不是抽象而是最直接的写法。

反过来，抽得晚的代价是具体的：KEK 调用会散进取凭据的每条路径，
等到要加本地实现时就是一次跨多个文件的改动，
而这些路径恰好是最不该被大改的地方。

## 代价

- 多一层间接，读代码时要多跳一次。
- `EnvKek` 存在本身就是个风险面：它把 KEK 明文放进进程环境。
  必须用 `production` 下拒绝启动兜住（`TGM_LOCAL_KEK` 在生产环境 = 启动失败），
  这条检查本身要有测试，否则它是句注释。
- trait 的方法签名要求「返回值用后必须 zeroize」，
  这个约束靠文档和类型（`Secret` 包装）表达，编译器不能完全保证。
