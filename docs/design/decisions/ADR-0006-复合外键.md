# ADR-0006：跨表外键一律复合 `(tenant_id, x)`

状态：已定案

## 决定

所有跨表外键都是复合的：`FOREIGN KEY (tenant_id, rule_id) REFERENCES rules (tenant_id, id)`，
不是 `FOREIGN KEY (rule_id) REFERENCES rules (id)`。
被引用侧因此需要一个 `(tenant_id, id)` 的唯一约束。

**唯一例外**：指向 `identities` 的外键。

## 背景

单列外键允许一种很难发现的错误：A 租户的规则指向 B 租户的源订阅。
数据库会愉快地接受它，因为 `source_subscription_id` 确实存在。
之后这条规则跑起来，就是一条合法建立的跨租户数据通道 ——
RLS 挡不住，因为每次查询单看都在自己租户内。

复合外键把这条通道在数据库层封掉：`(tenant_id, x)` 必须成对存在于被引用表，
跨租户引用直接违反约束。

这条铁律依赖「`tenant_id` 一律 NOT NULL」（[[ADR-0007]]）——
如果 `tenant_id` 可空，`MATCH SIMPLE` 语义下整个外键检查被跳过，
复合外键就成了装饰。

例外是 `identities`：平台自营演示源是一个所有租户共享的 identity
（[[ADR-0014]]），它的 `tenant_id` 必须可空。于是指向 `identities` 的外键
只能是单列的。

## 代价

- **例外处的隔离在数据库层是缺口。** 取用别人的 `identity_id`
  数据库不会拒绝，必须由应用层返回 403，并由反向测试 R19 守住。
  这是全库唯一一处「隔离只有一道防线」的地方。
- 静态断言 A9 的形状必须**显式排除 `identities`** ——
  也就是说断言本身承载了这条例外。读断言的人能看到例外，
  这比把例外写在文档里可靠。
- 被引用表都要多一个 `(tenant_id, id)` 唯一约束，索引数量与写入开销上升。
- 所有 JOIN 都要带 `tenant_id`，SQL 变长。
