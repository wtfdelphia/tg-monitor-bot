# ADR-0010：组件间只经 PG 与 Redis，没有 RPC

状态：已定案

## 决定

7 个组件之间没有 gRPC、没有内部 HTTP、没有消息中间件。
交接介质只有两个：PostgreSQL（事实源）与 Redis Stream（唤醒信号）。

配套约束：**Redis 只是唤醒信号，不是事实源。**
每个 Worker 必须能在 Redis 完全丢失的情况下靠扫库自行恢复，
队列里的消息体只带主键，不带业务数据。

## 背景

架构图上的箭头是数据流向，不是调用关系 —— 这一点必须明说，
否则看图的人会以为 `fanout-worker` 调用 `rule-worker`。

不引入 RPC 的理由：

- 每一级交接都是「先落库，再入队」（[[ADR-0009]] 的纪律）。
  既然状态已经在库里，再加一层调用只是多一个可以失败的地方。
- RPC 会引入服务发现、超时重试、熔断这一整套东西，
  而它们的价值在于降低延迟 —— 本系统的延迟预算是采集 P99 < 60s，
  多一次写库完全吃得下。
- 组件挂掉的语义变简单：没有 RPC 就没有「调用方等在那里」的状态，
  重启后从库里接着做。

Redis 不作为事实源，是因为它的持久化保证达不到「不能丢事件」的要求。
把它限制成唤醒信号之后，Redis 宕一次的后果是延迟变大，而不是丢数据。
顺带一个安全收益：**凭据不进队列**。

队列键的分片维度是身份或全局，**不按 `tenant_id` 分片** ——
租户隔离在库层（[[ADR-0003]]），不靠队列拆分。

## 代价

- 每级交接多一次写库，吞吐上限被 PG 写入能力压住。
  在稳态 20~30 万行的量级不是瓶颈，但这个上限是真实存在的。
- 端到端延迟由几段轮询/唤醒串起来，比同步调用长。
- 「必须能靠扫库恢复」这条要求每个 Worker 都写两套驱动路径
  （队列驱动 + 扫库兜底），代码量上升。**这是有意付的**：
  只有队列驱动的 Worker 在 Redis 出问题时会静默停工。
- 数据库连接数成为跨组件的共享资源，于是 PgBouncer 成了必需件 ——
  而 transaction 模式的 PgBouncer 会跨进程泄漏会话变量，
  `server_reset_query_always = 1` 因此是安全配置而不是性能调优
  （见 [[ADR-0007]] 的 `::bigint`、`ops/00`）。
