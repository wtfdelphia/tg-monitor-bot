# ADR-0024：`tenant_events` 暂不分区，挂在阈值上

状态：已定案

## 决定

不分区。分区挂在明确阈值上（`canonical_events` 或 `tenant_events`
超 5000 万行 / 20GB），届时才做，并且做之前必须先过分区与 RLS 的前置条件。

## 背景

两个理由，一个是量级，一个是安全。

量级：按 1000 个活跃订阅、日均每订阅 200 条消息估，
`canonical_events` 去重后约 20 万/日，未命中 24h 物理删除，
**稳态只有 20~30 万行**。这个数量级离分区的必要性差两个数量级。

> 记住这个数字：它意味着首发阶段几乎所有「性能优化」都是过早优化。
> 分区、`sender_id` 索引、读写分离，全部挂在阈值上。

安全：**分区不继承父表的 RLS**，已在 PG 17.11 实测：

```text
父表 ENABLE + FORCE ROW LEVEL SECURITY，建策略
  pg_class.relrowsecurity:  te(父)=t   te_2026_09=f   te_2026_10=f
                            分区一律为 f，且在父表启用 RLS 之后新建的分区同样是 f

经父表查询（租户 1）：只返回租户 1 的行          ✓
直接查分区   （租户 1）：租户 1 和租户 2 的行都返回  ✗ 跨租户泄漏
```

这是 PostgreSQL 的**设计行为**，不是 bug：父表策略只在经父表查询时应用。
它写在文档的「继承」章节而不是 RLS 章节，很容易漏掉 ——
也就是说照着 RLS 文档做一遍不会发现这个洞。

`canonical_events` 不带 RLS（丙类，见 [[ADR-0009]]），分区无碍；
问题只在 `tenant_events`。

## 代价

- 清理靠 `DELETE` 而不是 `DROP PARTITION`，删除成本高，
  而且会产生膨胀需要 autovacuum 跟上。
- 阈值到了之后分区不是纯运维动作，要先补齐：
  一条断言（分区子表的 `relrowsecurity`）、
  一条反向测试（直接指名分区查询应当不泄漏），
  以及一条新增分区时自动启用 RLS 的机制 —— pg_partman 的模板表不会替你做。
- 「挂在阈值上」要求真的有人看那个阈值。它不在三个告警指标里，
  目前只靠容量复核，这是个薄弱点。
