# ADR-0019：目标频道连通性自检提到首发

状态：已定案

## 决定

租户配置目标频道时，立刻做一次连通性自检（Bot 是否在频道里、是否有发言权），
结果当场返回。不等到第一条消息投递失败才发现。

原本这条排在演进期，提前到首发范围内。

## 背景

「配好了但投不出去」是这类工具最常见的首次使用失败，而且它的表现形式最糟：
用户看到的是「什么都没发生」。日志里有 403，但用户看不到日志。

失败原因基本是三类：Bot 没被拉进目标频道、被拉进了但没有发消息权限、
频道 id 填错。三类都能在配置时一次 `getChat` + 一次权限判断里查出来，
成本是一次 API 往返。

提前的另一个原因是它和投递退避纪律的关系：
如果不自检，这类永久性失败会走进重试队列，
占着退避预算反复撞同一面墙 —— 而退避是按目标频道维度算的，
一个配错的频道会拖慢那个租户其它正常的投递。
**这不是体验问题，是会传染的**。

## 代价

- 配置路径上多一次 Telegram API 调用，要计入 FloodWait 预算。
  自检不能做成「每次打开配置页都跑一遍」。
- 自检只能证明「此刻可投递」。之后 Bot 被踢出频道、权限被收回，
  自检结果就过期了。所以它不替代运行时的投递失败率告警
  （见 `ops/01-上线就绪与运维.md` 的三指标）。
- 挤占首发工期。这部分工期传导已经反映在 `plan/00-里程碑与工期.md`，
  本文不重复数字。
