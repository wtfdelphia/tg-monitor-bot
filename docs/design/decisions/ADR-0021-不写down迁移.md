# ADR-0021：不写 down 迁移，上线后只前滚

状态：已定案

## 决定

迁移只有 up，没有 down。
本地与上线前的失败处置是「从零重建库」；上线后只能前滚 ——
写一个新的迁移修正它。

## 背景

这个库里的迁移有一半是安全配置（RLS 启用、FORCE、policy、角色与 GRANT）。
而「回退安全配置」这个动作本身就是事故：
**一个能把 FORCE 撤掉的脚本存在于仓库里，被误跑一次的代价
远大于它的便利。**

而 down 迁移的实际使用场景在本项目里很小：
本地 `docker compose down -v` 从零重建只要几十秒；
上线前的租户是手工开通的，重建库的数据代价可控。
真正需要回退的只有上线后，而那时候 down 迁移也不该用 ——
生产库的回退是数据操作，不是 schema 操作。

前滚的前提是**迁移必须可重入**（DDL 用 `IF NOT EXISTS`，
种子用 `ON CONFLICT DO NOTHING`）。
理由是失败的迁移可能已经部分提交：PG 的 DDL 虽然事务安全，
但 sqlx 的迁移器是**按文件**记录版本的，
一个文件里多条语句时部分成功的状态是真实存在的。
所以每个迁移文件尽量只做一件事，把部分成功的窗口压到最小。

## 代价

- 上线后一次写错的迁移要靠新迁移修，历史里会留下「加了又改回去」的痕迹。
  这是有意的：那个痕迹本身是记录。
- **前滚的时候不许手工 `ALTER`。** 手改会让数据库偏离迁移文件能产生的状态，
  之后每一次迁移都在一个无人知道形状的库上跑。
  这条写在 `ops/01` 的迁移流程里，是那套流程的承重点。
- 上线后迁移必须先在「恢复出来的昨天备份」上跑一遍 ——
  空库能跑不代表有数据的库能跑。这让迁移流程依赖备份恢复演练，
  两者互为前提。
- 不能在迁移里做数据回填的长事务：27 张表都带 RLS，
  回填走 owner 身份 + FORCE 会撞上 [[ADR-0004]] 的静默 0 行。
  需要回填时单独写 `tgm` subcommand，用 `app_user` 按租户分批做。
