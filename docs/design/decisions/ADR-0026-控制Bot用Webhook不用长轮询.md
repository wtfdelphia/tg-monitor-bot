# ADR-0026：控制 Bot 用 Webhook，不用长轮询

状态：已定案

## 决定

控制 Bot 与数据 Bot 都走 Webhook。**长轮询（`getUpdates`）不作为任何 Bot 的入站方式。**

这条取代 [[ADR-0017]] 正文里「控制 Bot 走长轮询是纯出站」的表述。

## 背景

ADR-0017 写的时候，控制台扫码登录（路径 B）的核心卖点是「零入站端口」——
私有化部署在内网、无公网域名、无入站端口，长轮询是唯一能工作的方式。

[[ADR-0016]] 把私有化部署砍掉之后，这个前提消失了：平台只有自己这一套部署，
公网域名和入站端口都是现成的。而长轮询留下来的代价没有跟着消失：

- 长轮询要一个常驻循环去拉，空闲时也在拉。Webhook 是 Telegram 推过来，
  没有消息就没有请求
- 两个 Bot 若一个 Webhook 一个长轮询，入站鉴权就有两套模型 ——
  Webhook 侧的根是 `secret_token`，长轮询侧根本没有入站面。
  混用意味着安全论证要分两条写，而其中一条会被长期遗忘
- 令牌桶隔离（ADR-0018 的核心诉求）在两种传输下的表现不一样，
  但设计文档只描述了 Webhook 那一种

实际上文档集的其余部分早就是按 Webhook 写的：独立 Webhook 端点、
`secret_token` 必设并作为整个鉴权链的根、`/hook/console/<random>` 的路径设计、
`allowed_updates` 的显式声明。长轮询只剩两处零散表述，是漏改而非另一套设计。

## 代价

- 控制台扫码（路径 B）从此没有「零入站端口」这个优势。
  保留它的理由收窄成一条：Allowed URLs 要在 BotFather 按域名逐一预登记，
  多环境下是持续的运维摩擦。这条理由比原来弱，**但仍然成立**
- Webhook 要求 TLS 与公网可达，本地开发要靠隧道工具或改用轮询跑测试 ——
  也就是说开发态和生产态的入站方式会不一致，这个差异要在测试里显式处理
- 如果哪天重新考虑私有化交付，这条要连同 ADR-0016 一起重估
