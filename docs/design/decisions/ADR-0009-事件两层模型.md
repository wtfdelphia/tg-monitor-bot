# ADR-0009：事件分两层，CanonicalEvent → TenantEvent

状态：已定案

## 决定

一条 Telegram 消息落成 1 条 `CanonicalEvent`（按接收身份维度，与租户无关），
再扇出成 N 条 `TenantEvent`（一租户一条）。
配套纪律：**先落库再处理** —— 接入层收到消息立刻落 CanonicalEvent，之后才 ACK、才入队。

## 背景

单层模型（一条消息一条记录）在多租户下表达不出归属：
两个租户订阅同一个公开频道，同一条消息属于谁？
如果按租户存两份，同一条原始内容被重复接收、重复存储；
如果只存一份，两个租户的去重窗口、规则命中、投递配额就混在一起了。

两层把「内容」和「归属」分开：内容只接收一次、只存一份；
归属与处理状态每租户一条。这也是 [[ADR-0015]]「不做聚合器」能落地的前提 ——
CanonicalEvent 是过路的（未命中任何规则即短 TTL 物理删除），
不是一个内容库。

「先落库再处理」这条纪律来自单租户版本的实际教训：
**接入层是唯一不可重放的环节。** Telegram 的 update 错过就没了，
而落库之后的任何一步都能从库里重新驱动。
所以处理器里不许直接查库、调 Telegram API、发消息。

## 代价

- `canonical_events` 不带 `tenant_id`，属于丙类表：**RLS 套不上去**。
  它的隔离完全靠「只有平台自己的组件读它，租户接口不暴露它」这条约定，
  没有数据库层的兜底。
- 删租户时不能简单级联。CanonicalEvent 可能还被别的租户引用，
  清理逻辑要判引用计数。
- 演示源（[[ADR-0014]]）的 `canonical_events` 为全平台共享，
  清理存在竞态（风险 RK-16）。
- 多一次写入与一次扇出，延迟增加。这是为什么采集延迟 P99 是三个告警指标之一。
