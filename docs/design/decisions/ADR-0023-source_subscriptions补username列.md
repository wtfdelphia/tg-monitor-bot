# ADR-0023：`source_subscriptions` 是否补 `username` 列

状态：**已定案**（2026-09-21，选 A）

## 决定

**建表时补 `username TEXT`**，在 27 表迁移里就位，不走投递时查 Telegram。

三条配套约束，缺一条这个决定就不成立：

```text
1 刷新时机 = 权限探测（POST /api/v1/sources/{id}/probe）
  探测本来就要调 Telegram 拿频道状态，username 顺带取回，零额外往返
2 链接构造失败一律退化为文本，不输出可能打不开的 URL
  判据：username 为空 → 走 /c/ 私有分支；两支都不可用 → 输出
  "chat_id=... message_id=..."
3 username 为空不是异常，不记 error、不告警
  私有群本来就没有 username，这是正常态
```

## 背景（原「待决」节，保留）

`source_subscriptions` 只有 `title`，没有 `username`。
而 `{username}` 占位符与 `{message_link}` 的公开分支
（`https://t.me/{username}/{tg_message_id}`）都需要它。

```text
A 建表时补 username TEXT      省一次 API 往返，但频道改名后失效，
                              需在权限探测时一并刷新
B 投递时查 Telegram           总是最新，但每条投递多一次调用，
                              且要计入 FloodWait 预算
```

## 理由

投递路径上加 API 调用与退避纪律冲突：拿链接失败会让一条**本可投递**的消息进重试，
而重试是按目标维度退避的，一次拿链接失败会拖慢那条链路上其它正常的投递。

改名失效的代价小得多 —— 只是链接失效，
按现有的「无法生成时退化为文本」兜底即可，不报错、不重试。

## 代价

- 多一列会过期的缓存数据，刷新时机（权限探测时）必须真的实现，
  否则它会慢慢全部失效而没有任何信号。
- 频道改名后生成的链接是坏链接。**坏链接比没链接更糟** ——
  用户点了打不开会以为是平台的 bug。这条代价由上面的约束 2 兜住：
  构造失败退化为文本，而不是输出一个可能打不开的 URL。
- **改名到下一次权限探测之间有一个窗口，窗口内链接是坏的。**
  这个窗口没有上界 —— 权限探测是上线阶段的能力且由租户手工触发，
  没有定时刷新。**接受它**：代价是少数链接失效，
  换来的是投递路径上零 API 调用。
  若日后要收窄，加定时刷新即可，不影响本决定。
