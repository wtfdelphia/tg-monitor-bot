# ADR-0015：对外定位为转发工具，不是内容聚合器

状态：已定案

## 决定

平台对外的定位是：**帮租户把自己有权访问的消息，按自己的规则转发到自己的频道**。
不做内容聚合、不做站内检索、不做公开的内容库。

## 背景

同一套技术能力有两种产品形态：

- **聚合器**：平台抓取大量公开频道，建索引，对外提供搜索和浏览。
  商业上更有吸引力 —— 有内容就有流量。
- **转发工具**：平台不持有内容视角，每条消息的读取主体是租户自己的身份，
  处理完就投给租户自己指定的去处。

选后者的理由是合规上的单向门：

聚合器一旦上线，平台就在向第三方分发它无权分发的内容，
而且这件事无法事后收回 —— 索引已经建了，页面已经被抓了。
转发工具的每一次读取都能追溯到「某个租户用自己的凭据读了自己能读的东西」，
平台在链路上只是搬运。

这条定位是很多下游约束的源头，不是一句市场话术：

- 不存原始消息正文超过投递所需的时长（`spec/03` 的保留策略）
- 不建跨租户的内容索引 —— 这也是 `tenant_events` 分两层的动机之一（[[ADR-0009]]）
- 不提供「看看别人在监控什么」这类功能，哪怕它对增长有用

## 代价

- 天花板低。没有内容护城河，产品价值完全等于「省了写脚本的时间」，
  可替代性高，定价上不去。
- 冷启动难。新租户进来看到的是空的（这是 [[ADR-0014]] 演示源存在的原因）。
- 长期会反复有人提「加个搜索吧」。**这条 ADR 的作用就是让那次讨论回到这里，
  而不是重新论证一遍。** 真要改，写新的 ADR 取代本条，并同时处理保留策略与
  两层事件模型 —— 那是一次架构级改动，不是加个接口。
