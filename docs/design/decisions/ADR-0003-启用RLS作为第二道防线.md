# ADR-0003：启用 PG RLS 作为第二道防线

状态：已定案

## 决定

27 张表按三类启用 Row Level Security。
应用层**照旧**在每个查询里显式写 `tenant_id` 条件 ——
RLS 是第二道防线，不是唯一防线。

## 背景

早期方案是「只靠应用层」：所有数据访问走 Repo，Repo 强制要求 `AuthContext`。
理由是 RLS 有性能与心智成本，而且应用层已经有 newtype 约束。

推翻它的原因是**失效模式的形状**：

应用层漏一个条件，结果是查询返回别的租户的行，且一切正常运行 ——
没有报错，没有日志，除了被看到的人自己发现，没有任何信号。
加上 RLS 之后，同一个漏写的查询返回 0 行：功能坏掉，**立刻可见**。

> 把静默的数据泄漏换成吵闹的功能故障，这就是这条决策买到的东西。
> 反过来说，如果谁提议「既然有 RLS 了，应用层就不用写 `tenant_id` 了」——
> 那是把两道防线合成一道，方向反了。

为什么不用 `CHECK` 约束或视图代替，见 [[ADR-0005]]、[[ADR-0004]]。

## 代价

- **RLS 不覆盖 TRUNCATE。** `app_user` 必须被显式收掉 TRUNCATE 权限，
  这件事 RLS 自己不管（静态断言 A1）。
- **唯一约束是 RLS 补不上的侧信道。** 唯一约束漏 `tenant_id` 时，
  攻击者可以用 duplicate key 错误探测别的租户是否存在某条记录 ——
  RLS 挡查询，不挡约束检查。所以铁律「唯一约束必须含 `tenant_id`」
  和 RLS 是两件独立的事（静态断言 A4）。
- 分区表不继承 RLS，这是 `tenant_events` 暂不分区的原因之一（[[ADR-0024]]）。
- leakproof 相关的优化被禁用，函数索引与 `LIKE` 下推失效
  （实测有一处 150× 堆块放大）。
- 整套机制依赖部署期配置：`app_user` 必须 NOSUPERUSER NOBYPASSRLS 且非表 owner，
  PgBouncer 必须 `server_reset_query_always = 1`。
  这些是 [[ADR-0016]] 不做私有化部署的直接依据。
- **静态审计全绿不等于隔离正确**：`USING (true)` 能骗过所有断言，
  `#[sqlx::test]` 注入的 pool 是超级用户 pool，整个 RLS 被旁路。
  所以反向测试必须显式切到 `app_user`（`eng/03`）。
