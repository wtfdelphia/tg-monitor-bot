# ADR-0040：租户物理清理终结函数精确例外

状态：已定案

## 决定

在 ADR-0004 全面禁止 `SECURITY DEFINER` 的基础上，只批准一个可执行的精确例外：
`public.tenant_purge_finalize(bigint)`。

该函数由独立的 `tenant_purge_finalizer` `NOLOGIN` 角色持有，调用者必须是
`tenant_purge` 登录角色。函数固定使用 `search_path = pg_catalog, pg_temp`、
`READ COMMITTED` 和生命周期 advisory lock，在数据库内重新检查注销状态、恢复窗口、
全部残留与跨租户引用后，才允许删除租户根行，并在同一事务写入平台级完成日志。

`tenant_purge` 不直接持有根表 `DELETE`，也不能建对象、提升角色、读取密文、会话标识、
消息正文或对象 key。`tenant_purge_finalizer` 只拥有该函数所需的根表删除、候选列读取、
残留存在性读取和固定完成日志写入权限，不拥有子表删除或 `TRUNCATE` 权限。

A8 仍禁止所有其他 schema、函数重载和其他 `SECURITY DEFINER` 函数；C16 固定校验
角色属性、owner、函数属性、正文摘要、ACL、列/表/序列权限和 RLS 策略。该例外不批准
CLI、systemd 调度、真实生产租户删除或跨存储副本删除。

## 背景

物理清理必须在数据库事务内对生命周期锁、注销状态、恢复窗口和共享引用做最终复查，
但 `tenants` 根表没有 RLS，受限运行角色也不能直接删除根行。若给运行角色根表删除权限，
安全边界会退化为触发器或应用层自觉；若使用 owner 连接，则无法满足最小权限和可审计要求。

因此需要一个窄到可静态核验的数据库入口，而不是把原先全面禁止提权函数的规则改成泛化许可。

## 代价

数据库中出现一个提权函数，A8 不再能用“任何函数即报红”作为完整判据，必须依赖 A8 的精确
放行条件与 C16 的正文、ACL 和权限审计。入口实现错误可能影响租户根行，所以必须同时保留
受限角色反向测试、迁移重入、审计双遍和真实生产调度前的独立验收。

共享引用仍可能使清理返回 `blocked`，主库完成也不代表备份、Redis、运行日志、Telegram
已投递内容或底层对象副本已经删除；这些边界继续由 ADR-0039 和生命周期规格管理。
