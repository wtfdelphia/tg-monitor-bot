# ADR-0022：用 CI 断言替代安全面的第二人复核

状态：已定案

## 决定

安全面（RLS、角色权限、约束形状）不设「第二人复核」流程，
改为 9 条静态断言 + 3 条补充断言在 CI 里强制，
断言由 `tgm audit-rls` 执行，每个 PR 都跑。

## 背景

标准做法是「涉及安全配置的 PR 必须有第二人 approve」。
在当前团队规模（1 人全职）下这条是句空话 —— 没有第二个人。
写进流程文档只会制造一个所有人都知道没在执行的规则。

断言比人审可靠的地方在于它检查的是**状态而不是 diff**：

- 人审只能看到这次改了什么。`tgm audit-rls` 查的是数据库当前的实际状态，
  所以「有人手工连上生产库做过一次 `ALTER`」这种情况人审永远发现不了，
  断言会。
- 断言的判据是「表里有没有 `tenant_id` 列」而不是一份人维护的表清单。
  清单会腐烂，列的存在不会 —— 新建的表自动被纳入检查，
  不需要有人记得去加。
- 有几条根本不适合人审：A3（`CHECK` + `current_setting`）是
  「建表时接受、恢复时失败」的定时炸弹，评审时看不出问题；
  A8 的两个写法坑（依赖记在 `pg_rewrite` 上、`on` 与 `true` 存成不同字符串）
  连写断言的人自己都踩过。

## 代价

- **断言全绿不等于隔离正确。** `USING (true)` 能通过全部断言，
  而 `app_user` 照样能跨租户读到数据。这是实测验证过的。
  所以断言必须和反向测试（`eng/03` 的 42 条）成对存在，
  少任何一套都不成立。
- 断言覆盖不到的地方要明写成已知边界，不能当作已解决：
  主查询覆盖不了乙类表（无 `tenant_id` 列），
  A2 只硬编码检查了 `app_user` 一个角色，
  A7 只覆盖了 A4 三条白名单中的一条。
- 有一条断言（`identities.tenant_id` 不可改）比它想表达的属性弱：
  它查的是 `UPDATE` 权限，拦不住「先删后建」。
- 全部断言 SQL 是在玩具表上验证的，**没有在真实的 27 张表上跑过**。
- 本条决策的工期影响记在 `plan/00-里程碑与工期.md`，本文不写数字。

## 落地追记（2026-09-22）

上面三节按 README 规则 2 不动。这一节记落地后发生的变化 ——
**它们都不是改主意，是这个决定被执行之后才能知道的事。**
规则 2 保护的是理由，而下面这些是理由的后果。

**判据比原文强了一档。** 原文只说「每个 PR 都跑」，而「跑了」不携带信息：
`USING (true)` 能通过全部断言（代价第一条已写明），所以全绿本身不证明任何事。
`plan/00` 的 WP-1 硬要求把判据定成「第二遍在 `DISABLE ROW LEVEL SECURITY`
之后必须红」，照字面做一次确实红了 —— **但那只验了主查询一条**，
其余十几条仍然可能是永远绿的。**一条永远绿的断言与一条不存在的断言，
在 CI 日志里长得一样**，而这正是本 ADR 要排除的情形。

所以实际落地成 `scripts/audit-double-pass.sh`，判据是逐条的两句：

```text
1  每条断言各自配一处针对性破坏，被针对的那条必须红
2  报红的必须恰好是它一条（预期的连带登记在脚本的 ALSO 表里）
```

第 2 句同样承重：一处破坏让五条断言一起红，退出码仍然对，但报告就失去了
「指出改哪里」的能力 —— 而那才是断言能替代第二人复核的前提。
当前只有一处登记的连带（`A2b` 必然触发 `A1`，因为 owner 隐含全部权限含
`TRUNCATE`，两条从不同角度抓同一个事实，是冗余不是耦合）。

**代价一节里有三处数字与编号已被实际落地推翻**，按规则 2 不在原文改，列在这里。
第四处「42 条」我一度也列成推翻了，它其实是对的 —— 连同那次返工一并记在下面：

```text
「9 条 + 3 条补充」   实际 16 条（A0 A1 A2a A2b A3~A9、MAIN、C1 C2 C4 C5）。
                     A2 拆成 a/b 两条，A0 与 C4 C5 是落地时新增的。
                     C3（openapi 契约）不属 tgm audit-rls，随 WP-5
「A2 只硬编码检查了 app_user」
                     已不成立。A2 不再写角色名，改为从 GRANT/策略/列权限
                     三处派生「运行时角色」集合。代价是派生自己会失效 ——
                     故新增 A0 断言派生非空（已在空库上验过它报红）
「A7 只覆盖三条白名单中的一条」
                     已不成立。A7 不再写表名，白名单写成索引名列表、
                     表名由索引名反查。而白名单本身已从三项减到两项 ——
                     uq_task_idem 的破例论证不成立（哈希不能补唯一约束的
                     侧信道，泄漏的是存在性不是值），已改索引形状
「eng/03 的 42 条」    **这一处没被推翻，42 仍然是对的。**
                     42 = R1~R22(22) + A1~A9(9) + Q1~Q6(6) + X1~X5(5)。
                     已验 10 条反向测试 + 16 条断言，全在 L2/L3；
                     欠账集中在 L4 —— 不是难，是应用层代码还没有
```

上面那一行**本身就是这一节的第一次返工**。我先把它写成「实际 23 条」，
依据是数 `R` 编号数到了 `R23` —— 而 `eng/03` §3.1 与 §3.3 对那两条各写了一句
「这条不进上面的 42」，`R23` 是其中之一。**编号的最大值不是清单的长度**，
何况 42 还含 A/Q/X 三族。

留着这段而不是删掉写错的那行，是因为**它错得很像对的**：数得出来、
有依据、方向还符合「文档里的数字通常偏旧」这个先验。而修正它的唯一办法是
读原文那句话，不是数编号 —— 全仓库有七处引用这个数字，如果我照原判断
批量改，七处会一起变错，且没有任何检查会报警
（`pre-do/03` 四已记过这个形状：改坏的方式是「看起来仍然合理」）。

**代价最后一条已销账**：「全部断言 SQL 是在玩具表上验证的，没有在真实的
27 张表上跑过」—— 现在 27 张表已建（12 个迁移文件），16 条断言在其上 0 红，
双遍逐条验过每条能被单独打红。

**原文没预见到的一条代价，记在这里**：断言的覆盖范围改一次，
**快照的覆盖范围要跟着改**，否则针对新覆盖面的破坏无从验证，而 diff 会
干净得很有说服力。已踩过一次（快照漏了 `NSP`/`MBR` 两段与策略、约束三段）。
