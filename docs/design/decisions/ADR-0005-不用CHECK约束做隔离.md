# ADR-0005：不用 `CHECK` 约束做租户隔离，并用 CI 拦住它

状态：已定案

## 决定

禁止在表上写 `CHECK (tenant_id = current_setting('app.tenant_id')::bigint)`
这类约束。静态断言 A3 在 CI 里拦。

同时：拒绝「用 `nullif(current_setting('app.tenant_id', true), '')` 让缺失时安全降级」
这条常见建议。

## 背景

`CHECK` + `current_setting` 看起来是个便宜的写入侧防护：
写错租户直接被约束拒掉，不依赖 policy。

它是个定时炸弹。**建表时 PG 接受它，恢复备份时失败。**
`pg_restore` 恢复约束定义时会重新求值，而那个会话里没有 `app.tenant_id`，
于是整个恢复过程报错中断。

这类错误的特征是：开发期、测试期、生产运行期全部正常，
**只在你最需要它工作的那一刻失败** —— 灾难恢复的时候。
所以这条不能靠代码评审，必须靠断言。A3 是 A1~A9 里最值得自动化的一条。

关于 `nullif(...)`：这条建议的效果是把「参数缺失时报错」
换成「参数缺失时匹配不到任何行」。它确实让恢复不报错了，
但它同时让**忘记设置 `app.tenant_id` 的业务代码静默返回零行**。

> 方向反了。我们要的是 fail-loud：参数没设好就炸，
> 而不是安静地查不到东西然后让人去猜。

`::bigint` 这个类型转换在这里是安全机制而不是写法偏好 ——
它保证空串会抛 `invalid input syntax for type bigint: ""` 而不是被当成假值吞掉。

## 代价

- 写入侧少一层防护。补偿是应用层显式写 `tenant_id`（[[ADR-0003]]）
  加 policy 的 `WITH CHECK`。
- A3 是按「约束表达式文本里出现 `current_setting`」匹配的，
  绕过方式存在（比如包一层函数）。断言拦的是无意的引入，不是有意的规避。
- fail-loud 的代价是错误会打到用户面前。这是有意的：
  `app.tenant_id` 没设好属于编程错误，不该降级成空结果。
