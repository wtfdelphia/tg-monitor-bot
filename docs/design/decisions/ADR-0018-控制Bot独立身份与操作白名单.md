# ADR-0018：控制 Bot 独立身份 + 两类操作永久不上 Bot

状态：已定案

## 决定

控制 Bot 与数据 Bot 是两个 Bot：独立身份、独立 Webhook 端点、独立令牌桶。

并且两类操作**永久**不通过 Bot 做：
提交 Bot Token、MTProto QR 登录码 / `login_token`。
Bot 侧遇到凭据类操作的正确响应是回一个 Web 链接，不是代为收集。

## 背景

### 独立身份

Telegram 限流按身份计，所以令牌桶按 `sender_identity_id` 分。
若控制入口复用数据 Bot 身份：

```text
一个租户暴力转发耗尽该 Bot 令牌桶
  → 该租户的 /status、/pause 一起超时
  → 恰好在最需要干预的时刻，干预通道不可用
```

**过载时控制面必须仍然可达** —— 这是独立身份换来的唯一东西，也够了。

顺带：控制 Bot 不订阅 `channel_post`。它不是采集通道。

### 操作白名单

被禁的两类都是 bearer 凭据：
明文经 Telegram 服务器、留在聊天记录、进 update 日志。
**把凭据存得再严，从私聊漏出去是一样的结果。**

这条禁令的边界要说清：禁的是 bearer 凭据，不是「扫码」这个动作
—— 控制台扫码登录（[[ADR-0017]] 路径 B）的二维码里只有随机 nonce，
方向相反，不在禁令内。

## 代价

- **用户要加两个 Bot**，引导流程多一步，而且「为什么要两个」这个问题
  会反复出现在支持工单里。
- 两套 Webhook 端点、两套令牌桶、两份配置，部署与监控面翻倍。
- 两个 Bot 都会收到自己的 `my_chat_member`，采集订阅只认数据 Bot 那一条 ——
  这是个容易写错的地方。
- 幂等键不能只用 `(tenant_id, update_id)`，否则控制 Bot 的命令
  会被误判成数据 Bot 的重投。
- 审计日志在首发既没有页面也没有 Bot 命令（不在白名单里），
  **首发只能 curl**。这是已知缺口。
