# ADR-0014：废除官方 Bot 托管，改平台自营演示源

状态：已定案

## 决定

不提供「用平台官方 Bot 帮你采集」这条路径。
取而代之，平台自营少量公开频道作为**演示源**，新租户零配置即可看到端到端效果。

## 背景

原设计里有一档「官方 Bot 托管」：租户不填凭据，把平台的 Bot 拉进目标频道，
平台用官方身份采集并投递。它的作用是降低接入门槛。

废除的原因不是技术的，是责任边界的：

- Bot 能读到什么，取决于谁把它拉进了哪里。平台无法验证租户对那个频道有权限，
  也就无法证明这次采集是被授权的。
- 一旦平台身份出现在采集链路上，平台就从「工具提供方」变成「内容访问方」。
  这和 [[ADR-0015]] 的定位直接冲突。
- 与 [[ADR-0013]] 同一个爆炸半径问题：官方身份被限流，所有托管租户一起停。

演示源换了个思路 —— 不降低租户自己采集的门槛，而是让「先看效果」这件事
不需要采集租户的任何东西。演示源的内容是平台自己选的公开频道，
读取主体是平台自己，责任归属清晰。

演示源在数据模型里落在一个共享的 `identities` 行上，
这也是 `identities.tenant_id` 允许为 NULL 的唯一原因（见 [[ADR-0006]] 的例外）。

## 代价

- 演示源是只读的单向体验：能看到消息流过规则并投递，
  但看不到「我关心的那个频道」。转化漏斗中间少了一段。
- `identities.tenant_id` 可空，撕开了铁律「`tenant_id` 一律 NOT NULL」的一个口子。
  代价在应用层付：所有指向 `identities` 的外键不是复合的，
  于是跨租户取用别人的 identity 在数据库层拦不住，
  必须由应用返回 403，并由反向测试 R19 守住。
- 平台自己维护一组 Telegram 账号/频道订阅，属于运营负担，而且它会被
  Telegram 的策略变化影响 —— 演示源挂了不影响付费租户，但首页会很难看。
