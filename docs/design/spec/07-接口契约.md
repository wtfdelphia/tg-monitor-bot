# 接口契约

本文是控制面**对外接口的唯一定义处**：Web 侧怎么登录、REST 端点有哪些、
错误码怎么回、契约怎么防漂移。

两条入口（REST 与 Bot）共用同一套鉴权检查点，那套检查点定义在
`05-安全与租户隔离.md` §八，本文只补 REST 分支的具体形态。
Bot 入口的安全设计在 `02-总体架构.md` §六。
表结构一律以 `03-数据模型.md` 为准，本文不重复 DDL。

---

## 一、Web 侧鉴权

### 1.1 前置问题：Web 用户拿什么登录

**本方案没有 Web 口令这个东西。** `tenant_members` 只有 `user_id`
（Telegram user id），`tenants.owner_user_id` 同样是 Telegram id ——
27 张表里没有任何邮箱、口令哈希、邮箱验证字段。整套身份体系是 Telegram 原生的。

口令方案的真实代价不是「加一张 users 表」，而是顺带引进口令哈希、
找回流程、邮箱发信、邮箱验证、弱口令策略、撞库防护 —— 一条都不在工期里。
所以不做口令，也不做邮箱。这是唯一需要新增一套并行账号体系的选项，
被排除的理由就是这个。

**两条路径都做，且都签发进同一张 `web_sessions`：**

```text
A  Telegram Login Widget（OIDC）      主路径
B  控制 Bot 扫码登录（自建挑战应答）    并行路径，不是降级备选
```

B 不是 A 的降级备选，理由是**运维摩擦，不是部署形态**：A 的 Allowed URLs
是 BotFather 里的预登记项，每个域名与每套环境（预发、演示、正式）都要登记一次，
而 B 没有这个约束。私有化部署已按 ADR-0016 不做，所以「内网无公网域名」
这条原始动因不再成立 —— 保留 B 的理由只剩上面这一条（见 ADR-0017 的追加注）。

> **控制 Bot 走 Webhook，不是长轮询。** 这在 `02-总体架构.md` §6.4 定案：
> 独立身份、独立 Webhook 端点、独立令牌桶，`secret_token` 必设。
> B 的「零入站端口」曾是它的卖点之一，随私有化部署一起作废了。

### 1.2 路径 A：Login Widget 已经是 OIDC 了，不是 HMAC

**2026-05 起 Telegram 把 Login Widget 改成了标准 OpenID Connect Provider。**
老文档里那套「用 bot_token 算 HMAC-SHA256 验 `hash` 字段」的做法已归档，
**不要照着实现** —— 网上能搜到的绝大多数示例代码都还是旧的那套。
现在的流程是标准 Authorization Code + PKCE：

```text
端点   授权    https://oauth.telegram.org/auth
       令牌    https://oauth.telegram.org/token
       JWKS    https://oauth.telegram.org/.well-known/jwks.json
       发现    https://oauth.telegram.org/.well-known/openid-configuration
scope  openid（必需）+ profile；phone 与 telegram:bot_access 本方案不需要
验证   id_token 是 JWT，按 JWKS 验签（默认 RS256，BotFather 可配
       ES256 / EdDSA / ES256K），并校验 iss / aud / exp
```

`aud` 是 bot id，`sub` 即 Telegram user id —— 与 `tenant_members.user_id`
和 Bot 入口的 `update.from.id` 是同一个值域，这正是「身份同源」的由来。

实现上不要手写 JWT 验证与 JWKS 轮换：用 `openidconnect` crate（走发现文档，
PKCE、nonce、JWKS 缓存都在里面），或退一步用 `jsonwebtoken` 自己缓存 JWKS。

**验证侧的三条硬要求**，`openidconnect` 默认不全给，
退到 `jsonwebtoken` 时更要逐条落实：

```text
算法钉死   只接受 BotFather 里为本 bot 实际配置的那一个 alg（如 RS256），
           从配置读，不从 id_token 的 header 读。
           照 header 选算法 = 攻击者改 header 就换了验签规则；
           同理必须拒 alg=none 与任何对称算法（HS*：公钥会被当 HMAC 密钥）

nonce      授权请求生成随机 nonce → 存进登录态（服务端，非 cookie 可读）→
           校验 id_token.nonce 逐字节相等 → 校验后立即作废。
           单次使用是重点：只比不删 = id_token 可重放。
           state 防 CSRF、nonce 防重放，两个都要，不能拿一个顶另一个

JWKS 失败  取 JWKS 失败或 kid 找不到时一律拒绝登录（HTTP 503 + 重试提示），
           不得回落到「跳过验签」或「用过期缓存无限期顶着」。
           缓存有 TTL 上限；kid miss 只允许触发一次强制刷新，
           且刷新要限速，否则伪造 kid 的请求就是一条打向
           oauth.telegram.org 的放大管道
```

前两条要各有一条反向测试（改 `alg` 的 token、重放同一个 `id_token`），
见 `../eng/03-测试策略.md`。JWKS 失败路径的三个具体参数取决于 §七-2 的实测结果。

> **回调地址是白名单制**：Allowed URLs 要在 BotFather 预登记。
> 每套环境（预发、演示、正式）的域名都要单独登记一次 —— 又一条 B 值得留的理由。

### 1.3 路径 B：控制台扫码，以及它和 MTProto 扫码的区别

**这两件「扫码」性质完全不同，不要相互套用**（`02-总体架构.md` §6.3
已就此加了边界说明）：

```text
MTProto 扫码（见 08-账号接入.md）  登录的是「Telegram 账号」，产出采集身份，
                                 写入 identity_secrets，用来读频道
控制台扫码（本节）                登录的是「我们的控制台」，产出 web_sessions 行，
                                 查 tenant_members 定角色
```

让 MTProto 扫码兼作控制台登录是错的：那会逼用户为了进后台而把整个 Telegram
账号授权给我们（等于交出全部私聊的读取权），与 `05-安全与租户隔离.md` §八
的权限模型相悖。

安全形态的关键：**二维码里只放一个随机 nonce，绝不放会话 token**。
nonce 单独毫无用处，必须由一个 Telegram 账号向控制 Bot 应答才有意义。
表结构与状态机见 `03-数据模型.md` §7.2。

> **必做的确认步：不是可选加固。** 朴素实现有一条完整的账号接管路径 ——
> 攻击者在自己浏览器开登录页、截图二维码发给受害者，受害者一扫，
> 服务端收到带受害者 `from.id` 的应答，**会话签发给了攻击者的浏览器**。
> 所以 Bot 收到应答后**不能直接签发**：回一张确认卡片，展示
> `origin_ip` / `user_agent` / 4 位 `confirm_code`（与网页上显示的同一个码），
> 用户目视比对后点确认才签发。Telegram 官方客户端的扫码登录也是这么做的。

### 1.4 会话表要点

DDL 与侧信道处置见 `03-数据模型.md` §7.3。三条要点：

**主键 `(tenant_id, id)`，`id` 是随机 32 字节。** 自增 session id 可被枚举 ——
这与 `03-数据模型.md` §7.1 记录的唯一约束侧信道是同一类问题：
可预测的标识符本身就是泄漏。随机 `id` 还使它**不必像 `bot_console_sessions`
那样破铁律 1**，因为随机值能和 `tenant_id` 组成复合主键而不影响按 id 查询。

**`id` 不进任何日志。** session id 等价于口令，落进 `system_logs`
或 access log 就等于明文存口令。日志记 `user_id` 与 `tenant_id`。

**它是甲类 RLS 表，但有和 `tenant_members` 一样的鸡生蛋问题** ——
按 cookie 查 session 时还不知道 `tenant_id`。**不要为它再开一个新角色**：
复用现有的 `auth_lookup`（`05-安全与租户隔离.md` §3.7），
同一条 SELECT-only、`TO auth_lookup` 的策略形状：

```sql
CREATE POLICY session_self_lookup ON web_sessions FOR SELECT TO auth_lookup
  USING (id = current_setting('app.session_id')::bytea);
```

`console_login_challenges` 也只授给 `auth_lookup`，但那张表**不启用 RLS** ——
它是登录前表，租户未知，隔离靠 GRANT 层（`app_user` 上是 REVOKE ALL）。

### 1.5 会话与 CSRF

```text
Cookie      HttpOnly + Secure + SameSite=Lax + Path=/
CSRF        双提交：cookie 里的 csrf_token 与请求头 X-CSRF-Token 必须一致
            SameSite=Lax 已挡住大部分场景，但不足以覆盖 GET 导航型攻击
            与同站子域名，故 CSRF token 照做
有效期      滑动续期，绝对上限 30 天
登录限流    没有「口令错误」这回事，但两条路径各有要限的：
            A 路径 —— id_token 验签失败按 ip 限流，60s 内 10 次 → 429
            B 路径 —— 建挑战按 ip 限流（否则可批量刷二维码去钓鱼），
                     同时 console_login_challenges 上有
                     uq_console_login_pending 保证一个账号同时只有一个待确认挑战
登出        服务端删除 session 行，不依赖客户端清 cookie
```

**为什么不用无状态 JWT**：登出与权限回收无法即时生效。
租户把某成员移出（`DELETE FROM tenant_members`）后，
JWT 在过期前仍然有效 —— 这与「`tenant_id` 一律从已验证的成员关系推导」
直接冲突。有状态会话每次请求查库，成员关系变更立即生效。
代价是每请求一次 Redis/PG 查询，可接受。

### 1.6 与 Bot 入口的收敛点

```text
登录（两条，只在拿到 user_id 的方式上不同）：
  A  id_token（JWKS 验签）→ sub
  B  nonce 应答 + 用户确认 → update.from.id
                ↓ 两者都到这里
         查 tenant_members → 写一行 web_sessions      ← 签发后完全无差别
                                （差异只记进 audit_logs 的登录方式字段）
请求鉴权（两条入口）：
REST:  Cookie → web_sessions → tenant_members → AuthContext{source: web, ip}
Bot:   secret_token → update.from.id → tenant_members → AuthContext{source: bot, ip: NULL}
                         ↓
                   同一个业务层
```

两条入口的差异只体现在 `AuthContext` 的 `source` 与 `ip` 两个字段上，
其余完全一致。**业务层不得出现 `if source == bot` 的分支** ——
一旦出现，就是两套权限逻辑，漂移的那一侧就是越权入口。

唯一的例外是凭据类操作（`02-总体架构.md` §6.3）：那不是权限分支，
是**入口能力白名单**，在入口层就拒绝，不进业务层。

## 二、通用规范

```text
前缀        /api/v1
认证        Cookie 会话（浏览器）；服务间调用不在首发范围
租户        绝不出现在 URL 或请求体里 —— 从 AuthContext 取
分页        ?page=&per_page=（默认 20，上限 100）
排序        ?sort=field&order=asc|desc，白名单字段
错误包络    { error: { code, message, details? } }
幂等        写操作接受 Idempotency-Key 头（可选）
```

**`tenant_id` 不进 URL 这一条是硬约束。** 出现 `/api/v1/tenants/{id}/rules`
这种形状就意味着服务端要校验「URL 里的 id 是否等于会话里的 id」，
多一次校验就多一处漏检的可能。平台级跨租户操作（`SUPER_ADMIN`）走
独立前缀 `/api/v1/admin/tenants/{id}/...`，与租户端点物理分离。

### 2.1 错误码

| code | HTTP | 场景 |
|---|---|---|
| `UNAUTHENTICATED` | 401 | 无会话或已过期 |
| `FORBIDDEN` | 403 | 角色不足 |
| `CSRF_INVALID` | 403 | 双提交不匹配 |
| `NOT_FOUND` | 404 | 含「存在但不属于本租户」——**不返回 403** |
| `RULE_CONFLICT` | 409 | `uq_rule_conflict` 命中，body 带已有规则 |
| `CONDITION_INVALID` | 400 | 如 `size_min` 给了两条（`03-数据模型.md` §4.3） |
| `REGEX_INVALID` | 400 | details 带 Rust regex 的原始编译错误 |
| `QUOTA_EXCEEDED` | 429 | 超套餐配额 |
| `RATE_LIMITED` | 429 | 登录失败限流等 |
| `CREDENTIAL_VIA_WEB_ONLY` | 403 | Bot 入口提交凭据（`02-总体架构.md` §6.3） |
| `NOT_INVITED` | 403 | 身份已验证但不属于任何租户（首发白名单制，见 §3.1） |

> **跨租户访问返回 404 而非 403**，理由与 `03-数据模型.md` §7.1 的侧信道同源：
> 403 泄漏「该 id 存在」。这一条必须写进测试，否则实现者会按直觉写 403。

### 2.2 契约形态：OpenAPI 3.1，从代码生成

§三 的端点清单是给人读的。**Markdown 表格不是契约** ——
它不能做契约测试、不能生成客户端、前后端只能靠人读。

```text
生成方式   utoipa + utoipa-axum（选型见 ../eng/00-工程约定.md），标注在 handler 上
版本       OpenAPI 3.1
产出       target/openapi.json，并由 CI 导出为仓库内的 openapi.json
UI         Swagger UI 仅在 dev profile 挂载于 /api/docs；
           生产构建不编译（feature gate），理由见下
```

**三条约定，都是这个方案容易写错的地方**：

```text
1 错误包络只定义一次
  §2.1 的 { error: { code, message, details? } } 必须是一个
  #[derive(ToSchema)] 的类型，所有端点的 4xx/5xx 都引用它。
  若每个 handler 各写一遍 responses(...)，64 个端点就有 64 份定义，
  与「错误包络一致性测试」这个出口条件自相矛盾

2 tenant_id 不得出现在任何 schema 里
  这是 §二 那条硬约束在契约层的延伸。请求体、路径参数、查询参数
  一律无 tenant_id；它只从 AuthContext 来。
  契约里一旦出现，就意味着有人把它当成了入参

3 平台端点单独一份契约
  §3.11 的 /api/v1/admin/** 与租户端点物理分离（§二 已定），
  契约也分两份：openapi.json 与 openapi-admin.json。
  合成一份会让租户侧的客户端生成器带出平台端点的存在
```

> **Swagger UI 不进生产构建**，不是洁癖：它会把全部端点、
> 全部 schema、全部错误码暴露给未认证访问者，等于免费提供攻击面地图。
> 平台自己的运维如果需要，可用导出的 `openapi.json`
> 配合任意离线 UI 在本地看，不需要平台内置。

**契约变更即 CI 失败**：`openapi.json` 提交进仓库，CI 重新生成后比对，
不一致则失败 —— 逼迫改了端点的人在同一个提交里更新契约。
卡口命令见 `../eng/04-CI门禁.md`。这与 `.sqlx/` 离线缓存必须提交是同一个模式：
**把「代码与契约一致」变成机器能判的事，而不是评审时靠眼睛看。**

## 三、端点清单

阶段标注含义见 `00-范围与非目标.md` §三；未标注的即首发必须有。

### 3.1 认证与会话

A 路径（Login Widget / OIDC，见 §1.2）：

```text
GET    /auth/oidc/start         生成 state + PKCE verifier，302 到
                                oauth.telegram.org/auth
GET    /auth/oidc/callback      code → token 端点 → 验 id_token（JWKS）
                                → sub → tenant_members → Set-Cookie
```

B 路径（控制台扫码，见 §1.3）：

```text
POST   /auth/qr/challenge       建 console_login_challenges 行，返回
                                { nonce, confirm_code, expires_at, deep_link }
                                deep_link = https://t.me/<bot>?start=login_<nonce>
GET    /auth/qr/challenge/{nonce}   网页轮询状态：pending / awaiting_confirm /
                                confirmed（confirmed 时同时 Set-Cookie）/ expired
```

Bot 侧的两步（`/start login_<nonce>` 与确认卡片的 callback）不是 REST 端点，
走 Bot 入口（`02-总体架构.md` §六），但**改的是同一张挑战表**，状态机也同一套。

```text
POST   /auth/logout             服务端删 session 行
GET    /auth/me                 当前用户 / 角色 / 租户
GET    /auth/sessions           本人的活跃会话列表（含 ip / ua / 登录方式 / 创建时间）
DELETE /auth/sessions/{id}      踢掉指定会话（含当前之外的）
```

`/auth/sessions` 首发就要 —— 多租户场景下用户需要能看到
「谁在用我的账号」。两条登录路径共用这张列表，故列表里要带登录方式，
否则用户无法判断一条陌生会话是怎么进来的。

**验证通过但不属于任何租户的用户，不能回一个裸 403。** 注册路径已定：
**首发平台白名单**（运维手工插 `tenants` + `tenant_members`），**上线放开自助**。
所以首发的正确响应是一个可理解的终态 ——
`{ error: { code: "NOT_INVITED", ... } }`（403），页面上给「你的 Telegram
账号已验证，但尚未被邀请加入任何工作区」加联系方式，
而不是让用户对着 403 猜是不是自己点错了。上线阶段这里换成引导建租户的流程。

### 3.2 Dashboard

```text
GET /api/v1/dashboard/summary   身份状态 / 队列深度 / 今日统计 / FloodWait 冷却
```

运行时指标不走这个端点，走 Prometheus（见 `../ops/01-上线就绪与运维.md`），
所以数据模型里没有 `runtime_stats` 这类表。

### 3.3 身份

```text
GET    /api/v1/identities
POST   /api/v1/identities/bot               提交 Bot Token（仅 Web）
POST   /api/v1/identities/login/qr          → {login_id, qr_png_base64}
GET    /api/v1/identities/login/qr/{id}     轮询 → pending|awaiting_password|
                                                   confirmed|expired|failed
POST   /api/v1/identities/login/password    两步验证密码
PATCH  /api/v1/identities/{id}              {proxy_url, display_name}
POST   /api/v1/identities/{id}/reset-status 状态机手动复位
DELETE /api/v1/identities/{id}
```

**QR 轮询端点是全套 API 里唯一必须做速率限制的读端点** ——
前端每 25s 拉一次（`login_token` 30s 过期，见 `08-账号接入.md`），
但 `login_id` 若可枚举，就成了「探测他人登录状态」的通道。
`login_id` 用随机字节，理由同 §1.4。

session 存 `identity_secrets`（信封加密），不落文件，
所以没有「查 session 文件元信息」这类端点。

### 3.4 源（订阅）

```text
GET    /api/v1/sources?status=&identity_id=&q=&page=
GET    /api/v1/sources/{id}
POST   /api/v1/sources                      手工添加 {chat: "@x" | -100...}
PATCH  /api/v1/sources/{id}                 {enabled, receiver_identity_id}
POST   /api/v1/sources/{id}/probe           权限探测（上线）
GET    /api/v1/sources/discovered           自动发现的 dialogs（上线）
POST   /api/v1/sources/discovered/{id}/enable
```

**路径参数用 `source_subscriptions.id`，不用 `tg_chat_id`。**
两个租户可以订阅同一个 chat，`chat_id` 不唯一标识一条订阅 ——
单租户时代的 `/{chat_id}` 形状直接搬过来会错。

### 3.5 关键词

```text
GET    /api/v1/keywords?q=&match_type=&category=&page=
POST   /api/v1/keywords
PATCH  /api/v1/keywords/{id}
DELETE /api/v1/keywords/{id}                → 响应带受影响规则数
POST   /api/v1/keywords/test                {text} → 命中详情（上线）
POST   /api/v1/keywords/import              CSV/JSON（上线）
GET    /api/v1/keywords/export              （上线）
```

`DELETE` 返回受影响规则数而非直接删：`rules.keyword_id` 是
`ON DELETE RESTRICT`，有规则引用时删不掉。响应必须说明**哪些规则**在引用，
否则用户只看到 409 不知道该改哪。

**`/keywords/import` 必须支持同时批量建规则**：
导入 200 个关键词后要手工建 200 条规则，功能等于没做。
请求体形状：`{keywords: [...], create_rules_with: {target_ref, action, ...}}`。

### 3.6 规则

```text
GET    /api/v1/rules?enabled=&target_ref=&source_ref=&page=
POST   /api/v1/rules                        409 带已有规则
GET    /api/v1/rules/{id}                   含 conditions 与 replacements
PATCH  /api/v1/rules/{id}                   conditions 整体替换
DELETE /api/v1/rules/{id}
POST   /api/v1/rules/{id}/test              {text, media_type, sender} → 路由结果（上线）
POST   /api/v1/rules/{id}/copy              复制为新规则（上线）
GET    /api/v1/rules/{id}/versions          版本历史
GET    /api/v1/rules/{id}/versions/{v}      某版本快照原文
```

**`/rules/{id}/test` 的响应必须解释「为什么不命中」**，不能只回 true/false。
规则引擎有范围门 + 触发 + 收窄 + 否决四段（`03-数据模型.md` §4.3），
用户调不出效果时需要知道卡在哪一段：

```json
{
  "matched": false,
  "trace": [
    {"stage": "scope_gate",   "field": "media_type", "pass": true},
    {"stage": "trigger",      "field": "keyword",    "pass": true, "matched_at": [12, 16]},
    {"stage": "veto",         "field": "exclude_word", "pass": false,
     "detail": "命中排除词「广告」于偏移 40"}
  ]
}
```

没有这个 trace，试跑功能的价值减半 —— 这是试跑被列为必做项而非可选项的原因。

### 3.7 替换规则

```text
GET    /api/v1/rules/{id}/replacements
PUT    /api/v1/rules/{id}/replacements      整体替换（seq 顺序敏感）
POST   /api/v1/rules/{id}/replacements/test {text} → 逐步结果
POST   /api/v1/replacements/copy            {from_rule, to_rules[]}
```

`PUT` 整体替换而非逐条 `POST`：`seq` 是顺序敏感的，
逐条增删会产生「中间态顺序错乱」的窗口。整体提交，服务端事务内重写。

`/replacements/test` 返回**逐步**结果而非最终文本 ——
多条替换按序执行时，用户需要看到每一步的中间结果才能调出想要的效果。

### 3.8 目标频道

```text
GET    /api/v1/targets?page=
POST   /api/v1/targets                      创建即触发连通性自检
PATCH  /api/v1/targets/{id}
DELETE /api/v1/targets/{id}
POST   /api/v1/targets/{id}/probe           → {can_send, can_forward,
                                                content_protected, bot_role}
```

`content_protected` 必须探测并展示：源频道开了内容保护时 `FORWARD`
动作会失败，用户需要提前知道该改用 `RESEND`。
创建即自检的决策见 `../decisions/ADR-0019-目标频道连通性自检.md`。

### 3.9 投递任务与日志

```text
GET    /api/v1/tasks?status=&target_ref=&since=&page=
GET    /api/v1/tasks/{id}                   含 delivery_logs 明细 + 规则版本快照
POST   /api/v1/tasks/{id}/retry             仅 DEAD / FAILED 可重投
GET    /api/v1/audit-logs?actor=&source=&since=&page=
GET    /api/v1/logs?level=&module=&page=    （上线）
GET    /api/v1/logs/export?format=csv       （演进）
```

`GET /tasks/{id}` 必须一并返回**当时的规则快照**，不是当前规则 ——
这是 `rule_versions` 表存在的全部目的，API 不暴露就白做了。

`/audit-logs` 的 `source` 过滤器（`web` / `bot` / `system`）是 Bot 入口引入的，
用来回答「这个改动是谁从哪改的」。

### 3.10 运维与设置

```text
GET    /health                              {pg, redis, mtproto, bot} 逐项
GET    /healthz                             存活探针
GET    /api/v1/settings                     租户级设置
PATCH  /api/v1/settings
GET    /api/v1/quota                        当前用量 / 套餐上限
```

**不提供「应用自我更新」类端点**（reload / update check / apply / rollback）。
那是单机自用工具的形态：多租户 SaaS 里应用更新由部署流水线负责
（见 `../ops/00-部署与运行时.md`），暴露成 API 等于给了一条远程代码执行路径。
配置导入导出留到演进阶段。

### 3.11 平台端（`SUPER_ADMIN`）

```text
GET    /api/v1/admin/tenants
POST   /api/v1/admin/tenants
PATCH  /api/v1/admin/tenants/{id}           套餐 / 配额 / 启停
GET    /api/v1/admin/system-logs            含 tenant_id IS NULL 的平台日志
```

**这组端点必须走独立的数据库角色。** `system_logs.tenant_id` 可空，
等值比较让 `NULL` 行对所有租户不可见 —— 读平台日志需要
`platform_ops`（`05-安全与租户隔离.md` §六），**不能复用租户连接池**。
这是本节存在的主要技术原因，不只是权限分级。

且 `SUPER_ADMIN` 也看不到明文 Token / Session / 消息正文 ——
这组端点在设计时就不提供这些字段。

### 3.12 端点数量

```text
认证会话     8        Dashboard    1        身份         8
源           7        关键词       7        规则         9
替换规则     4        目标         5        任务日志     6
运维设置     5        平台端       4
                                        合计 64 个端点
```

## 四、Web 控制台

### 4.1 技术栈：服务端渲染，不上 SPA

```text
模板     askama 或 minijinja（编译期检查模板，与 sqlx 的哲学一致）
交互     HTMX + 少量原生 JS
样式     单个 CSS 文件，不引入构建链
```

依据是同类产品的实证：`miniflux/v2`（⭐9712，2026-09 活跃）纯 Go 服务端渲染 +
**5 个原生 JS 文件、零前端框架**，撑起 30 个模板页面，设置区只有 6 项。

上 React/Vue 的代价是多一套鉴权（SPA 需要 token 或 cookie + CORS 设计）
与一整条前端构建链。本方案的页面都是表单与列表，SSR 完全够。

### 4.2 信息架构：列表页 + 单对象多 tab 编辑页

`rules` 是个多维对象（keyword + source + media_type + target + action +
conditions + replacements + template + version），**平铺成一个表单会很糟**。
所以编辑页按 tab 切分，切分方式与数据模型对齐：
`条件` tab 对应 `rule_conditions`，`统计` 对应 `delivery_logs`，
`任务中心` 对应 `delivery_tasks` 与 DLQ。

顶层导航：

```text
首发  登录           Login Widget 按钮 + 扫码（含确认码比对）+ 未受邀终态
首发  身份           接入 / 扫码登录 / 代理 / 状态复位
首发  规则           列表（这一页只做列表与批量操作）
首发    └ 规则编辑   tab: 基本 · 条件 · 替换 · 投递 · 统计 · 版本历史
首发  关键词         列表 + 批量导入导出 + 试跑
首发  目标频道       列表 + 连通性自检
上线  Dashboard      身份状态 / 队列深度 / 今日统计 / 连续失败告警
上线  源             列表 + 权限探测 + 自动发现
上线  任务中心       队列 / 失败 / 死信 + 单任务重试
上线  审计与日志      审计日志（含 source 列）/ 系统日志
上线  设置           租户设置 / 配额用量 / 会话管理
```

**「关键词」与「规则」不能挤在一页。** 规则有 8 个维度，合并后无法操作。

首发六页里，「替换」tab 与「试跑」**只出框架不出功能** —— 引擎在上线阶段。
页面上留位并标「即将支持」，不要为了填满 tab 把引擎也提前。

### 4.3 为什么首发就要六页，而不是三页

凭据操作永久只走 Web（`02-总体架构.md` §6.3），而**首发的 Bot 只有只读观测命令**
（配置类命令在上线阶段）。若首发只做接入三页，用户接入完账号后
配规则、建关键词、加目标仍然只能 curl，「首发可小范围内测」这句话不成立。
所以配置三页（规则 / 关键词 / 目标）一起进首发。代价记在
`../plan/00-里程碑与工期.md`，不在本文。

配套两条：

- **注册路径**：首发平台白名单（运维手工插 `tenants` + `tenant_members`），
  上线放开自助。所以六页里**没有注册页**，登录页要正确呈现 `NOT_INVITED`
  这个终态（§3.1）
- **登录路径**：两条都做（§1.1），扫码是并行路径不是备选 ——
  理由是 Allowed URLs 的多环境登记摩擦，不是部署形态（ADR-0016 后私有化已不做）

## 五、必须写进测试的四条

这四条实现者会按直觉写错，且功能测试全绿时看不出来。
清单归口在 `../eng/03-测试策略.md`，此处列出与本文对应的四条：

```text
1  跨租户访问返回 404，不是 403        403 泄漏「该 id 存在」（§2.1）
2  tenant_id 不从 URL/请求体读取       任何形如 ?tenant_id= 的参数应被忽略而非采信
3  成员被移出后会话立即失效            不是等到 session 过期（§1.5 不用 JWT 的理由）
4  扫码会话签发给应答者，不是发起者      钓鱼路径的反向测试（§1.3）：
                                     以 A 的浏览器建挑战、用 B 的账号应答，
                                     未经确认前不得签发；确认后签发的会话
                                     其 user_id 必须是 B
```

第 3 条是有状态会话相对 JWT 的全部价值所在，不测等于白付每请求一次查询的代价。
第 4 条测的是 `console_login_challenges` 的状态机（`03-数据模型.md` §7.2），
另需一条并发测试：两个应答同时打到 `pending` 行，
只有一个能推进状态（`UPDATE ... WHERE state = 'pending'` 看影响行数）。

## 六、必须先试出来的三件事

这三件影响设计而非实现细节，越早试越好，**建议放进动工前的验证期**：

```text
1  BotFather 的 Allowed URLs 是否接受 localhost / http
   官方文档未说明。若不接受 → 本地开发用不了 Login Widget，
   开发环境必须走扫码或自己写桩。直接影响首发登录页的开发体验

2  oauth.telegram.org 的 JWKS 轮换节奏与缓存策略
   决定是否需要自建缓存与容错（openidconnect crate 自带一层，
   但轮换期的失败处置要自己定）。要试出来的是三个数：
   缓存 TTL 取多少、kid miss 的强制刷新限速取多少、
   轮换期新旧 kid 是否并存（并存则无需容忍空窗，不并存则必须）。
   §1.2 已定「失败即拒绝登录」的方向，本项定的是这三个数

3  MTProto 扫码与控制台扫码在 UI 上如何区分
   两个都是二维码、都在「身份」相关页面、语义完全不同。
   混淆的后果是用户拿 Telegram 官方客户端去扫控制台登录码
   （扫不通，但会浪费一轮支持沟通），或反过来用我们的页面扫账号登录码。
   这不是技术问题，是文案与页面归属问题，但得在做页面前定
```

## 七、局限

- **端点清单是设计意图，不是实现契约。** 真正的契约是
  `openapi.json`（§2.2），它目前不存在 —— 本文与它一致的那天才算收口
- §3.12 的 64 个端点里，请求体与响应体的字段级形状**只写了必须解释的那些**
  （trace、快照、探测结果）。其余端点的字段以数据模型的列为准，
  没有逐个枚举，实现时会出现「这个字段要不要返回」的判断空间
- §1.2 的 OIDC 流程**未实际跑通**。Telegram 2026-05 改版的信息来自官方文档，
  但端点行为、错误码形状、JWKS 轮换节奏都没有实测过（§六 第 2 项）
- §4.1 的模板引擎在 askama 与 minijinja 之间未定。
  两者取舍在编译期检查强度与运行期灵活性之间，做第一页时再定即可
- §四 的页面清单与 §三 的端点清单**没有做双向核对**。
  可能存在「页面需要但端点没列」或反之的缺口，首发前需要一次对齐
