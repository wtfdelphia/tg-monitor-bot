# 账号接入

本文管四件事：**MTProto 客户端怎么接、Bot 怎么接、扫码登录怎么自研、
多实例怎么不脑裂**。

依赖的版本号统一记在 `../eng/00-工程约定.md`，本文只写 feature 开关与用法。
表结构以 `03-数据模型.md` 为准。控制台扫码登录（登录的是我们的后台）
不在本文，见 `07-接口契约.md` §1.3 —— 两件「扫码」性质不同，见 §3.1。

## 一、grammers 接入

### 1.1 仓库位置：Codeberg，不是 GitHub

```text
crates.io  grammers-client
仓库       https://codeberg.org/Lonami/grammers     ← 活跃
不是       https://github.com/Lonami/grammers       ← 已归档（2026-02-10）
```

GitHub 侧最后一条提交的信息就是 `Migrate off GitHub`。
**只看 GitHub 会误判「库已死」** —— 实际 Codeberg 上 1356 次提交、
最后更新 2026-09-19、4 个 open issue（2026-09 查阅）。

**纪律**：升级前看 Codeberg 的 CHANGELOG，不要看 GitHub。
提 issue 也去 Codeberg，GitHub 上提没人看。

这条值得单独写一节，是因为选型判断在这里最容易出错：
`archived` 标记只说明作者离开了 GitHub，不说明项目状态。
判断一个 crate 是否活跃，看 crates.io 的发布时间与真实托管地，不看 GitHub 徽章。

### 1.2 连接与会话

```rust
use grammers_client::{Client, Config, InitParams};
use grammers_session::Session;

let client = Client::connect(Config {
    session: Session::load_file_or_create(&session_path)?,
    api_id,
    api_hash: api_hash.to_string(),
    params: InitParams {
        // 每身份独立代理，从 identities.proxy_url 读
        proxy_url: identity.proxy_url.clone(),
        catch_up: true,          // 断线期间的更新补齐
        ..Default::default()
    },
}).await?;
```

`proxy_url` 需要开启 `proxy` feature，默认不带。

### 1.3 会话存储：不落文件，落库

grammers 默认 `Session::load_file_or_create` 存本地文件。
多实例部署下这行不通（实例漂移会话就丢），且与凭据信封加密
（`05-安全与租户隔离.md` §七）冲突。做法：

```rust
// 启动：从 identity_secrets.secret_ciphertext 解密出字节，加载
let plain = decrypt(&secret.secret_ciphertext, &secret.nonce, &dek)?;
let session = Session::load(&plain)?;

// 变更后：序列化 → 加密 → 落库
let bytes = session.save();
let (ct, nonce) = encrypt(&bytes, &dek)?;
repo.update_secret(identity_id, &ct, &nonce).await?;
```

**落库时机**：不要每次 update 都写。登录完成、`set_home_dc_id` 之后、
以及每 60s 定时各写一次即可。`plain` 与 `bytes` 用后 `zeroize`。

### 1.4 更新流与只读纪律

```rust
while let Some(update) = client.next_update().await? {
    match update {
        Update::NewMessage(msg) if !msg.outgoing() => {
            // 只读纪律：采集账号绝不调用发送类方法
            handle(msg).await?;
        }
        _ => {}
    }
}
```

`catch_up: true` 负责断线期间的更新补齐。会话里的 `updates_state`
由 grammers 自行维护，随 `session.save()` 一起持久化 ——
不要自己记录 pts/qts。

**采集身份只读**这条不只是风格：MTProto 账号一旦发出消息，
就从「监控」变成了「以用户身份行事」，直接落到官方条款的禁止行为上
（`06-合规与凭据责任.md` §1.1）。投递一律走 Bot 身份。

## 二、Bot 接入

Bot 侧承担三类角色，**同一个 crate 三种用法**：

```text
接收（free 档的采集通道）   数据 Bot 加入源频道，收 channel_post
发送（所有档的投递通道）     按 target_channels.sender_identity_id 选 Bot 实例
交互（控制面入口）           控制 Bot 收私聊指令 / callback / my_chat_member
                            ← 独立身份、独立 Webhook 端点，见 02-总体架构.md §六
```

发送端按身份维护实例池，避免每次投递重建 HTTP 连接池：

```rust
// key = identity_id
struct BotPool { bots: DashMap<IdentityId, Bot> }
```

> **Bot API 的硬限制**（决定 free 档的能力边界）：
> - 无法读取加入前的历史消息
> - 私有频道必须由管理员主动添加
> - `file_id` 与 Bot 自身绑定，换 Bot 即失效（跨身份中转见 `02-总体架构.md` §4.2）
> - 隐私模式下群组普通消息收不到，需关闭 privacy 或设为管理员。
>   **已实测：`can_read_all_group_messages` 默认为 `false`**
>   （`../eng/02-本地环境与迁移.md` §6.1），即默认值就是收不到的那一侧，
>   且关闭它没有 API、只能在 BotFather 手工做

### 2.1 数据 Bot 与控制 Bot 的配置差异

两者都是 `identities` 里 `kind='bot'` 的行，但 Webhook 配置完全不同，
**不要共用一套 `setWebhook` 参数**：

| | 数据 Bot | 控制 Bot |
|---|---|---|
| `tenant_id` | 租户自有 | NULL（平台级，全局一个） |
| `allowed_updates` | `channel_post` / `edited_channel_post` / `message` | `message` / `callback_query` / `my_chat_member` |
| `secret_token` | 必设 | **必设，且是整个鉴权链的根** |
| 令牌桶 | 与投递共用（按 `sender_identity_id`） | 独立，不受业务配额影响 |
| privacy 模式 | **需手工关闭**（默认 `false`，要收群组消息） | 保持开启（只处理私聊与命令） |

> **控制 Bot 的 privacy 模式曾被手工关闭，已于 2026-09-21 改回开启**
> （`can_read_all_group_messages: false`，见 `../eng/02-本地环境与迁移.md`），
> 现与上表一致。关掉期间不影响功能，但它扩大了数据面：
> 控制 Bot 只处理私聊与命令，关掉 privacy 意味着它一旦被拉进任何群，
> 就会收到该群的全部消息 —— 拿不到好处。
>
> 这次关了又开的往返值得留下，因为它证明了**这个字段是可反复读的当前值**，
> 于是它能做成启动自检：控制 Bot 的 `can_read_all_group_messages`
> 为 `true` 就告警。**注意判据方向与数据 Bot 相反** ——
> 同一个字段，数据 Bot 要求 `true`、控制 Bot 要求 `false`，
> 写成一条通用校验会把其中一个判反。

两个易错点：

1. **控制 Bot 不要订阅 `channel_post`。** 它不是采集通道，多订阅只会白拿流量，
   并且让「哪个 Bot 负责采集」在代码里变得可疑。
   **这条要落成显式参数，不是靠不写**（2026-09-21 实测）：
   未设过 `allowed_updates` 的控制 Bot 在演示频道收到了 `channel_post` ——
   Telegram 的默认是「除 `chat_member` 外全给」。
   不写等于订阅全部，而且是静默的：功能全对，只是它在替采集链路收消息。
2. **`my_chat_member` 必须显式写进 `allowed_updates`。**
   它在「不指定 `allowed_updates`」或「指定空列表」时属于默认下发范围，
   但一旦给出非空列表，就只下发列表里的类型 —— 漏写它，
   拉群授权（`02-总体架构.md` §6.5）整条链路**静默失效**：收不到事件，也不报错。
   区别于 `chat_member`（**别人**的成员变化）：那个即使指定也要求 Bot 是管理员，
   本方案不需要，不要顺手加上。

## 三、自研 MTProto 扫码登录

### 3.1 先分清：这个扫码和控制台扫码不是一回事

```text
本节的扫码          登录的是「Telegram 账号」，产出一个采集身份，
                   写入 identity_secrets，用来读频道。
                   二维码里是 login_token —— 那是 bearer 凭据
控制台扫码          登录的是「我们的后台」，产出一行 web_sessions。
（07 §1.3）         二维码里只有一个随机 nonce，单独毫无用处
```

**照本节的样子实现控制台扫码是错的**，反之亦然。
本节的 `login_token` 因为是凭据，所以它永久不许进任何聊天记录
（`02-总体架构.md` §6.3 的禁令指的就是它）。

### 3.2 为什么必须自研

`grammers-client` 的 `client/auth.rs` 公开方法只有
`request_login_code` / `sign_in` / `check_password` / `bot_sign_in` /
`is_authorized` / `sign_out`，**没有任何 QR 相关 API**。

而产品前提是「扫码接入自己的账号」—— 让用户在网页里输手机号和验证码，
体验和信任度都不可接受。所以 QR 必须自研，且**首发就自研**，不降级为验证码登录。
代价是把一个未知风险项放进首发关键路径，因此它是动工前验证项（§3.5）。

### 3.3 TL 层原语

```text
auth.exportLoginToken#b7e085fe  api_id:int api_hash:string except_ids:Vector<long>
                                → auth.LoginToken
auth.importLoginToken#95ac5ce4  token:bytes
                                → auth.LoginToken
auth.acceptLoginToken#e894ad4d  token:bytes
                                → Authorization    （在已登录设备上确认，本系统不用）
```

返回的三个变体：

```text
auth.loginToken#629f1980         expires:int token:bytes
                                 → 拿去生成二维码，等待扫码
auth.loginTokenMigrateTo#68e9916 dc_id:int token:bytes
                                 → 需要迁移到 dc_id，再 importLoginToken
auth.loginTokenSuccess#390d5c5e  authorization:auth.Authorization
                                 → 登录成功
```

二维码内容：

```text
tg://login?token=<base64url(token)>     ← 注意是 base64url 且去掉 padding
```

### 3.4 状态机与关键实现点

```text
                 exportLoginToken
                        │
                        ▼
          ┌──── auth.loginToken ────┐
          │   生成二维码，展示给用户   │
          │   轮询/等待 UpdateLoginToken
          └────────────┬────────────┘
                       │ 用户扫码
                       ▼
              再次 exportLoginToken
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
  loginTokenSuccess  MigrateTo    仍是 loginToken
        │              │              │
        │              ▼              └─► 继续等待（未确认）
        │      invoke_in_dc(dc_id,
        │        importLoginToken)
        │              │
        │              ▼
        │      set_home_dc_id(dc_id)
        │              │
        └──────┬───────┘
               ▼
      SESSION_PASSWORD_NEEDED?
         是 ─► check_password(2FA)
         否 ─► 完成，落库 session
```

```rust
use grammers_tl_types as tl;

// 1. 导出 token
let res = client.invoke(&tl::functions::auth::ExportLoginToken {
    api_id,
    api_hash: api_hash.to_string(),
    except_ids: vec![],
}).await?;

match res {
    tl::enums::auth::LoginToken::Token(t) => {
        // t.token → base64url → 二维码；t.expires 通常 30s 左右
        save_login_session(tenant, &t.token, t.expires).await?;
    }
    // 2. DC 迁移：必须用 invoke_in_dc，不能在当前 DC 调
    tl::enums::auth::LoginToken::MigrateTo(m) => {
        let done = client.invoke_in_dc(
            m.dc_id,
            &tl::functions::auth::ImportLoginToken { token: m.token },
        ).await?;
        // 迁移成功后必须改 home DC，否则后续请求仍走旧 DC
        client.session().set_home_dc_id(m.dc_id);
        handle_success(done)?;
    }
    tl::enums::auth::LoginToken::Success(s) => handle_success(s)?,
}
```

已核实的支撑 API（2026-09，对照 `grammers-client` 源码）：

```text
Client::invoke_in_dc(&self, dc_id: i32, request: &R)   存在，公开
Session::set_home_dc_id                                存在，公开
copy_auth_to_dc                                        内部方法，非公开，不可依赖
```

**二维码刷新**：token 约 30s 过期。前端每 25s 重新拉一次，
后端重新 `exportLoginToken` 并更新 `login_sessions.login_token`。
不要复用过期 token。轮询端点必须限流，理由见 `07-接口契约.md` §3.3。

**2FA**：`loginTokenSuccess` 后若返回需要密码，走 `check_password`。
QR 路径下这一步与验证码路径共用同一实现。

`api_id` 由租户自带（`../decisions/ADR-0013-租户自带api_id.md`），
`exportLoginToken` 的入参从 `identity_secrets.api_id` 取，不是平台的。

### 3.5 动工前必须实测的清单

自研 QR 的风险集中在 DC 迁移分支，以下六条必须在写首发代码前跑通：

```text
[ ] 正常扫码登录成功（同 DC）
[ ] 触发 MigrateTo 分支并成功（需要一个注册在非默认 DC 的账号）
[ ] 开启 2FA 的账号能完成登录
[ ] token 过期后刷新二维码，旧 token 不可用
[ ] 登录后 session 落库、重启进程后仍处于已授权态
[ ] 用户在手机端取消授权后，系统能检测到 unauthorized 并置位 identities.status
```

**如果 MigrateTo 分支跑不通**：降级方案是先只支持默认 DC 的账号
（多数用户落在这里），MigrateTo 的账号临时引导走验证码登录。
这个降级不影响首发交付，但必须在产品文案里说明 ——
**不要让用户扫到一半卡住却不知道原因**。

## 四、租约与防脑裂

### 4.1 问题

MTProto 有一条硬约束：**同一个 session 同时被两个客户端使用会导致会话失效**，
Telegram 侧可能直接终止授权。代价是租户要重新扫码，且我方无法自愈。

单机工具用 PID 文件锁 + 单实例假设就能解决。多租户下这个前提不成立：
需要多实例、需要故障转移、需要滚动更新。所以换成租约 + fencing token。

**两种方案互斥**：不能既用 PID 锁又用租约。本方案选租约。

### 4.2 机制

```text
worker 启动 → 尝试获取 identity 的租约
  成功 → 拿到 fencing_token（单调递增），连接 MTProto
  失败 → 该 identity 已被占用，跳过

运行中 → 每 10s 续租（更新 heartbeat_at / expires_at）
  续租失败（租约已被他人抢走）→ 立即断开连接、停止消费

租约 TTL = 30s（3 个心跳周期的容错）
```

获取租约的 SQL，靠 `ON CONFLICT` 保证原子：

```sql
INSERT INTO account_leases (identity_id, worker_id, fencing_token, heartbeat_at, expires_at)
VALUES ($1, $2, 1, now(), now() + interval '30 seconds')
ON CONFLICT (identity_id) DO UPDATE SET
  worker_id     = EXCLUDED.worker_id,
  -- 关键：每次抢占都递增，旧持有者的 token 永久失效
  fencing_token = account_leases.fencing_token + 1,
  heartbeat_at  = now(),
  expires_at    = now() + interval '30 seconds'
WHERE account_leases.expires_at < now()      -- 仅当已过期才允许抢占
   OR account_leases.worker_id = EXCLUDED.worker_id   -- 或自己续租
RETURNING fencing_token;
```

返回空行 = 抢占失败（租约仍被他人有效持有）。

`account_leases` 是丙类表（无 `tenant_id` 列，不启用 RLS），
理由见 `03-数据模型.md` §1.3：它是 worker 的运行时协调表，
按 `identity_id` 定位，不存在按租户过滤的语义。

### 4.3 fencing token 的作用

租约本身挡不住「GC 停顿后复活的僵尸 worker」：
worker A 持有租约、卡住 40s、租约过期、worker B 接管、
A 恢复后以为自己还持有 —— 这一刻就是双连接。

fencing token 解决这个：A 的 token 是 5，B 抢占后是 6。
**所有写操作都带 token，数据库拒绝比当前值小的 token**。

```sql
-- A 复活后尝试写入，token=5 < 当前 6，WHERE 不成立，0 行受影响
UPDATE account_leases SET heartbeat_at = now()
WHERE identity_id = $1 AND fencing_token = $2;
```

应用侧：续租返回 0 行 → 立即断开、退出该 identity 的消费循环。

```rust
// 纪律：token 不匹配不是「重试」场景，是「立刻自杀」场景
if repo.renew_lease(identity_id, my_token).await? == 0 {
    warn!(identity_id, "lease lost, shutting down worker");
    client.disconnect().await;
    return Ok(());   // 不重试，不重连
}
```

**「立刻自杀」这条最容易被写成重试。** 通用的重试中间件会把续租失败
当成一次可恢复的数据库错误 —— 但续租失败的含义不是「没写成功」，
是「你已经不是持有者了」。重试只会延长双连接的窗口。
所以续租调用不能套通用重试策略。

### 4.4 为什么不用 Redis 锁

Redis 的 `SETNX` 锁在主从切换时可能双主授予同一把锁（Redlock 争议的核心）。
租约信息放 PostgreSQL，与业务数据同一个一致性域，省掉一个跨系统一致性问题。
心跳频率 10s × 身份数，PG 完全吃得下。

这与架构上「组件间只经 PG 与 Redis，Redis 只做唤醒信号」
（`02-总体架构.md` §1.1）是一致的：**需要正确性保证的状态一律在 PG**。

### 4.5 混沌测试要求

多实例上线的**前置条件**，缺一不可：

```text
[ ] kill -9 持有租约的 worker → 30s 内另一实例接管
[ ] SIGSTOP 40s 再 SIGCONT → 僵尸 worker 检测到 token 失效并自行退出
[ ] 网络分区（iptables DROP 到 PG）→ worker 续租失败后断开 MTProto
[ ] 滚动更新（新旧实例并存）→ 全程无双连接，Telegram 侧无授权终止
[ ] 100 个 identity × 3 实例 → 租约分布均衡，无饥饿
```

> 未通过此清单前，**部署形态固定为单实例**（`02-总体架构.md` §七 形态 A）。
> 这不是保守：MTProto 会话被终止的代价（租户重新扫码、期间数据全丢）
> 远高于多实例带来的收益。

清单归口在 `../eng/03-测试策略.md`，运维侧的判定见 `../ops/01-上线就绪与运维.md`。

## 五、身份状态机

```text
                    ┌──────────┐
     创建 ─────────► │ offline  │
                    └────┬─────┘
                获得租约  │       租约丢失 / 主动停止
                        ▼             ▲
                    ┌──────────┐      │
                    │  online  │──────┘
                    └────┬─────┘
          FloodWait      │      收到 AUTH_KEY_UNREGISTERED
        ┌───────────────┼───────────────┐
        ▼               │               ▼
 ┌────────────┐         │        ┌──────────────┐
 │ flood_wait │─────────┘        │ unauthorized │
 └────────────┘  等待结束         └──────────────┘
                                        │ 用户重新扫码
        Telegram 封禁                    ▼
        ─────► ┌────────┐          （回到 offline）
               │ banned │
               └────────┘
```

状态落 `identities.status`（五个值与 DDL 的 CHECK 一致）。
转入 `unauthorized` / `banned` 时三件事都要做：

1. 释放租约（删除 `account_leases` 行）—— 否则该身份在 TTL 内无人可接管
2. 通知租户「账号需要重新授权」
3. 写 `audit_logs`

`banned` 不自动重试。`unauthorized` 需用户介入，也不自动重试。
**只有 `flood_wait` 是自愈状态** —— 把另外两个也做成自动重试，
等于对着已失效的凭据反复敲 Telegram，会加速封禁。

## 六、局限

- §3.5 的六条**全部未实测**。MigrateTo 分支的风险最高，
  因为它需要一个注册在非默认 DC 的真实账号才能触发，
  本地环境造不出来 —— 这是首发前最有可能推翻设计的一项
- §一 的 grammers 用法来自源码与文档阅读，**没有跑过**。
  `invoke_in_dc` 与 `set_home_dc_id` 确认存在且公开，但它们组合起来
  在 DC 迁移场景下的实际行为未验证
- §4.5 的混沌测试一条都没跑。`fencing_token` 机制目前只有设计论证，
  它的正确性论证依赖「所有写操作都带 token」这个前提，
  而这个前提要靠代码评审保证，目前没有机器卡口
- §五 状态机缺少 `flood_wait` 的等待上限。Telegram 的 FloodWait
  可以长达数小时，超过多久应该转人工介入没有定
- 会话落库的时机（§1.3 的「每 60s」）是估的。写得太频会放大 KMS 调用量，
  写得太稀会在进程崩溃时丢掉 `updates_state`，两边的代价都没有实测
