## 一、组件划分

```text
                      Telegram
                    │          │
         MTProto ───┤          ├─── 数据 Bot API (Webhook)
                    ▼          ▼
        ┌───────────────┐  ┌──────────────┐
        │ mtproto-worker│  │ bot-gateway  │   接入层
        │ (grammers)    │  │ (teloxide)   │   持账号租约 / 收 Webhook
        └───────┬───────┘  └──────┬───────┘
                └────────┬─────────┘
                         ▼
                 CanonicalEvent（规范化原始事件，先落库）
                         │
                         ▼
        ┌────────────────────────────────┐
        │ fanout-worker                  │   扇出层
        │ 查 source_subscriptions        │   1 条 Canonical → N 条 Tenant
        │ 按租户派生 TenantEvent         │
        └────────────────┬───────────────┘
                         ▼
        ┌────────────────────────────────┐
        │ rule-worker                    │   规则层
        │ AC 自动机关键词 + 规则匹配     │   租户级并行
        │ 去重三级 + stop_processing     │
        └────────────────┬───────────────┘
                         ▼
                  delivery_tasks（Outbox，先落库）
                         │
                         ▼
        ┌────────────────────────────────┐
        │ delivery-worker                │   投递层
        │ 按 sender_identity 分队列限流  │
        │ FloodWait 退避 / DLQ           │
        └────────────────┬───────────────┘
                         ▼
                   目标频道 / 私聊

        ┌────────────────────────────────┐        控制 Bot API (Webhook)
        │ control-plane (axum)           │   控制面        │
        │ REST API                       │   租户管理 / 规则配置
        │ ┌────────────────────────────┐ │                 ▼
        │ │ bot-console（独立 Bot 身份）│◄┼──── 用户私聊指令 / 拉群事件
        │ └────────────────────────────┘ │
        └────────────────────────────────┘
```

所有组件共享 PostgreSQL（事实源）+ Redis（队列/缓存/去重窗口）。

### 1.1 组件间通信：只经 PG 与 Redis，没有 RPC

上图的箭头是**数据流向，不是调用关系**。这一点必须明说，
否则看图的人会以为 `fanout-worker` 调用 `rule-worker`。

```text
组件间调用       无。不存在 gRPC、不存在内部 HTTP、不存在消息中间件
交接介质         PostgreSQL 表（事实源）+ Redis Stream（唤醒与队列）
单机形态的实际形状 同一个二进制的不同 subcommand，
                 多进程但不互相连接，各自只连 PG 与 Redis
```

每一级交接都是**先落库，再入队**（§2.3 的纪律）：

```text
接入层  → 写 canonical_events            → XADD canonical:new
fanout  → 写 tenant_events               → XADD rule:pending
rule    → 写 delivery_tasks（Outbox）    → XADD delivery:{sender_identity_id}
delivery→ 更新 delivery_tasks.state      → 写 delivery_logs
```

> **Redis 只是唤醒信号，不是事实源。** 每个 Worker 都必须能在
> Redis 完全丢失的情况下靠扫库自行恢复 —— 队列里的消息体只带主键，
> 不带业务数据（凭据不进队列，见 §3.2）。
> Redis 宕一次不能丢事件，只能让延迟变大。
>
> 键名清单：
>
> ```text
> canonical:new                        全局单流，接入层 → fanout
> rule:pending                         全局单流，fanout → rule
> delivery:{sender_identity_id}        按发送身份分片，rule → delivery
> ratelimit:{sender_identity_id}       令牌桶，与上一条同键空间
> mgroup:{identity}:{group_id}         媒体组聚合窗口
> ```
>
> 前两个是全局单流 —— 它们**不按 `tenant_id` 分片**。
> 分片键是身份或无，因为租户隔离在库层（见 `05-安全与租户隔离.md`），
> 不靠队列拆分。
>
> 代价诚实记一笔：每级交接都多一次写库，吞吐上限被 PG 的写入能力压住。
> 在本方案的量级（稳态 20~30 万行）不是瓶颈；
> 真成为瓶颈时的出路是合并 Worker 级数，不是换掉这条纪律。

**两个 Bot 身份，职责不混用**（见 §六）：`bot-gateway` 里的**数据 Bot** 只收
`channel_post` 与发投递；`bot-console` 里的**控制 Bot** 只处理人机交互。
分开的理由是限流与可用性解耦，不是洁癖 —— 见 §6.4。

## 二、事件两层模型

这是多租户的核心机制。

### 2.1 为什么要两层

场景：频道 X 同时被租户 A 和租户 B 监控。

```text
单层模型的问题：
  一条消息 → 一个 Envelope → 究竟属于谁？无法表达

两层模型：
  Telegram 一条消息
      ↓ 去重后
  1 条 CanonicalEvent（receiver_identity 维度，与租户无关）
      ↓ 查 source_subscriptions 扇出
  2 条 TenantEvent（租户 A 一条、租户 B 一条，各自独立走规则引擎）
```

收益：同一条原始消息只存一份、只经一次网络接收，但每个租户的规则、
去重窗口、投递配额完全隔离。

### 2.2 两层的职责边界

| | CanonicalEvent | TenantEvent |
|---|---|---|
| 维度 | `receiver_identity_id`（哪个身份收到的） | `tenant_id` + 来源订阅 |
| 与租户关系 | **无关**，可被多租户共享 | 一租户一条 |
| 内容 | 完整原始消息（含 text/caption/sender_id） | 引用 Canonical + 租户级匹配结果 |
| 保留期 | 未命中任何规则：短 TTL 物理删除 | 随命中结果保留（按套餐分级） |
| 落库时机 | **接收后立即落库**（削峰，避免丢消息） | 扇出时落库 |

`canonical_events` **不带 `tenant_id`**，这在建表规范里归为丙类表
（见 `03-数据模型.md`）。它的直接后果是两条：RLS 套不上去，
以及删租户时不能简单级联（见 `01-产品需求.md` §七 第 2 条）。

### 2.3 纪律：先落库再处理

```text
接入层收到消息 → 立刻写 CanonicalEvent → 才 ACK / 才入队
禁止：在事件处理器内直接查库、调用 Telegram API、发消息
```

理由：**接入层是唯一不可重放的环节。** Telegram 的 update 错过就没了，
而后续任何一步都可以从库里重新驱动。

这条纪律的来源是早期单租户版本的实际教训，在多 Worker 下更重要。

## 三、跨组件的两条约束

### 3.1 解密权限收敛

只有三个组件可以解密凭据：`bot-gateway`、`mtproto-worker`、`delivery-worker`。

`control-plane` 与 `fanout-worker` / `rule-worker` **不具备解密能力**，
KMS 侧按组件身份授权，**不是靠代码自律**。

### 3.2 明文凭据的流动边界

```text
明文凭据不进 Redis、不进队列消息体、不进日志
队列里只传 sender_identity_id，由消费侧自行解密
内存中的明文用后立即 zeroize
```

信封加密的层次与密钥管理见 `05-安全与租户隔离.md`。

## 四、双模式接入

同一套表结构支持两种接入方式，仅 `receiver_identity_id` 指向不同：

| | free 档（自有 Bot + 演示源） | 专业模式（pro） |
|---|---|---|
| 采集身份 | 租户自建数据 Bot；**另可订阅 1 个平台演示源**（只读，不可自选） | 租户自建 Bot / 自有 MTProto 账号 |
| 投递身份 | 租户自己的 Bot —— **真投递，不是预览** | 同左 |
| 用户操作 | 建自己的 Bot 拉进自己频道设管理员 | 再提交 `api_id` + 手机号登录（ADR-0013） |
| 能否监控他人频道 | **不能**（Bot 必须被加为管理员） | 能（MTProto） |
| 平台代持凭据 | **不代持任何凭据** | 代持 session（信封加密） |
| 风险隔离 | 采集侧演示源共享，投递侧物理隔离 | 全链路物理隔离 |

```sql
-- 表结构零差异，仅指向不同
source_subscriptions (tenant_id, chat_id, receiver_identity_id)
--                                        ↑
--   自有源   → 租户自己的 Bot / MTProto 账号 identity id
--   演示源   → 平台演示身份的 id（identities.tenant_id IS NULL）
--             这一行由平台开通时写入，租户不能自己指定，见下方硬边界 4
```

升级路径（free 转 pro）是**加一个身份**，不是改 `receiver_identity_id` ——
已配好的规则与目标频道全部保留，用户只需去申请 `api_id` 并登录 MTProto 账号。

> **原「托管模式」已废除**，见 ADR-0014。那个形态是平台官方 Bot 代持接收身份、
> 租户把它拉进自己频道 —— 它要求平台身份进入租户频道，连坐路径与授权链都压在
> 这条上。现在共享只发生在**采集侧的平台自营演示源**，投递侧完全隔离。

### 4.1 演示源的四条硬边界

缺一条这个形态就不成立：

1. 演示源必须是**平台自己拥有并运营的频道** —— 拿第三方公开频道充当就是 scraping
2. 演示源内容可控、可下架（平台是该频道管理员，发什么由平台决定）
3. 演示身份（`identities.tenant_id IS NULL`）**只用于接收演示源，不为任何租户投递**
4. 租户对演示源只有订阅/取消订阅 —— **源订阅端点必须拒绝租户指定
   `tenant_id IS NULL` 的身份**。否则租户可把任意频道挂到平台演示身份上采集，
   等于平台替他 scraping。这是承重墙，已列入反向测试

**演示源本身的产品边界**（必须向用户明示）：
只有 1 个且不可自选；它被封或停更会导致 free 档看不到外部内容（风险 RK-15）；
它的 `canonical_events` 为全平台 free 租户共享，清理有竞态（风险 RK-16）。

### 4.2 跨身份媒体中转

**Telegram 的 `file_id` 严格绑定获取它的身份。** 接收身份与发送身份不同时，
不能把 `file_id` 直接传给发送方 —— 会报 `wrong file identifier`。

而本架构下两者**几乎总是不同**：free 档用数据 Bot 收、租户目标频道发；
专业模式用 MTProto 收、Bot 发。所以中转是常态路径，不是边缘情况。

```text
receiver_identity == sender_identity ?
  是 → 直接用 file_id 转发（快路径，零下载）
  否 → 中转：
       接收侧流式下载 → 边下边算 content_hash → 写 MinIO/S3
                                                    │
                                     发送侧从对象存储流式读 → 上传
```

三条纪律：

1. **流式，不落磁盘。** Telegram 单文件上限 2GB，不能整个读进内存或临时文件。
   grammers 的 `download` 返回分片流，直接接到 S3 multipart upload。
2. **`content_hash` 在下载途中算**（边下边 hash），不为算哈希多读一遍。
   这个哈希同时是 L2 去重主键。
3. **命中 `media_archive` 已有 `content_hash` 且 `object_key` 未过期时，跳过下载**，
   直接从对象存储取。这是中转成本的主要优化点。

对象存储中的文件保留 3 天（`media_archive.object_expires_at`），
只服务重试窗口，不做长期存储。成本影响见 `01-产品需求.md` §八。

## 五、AI 增强（演进阶段，有合规前置）

```text
纪律 0（合规前置，优先于以下三条）：条款未核实前不得动工
  Telegram 官方条款禁止 "using, accessing or aggregating data obtained
  from the Telegram platform to train, fine-tune or otherwise engage in
  ... artificial intelligence"（原文见 06-合规与凭据责任.md）。
  "otherwise engage in" 措辞很宽，可能不止禁止训练，也覆盖推理调用。
  → 默认假设「把 Telegram 内容送入 LLM」是受限的，而非允许的
  → AI 功能启动前必须重新核实该条款，并由执业律师确认
  → 在此之前：不在定价页、不在任何对外材料承诺 AI 能力

纪律 1：异步旁路
  绝不在接入层同步等 LLM。硬规则先筛，命中后再推 AI 队列

纪律 2：两级过滤控成本
  硬规则（关键词/正则）先筛掉约 80%，仅剩余部分调 LLM

纪律 3：故障降级
  LLM 超时/限流/挂掉 → 跳过 AI 增强，按原始消息投递
  核心路由管道的可用性不允许被 AI 拖累
```

可选能力：语义过滤与意图识别、OCR 提取图片文字、语音转文字、
Embedding 语义去重（可抓改写版复读，纯指纹抓不到）、翻译、
自动摘要日报、PII 脱敏、自然语言转规则。

> 全部列为演进阶段。首发与上线阶段不含 AI，避免核心链路未稳先引入外部依赖。
> **纪律 0 是硬门槛**：一旦条款核实为禁止，上面这串可选能力整节作废 ——
> 所以别提前对外承诺。

## 六、Telegram Bot 入口

Bot 在本方案里有三个互不相干的角色，混着实现会出问题，先分清：

| 角色 | 组件 | 身份 | 方向 | 阶段 |
|---|---|---|---|---|
| 采集 | `bot-gateway` | 数据 Bot | 收 `channel_post` | 首发 |
| 投递 | `delivery-worker` | 数据 Bot（按 `sender_identity_id`） | 发消息 | 首发 |
| **交互** | **`bot-console`** | **控制 Bot（独立）** | **收指令 / 回按钮 / 收拉群事件** | **首发部分 + 上线** |

前两个是数据管道，本节只讲第三个。

### 6.1 它是安全设计，不是 UI 设计

Bot 入口是**第二个外部可达的鉴权入口**。REST 入口的鉴权成本已经付过了
（会话、CSRF、TLS、IP 记录都是现成的），Bot 入口一个都没有：

```text
REST                          Bot
  会话 Cookie / Token   →     只有 update.from.id，没有任何秘密
  IP 可记                →     没有 IP
  CSRF token            →     callback_data 由客户端回传，天然「跨站」
  请求体我方定义         →     命令文本 / callback_data 全是用户可控字符串
  HTTPS 端点我方控制     →     Webhook 端点 URL 是公网可探测的
```

所以它的设计重心在 §6.2（身份从哪来）和 §6.3（哪些操作不准上），
命令语法是最次要的部分。

### 6.2 身份认证：`tenant_id` 从 `from.id` 推导，且只从这里推导

「绝不信任请求体传入的租户标识」在 Bot 侧有两个具体形态，都必须堵住：

```text
✗ 把 tenant_id 编进 callback_data
    callback_data 由客户端回传，与请求体同级。用户可手工构造
    callback 打其他租户。这是 Bot ChatOps 最常见的越权写法
✗ 让用户发 /use <tenant_id> 切换租户
    同上，参数是用户给的
✓ 从 update.from.id 反查 tenant_members，服务端持有当前上下文
```

**一个 `tg_user_id` 可能属于多个租户**（`tenant_members` 主键是
`(tenant_id, user_id)`），而 Bot 私聊没有会话态。需要服务端侧的上下文表
`bot_console_sessions`，`callback_data` 里只放资源引用，
且**服务端必须二次校验该资源归属当前上下文租户** —— 引用本身也是用户可控的。

**不需要绑定环节。** `tenant_members.user_id` 本身就是 Telegram user id，
所以 `update.from.id` 直接就是成员标识，反查即认证：

```text
Webhook 请求 → 校验 X-Telegram-Bot-Api-Secret-Token（证明来自 Telegram）
            → update.from.id 反查 tenant_members
            → 命中 → AuthContext{ tenant_id, actor_user_id, role, source: bot }
            → 未命中 → 回「此账号未授权」，不做任何事
```

**认证强度完全押在第一步上。** `from.id` 的真实性由 Telegram 保证，
我方的唯一验证手段是 `secret_token` ——
没有它，任何人 POST 一个伪造 update 到公网端点就能冒充任意 `from.id`。

不引入 deep link nonce 绑定环节，理由是它不增加安全性：`from.id` 已经可信，
nonce 只是把同一个事实绕一圈，还多一条泄漏路径
（`/start <nonce>` 会作为可见消息留在聊天记录里）。
要引入的话，唯一正当理由是「Web 账号体系与 Telegram 账号不是同一套」——
本方案里它们是同一套，所以不引入。

> 鉴权反查 `tenant_members` 会撞上 RLS 的一个真实困境（反查发生在知道
> `tenant_id` 之前）。解法是策略按角色分离 + 独立连接池，
> 完整推导与实测见 `05-安全与租户隔离.md`。

### 6.3 操作白名单：两类操作永久不上 Bot

```text
✗ 提交 Bot Token          明文经 Telegram 服务器、留在聊天记录、进 update 日志
✗ MTProto QR 登录码 / login_token
                          聊天记录里的登录凭据，任何能看到该聊天的人都能扫走
```

把凭据存得再严，从私聊漏出去是一样的结果。
所以「提交 Bot Token 或手机号登录」**只能走 Web/REST**。

> **这条禁令的边界：禁的是 bearer 凭据，不是「扫码」这个动作本身。**
> 被禁的 `login_token`（MTProto `auth.exportLoginToken`）是凭据 ——
> 谁持有谁就能授权那个 Telegram 账号，把它发进聊天等于把密钥交出去。
> 而**控制台扫码登录**方向相反：二维码里只有一个随机 nonce，
> 它单独毫无用处，必须由一个 Telegram 账号向控制 Bot 应答才有意义，
> 会话签发给应答者 —— Bot 在这条路径上是**验证方**，不是凭据搬运工。
>
> 两者名字都带「扫码」，性质完全不同，不要相互套用：
> 照 MTProto 的样子实现控制台扫码（Bot 发一条含会话 token 的链接）
> 会把这个洞原样搬回来。

Bot 可以做的：

| 类别 | 操作 | 阶段 |
|---|---|---|
| 授权 | 拉群授权（`my_chat_member`，见 §6.5） | 首发 |
| 观测 | 订阅列表、投递状态、失败原因、队列积压 | 首发 |
| 干预 | 暂停/恢复订阅、DLQ 重试确认 | 上线 |
| 采集 | 转发消息给控制 Bot 以添加源（见 §6.6） | 上线 |
| 配置 | 增删关键词与规则 | 上线 |

凭据类操作在 Bot 侧的正确响应是**回一个 Web 链接**，不是代为收集。

### 6.4 独立 Bot 身份：把控制通道从业务配额里摘出来

限流按 `sender_identity_id` 分令牌桶，因为 Telegram 限流按身份计。
若控制入口复用数据 Bot 身份：

```text
一个租户暴力转发耗尽该 Bot 令牌桶
  → 该租户的 /status、/pause 一起超时
  → 恰好在最需要干预的时刻，干预通道不可用
```

所以控制 Bot 是**独立身份、独立 Webhook 端点、独立令牌桶**。
代价诚实列出：用户要加两个 Bot，引导流程变长一步。
这笔代价换的是「系统过载时控制面仍可达」，值得。

Webhook 端点的两条硬要求：

1. `setWebhook` 的 `secret_token`（1-256 字符，`A-Za-z0-9_-`）必须设，
   校验 `X-Telegram-Bot-Api-Secret-Token` 请求头。端点 URL 是公网可探测的，
   没有这个头就等于任何人都能伪造 update。
2. `allowed_updates` 显式声明为 `message` / `callback_query` / `my_chat_member`。
   不要订阅 `channel_post` —— 那是数据 Bot 的事。
   **`my_chat_member` 必须写进去**：给出非空列表后就只下发列表内的类型，
   漏写它 §6.5 会静默失效。

### 6.5 拉群授权：`my_chat_member` 是 `authorized_by` 的唯一可靠来源

`source_subscriptions` 有 `authorized_by`（授权操作人 Telegram user id）
与 `authorized_at` 两列，注释要求「私有群/频道须验证操作者为 Owner/Admin」。
`my_chat_member` 是这两列的填充来源：

```text
用户把 Bot 拉进频道并设管理员
  → Bot 收到 my_chat_member（ChatMemberUpdated）
     from                → 操作人，即 authorized_by
     chat                → tg_chat_id
     old/new_chat_member → 权限变化，可判定是否已是 administrator
  → 反查 from.id 的 tenant_members（§6.2）得到 tenant_id
  → 写 source_subscriptions(tenant_id, tg_chat_id, authorized_by, authorized_at)
```

四个实现要点：

1. **`my_chat_member` 在指定 `allowed_updates` 时必须列出**（见 §6.4 第 2 点）。
   而 `chat_member`（别人的成员变化）即使列出也要求 Bot 是管理员 ——
   本方案不需要它，不要顺手订阅。
2. **操作人未绑定时不能建订阅。** 此时只能回一句「请先绑定」并丢弃事件 ——
   不能凭 `chat` 猜租户，那又变成信任外部输入了。
3. **降级为管理员之外的状态**（被踢、被降权）同样走这条 update，
   应产生 `SOURCE_PERMISSION_CHANGED` 事件（上线阶段）。
4. 数据 Bot 与控制 Bot 都会收到自己的 `my_chat_member`。
   **采集订阅认数据 Bot 的那一条**，控制 Bot 的拉群事件与订阅无关。

### 6.6 转发消息添加源：能做，但边界要说清

用户把源频道的一条消息转发给控制 Bot，从 `forward_origin` 取源 chat 建订阅。
比让用户手输 `-100...` 的 chat id 友好得多。但它有一处硬限制：

```text
MessageOriginChannel     → 含 chat 与 message_id    ✓ 可用
MessageOriginChat        → 含 sender_chat            ✓ 可用
MessageOriginUser        → 只有 sender_user，无 chat ✗ 拿不到源
MessageOriginHiddenUser  → 只有一个名字字符串        ✗ 拿不到源
```

后两种发生在源是私聊、或用户开了「转发时隐藏账号」时。
产品上必须给出明确提示，不能静默失败。

更关键的是：**这条路径只解决「找到 chat_id」，不解决授权。**
能转发一条消息只证明用户能看到该频道，不证明他有权让平台监控它。

```text
转发添加源 → 只写入待确认状态，authorized_by 留空
           → 仍需 §6.5 的拉群，或 MTProto 账号自身可见性，才能真正启用
```

把两者混为一谈，等于用「我能看到」替换「我有权」，是越权。

### 6.7 命令幂等：不能复用消息侧的幂等键

消息侧的 `bot_update_id` 幂等键挂在 `canonical_events` 上，
是给采集路径挡 Webhook 重投的。控制命令走的是另一条链路，那个约束覆盖不到。

Telegram 会重投未被 2xx 确认的 update。用户发一次 `/addrule`，
重投两次就是三条规则。承载方式：

```sql
CREATE TABLE bot_console_updates (
  tenant_id BIGINT NOT NULL, bot_id BIGINT NOT NULL, update_id BIGINT NOT NULL,
  PRIMARY KEY (tenant_id, bot_id, update_id)
);
-- 重投同一 update_id → ERROR: duplicate key value violates unique constraint
-- ON CONFLICT DO NOTHING → INSERT 0 0，据此判定「已处理，直接返回」
```

`bot_id` 必须在键里：**Bot API 的 `update_id` 按 Bot 独立计数**，
两个 Bot 出现同号 `update_id` 是正常的（已实测 `(1,51,9001)` 插入成功）。
只用 `(tenant_id, update_id)` 会把控制 Bot 的命令误判成数据 Bot 的重投。
