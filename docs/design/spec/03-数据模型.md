## 一、公共约定

```sql
-- 主键：BIGINT IDENTITY（业务表）
-- 时间：全部 TIMESTAMPTZ，应用侧统一 UTC
-- 枚举：TEXT + CHECK 约束，不用 PG ENUM（迁移友好）
-- 软删除：配置域用 enabled=FALSE；历史域物理删除
```

### 1.1 命名纪律

```text
*_ref        → 内部主键外键        source_ref BIGINT REFERENCES source_subscriptions(id)
*_chat_id    → Telegram 原生值      tg_chat_id BIGINT  -- -1009876543210
*_id         → 本表主键或明确实体   tenant_id, bot_id
```

配合 Rust newtype（`SourceRef` / `TgChatId`），命名与类型双重约束。
这条纪律的直接动因是 `chat_id` 一名三义（内部主键 / Telegram 原生值 / 目标频道引用）
—— 三者都是 `BIGINT`，混用不报错，只是链接打不开或查错了行。

### 1.2 五条铁律

```sql
-- 1 所有业务表唯一约束必须含 tenant_id
-- 2 所有业务表查询索引以 tenant_id 为首列
-- 3 所有带 tenant_id 的表启用 RLS（ENABLE + FORCE + 策略，模板见 05 §2.2）
-- 4 跨表外键走复合键 (tenant_id, xxx)，不用单列外键
--   唯一例外：指向 identities 的 FK
-- 5 tenant_id 一律 NOT NULL
--   有意可空三张表：identities / system_logs / audit_logs
```

**铁律 4 是唯一一条超级用户也绕不过的防线** —— 它让跨租户关联在数据库层面
*不可表达*，而不是「不被允许」：

```sql
-- ✗ 单列外键：租户 1 的子行可以指向租户 2 的父行，PG 不拦
FOREIGN KEY (par_ref) REFERENCES par(id)

-- ✓ 复合外键：同样的插入直接 ERROR
PRIMARY KEY (tenant_id, id)                       -- 父表
FOREIGN KEY (tenant_id, par_ref) REFERENCES par(tenant_id, id)
```

这与 RLS 正交：RLS 防越权**访问**，复合外键防数据本身长出跨租户的**边**。
顺带满足了 Citus 分片的前置条件（分布列必须在唯一约束内），
将来要水平扩展不用重做表结构。

**落地形态：父表补一条 `UNIQUE (tenant_id, id)`，主键不动。** 本方案多数表用
代理键单列主键（`id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`），
改宽主键要动 27 张表和所有引用；而复合 FK 只要求被引用列组上**存在**唯一约束，
不要求它是主键：

```sql
-- 父表（keywords / source_subscriptions / target_channels / rules / tenant_events）
CREATE UNIQUE INDEX uq_keywords_tenant_id ON keywords (tenant_id, id);

-- 子表 FK 走复合键
FOREIGN KEY (tenant_id, keyword_id) REFERENCES keywords (tenant_id, id)
```

**铁律 4 的准确适用范围**：子表与父表**双方都有 `tenant_id NOT NULL`** 时必须走复合键。
两种情况天然不适用，不算例外 —— 父表无 `tenant_id`（丙类，如 `canonical_events`），
或子表无 `tenant_id`（乙类 `rule_conditions` / `delivery_logs`，靠 EXISTS 策略兜）。
CI 断言 A9 按这个形状写，不靠白名单。

**真正的例外只有一个：指向 `identities` 的 FK 保持单列。** `identities.tenant_id`
**有意可空**（平台共享演示身份为 NULL，见 §三 与 `02-总体架构.md` §4.1）。
复合 FK 在 `MATCH SIMPLE` 下遇到 NULL 会跳过整个检查，
所以 `(租户1, NULL)` 既匹配不到父行、又不会报错 —— 改成复合键会直接坏掉演示源。
这条例外的代价由应用层补：源订阅端点必须拒绝租户指定 `tenant_id IS NULL`
的身份（403），反向测试在 `R19`。
**这是权限校验，不是数据模型约束，所以超级用户绕得过** —— 例外的代价要认。

**铁律 5 是铁律 4 的前提**：FK 默认 `MATCH SIMPLE`，**任一 FK 列为 NULL 就跳过整个检查**，
所以 `tenant_id` 可为 NULL 时复合外键形同虚设。
三张表有意破例：`identities`（共享演示身份）、`system_logs` 与 `audit_logs`
（平台级日志/审计无租户归属）。

**这里原先写着「这三张表都不做复合 FK 的父表，所以破例不会传导成跨租户边」，
是错的**（2026-09-22 实测更正）。`system_logs` 与 `audit_logs` 确实不被任何 FK 引用，
但 `identities` 是七张子表的父表，且因为它 `tenant_id` 可空，那七条 FK 只能是单列的 ——
**单列正是跨租户边能建起来的原因，不是它建不起来的理由。** 推论的方向反了：

```text
七条单列 FK  identity_secrets / source_subscriptions / target_channels /
             canonical_events / delivery_tasks / account_leases /
             bot_console_updates

tenant 21 上下文、app_user 身份，目标是 tenant 20 的私有身份 900
（不是池里 tenant_id IS NULL 的共享身份 —— 那种引用是设计允许的）

SELECT ... FROM identities WHERE id=900   → 0 行        RLS 挡住了读
INSERT target_channels (21, -1, 900)      → INSERT 0 1  边建成了
```

**读不到却能引用**，因为 FK 检查不过 RLS。另外两个后果也实测了：

```text
枚举   填存在的他租户 id → INSERT 0 1；填不存在的 → FK violation，可区分
钉住   建边之后 tenant 20 删自己的身份 900 → ERROR: still referenced
```

所以准确的说法是：**破例在 `identities` 这一处确实传导成了跨租户边。**
这与上面例外段所说的「库层缺口、由应用层守」是同一件事 ——
两段话原先自相矛盾（一段说有缺口、一段说不会传导），现在只留一个说法。

> **但那道兜比例外段写的窄。** 例外段点的 `R19` 测的是
> 「租户指定 `tenant_id IS NULL` 的演示身份建源 → 403」，
> 覆盖的是**共享身份**这一种形状；上面实测的是**他租户的私有身份**，
> 没有对应的反向测试。校验要求本身是有的
> （`06-合规与凭据责任.md` §2.5 第 1 条：身份接入端点必须校验
> `identities.tenant_id = 当前租户`），但它落在凭据那一节，
> 不在这里，也没进 `eng/03-测试策略.md` §三 的清单。
> 缺一条反向测试这件事登记在 `../../pre-do/03-文档待更正.md` 十九，未补。

`eng/04-CI门禁.md` §二 `A5` 与 `crates/db/src/audit/queries.sql` 的同一处表述
已一并更正；`decisions/ADR-0006-复合外键.md` 的代价一节本来就是对的。

> **实测（PG 17.11）**：这个形状把四个后果同时关掉了。
> 改之前（单列 FK），以 `app_user` 身份、租户 1 上下文：
>
> ```text
> INSERT INTO rules (tenant_id, keyword_id) VALUES (1, 1)   -- keyword 属租户 2
>   → INSERT 0 1                        ✗ 跨租户边建成了
> SELECT count(*) FROM rules                       → 1     规则可见
> SELECT count(*) FROM rules JOIN keywords ...      → 0     ✗ 规则静默失效，无报错
> 租户 2 DELETE 自己的 keyword
>   → ERROR: violates foreign key constraint "rules_keyword_id_fkey"
>                                        ✗ 租户 1 可单方面阻止租户 2 删自己的数据
> ```
>
> 改之后（复合 FK）：
>
> ```text
> INSERT INTO rules (tenant_id, keyword_id) VALUES (1, 1)
>   → ERROR: violates foreign key constraint "rules_tenant_id_keyword_id_fkey"
>     DETAIL: Key (tenant_id, keyword_id)=(1, 1) is not present in table "keywords"
> 租户 2 DELETE 自己的 keyword    → DELETE 1  ✓
> 引用 tenant_id IS NULL 的演示身份 → INSERT 0 1  ✓ 未被波及
> ```
>
> **第四个后果是一条侧信道**：单列 FK 下，租户 1 靠 FK 报错与否可枚举
> 其他租户的 id 空间 —— 填存在的 id（属他租户）`INSERT` 成功、
> 填不存在的报 FK violation，两者可区分。复合 FK 下两种情况的报错**完全一致**
> （都是 violation，DETAIL 里的键值是攻击者自己填的），探测无收益。

**铁律 1 也有安全理由，不只是正确性** —— 不含 `tenant_id` 的唯一约束会开一条
**RLS 原理上补不了**的侧信道：靠 duplicate key 报错与否可探测其他租户的数据
是否存在。唯一索引检查发生在 RLS 之下。实测见 `05-安全与租户隔离.md` §3.1。

**全库唯一一处破例**：`bot_console_sessions` 主键为 `tg_user_id`，
因为它服务的恰好是「鉴权前、还不知道 `tenant_id`」那一刻。
侧信道确实存在（已实测），改由 GRANT 层堵 —— 业务角色对该表零权限。
完整论证与实测见 §7.1。**不要把这个破例当先例**：新表一律按铁律建。

### 1.3 RLS 三分类

带 `tenant_id` 的表一律套用同一模板，不逐表另设策略：

```sql
ALTER TABLE <表名> ENABLE ROW LEVEL SECURITY;
ALTER TABLE <表名> FORCE  ROW LEVEL SECURITY;   -- owner 也不放过
CREATE POLICY tenant_isolation ON <表名>
  USING      (tenant_id = current_setting('app.tenant_id')::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);
```

27 张表按 RLS 处置分三类。**分类依据是表里有没有 `tenant_id` 列**，不是凭感觉划分：

```bash
# 核实方式（按表体范围判定，避免匹配到注释与索引语句）
awk '/^CREATE TABLE/{t=$3;inb=1;next} inb&&/^\);/{inb=0} inb&&/tenant_id/{print t}' \
  03-数据模型.md | sort -u
```

**甲类 — 直接套模板（19 张）**：`tenant_members`、`identities`、
`credential_keys`、`source_subscriptions`、`target_channels`、`keywords`、
`rules`、`rule_versions`、`rule_replacements`、`tenant_events`、`notify_dedup`、
`delivery_tasks`、`audit_logs`、`login_sessions`、`system_logs`、
`bot_console_sessions`、`bot_console_updates`、`web_sessions`、`tenant_consents`。

甲类里有五处差别，都在 GRANT 层或多加一条限定角色的策略，**RLS 模板本身不改**：

| 表 | 差别 | 理由 |
|---|---|---|
| `tenant_members` / `bot_console_sessions` / `web_sessions` | 另加一条 `TO auth_lookup` 的 SELECT 策略 | 鉴权反查发生在知道 `tenant_id` 之前 |
| `identities` | 另加一条 `TO app_user` 的 `FOR SELECT` 共享身份策略 | 租户要能解析演示身份 |
| `system_logs` / `audit_logs` | `tenant_id` 可空；平台日志读取另设 `platform_ops` 角色 | 平台级记录无租户归属 |
| `tenant_consents` | GRANT 只给 `SELECT, INSERT` | 凭证不可改，见 §7.4 |
| `bot_console_sessions` / `web_sessions` | `REVOKE ALL FROM app_user` | 补偿唯一约束侧信道，见 §7.1 / §7.3 |

这四条附加策略的完整推导、三种错误写法与实测见 `05-安全与租户隔离.md` §四。
关键纪律在这里先说一次：**任何附加的 PERMISSIVE 策略必须限定 `TO <role>`**，
否则 PERMISSIVE 之间的 OR 语义会直接作废租户策略。

**乙类 — 子表，需 EXISTS 策略（2 张）**：`rule_conditions`、`delivery_logs`。

这两张表**没有 `tenant_id` 列**，靠外键挂在租户域父表上。
不能套模板，也不能因此跳过 —— 否则拿到 `rule_id` 就能读任意租户的规则条件：

```sql
ALTER TABLE rule_conditions ENABLE ROW LEVEL SECURITY;
ALTER TABLE rule_conditions FORCE  ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON rule_conditions
  USING (EXISTS (
    SELECT 1 FROM rules r
    WHERE r.id = rule_conditions.rule_id
      AND r.tenant_id = current_setting('app.tenant_id')::bigint
  ));
```

`delivery_logs` 同理，经 `delivery_tasks.task_id` 关联。
已实测：以租户 1 的上下文、指定属于租户 2 的 `rule_id` 直查，返回 0 行。

> **性能实测（结论好于预期）**：曾担心「EXISTS 策略每行触发一次父表查找」。
> **不成立** —— PG 17 把子查询优化成 **hashed SubPlan，整个查询只执行一次**：
>
> ```text
> Filter: (ANY (rule_id = (hashed SubPlan 2).col1))
>   SubPlan 2
>     ->  Bitmap Index Scan on rl_tenant   (actual rows=100 loops=1)
>                                                        ^^^^^^^ 只一次
> ```
>
> 5000 条规则 / 20 万条子表记录，执行 0.327 ms。
> 所以**不需要**为性能给这两张表补冗余 `tenant_id` 列。
> 前提是父表的 `tenant_id` 上有索引（本方案有）。

**丙类 — 不启用（6 张）**：

| 表 | 原因 |
|---|---|
| `tenants` | 无 `tenant_id` 列，主键即租户本身；按 `id` 访问，靠应用层授权 |
| `canonical_events` | **租户无关层**，按接收身份维度存储，扇出后才有租户归属 |
| `media_archive` | 同上，按 `content_hash` 全局复用，跨租户共享是设计意图 |
| `identity_secrets` | 通过 `identities` 间接受约，且仅三个组件可解密 |
| `account_leases` | 运维层，Worker 抢租约时无租户上下文 |
| `console_login_challenges` | **登录前**表，租户未知正是它要解决的问题；靠 GRANT 层限 `auth_lookup` |

> `canonical_events` 与 `media_archive` 不设 RLS 是**有意的**，不是遗漏。
> 它们的跨租户可见性由扇出层控制：租户只能通过 `tenant_events` 看到自己
> 订阅派生出的那部分。直查这两张表的权限仅授予 `fanout-worker` 与
> `delivery-worker`，不暴露给 control-plane 的租户 API。
>
> 这意味着**这三张表的隔离完全依赖应用层**，是本方案 RLS 覆盖面的已知边界。
> control-plane 若将来需要给租户暴露原始事件查询，必须经 `tenant_events` 连接，
> 不得直查 `canonical_events`。

## 二、租户域

```sql
CREATE TABLE tenants (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name          TEXT NOT NULL,
  -- 两档。enterprise 不做，见 ADR-0016
  plan          TEXT NOT NULL DEFAULT 'free'
                CHECK (plan IN ('free','pro')),
  owner_user_id BIGINT NOT NULL,          -- Telegram user id
  status        TEXT NOT NULL DEFAULT 'active'
                CHECK (status IN ('active','suspended','deleted')),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_tenants_owner ON tenants (owner_user_id);

-- 首发：建表但硬编码单成员（API 层固定 user_id = tenants.owner_user_id）
-- 后续迭代无需改表
CREATE TABLE tenant_members (
  tenant_id  BIGINT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  user_id    BIGINT NOT NULL,            -- Telegram user id，Bot 入口按此反查
  -- 五级角色里的四级。SUPER_ADMIN 是平台级角色，不属于任何租户，故不在此表
  role       TEXT NOT NULL DEFAULT 'TENANT_OWNER'
             CHECK (role IN ('TENANT_OWNER','TENANT_ADMIN','MEMBER','VIEWER')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, user_id)
);
-- Bot 入口的鉴权反查路径：按 user_id 找「他属于哪些租户」
-- 主键是 (tenant_id, user_id)，缺此索引反查会走全表
CREATE INDEX idx_members_user ON tenant_members (user_id);
```

> **`role` 枚举现在就按五级写**，即使首发只用得到 `TENANT_OWNER`。
> 两个入口（Web 与 Bot）读同一列，枚举必须只有一种 ——
> 首发的硬编码单成员会掩盖不一致，Bot 入口是第二个鉴权检查点，会把它暴露出来。
> 角色与权限的对应见 `05-安全与租户隔离.md` §五。

## 三、身份与凭据域

```sql
-- 统一的「接收/发送身份」抽象，Bot 与 MTProto 账号共用
CREATE TABLE identities (
  id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  kind         TEXT NOT NULL CHECK (kind IN ('bot','mtproto')),
  -- 平台演示身份的 tenant_id 为 NULL（全局共享，仅供演示源使用）
  -- 这是铁律 5 的三处有意破例之一，也是铁律 4 唯一例外的成因
  tenant_id    BIGINT REFERENCES tenants(id) ON DELETE CASCADE,
  tg_user_id   BIGINT,                    -- 该身份自身的 Telegram user id
  display_name TEXT,
  status       TEXT NOT NULL DEFAULT 'offline'
               CHECK (status IN ('online','offline','flood_wait','banned','unauthorized')),
  proxy_url    TEXT,                      -- 按身份独立代理，SOCKS5/HTTP
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_identities_tenant ON identities (tenant_id) WHERE tenant_id IS NOT NULL;
CREATE INDEX idx_identities_shared ON identities (kind) WHERE tenant_id IS NULL;

-- 每租户一个 DEK，密文由 KMS 中的 KEK 加密
CREATE TABLE credential_keys (
  tenant_id     BIGINT PRIMARY KEY REFERENCES tenants(id) ON DELETE CASCADE,
  dek_ciphertext BYTEA NOT NULL,          -- 被 KEK 加密后的 DEK
  kek_id        TEXT NOT NULL,            -- KMS 中的 KEK 标识
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  rotated_at    TIMESTAMPTZ
);

-- 凭据密文。AES-256-GCM，密钥为该租户 DEK
CREATE TABLE identity_secrets (
  identity_id      BIGINT PRIMARY KEY REFERENCES identities(id) ON DELETE CASCADE,
  -- Bot：token 密文；MTProto：session 密文
  secret_ciphertext BYTEA NOT NULL,
  nonce            BYTEA NOT NULL,
  api_id           INTEGER,               -- MTProto 专用，租户自带（ADR-0013）
  api_hash_ciphertext BYTEA,              -- MTProto 专用
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

> 纪律：明文凭据在内存中用后立即 `zeroize`。
> 效果：DBA 仅凭库内容无法解密（DEK 密文需 KMS 中的 KEK 才能解）。
> 信封加密的层次与密钥轮换见 `05-安全与租户隔离.md` §六。

## 四、订阅与规则域

```sql
-- 「哪个租户、监控哪个频道、由哪个身份接收」—— 双模式共存的关键
CREATE TABLE source_subscriptions (
  id                   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id            BIGINT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  tg_chat_id           BIGINT NOT NULL,           -- Telegram 原生值
  title                TEXT,
  -- 公开频道的 @username，不含 @。私有群为 NULL（正常态，非异常）。
  -- 缓存列，随权限探测刷新；ADR-0023。不得进任何唯一约束 ——
  -- 多个租户会订阅同一个公开频道。
  username             TEXT,
  receiver_identity_id BIGINT NOT NULL REFERENCES identities(id) ON DELETE RESTRICT,
  -- 授权准入：私有群/频道须验证操作者为 Owner/Admin，来源是 my_chat_member
  authorized_by        BIGINT,                    -- 授权操作人 Telegram user id
  authorized_at        TIMESTAMPTZ,
  enabled              BOOLEAN NOT NULL DEFAULT TRUE,
  discovered           BOOLEAN NOT NULL DEFAULT FALSE,  -- dialogs 自动发现
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at           TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uq_subscription
  ON source_subscriptions (tenant_id, tg_chat_id, receiver_identity_id);
-- 承铁律 4：供子表（rules / tenant_events）挂复合外键
CREATE UNIQUE INDEX uq_source_subscriptions_tenant_id
  ON source_subscriptions (tenant_id, id);
-- 扇出层的核心查询路径
CREATE INDEX idx_subscription_fanout
```

### 4.1 规则：关系表，不用 JSONLogic

```sql
CREATE TABLE rules (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id  BIGINT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  keyword_id BIGINT NOT NULL,
  -- NULL = 该租户全部来源
  source_ref BIGINT,
  media_type TEXT CHECK (media_type IN
             ('ANY','TEXT','PHOTO','VIDEO','AUDIO','VOICE','VIDEO_NOTE',
              'DOCUMENT','STICKER','ANIMATION','OTHER')),
  target_ref BIGINT NOT NULL,
  action     TEXT NOT NULL DEFAULT 'COPY'
             CHECK (action IN ('COPY','FORWARD','RESEND')),
  priority   INTEGER NOT NULL DEFAULT 0,
  -- 命中即停，用于黑名单拦截
  stop_processing BOOLEAN NOT NULL DEFAULT FALSE,
  template   TEXT,                        -- 来源头模板，NULL = 不加头
  -- 规则版本。每次语义变更 +1，使历史投递可解释
  version    INTEGER NOT NULL DEFAULT 1,
  enabled    BOOLEAN NOT NULL DEFAULT TRUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  -- 承铁律 4：三条引用全部走复合键，跨租户边在库层不可表达
  FOREIGN KEY (tenant_id, keyword_id)
    REFERENCES keywords (tenant_id, id) ON DELETE RESTRICT,
  FOREIGN KEY (tenant_id, source_ref)
    REFERENCES source_subscriptions (tenant_id, id) ON DELETE RESTRICT,
  FOREIGN KEY (tenant_id, target_ref)
    REFERENCES target_channels (tenant_id, id) ON DELETE RESTRICT
);
-- 承铁律 4：供子表（rule_versions / rule_conditions / rule_replacements）挂复合外键
CREATE UNIQUE INDEX uq_rules_tenant_id ON rules (tenant_id, id);
-- 冲突检查（API 统一返回 409）
CREATE UNIQUE INDEX uq_rule_conflict ON rules (
  tenant_id, keyword_id,
  COALESCE(source_ref, 0),
  COALESCE(media_type, 'ANY'),
  target_ref
) WHERE enabled;

-- 规则版本历史。只存快照，供投递记录反查「当时的规则长什么样」
CREATE TABLE rule_versions (
  rule_id    BIGINT NOT NULL,
  version    INTEGER NOT NULL,
  tenant_id  BIGINT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  snapshot   JSONB NOT NULL,              -- 规则 + 条件 + 替换的完整快照
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (rule_id, version),
  FOREIGN KEY (tenant_id, rule_id) REFERENCES rules (tenant_id, id) ON DELETE CASCADE
);
CREATE INDEX idx_rule_versions_tenant ON rule_versions (tenant_id, created_at DESC);

CREATE TABLE rule_conditions (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  rule_id  BIGINT NOT NULL REFERENCES rules(id) ON DELETE CASCADE,
  kind     TEXT NOT NULL CHECK (kind IN
           ('exclude_word','file_name','size_min','size_max','sender',
            'ext_allow','ext_deny')),
  value    TEXT NOT NULL
);
CREATE INDEX idx_rule_cond ON rule_conditions (rule_id);

-- 正文改写。同类项目的高频需求
CREATE TABLE rule_replacements (
  rule_id     BIGINT NOT NULL,
  seq         SMALLINT NOT NULL,           -- 执行序，显式声明不靠 id 隐式定序
  tenant_id   BIGINT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  pattern     TEXT NOT NULL,               -- Rust regex 语法
  replacement TEXT NOT NULL DEFAULT '',    -- 空串 = 删除匹配内容
  enabled     BOOLEAN NOT NULL DEFAULT TRUE,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, rule_id, seq),
  FOREIGN KEY (tenant_id, rule_id) REFERENCES rules (tenant_id, id) ON DELETE CASCADE
);
```

> **`seq` 为什么必须显式**：多条替换按序执行，结果依赖顺序
> （`a→b` 再 `b→c` 与反序结果不同）。靠 `id` 隐式定序的话，
> 用户插入一条到中间就只能删了重建后面全部。理由与 §4.3 的
> `priority DESC, id ASC` 同源 —— **顺序敏感的东西不能靠自增侥幸**。
>
> 这张表带 `tenant_id`（而 `rule_conditions` 不带）是有意的：
> 它的写入路径是「整体替换」（`PUT`），需要
> `DELETE ... WHERE rule_id = $1` 这种不经父表的批量操作，
> 有本表自己的 `tenant_id` 才能套甲类模板，不必依赖 EXISTS 子查询。
> `rule_conditions` 是逐条读，无此需要。

**为何不用 JSONLogic**：关系表可被 SQL 直接校验冲突、可建索引、迁移可控。
JSONLogic 的表达力优势（任意嵌套 and/or/not）在首发阶段用不上。
两者不能并存，此处明确选关系表。若后续确需任意嵌套，另写 ADR 评估。

### 4.2 版本递增规则

不是每次 `UPDATE rules` 都递增 —— 否则版本号被无意义的改动淹没。

```text
递增 version（并写 rule_versions 快照）：
  keyword_id / source_ref / media_type / target_ref / action /
  stop_processing / template 变更，或 rule_conditions 增删改，
  或 rule_replacements 增删改（含 seq 重排 —— 顺序变了结果就变了）

不递增：
  priority 调整（不改变是否命中，只改顺序）
  enabled 切换（停用不是语义变更，重新启用仍是同一规则）
```

写 `delivery_tasks` 时快照 `(rule_id, rule_version)`。
用户三个月后问「为什么这条消息被转到了这里」，能拿出当时的规则原文，
而不是改了五版之后的现状。这是审计能力，不是锦上添花。

### 4.3 匹配语义：三类角色，不是一堆并列条件

**这一节必须先定，否则规则引擎和 UI 都无从下手。** 同类项目在此翻过车 ——
`Heavrnl/TelegramForwarder` 评论最多的 issue（44 条）就是：用户设了 2 个 sender
+ 3 个关键词，本意「只看这两人的、且含关键词的消息」，实际行为是这两人的
**全部**发言都被转发，其他人的才走关键词匹配。实现是 OR，用户以为是 AND。

规则的各个字段不是并列条件，分三类角色：

```text
① 范围门（scope gate）  决定「这条消息轮不轮到本规则」
     source_ref    NULL = 本租户全部来源
     media_type    NULL 或 'ANY' = 不限
   门不通过 → 本规则直接跳过，不参与后续任何判断

② 触发（trigger）        决定「是否命中」
     keyword_id    必须命中。一条规则恰好一个关键词（表结构已强制 NOT NULL）
   未命中 → 本规则不命中

③ 修饰（modifier）       在触发的基础上收窄或否决 —— 即 rule_conditions
```

`rule_conditions` 内部按 `kind` 再分两种语义，这是本节的核心：

| kind | 语义 | 同 kind 多条之间 | 与其他 kind 之间 |
|---|---|---|---|
| `sender` | 收窄 | **OR** | AND |
| `file_name` | 收窄 | **OR** | AND |
| `size_min` / `size_max` | 收窄 | 各自最多一条 | AND |
| `ext_allow` | 收窄 | **OR** | AND |
| `exclude_word` | **否决** | OR（任一命中即否决） | 优先于全部收窄项 |
| `ext_deny` | **否决** | OR（任一命中即否决） | 同上 |

同 `kind` 多条取 OR 的理由：`sender` 列三个人，意思只可能是「这三人中任一」，
不可能是「同时是这三个人」。`file_name` 同理。**所以 sender 是收窄，不是追加来源**
—— 这正是上述 44 条评论 issue 的分歧点，此处明确取收窄语义。

`size_min` / `size_max` 每种超过一条无意义，**API 层直接返回 400**，
不做「取最严」这类静默兜底 —— 静默兜底会让用户永远查不出规则为何不生效。

`ext_allow` 与 `ext_deny` 同时存在时，**`ext_deny` 赢**（它是否决类）。
这不是「后者优先」的任意约定，而是否决语义的必然结果：
一条同时进白名单和黑名单的扩展名，用户的真实意图不可知，
选拒绝是因为**误拒可被用户看见并修正，误放过则不会**。

完整判定顺序（单条规则）：

```text
范围门不通过                      → 跳过
keyword 未命中                    → 不命中
任一否决项命中                    → 不命中（exclude_word / ext_deny，
                                     即使收窄项全通过）
任一收窄 kind 不满足              → 不命中
以上全过                          → 命中
```

否决项置于收窄项之前，是因为否决只要成立，收窄项的计算就无意义。
这是短路顺序，不改变结果，但省掉媒体元数据的读取（`file_name` / `size_*`
需要 `media` 字段，`exclude_word` 只看文本）。

#### 多规则：全部执行，不做 ONLY_TOP

```text
按 priority DESC, id ASC 遍历本租户全部 enabled 规则
  命中 → 产出一条 delivery_task
       → 若该规则 stop_processing = TRUE，停止遍历后续规则
  未命中 → 继续
```

不做 ONLY_TOP 的理由：`stop_processing` 已经能表达「到此为止」，且表达力更强
（可以在任意优先级位置截断，ONLY_TOP 只能截断在第一条）。两个机制并存
会产生「ONLY_TOP 模式下 stop_processing 有什么用」这种无解组合。

> **`priority` 同值时靠 `id ASC` 定序，不是未定义行为。** 遍历顺序必须稳定，
> 否则 `stop_processing` 的结果随机 —— 同一条消息两次处理可能投到不同目标。

#### 一条规则一个关键词，靠多条规则表达「多关键词」

表结构 `rules.keyword_id NOT NULL` 意味着不能在单条规则里写「关键词 A 或 B」。
需要时建两条规则，指向同一 `target_ref`。代价是规则数量膨胀，
换来的是 `uq_rule_conflict` 唯一索引能在 SQL 层直接校验冲突 ——
若一条规则挂多个关键词，冲突检查就得搬到应用层。

这个取舍的实际影响：**关键词批量导入功能必须同时批量建规则**，
否则用户导入 200 个关键词后要手工建 200 条规则。

### 5.1 事件类型的处理语义

光有枚举不够，必须明确每种类型是否重新执行规则、是否产生投递。

| event_type | 是否跑规则 | 是否投递 | 阶段 | 说明 |
|---|---|---|---|---|
| `MESSAGE_CREATED` | 是 | 是 | 首发 | 主路径 |
| `MEDIA_GROUP_COMPLETED` | 是 | 是 | 首发 | 见下方聚合规则 |
| `MESSAGE_EDITED` | 是 | **默认否** | 演进 | 见下方编辑策略 |
| `MESSAGE_DELETED` | 否 | 否 | 演进 | 仅标记，不撤回已投递内容 |
| `SOURCE_PERMISSION_CHANGED` | 否 | 否 | 上线 | 触发订阅状态复检，通知租户 |

**首发只实现前两种**。后三种落表结构但不产生事件，避免枚举形同虚设。

**媒体组聚合（`MEDIA_GROUP_COMPLETED`）**：
Telegram 的相册作为多条消息下发，共享 `media_group_id`。
纪律是**等聚合完成再跑规则**，否则一个相册会触发 N 次投递。

```text
收到带 media_group_id 的消息 → 落 canonical_events（MESSAGE_CREATED）
                             → Redis 键 mgroup:{identity}:{group_id} 累积
                             → 2 秒静默窗口无新消息 → 生成 MEDIA_GROUP_COMPLETED
                             → 该事件持有组内全部 message_id，规则只跑一次
```

2 秒是经验值，Telegram 同组消息通常在数百毫秒内到齐。
窗口内的单条 `MESSAGE_CREATED` **不投递**，只有聚合事件投递。

**编辑策略（`MESSAGE_EDITED`）**：
默认不重投，原因是频道常有排版微调，重投会造成目标频道噪音。
`edit_version` 递增使编辑事件能落库、可审计，但不触发投递。
演进阶段可提供两个租户级开关：`resend_on_edit`（编辑后重新投递，
适合价格/库存类频道）与 `reedit_target`（编辑目标频道的已投递消息，
需 `delivery_tasks.telegram_message_id`）。

**删除策略（`MESSAGE_DELETED`）**：
不追删已投递内容。目标频道的内容归属租户，
平台不应因源频道删除而擅自删除租户频道的消息。仅记录事件供审计。

### 5.2 幂等键：数据库唯一约束，不只靠 Redis

**纪律：每个幂等键都必须有对应的唯一约束，不得仅依赖 Redis 短期锁** ——
Redis 键过期或实例重启后，重复就漏进来了。Redis 只做快路径，数据库是最终防线。

| 层 | 幂等键 | 承载约束 |
|---|---|---|
| Bot 接入 | `(receiver_identity_id, update_id)` | `uq_canonical_update` |
| MTProto 接入 | `(receiver_identity_id, tg_chat_id, tg_message_id, event_type, edit_version)` | `uq_canonical` |
| 租户派生 | `(tenant_id, canonical_event_id)` | `uq_tenant_event` |
| 投递 | `(tenant_id, rule_id, rule_version, tenant_event_id, target_tg_chat_id)` | `uq_task_idem`（哈希入 `idem_key`） |

投递幂等键含 `rule_version`：规则改版后同一事件**允许**重新投递一次
（这是有意的，语义是「新规则产生新结果」），但同版本内绝不重复。

```rust
// idem_key 由五元组哈希而来，不是随机串
fn delivery_idem_key(
    tenant: TenantId, rule_id: i64, rule_version: i32,
    event_id: i64, target: TgChatId,
) -> String {
    let raw = format!("{}|{}|{}|{}|{}",
        tenant.get(), rule_id, rule_version, event_id, target.get());
    format!("{:x}", Sha256::digest(raw.as_bytes()))
}
```

### 5.3 三级去重

幂等（§5.2）解决「同一件事被处理两次」，去重解决「不同的事产生冗余通知」。
两者目的不同，不要混。

```text
L1 消息级  uq_canonical 唯一索引 + Redis SETNX  → 同一身份同一消息只处理一次
L2 文件级  content_hash（主）                    → 同一文件跨频道只投一次
L3 通知级  notify_dedup 指纹 + 窗口              → 同一资源被多群复读时抑制
```

```sql
CREATE TABLE notify_dedup (
  tenant_id   BIGINT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  fingerprint TEXT NOT NULL,              -- sha256(sender|hits|text[:300])
  target_ref  BIGINT NOT NULL,
  last_sent_at TIMESTAMPTZ NOT NULL,
  expires_at  TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (tenant_id, fingerprint, target_ref)
);
CREATE INDEX idx_notify_expire ON notify_dedup (expires_at);
```

> **指纹可复算是有意的设计**：因 `canonical_events` 存了
> `text`/`caption`/`sender_id`，指纹可从库中重算，L3 行为可审计、可回溯。
> 不存这些字段的话，指纹一旦生成就无法验证 —— 用户问「为什么这条被抑制了」
> 只能回答「算出来的指纹一样」，拿不出依据。

### 6.1 FloodWait 与 DLQ

```text
捕获 FloodWait(X 秒) → 不阻塞 Worker 线程：
  status = PENDING
  next_retry_at = now() + X + jitter
  attempt_count += 1
  last_error_code = 'FLOOD_WAIT'

退避阶梯：30s → 5min → 30min → DEAD

不可重试错误（立即 DEAD，不占重试额度）：
  CONTENT_PROTECTED / FORBIDDEN / ChatWriteForbidden / 频道不存在

进入 DEAD 时：通知租户「目标权限失效，请重新授权」
```

最后一条是承重的：只写日志告警管理员的话，用户完全不知道自己的投递已经停了。

### 6.2 来源头模板与直达链接

`rules.template` 的内容形态与占位符。

```text
默认模板（HTML parse_mode）：
  📢 来源: {chat_title} (@{username})
  👤 发送者: {sender}
  🔑 命中: {matched_keywords}
  🔗 原始消息: {message_link}

来源头是规则级开关（template IS NULL = 不加头）。
目标频道用于「资源整理」时通常关闭。
```

| 占位符 | 取自 |
|---|---|
| `{chat_title}` | `source_subscriptions.title` |
| `{username}` | `source_subscriptions.username`（ADR-0023，可为 NULL） |
| `{sender}` | `canonical_events.sender_id` |
| `{matched_keywords}` | `tenant_events.matched_keywords` |
| `{message_link}` | 按下方规则构造 |

> **模板走 HTML parse_mode，占位符替换必须转义。** `{chat_title}` 与
> `{sender}` 来自 Telegram 的用户可控内容，含 `<` `&` 就会让整条
> `sendMessage` 报 `can't parse entities` 并进入重试 —— 且重试必然重复失败，
> 白占三次退避直到 DEAD。替换时对文本占位符做 HTML 转义，
> `{message_link}` 不转义（它是自己拼的 URL）。

`{message_link}` 的构造规则，按来源是否公开分两支：

```text
公开聊天:   https://t.me/{username}/{tg_message_id}
私有聊天:   https://t.me/c/{tg_chat_id 去掉 -100 前缀}/{tg_message_id}
无法生成时: 退化为文本 "chat_id=... message_id=..."，不报错
```

> **`-100` 前缀这一步不能省。** Telegram 的超级群/频道原生 `chat_id` 形如
> `-1009876543210`，而 `/c/` 链接要的是去掉 `-100` 后的 `9876543210`。
> 直接拼原生值得到的链接打不开。这正是 §1.1 命名纪律要区分
> `tg_chat_id` 与内部主键的原因之一 —— 两者都是 `BIGINT`，混用不报错。

公开分支与 `{username}` 占位符取的是同一个字段：`source_subscriptions.username`，
**建表时就补，不在投递时查 Telegram**（ADR-0023）。理由是投递路径上加 API 调用
与 §6.1 的退避纪律冲突 —— 拿链接失败会让一条本可投递的消息进重试。
刷新时机是权限探测，那次调用本来就要发。

`username` 可为 NULL（私有群没有），所以两处渲染都要定义空值行为：

```text
{username} 占位符   为空时连同外层的 "(@...)" 一起省掉，
                    不输出 "(@)" —— 即占位符的省略是连带括号的
{message_link}      为空时走 /c/ 私有分支，不是「生成一个坏链接」
```

> **`(@)` 这种输出是最容易漏的一种。** 占位符替换若按「逐个 replace 成空串」
> 实现，私有群的来源头就会渲染出 `📢 来源: 某群 (@)`。
> 默认模板里 `@` 和括号是**模板字面量**，不在占位符内 ——
> 空值处理必须按「整段可选片段」做，不能按「单个占位符」做。

### 7.1 控制 Bot 入口两表

这两张表只服务控制 Bot，与采集/投递链路无关。设计见 `02-总体架构.md` §六。

**没有绑定表。** Bot 侧的认证就是 `update.from.id` 反查 `tenant_members`
（`user_id` 本身即 Telegram user id），不需要额外的 nonce 绑定环节。

```sql
-- Bot 私聊的服务端会话上下文。一个 tg_user_id 可属多个租户，
-- 当前选中哪个必须存在服务端 —— 放 callback_data 里就是可被篡改的越权入口
CREATE TABLE bot_console_sessions (
  tg_user_id BIGINT PRIMARY KEY,         -- 鉴权入口，故不以 tenant_id 为主键
  tenant_id  BIGINT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  state      JSONB,                      -- 多步命令的中间态
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  FOREIGN KEY (tenant_id, tg_user_id) REFERENCES tenant_members(tenant_id, user_id)
    ON DELETE CASCADE                    -- 成员关系被撤销时上下文自动失效
);
-- 本表只授权给 auth_lookup，业务角色一律无权限。理由见下方侧信道实测
REVOKE ALL ON bot_console_sessions FROM app_user;
GRANT SELECT, INSERT, UPDATE, DELETE ON bot_console_sessions TO auth_lookup;

-- 控制命令的幂等承载
CREATE TABLE bot_console_updates (
  tenant_id   BIGINT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  -- Bot API 的 update_id 按 Bot 独立计数，两个 Bot 出现同号是正常的，
  -- 故 bot_id 必须在键里（实测 (1,51,9001) 与 (1,52,9001) 均插入成功）
  bot_id      BIGINT NOT NULL REFERENCES identities(id) ON DELETE CASCADE,
  update_id   BIGINT NOT NULL,
  processed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, bot_id, update_id)
);
CREATE INDEX idx_console_updates_time ON bot_console_updates (processed_at);
```

#### `bot_console_sessions` 主键破例，以及它开的洞（已实测并已堵）

主键是 `tg_user_id` 而非 `(tenant_id, tg_user_id)`，因为它服务的恰好是
「还不知道 `tenant_id`」的那一刻。**这违反了铁律 1**，
CI 审计断言 A4 会命中它 —— 而且命中是对的，不是误报。实测的侧信道：

```text
999 同属租户 1 和 2，会话在租户 2。租户 1 的攻击者在自己上下文里探测：
  INSERT (999, 1) → ERROR: duplicate key ...  ← 999 当前会话在另一租户
  INSERT (111, 1) → INSERT 0 1（111 同属两租户但无会话，可回滚）
                    两种结果可区分，据此判定他人会话状态
```

唯一索引检查发生在 RLS 之下，所以 **RLS 原理上补不了这个洞**。
也不能靠加 `tenant_id` 进主键来修 —— 那就取消了破例，反查时又不知道 `tenant_id` 了。

**修法在 GRANT 层**：业务角色对本表零权限，只有 `auth_lookup` 能碰。
实测两种探测的错误合并为同一个，不可区分：

```text
REVOKE ALL ON bot_console_sessions FROM app_user;
  INSERT (999, 1) → ERROR: permission denied for table
  INSERT (111, 1) → ERROR: permission denied for table   ← 不可区分 ✓
  SELECT *        → ERROR: permission denied for table   ← 读也拒
```

这是全套设计里**唯一一处**允许违反铁律 1 的表。CI 断言 A4 对它单独白名单，
并在白名单注释里写明「靠 GRANT 层补偿」——
**不要改断言逻辑**，否则下一张真漏了的表也会被放过。

### 7.2 控制台扫码登录：挑战表

**这张表和 `login_sessions` 不是一回事，不要合并。** 两者名字像、方向相反：

```text
login_sessions              MTProto 账号登录。存 login_token —— 那是 bearer 凭据，
                            拿到就能授权某个 Telegram 账号。tenant_id 已知
console_login_challenges    控制台登录。存 nonce —— 它本身毫无用处，
                            必须由一个 Telegram 账号应答才有意义。tenant_id 未知
```

合并会带来两个后果：`login_sessions.tenant_id` 是 `NOT NULL`，而控制台登录
**在扫码那一刻还不知道租户**（那正是登录要解决的问题）；且两者的
`kind`/`state` 含义不同，挤进一张表后判定逻辑会互相污染。

```sql
-- 控制台扫码登录的挑战。租户未知，故本表无 tenant_id（丙类，不启用 RLS）
CREATE TABLE console_login_challenges (
  nonce        BYTEA PRIMARY KEY,           -- 随机 32 字节，进二维码的就是它
  -- 确认码。网页与 Bot 确认卡片同时展示，用户目视比对以防钓鱼
  confirm_code CHAR(4) NOT NULL,
  state        TEXT NOT NULL DEFAULT 'pending' CHECK (state IN
               ('pending','awaiting_confirm','confirmed','rejected','expired')),
  -- 应答者。awaiting_confirm 起有值；确认后据此查 tenant_members
  tg_user_id   BIGINT,
  -- 发起端指纹。确认卡片必须展示这两项，否则用户无从判断是否是自己发起的
  origin_ip    INET NOT NULL,
  user_agent   TEXT,
  expires_at   TIMESTAMPTZ NOT NULL,        -- 2 分钟
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_console_login_expire ON console_login_challenges (expires_at);
-- 一个 tg_user_id 同时只允许一个待确认挑战，防「连发多张卡片诱导误点」
CREATE UNIQUE INDEX uq_console_login_pending
  ON console_login_challenges (tg_user_id) WHERE state = 'awaiting_confirm';
REVOKE ALL ON console_login_challenges FROM app_user;
GRANT SELECT, INSERT, UPDATE, DELETE ON console_login_challenges TO auth_lookup;
```

> **为什么需要 `confirm_code` 与确认态** —— 不加就有一个真实的钓鱼向量：
>
> ```text
> 攻击者在自己浏览器开登录页 → 截图二维码发给受害者
>   → 受害者扫码，服务端收到带受害者 from.id 的应答
>   → 会话签发给了攻击者的浏览器           ← 账号被接管
> ```
>
> 修法是**签发前必须有一次带上下文的确认**：Bot 收到应答后不签发会话，
> 而是回一张卡片，展示 `origin_ip` / `user_agent` / `confirm_code`，
> 用户核对网页上的同一个码后点「确认」才置 `confirmed`。
> 受害者看到的是一个陌生 IP 和一个与自己屏幕不符的码。
> Telegram 官方客户端为同一问题做了同样的确认页 —— 这不是可选加固。
>
> `state` 机的关键纪律：**`pending → awaiting_confirm` 的迁移必须原子**
> （`UPDATE ... WHERE state = 'pending'` 判受影响行数），
> 否则两个人同时扫同一张码会各自推进状态。
>
> 另有一条：`nonce` 与 `web_sessions.id` 同性质，**不得进任何日志**。

**它不需要 `bot_console_sessions` 那样的破例。** 两者的差别在查询入口：
`bot_console_sessions` 必须按 `tg_user_id` 查（那是它唯一的鉴权输入），
所以主键被迫是单列；`web_sessions` 按随机 `id` 查，而随机 `id`
可以和 `tenant_id` 组成复合主键、由 `uq_web_session_id` 保证全局唯一性，
铁律 1 不用破。

> 但**唯一索引 `uq_web_session_id` 又把侧信道带回来了** ——
> 攻击者可用 `INSERT` 的 duplicate key 探测某个 session id 是否存在。
> 与 §7.1 同样的修法：GRANT 层封死，业务角色零权限。
> 差别是这里代价更低：session id 是 32 字节随机值，猜中的前提是已经拿到了它，
> 而拿到了就直接能用，探测本身无收益。**仍然照堵** ——
> 「这个洞用不上」和「这个洞不在」是两回事。
>
> 另有一条纪律：**`web_sessions.id` 不得进任何日志**（含 `system_logs`
> 与 access log）。它等价于口令，落进日志就是明文存口令。日志记 `user_id`
> 与 `tenant_id`。

### 7.4 授权凭证表（第 27 张表）

`audit_logs` 记的是**操作审计**（谁改了什么），缺的是**授权凭证**
（租户在何时、看到什么措辞、同意了平台以其账号名义做哪些事）。
租户被封号后提出异议时，这是唯一的防线。

```sql
-- 租户授权凭证。与 audit_logs 的区别：这里记「同意了什么」，不是「做了什么」
CREATE TABLE tenant_consents (
  id           BIGINT GENERATED ALWAYS AS IDENTITY,
  tenant_id    BIGINT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  -- free 档只需 tos（free 不代持凭据，无需代持授权）
  consent_type TEXT NOT NULL
               CHECK (consent_type IN ('tos','privacy','credential_custody')),
  -- 授权文本版本。文本改了而旧租户没重新同意，旧授权就不覆盖新行为
  text_version TEXT NOT NULL,
  -- 同意者。落在具体自然人身上，不是「租户」这个抽象
  user_id      BIGINT NOT NULL,
  agreed_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  ip           INET,
  user_agent   TEXT,
  PRIMARY KEY (tenant_id, id),
  FOREIGN KEY (tenant_id, user_id) REFERENCES tenant_members(tenant_id, user_id)
    ON DELETE CASCADE
);
-- 查询形态：「租户 X 对 Y 类授权的最新同意是什么」
CREATE INDEX idx_tenant_consents_latest
  ON tenant_consents (tenant_id, consent_type, agreed_at DESC);
```

> **两处刻意不加的索引**：
>
> ```text
> UNIQUE (tenant_id, id) —— 不加，主键已经是它（对照 web_sessions §7.3）。
>   铁律 4 要求的是父表存在这个唯一性，不要求它额外建一条索引。
>
> UNIQUE (tenant_id, consent_type, text_version, user_id) —— 不能加。
>   本表是追加式的：撤回后再次同意同一版本文本是合法动作，
>   加了唯一约束就会撞 duplicate key，把「同意过又撤回又同意」
>   这条审计链变成写不进去。上面那条普通索引已覆盖查询形态。
> ```

**甲类表，套 §1.3 的 RLS 模板**（带 `tenant_id`，无破例）。
全库表数 **27**：甲类 19 / 乙类 2 / 丙类 6。

> **`INSERT` 之后不得 `UPDATE` 或 `DELETE`**（除租户注销的级联）。
> 凭证一旦被改就不是凭证了。这条靠 GRANT 层落实：
>
> ```sql
> GRANT SELECT, INSERT ON tenant_consents TO app_user;   -- 无 UPDATE/DELETE
> ```
>
> 注意这与模板有一处差别：模板给 `app_user` 全量 DML，这里**故意只给两项**。
> RLS 策略照套（`USING` + `WITH CHECK` 都要），
> 因为 GRANT 管「能做什么动作」，RLS 管「能碰哪些行」，两层都需要。
>
> 撤回同意不是删行，是**再插一条**反向记录（`consent_type` 相同、
> 文本版本指向撤回声明文本）—— 审计链要能看出「同意过又撤回了」，
> 而不是「从来没同意过」。
>
> **排期硬顺序**：本表必须在身份管理 + QR 登录接入产品**之前**建好，
> 否则第一批租户的授权就是无凭证的。建表部分与 27 表迁移同批。

## 九、局限

- **这 27 张表的 DDL 没有在真实 PostgreSQL 上跑过一次。** 本文是设计稿，
  不是迁移产物 —— 语法错、类型不兼容、约束顺序依赖都要到 27 表迁移
  那个工作包里才会暴露。`psql` 已装但库还没建 —— **有客户端不等于验过**。
- **45 个索引全部是按预期查询形态推的，没有一条 `EXPLAIN` 支撑。**
  首列 `tenant_id` 那条铁律保证的是 RLS 下索引可用，
  不保证选择性够 —— 真实数据分布出来后大概率要增删。
- **`username` 是本文唯一一个会静默过期的列（ADR-0023）。**
  它随权限探测刷新，而权限探测是租户手工触发的 ——
  没有任何机制保证它是最新的，也没有信号提示它已过期。
  本文管到「列存在、可为 NULL」，管不到「值是对的」。
- **分区不在本文的 DDL 里（ADR-0024）。** `tenant_events` 的表定义是普通表，
  超过 `04-数据生命周期与容量.md` §三 那个阈值（5000 万行 / 20GB）后
  要改成分区表 —— 而分区不继承 RLS，改造时同文件 §3.1 的前置条件要先满足，
  不是加一句 `PARTITION BY` 的事。
- **四张表用了 `JSONB`（`rule_versions` / `audit_logs` / `system_logs`
  / `bot_console_sessions`），它们的内部结构没有 schema 约束。**
  `rule_versions.snapshot` 最重要：它是规则回滚的唯一依据，
  但「快照结构随规则表演进而变化」这件事没有版本号字段来承载。
  今天回滚旧快照是否还能正确解析，无法从本文判断。
- §八 那条表数核实命令是**人工纪律，不是机器卡口**。
  它没有进 `../eng/04-CI门禁.md` —— 也就是说漏跑它不会有任何报错。
