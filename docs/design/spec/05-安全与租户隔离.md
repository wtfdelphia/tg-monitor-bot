# 安全与租户隔离

本文是隔离机制的**唯一定义处**。表结构与建表铁律见 `03-数据模型.md`；
CI 如何把这里的纪律变成卡口见 `../eng/04-CI门禁.md`；
反向测试清单见 `../eng/03-测试策略.md`。

所有标注「已实测」的结论都在 PostgreSQL 17.11 本地容器上复现过
（2026-09-19，测完即销毁）。它们的共同特征是**报错信息指不到真因** ——
这也是它们值得逐条写下来的原因。

---

## 一、五层防线，各拦一类错

| 防线 | 拦截时机 | 能拦住 | 拦不住 | 超级用户能绕过 |
|---|---|---|---|---|
| newtype（§二） | 编译期 | 忘传 `tenant_id` 参数 | 传错了租户的值 | — |
| 应用层显式谓词（§3.6） | 运行期 | 主机制，覆盖自己写的路径 | 手写 SQL、运维直连 | 能 |
| RLS（§三） | 运行期 | 传错租户、漏写 WHERE、注入后的越权读 | 上下文本身被设错、`TRUNCATE` | **能**（`FORCE` 也拦不住） |
| 复合外键（§4.2） | 写入时 | 数据长出跨租户的边 | 只覆盖走复合外键的那些边 | **不能** |
| GRANT 层（§3.5、§六） | 运行期 | 唯一约束侧信道、`TRUNCATE` | 行级可见性 | 能 |

**定位必须说清：应用层显式 `tenant_id` 是主机制，RLS 是兜底。**
反过来理解会导致一类真实事故 —— 见 §3.6。

## 二、编译期隔离：newtype

**这是选择 Rust 的首要理由。**

```rust
// 所有 ID 用 newtype 包裹，禁止裸 i64
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, sqlx::Type)]
#[sqlx(transparent)]
pub struct TenantId(i64);

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, sqlx::Type)]
#[sqlx(transparent)]
pub struct TenantEventId(i64);

// Telegram 原生 chat_id 与内部主键，类型上就不可混用
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, sqlx::Type)]
#[sqlx(transparent)]
pub struct TgChatId(i64);        // -1009876543210 这种

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, sqlx::Type)]
#[sqlx(transparent)]
pub struct SourceRef(i64);       // source_subscriptions.id
```

`TgChatId` 与 `SourceRef` 分开是为了根治「`chat_id` 同名三义」——
Telegram 原生 chat id、内部订阅主键、投递目标 id 曾经共用一个名字，
命名纪律见 `03-数据模型.md` §1.1。

配合仓储层强制签名：

```rust
// 每个查询方法都必须显式传 TenantId，漏传则编译不过
impl RuleRepo {
    pub async fn list_enabled(
        &self,
        tenant: TenantId,          // ← 不可省略
        source: SourceRef,
    ) -> Result<Vec<Rule>> { ... }
}
```

这样「漏写 `WHERE tenant_id`」从运行时的数据泄漏事故，变成一个编译错误。

## 三、RLS：第二道防线

### 3.1 为什么它与连接池不冲突

有一个流传很广的判断：「RLS 需要按租户切连接角色，与连接池复用冲突」。
**该判断不成立** —— 它假设 RLS 只能靠 `SET ROLE` 实现。
实际做法是 `SET LOCAL` + `current_setting()`：

```text
SET LOCAL 的作用域是当前事务，不是连接。
官方原文：The effects of SET LOCAL last only till the end of the
         current transaction, whether committed or not.
COMMIT / ROLLBACK 后自动失效，回到会话级值。

→ 连接归还池中时，租户上下文已随事务结束而清除，不会泄漏给下一个借用者。
```

策略定义（完整模板与三分类见 `03-数据模型.md` §1.3）：

```sql
ALTER TABLE tenant_events ENABLE ROW LEVEL SECURITY;
-- 关键：表 owner 默认绕过 RLS，必须 FORCE 才对 owner 生效
ALTER TABLE tenant_events FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON tenant_events
  USING      (tenant_id = current_setting('app.tenant_id')::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);
```

`USING` 管读（SELECT/UPDATE/DELETE 可见性），`WITH CHECK` 管写
（INSERT/UPDATE 的新值）。**两个都要写** ——
只写 `USING` 挡不住往别的租户塞数据。

### 3.2 唯一的租户事务入口

```rust
/// 唯一的租户事务入口。业务代码拿不到裸 Transaction
pub async fn tenant_tx<F, T>(pool: &PgPool, tenant: TenantId, f: F) -> Result<T>
where
    F: for<'a> FnOnce(&'a mut PgConnection) -> BoxFuture<'a, Result<T>>,
{
    let mut tx = pool.begin().await?;          // 独占一条连接直至结束
    // set_config 而非字符串拼接 SET LOCAL，避免注入
    sqlx::query("SELECT set_config('app.tenant_id', $1, true)")
        .bind(tenant.get().to_string())
        .execute(&mut *tx)
        .await?;
    let out = f(&mut tx).await?;
    tx.commit().await?;
    Ok(out)
}
```

`set_config(..., true)` 的第三参数 `is_local = true` 等价于 `SET LOCAL`。
用它而不是拼 `SET LOCAL app.tenant_id = '...'`，因为
**`SET` 是 utility 命令，不接受绑定参数**，只能拼字符串 ——
那等于在多租户边界上开一个 SQL 注入面。`set_config` 是普通函数，可以绑参。

> **但这个选择带来一个必须知道的陷阱**：`set_config(..., true)`
> 在事务外调用会**静默失效**，而 `SET LOCAL` 至少会告警。已实测：
>
> ```text
> SELECT set_config('app.tenant_id','ccc',true);   → 返回 'ccc'，看起来成功
> SELECT current_setting('app.tenant_id', true);   → 空，未生效，无任何 WARNING
>
> SET LOCAL app.tenant_id='bbb';  （事务外）
>   → WARNING: SET LOCAL can only be used in transaction blocks
> ```
>
> 即**更安全的写法恰好是失效时更安静的写法**。所以 `tenant_tx` 必须
> 自己保证事务已开启 —— 上面的实现里 `pool.begin()` 在 `set_config` 之前，
> 这个顺序是安全要求，不是风格。**不要**把 `set_config` 提取成
> 能在事务外被调用的独立函数。

### 3.3 五条配套纪律

#### 纪律 1：应用角色不能是表 owner，且不得有 `BYPASSRLS`

迁移用 owner 角色跑，运行时用受限角色连。这是 RLS 生效的前提，
配错了策略形同虚设，而且不会报错 —— 静默失效。

> **`FORCE` 的作用比「让 owner 也受约束」大得多，这点容易被低估。**
> 实测发现两条绕过路径，它们都**以 owner 身份执行**，因此都吃 `FORCE`
> （租户 1 应见 2 行）：
>
> | 访问路径（`app_user` 调用，`app.tenant_id=1`） | owner 非超级用户 + 无 FORCE | + FORCE |
> |---|---|---|
> | 直接 `SELECT` 基表 | 2 行 ✓ | 2 行 ✓ |
> | owner 的 `SECURITY DEFINER` 函数 | **全表 ✗ 泄漏** | **0 行**（安全，但功能坏掉） |
> | owner 的普通视图 | **全表 ✗ 泄漏** | **0 行**（同上） |
> | owner 的 `security_invoker = true` 视图 | 2 行 ✓ | 2 行 ✓ |
>
> 关键在于：泄漏与 owner 是不是超级用户**无关** —— 上表的 owner 是
> `NOSUPERUSER` 且无 `BYPASSRLS`，照样泄漏。**决定因素只有 `FORCE`。**
> 所以「用非超级用户当 owner」这条常见建议**并不足以**关掉这两条路径。
>
> **但 `FORCE` 后的那两个 0 行不是「修好了」，是换了一种坏法**：策略写的是
> `TO app_user`，这两条路径以 owner 身份执行，`FORCE` 让 owner 也受约束
> 却无任何策略匹配 owner → 默认拒绝 → 静默空集。它在功能测试里表现为
> 「查不到数据」，极易误诊成数据没写进去。所以定案不是「靠 FORCE 兜」：
> **视图一律 `security_invoker = true`；带 `tenant_id` 的表上一律不用
> `SECURITY DEFINER`**（提权走 `../eng/00-工程约定.md` 的 `admin_tx`），
> 并由 CI 静态断言 A8 拦住。

#### 纪律 2：PgBouncer 必须用 `transaction` 或 `session` 模式

不能用 `statement` 模式。该模式下同一事务的语句可能落到不同连接，
`SET LOCAL` 与后续查询就分家了 ——
实测报 `FATAL: transaction blocks not allowed in statement pooling mode`，
这一条至少是响亮失败。

> **同一环境下，裸 `SET` 会造成跨进程的真实泄漏**（已实测）：
> transaction 模式下客户端 A 执行 `SET app.tenant_id = '7'`，
> 客户端 B 复用同一条服务端连接后继承了该值并读到他租户数据；
> 一个完全无关的进程也观察到了 `inherited tenant = Some("7")`。
> 这是「必须用 `set_config(..., true)` 而非裸 `SET`」的最硬证据 ——
> 纪律 1 下方讲的是注入面，这里讲的是泄漏面，两个理由独立成立。
>
> 兜底配置：`server_reset_query = DISCARD ALL` 配
> `server_reset_query_always = 1`（transaction 模式下前者默认**不执行**）。
> **这是安全配置，不是性能调优项。** 注意它是兜底不是依赖项 ——
> 正确写法本身不需要它。sqlx 侧可用 `after_release` 跑一次 `RESET ALL`
> 达到同样效果（sqlx 自身不发 `DISCARD ALL`）。
>
> 版本要求：PgBouncer **≥ 1.25.1**，修复 CVE-2025-12819 ——
> auth_query 处理中的 search_path 注入，未认证攻击者可在认证阶段
> 执行任意 SQL。另需 ≥ 1.21 才支持 transaction 模式下的预编译语句
> （`max_prepared_statements`），而 sqlx 默认走预编译。

#### 纪律 3：绝不要写 `current_setting('app.tenant_id', true)`

带 `missing_ok = true` 的两参数形式在未设置时返回 NULL，
策略条件变成 `tenant_id = NULL` → 恒为 NULL → **静默返回零行**。
这是 RLS 最难排查的失效模式：没有报错，只是「数据不见了」。
单参数形式在未设置时直接 ERROR，是有意选择。

> **这条要顶住一个流传很广的反向建议。** 社区（含多份调研报告）
> 常推荐 `nullif(current_setting('app.tenant_id', true), '')`，
> 理由是「避免空串导致的报错」。**采纳它等于把 fail-loud 换成 fail-silent**，
> 已实测对比：
>
> | 策略写法 | 从未设置 | 空串残留 |
> |---|---|---|
> | `current_setting(...)::bigint`（本方案） | `ERROR: unrecognized configuration parameter` | `ERROR: invalid input syntax for type bigint: ""` |
> | `nullif(current_setting(...,true),'')::bigint` | **静默 0 行** | **静默 0 行** |
>
> 两种状态下本方案都报错，`nullif` 版本都静默。
> 「报错信息不好看」不是采纳静默失败的理由。
> 若确实要改善报错信息，正确做法是写一个 `RAISE EXCEPTION` 的
> `STABLE` 函数显式抛错，**而不是**让条件求值成 NULL ——
> 但那又会踩纪律 5 的包装函数坑，所以本方案选择接受不直观的报错。

#### 纪律 4：`::bigint` 转换是安全机制，不是类型细节

`set_config` 在事务中用过一次后，会话级会残留**空字符串**而非回到未定义。
此时单参数 `current_setting` 不再报「参数不存在」，而是返回 `''`。
`''::bigint` 会 ERROR（fail-loud，安全）；
但若把 `tenant_id` 设计成 TEXT 并直接比较，`tenant_id = ''` 恒不成立
→ **静默零行，保护失效**。已实测两种写法：

| 策略写法 | GUC 从未设置 | 有空串残留 |
|---|---|---|
| `tenant_id = current_setting(...)::bigint` | ERROR ✓ | ERROR ✓ |
| `tenant_id = current_setting(...)`（TEXT，无转换） | ERROR | **静默 0 行** ✗ |

所有 `tenant_id` 均为 `BIGINT`，两种连接状态下都 fail-loud。
**这条约束必须写进评审清单** —— 将来若有人为「支持字符串租户标识」
把某张表的 `tenant_id` 改成 TEXT，会静默拆掉 fail-loud 特性。

#### 纪律 5：策略里不要包装 `current_setting()`；若要包装，绝不能标 `IMMUTABLE`

这是调研中发现的**唯一能造成真实跨租户数据泄漏**的写法，已复现：

```sql
-- 致命错误：IMMUTABLE 让租户值被烘进缓存的执行计划
CREATE FUNCTION bad_tid() RETURNS bigint AS
  $$ SELECT current_setting('app.tenant_id')::bigint $$
  LANGUAGE sql IMMUTABLE;        -- ← 错。current_setting 是 STABLE
CREATE POLICY p ON t USING (tenant_id = bad_tid());
```

```text
实测（PG 17.11）：
  租户 1 上下文，PREPARE + 反复 EXECUTE  → 返回 bmw-secret（正确）
  切到租户 2，同一 prepared statement    → 仍返回 bmw-secret  ← 泄漏
```

模板把 `current_setting()` **直接内联在策略里，不经包装函数**。
同样的 prepare/execute 测试下，切租户后正确返回租户 2 的数据。
这不是运气 —— 内联写法让计划依赖 RLS，角色/环境变化会触发重新规划。

> 为什么这个坑能活到生产：它**只在开启语句缓存的驱动上显形**
> （pgx 默认开启，JDBC 不显形）。与连接池卫生无关，
> `DISCARD ALL`、`SET LOCAL` 都救不了。sqlx 也会缓存 prepared statement，
> 所以我们同样在射程内 —— 守住「不包装」这一条即可。

**若因其他原因仍要包装，必须是 `STABLE`，且不能用 plpgsql。** 实测
（20 万行 / 50 租户，受限角色，策略是唯一的租户谓词）：

| 策略写法 | 执行计划 | 耗时 |
|---|---|---|
| 内联 `current_setting()` | Index Cond（下推进索引） | 0.76 ms |
| SQL 函数，`STABLE` | Index Cond（函数被内联展开） | 0.69 ms |
| SQL 函数，`VOLATILE` | Index Cond（**仍被内联**） | 1.88 ms |
| plpgsql 函数，`STABLE` | Index Cond | 1.24 ms |
| plpgsql 函数，`VOLATILE` | **Filter，逐行调用** | **195 ms（约 260×）** |

```text
plpgsql VOLATILE 的计划：
  Index Only Scan using perf_tid on perf
    Filter: (tenant_id = tid_pl_vol())     ← 没进 Index Cond
    Rows Removed by Filter: 196000         ← 全表扫完再逐行过滤
```

注意 `VOLATILE` 本身**不是**触发条件 —— SQL 语言的单表达式函数会被
规划器内联，`VOLATILE` 标记随之失效，所以看不出差别。
**只有 plpgsql（不可内联）+ `VOLATILE` 才会掉到逐行调用。**
这个组合恰好是「把校验逻辑写进策略函数」时最自然的写法，因此值得单列。

### 3.4 基线实测

| 场景 | 实测结果 |
|---|---|
| 未设 `app.tenant_id` 直接查 | `ERROR: unrecognized configuration parameter` ✓ 报错而非零行 |
| 设 `tenant_id=1` 后查 | 只返回租户 1 的行；`tenant_id IS NULL` 的行不可见 ✓ |
| 租户 1 上下文插入 `tenant_id=2` | `ERROR: new row violates row-level security policy` ✓ |
| `COMMIT` 后再查 | 报错 ✓ 证实设置未跨事务残留 |
| 子表 EXISTS 策略，指定他租户 `rule_id` 直查 | 0 行 ✓ |

> 第四项的实际报错是 `invalid input syntax for type bigint: ""`，
> 因为 `set_config` 在事务中设过一次后，会话级留下空字符串而非未定义状态。
> **仍然报错，隔离没破**，但报错信息不直观。生产环境建议在会话初始化时
> 显式 `RESET app.tenant_id`，或接受这个次优的报错信息 —— 不要因为
> 信息不好看就改用两参数形式（纪律 3）。

### 3.5 「所有路径」的例外，必须知道

RLS 的价值在于它对**所有**进入数据库的路径生效，包括手写 SQL、
未来新增的代码、以及运维直连（只要用受限角色）。但有例外，均已实测：

| 操作 | RLS 是否生效 | 后果 |
|---|---|---|
| `DELETE FROM t`（受限角色，租户 1） | 生效 | 只删 1 行 ✓ |
| `TRUNCATE t`（同上） | **不生效** | 清空全部租户 ✗ |
| owner 的 `SECURITY DEFINER` 函数 | 仅 FORCE 后生效 | 见纪律 1 |
| owner 的普通视图 | 仅 FORCE 后生效 | 见纪律 1 |
| 超级用户 / `BYPASSRLS` 角色 | 永不生效 | `FORCE` 也拦不住 |

**`TRUNCATE` 不受 RLS 约束**，所以运行时角色**不要授予 `TRUNCATE` 权限** ——
它不在 RLS 的射程内，只能靠 `GRANT` 层面挡。清表交给迁移角色。

**还有一条 RLS 原理上修不了的侧信道：全局唯一约束。** 已实测：

```text
表 users_g(tenant_id, email UNIQUE)   ← 唯一约束不含 tenant_id
受限角色以租户 1 身份，只能看到 1 行（RLS 正常工作）：

  INSERT 不存在的 email        → INSERT 0 1        （可回滚）
  INSERT 租户 2 的 secret email → ERROR: duplicate key value
                                  violates unique constraint "users_g_email_key"

→ 报错与成功的差异泄漏了「该 email 在别的租户是否存在」。
   可以逐个探测，RLS 一行都没多给，信息照样漏出去。
```

唯一索引的检查发生在 RLS 之下，PostgreSQL 官方文档也承认这点。
**唯一的修法是让唯一约束本身带 `tenant_id`** —— 同一测试换成
`UNIQUE (tenant_id, email)` 后，探测租户 2 的 email 返回 `INSERT 0 1`，
与探测不存在的值无法区分，通道关闭。

这正是铁律 1「所有唯一约束必须含 `tenant_id`」的**安全**理由。
起初写它是为了正确性（不同租户可以有同名资源），现在它还是一道防线：
**漏了 `tenant_id` 的唯一约束会开一个 RLS 补不上的洞。**
无法遵守铁律 1 的那三张表（`bot_console_sessions` / `web_sessions` /
幂等表，见 `03-数据模型.md` §7.1 与 §7.3）只能靠 GRANT 层补偿，见 §六。

另外，`row_security = off` 这个 GUC **不是绕过开关**，容易误解。实测受限角色
设了它之后查询直接报 `ERROR: query would be affected by row-level security
policy for table "t"` —— 它的语义是「如果会被策略影响就报错」，用于确认
某查询未被静默过滤，而非跳过策略。只有超级用户和 `BYPASSRLS` 能真正绕过。

**这条对备份有直接影响**：受限角色跑 `pg_dump` 会失败而非产出部分数据 ——

```text
pg_dump -U app_user           → ERROR: query would be affected by RLS policy
pg_dump -U app_user --enable-row-security
                              → ERROR: unrecognized configuration parameter "app.tenant_id"
```

两种都拿不到备份。**备份必须用 owner 或超级用户角色跑**，这是运维前提，
不是可选项（见 `../ops/01-上线就绪与运维.md`）—— 配错了会得到
「备份任务一直在失败」而不是「备份不完整」，算是好的失败方式，但必须提前知道。

### 3.6 SQL 里照样显式写 `WHERE tenant_id = $1`

不因为有 RLS 就省掉。理由有三条，都不是洁癖：

1. RLS 的正确性依赖 PostgreSQL 的计划缓存与角色跟踪，那个面两年内修过
   两次同类 CVE（见 §五）。把它当唯一防线是把安全押在一个仍在修 bug 的子系统上。
2. 显式谓词让查询计划更好 —— RLS 的策略条件在性能上**不等价于**
   自己写的 WHERE 子句，补写显式过滤是公认的 RLS 优化手段。
3. 可审计性。隐式安全的代价是「看一段代码无法确认它能访问什么数据」，
   那取决于连接的会话状态。显式谓词是看得见的。

> 行业现状值得警惕：RLS 正在被越来越多地当作**唯一**授权层而非补充层。
> 连最依赖 RLS 的厂商（Supabase）自己的文档都写
> "Do not rely on RLS for filtering but only for security" ——
> 出自最有动机推销 RLS 的一方，这条建议因此格外可信。
>
> 配套要求：反向测试里必须有一组**关掉 RLS 跑的跨租户测试**，
> 用来验证应用层自己是否站得住。如果关掉 RLS 后测试就泄漏，
> 说明主机制根本没实现，只是被 RLS 遮住了。清单见 `../eng/03-测试策略.md`。

### 3.7 鉴权反查困境：`auth_lookup` 角色

按 `from.id` 反查 `tenant_members` 是**鉴权发生之前**的操作，此时还不知道
`tenant_id`，但 `tenant_members` 套了 RLS 模板（甲类）。实测的失败链条：

```text
受限角色，未设 app.tenant_id，SELECT tenant_id FROM tm WHERE user_id=777
  → ERROR: unrecognized configuration parameter "app.tenant_id"
     ← fail-loud 按设计生效了，但这条路径本就不该有 tenant_id
```

三条错误解法与它们的实测后果：

```text
✗ 加一条自查策略但不限定角色
    CREATE POLICY member_self_lookup ON tm
      FOR SELECT USING (user_id = current_setting('app.auth_user_id')::bigint);
  PERMISSIVE 策略之间是 OR。实测：业务连接设 app.tenant_id='0'
  （不匹配任何租户）+ app.auth_user_id='777' → 返回 2 行，横跨租户 1 和 2
  ← 等于给租户隔离策略开了个洞，且洞在最难发现的地方
✗ 用 SECURITY DEFINER 函数绕过
  实测同样返回跨租户 2 行。这条路径以 owner 身份执行，
  FORCE 只能让它受策略约束，而策略被上一条写坏了 —— 坏策略照样被绕
✗ 给反查加 BYPASSRLS 角色
  等于承认这张表的隔离靠自觉。而且 BYPASSRLS 一给就是全库范围
```

正确解法是**策略按角色分离**，两条策略各自限定 `TO`，互不构成 OR：

```sql
-- 业务路径：只有业务角色能走租户策略
CREATE POLICY tenant_isolation ON tenant_members TO app_user
  USING      (tenant_id = current_setting('app.tenant_id')::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);

-- 鉴权反查路径：独立角色，只能看见「自己是谁的成员」，且只读
CREATE ROLE auth_lookup LOGIN NOSUPERUSER NOBYPASSRLS;
GRANT SELECT ON tenant_members TO auth_lookup;   -- 只 SELECT，不给写
CREATE POLICY member_self_lookup ON tenant_members FOR SELECT TO auth_lookup
  USING (user_id = current_setting('app.auth_user_id')::bigint);
```

实测五项行为，与设计一致：

| 场景 | 结果 |
|---|---|
| `auth_lookup` 设 `app.auth_user_id=777` 全表查 | 只见 777 自己的 2 行成员关系 ✓ |
| `auth_lookup` 查 `user_id=888` | 0 行 ✓ |
| `auth_lookup` 不设 `app.auth_user_id` | `ERROR: unrecognized configuration parameter` ✓ fail-loud 保留 |
| `auth_lookup` 尝试 `INSERT` | `permission denied for table` ✓（GRANT 层拦住，不靠策略） |
| `app_user` 设 `app.tenant_id=2` | 只见租户 2 的行，不受自查策略影响 ✓ |

`auth_lookup` 是**独立的连接池**，用完即回，不与业务连接共用。
它能看到的全部信息是「某个 `tg_user_id` 属于哪些租户、什么角色」——
这正是鉴权需要的最小集，不多一个字节。

> **纪律：带 `tenant_id` 的表上，除租户策略外的任何 PERMISSIVE 策略
> 都必须限定 `TO <角色>`。** 未限定角色的策略（`polroles = '{0}'`，即 PUBLIC）
> 与租户策略构成 OR，直接作废隔离。CI 审计断言 A6 查的就是这一条。

## 四、为何不选其他隔离方案

| 方案 | 不选的理由 |
|---|---|
| schema-per-tenant | 租户数上千后 `pg_class` 膨胀，迁移要遍历所有 schema，连接池难复用 |
| database-per-tenant | 运维成本与租户数线性增长，跨租户统计查询不可能 |
| 仅靠数据访问层强制谓词 | 就是 §二 的 newtype，已采用。但它只覆盖走该层的代码 |
| `security_barrier` 视图 | 复杂度高于 RLS，**且性能更差**，见 §五 |
| 写入触发器校验 `tenant_id` | 只管写不管读，读越权是更常见的泄漏方向 |
| **`CHECK` 约束校验 `tenant_id`** | **是陷阱，绝不能用。见 §4.1** |

RLS 的综合代价最低：一次配置，覆盖读写全路径，对业务代码近乎透明。

### 4.1 `CHECK` 约束方案必须明确否掉，因为它看起来能用

PostgreSQL 假定 `CHECK` 条件是 immutable，但引用非 immutable 表达式
**不被禁止** —— 不报错，于是很容易被当成一条廉价防线写进去。实测：

```sql
ALTER TABLE chk ADD CONSTRAINT c1
  CHECK (tenant_id = current_setting('app.tenant_id')::bigint);
-- ALTER TABLE  ← 接受了
```

插入时它确实拦住了跨租户写入。**但它把定时炸弹埋进了备份：**

```text
pg_dump 导出正常，恢复时：
  ERROR: unrecognized configuration parameter "app.tenant_id"
  CONTEXT: COPY chk, line 1
→ 表结构建出来了，数据一行都进不去。备份等于废的。
```

对比：同样写法用在**生成列**上，PG 会**正确拒绝**
（`generation expression is not immutable`），不留隐患。
只有 `CHECK` 这条路是「接受 + 事后爆炸」。

**这就是 CI 审计 A3 存在的理由** —— 建表时不报错、恢复时才爆的东西，
只能靠静态检查拦。

### 4.2 复合外键：唯一不受权限绕过影响的防线

**复合主键 / 外键都带 `tenant_id`。** 这让跨租户关联在数据库层面
**不可表达**，与 RLS 正交 —— RLS 防越权访问，它防数据本身长出跨租户的边。
实测对比：

```text
单列外键  chi2(par_id) REFERENCES par2(id)
  租户 1 的子行指向租户 2 的父行 → INSERT 0 1  ✗ 静默接受

复合外键  chi(tenant_id, par_id) REFERENCES par(tenant_id, id)
  同样的插入 → ERROR: violates foreign key constraint
               DETAIL: Key (tenant_id, par_id)=(1, 200) is not present  ✓
```

代价是父表要多一条唯一约束、所有唯一约束都得带上 `tenant_id`。
**主键不必变宽** —— 复合 FK 只要求被引用列组上存在唯一约束，
所以父表加一条 `UNIQUE (tenant_id, id)` 即可，主键照旧用单列代理键
（落地形态见 `03-数据模型.md` §1.2 铁律 4）。
这恰好也是将来若上 Citus 做水平分片的前置条件（分布列必须在唯一约束里），
所以现在做等于顺手把扩展路径留出来。

**它的独特价值：超级用户也绕不过。** 已实测 —— 以 `postgres`（超级用户）
身份插入跨租户的复合外键行，同样报 `violates foreign key constraint`。
因为它是**数据模型约束，不是权限机制**：

| 防线 | 超级用户 / `BYPASSRLS` 能绕过吗 |
|---|---|
| RLS 策略 | 能（`FORCE` 也拦不住） |
| `GRANT` 权限 | 能 |
| 复合外键 | **不能** |

这让它成为唯一不受权限绕过影响的租户防线 ——
**但它只覆盖走复合外键的那些边**。指向 `identities` 的 FK 是全库唯一的例外
（`identities.tenant_id` 有意可空，承载演示源的共享身份，
见 `03-数据模型.md` §1.2 与 `02-总体架构.md` §4.1），
那条边的补偿是应用层 403 校验，**属于权限机制，所以超级用户绕得过**。
上表的「不能」不要读成「全库任何一条边都不能」。

**还有一个 NULL 缺口**：

```text
FK 默认 MATCH SIMPLE：任一 FK 列为 NULL → 整个检查被跳过
  chi_null(tenant_id NULL, par_ref 999)  → INSERT 0 1   ✗ 999 根本不存在

tenant_id 声明 NOT NULL：
  → ERROR: null value in column "tenant_id" violates not-null constraint  ✓
```

所以 **`tenant_id` 必须 `NOT NULL`**（铁律 5），
否则复合外键这道防线可以用 NULL 绕开。
（`MATCH FULL` 也能堵，但它要求所有 FK 列同时为 NULL 或同时非 NULL，
语义更受限；`NOT NULL` 更简单直接，本方案用后者。）

## 五、版本要求与性能约束

**版本要求分两条：性能下限 PG 10，安全下限见下。实测于 17.11。**

安全下限来自 CVE-2026-14666（2026-08-13 修复）：PostgreSQL 对角色成员关系、
角色属性、数据库归属的变更**跟踪不完整**，导致查询可以通过计划复用
继续使用已失效的 RLS 策略 —— 即权限刚被收回的用户仍能完成读写，
直到别的事件让缓存失效或连接终止。

```text
安全下限（必须 ≥ 其一）：18.6 / 17.11 / 16.15 / 15.19 / 14.24
```

> 两年内出现过两次同类 CVE（CVE-2024-10976 亦为「计划缓存 × RLS」），
> 说明 **RLS 的正确性依赖 PostgreSQL 其他子系统，而那个面仍在修 bug**。
> 这不是不用 RLS 的理由（它仍是第二道防线），但是
> **不能把 RLS 当作唯一防线**的实证理由 —— 应用层的显式过滤必须照写（§3.6）。
>
> 运维含义：小版本升级对本项目属安全更新，不是可选项。

PG 10 之前，RLS 的实现方式是把受保护表的引用改写成一个标记为
`security_barrier` 的子查询，该子查询**无法被展平**，只能独立规划，
结果是大量场景退化成全表扫描。Tom Lane 2016 年的原话是
"Currently, we don't produce very good plans when row-level security is enabled"。
PG 10 的 commit `215b43cd` 改为给每个 qual 标记 `security_level`，
不再套子查询，这才是 RLS 可用于生产的起点。

> **实务含义**：网上 2017 年之前的 RLS 性能评测若未注明版本，一律视为过时，
> 不要作为决策依据。
>
> **另一个几乎没人提的区分**：PG 10 的这项优化**只覆盖表上的 RLS policy**，
> 显式 `security_barrier` 视图至今（master 仍然如此）走的还是
> 「不可展平子查询」老路，仍会出现 2016 年描述的退化。
> 这是 §四 不选 SB 视图的真正理由 —— 不只是复杂，是更慢。

### 5.1 策略表达式的硬约束

**policy 表达式必须是「列 op 查询期恒定值」，否则必然全表扫描。**

```sql
-- 可索引：current_setting(...) 在查询期是固定值
USING (tenant_id = current_setting('app.tenant_id')::bigint)

-- 不可索引（反例）：两侧都有变量，索引无固定值可查
USING (tenant_id = some_function(tenant_id))
```

模板策略符合前者。**新增策略时必须守住这条**，
一旦策略里出现被保护列本身，索引即失效。

### 5.2 函数索引在 RLS 表上会被直接跳过

已实测，代价很大。`lower()` / `upper()` / `initcap()` 在 PostgreSQL 中
**不是 leakproof**（已核实 PG 17 `pg_proc.proleakproof = f`；2024 年社区
讨论过要不要改，Tom Lane 以「滑坡」为由反对，最终未改。
对比：`texteq` 是 leakproof）。
非 leakproof 函数不能在安全 qual 之前求值，函数索引因此失效：

```text
-- 20 万行，CREATE INDEX fx_lower ON fx (lower(email))
无 RLS：  Index Scan using fx_lower
          Index Cond: (lower(email) = 'user1234@x.com')

有 RLS：  Bitmap Heap Scan on fx
            Recheck Cond: (tenant_id = current_setting('app.tenant_id')::bigint)
            Filter: (lower(email) = 'user1234@x.com')   ← 降级为过滤，索引没用上
            -> Bitmap Index Scan on fx_tenant
```

精确索引查找变成「先按租户捞出全部行，再逐行过滤」。
当前 27 张表**无任何函数索引**，不受影响。
但这是新增索引时的硬约束：**RLS 表上不要依赖函数索引**，
需要大小写不敏感匹配时改用生成列（`GENERATED ALWAYS AS (lower(email)) STORED`）
并在生成列上建普通索引 —— 普通列的等值比较不涉及函数求值。
此条写进代码评审清单。

### 5.3 同一个 leakproof 机制也会打掉 `LIKE`

这比函数索引更容易撞到。§5.2 讲的是函数索引，但根因是 leakproof，因此
**任何非 leakproof 操作符都会失去下推**，跟有没有函数索引无关。
实测 PG 17 的 `pg_proc.proleakproof`：

| 操作符 | leakproof | RLS 表上能否下推 |
|---|---|---|
| `texteq`（`=`） | t | 能 |
| `int4eq` / `int4lt` | t | 能 |
| `textlike`（`LIKE`） | **f** | **不能** |
| `texticlike`（`ILIKE`） | **f** | **不能** |

```text
-- 20 万行，email 上有 text_pattern_ops 索引，受限角色
无 RLS， email LIKE 'user123%'：
  BitmapAnd → lk_tid + lk_email 两个索引都用上   Heap Blocks: 9      0.65 ms

有 RLS， 同一查询：
  Bitmap Index Scan on lk_tid（只剩租户索引）
    Filter: (email ~~ 'user123%')
    Rows Removed by Filter: 3978                 Heap Blocks: 1372   3.00 ms

同一张表、同一上下文，改成 email = 'user1237@x.com'（texteq，leakproof）：
  Index Scan using lk_email_eq                                       0.12 ms
```

即**等值查询正常，`LIKE` 退化成「先按租户捞全部行再逐行过滤」**，
堆块访问量差 150 倍。这不是可以忽略的常数因子。

> 影响评估：当前没有对用户可见文本做 `LIKE` 查询的热路径
> （关键词匹配走应用层 AC 自动机，不走 SQL `LIKE`）。
> **但运维排查时手写 `LIKE` 查大表会明显变慢，这是预期行为不是故障。**
> 若将来确实需要高频 `LIKE`，选项是：查询里显式带 `WHERE tenant_id = $1`
> 让租户条件先收敛（这正是 §3.6 那条纪律的又一个理由），
> 或改用 pg_trgm 索引，或该查询走 owner 角色的专用只读视图。

### 5.4 EXPLAIN 对比要测的三件事

不是笼统「看看有没有退化」：

1. 热路径 —— 扇出层按 `tg_chat_id` 查 `source_subscriptions`，
   确认仍走 `idx_subscription_fanout`，没退化成 Seq Scan。
2. 全库索引扫一遍，确认没有函数索引混进 RLS 表。
3. 确认没有 `LIKE` / `ILIKE` 出现在 RLS 表的热路径查询里。

> 乙类子表（`rule_conditions` / `delivery_logs`）的 EXISTS 策略性能
> **已提前实测，不是风险项** —— PG 17 优化成 hashed SubPlan 只执行一次，
> 20 万行 0.327 ms。详见 `03-数据模型.md` §1.3。

## 六、GRANT 层：RLS 补不了的那部分

三类洞只能在 GRANT 层堵，它们都不在 RLS 的射程内：

| 洞 | 堵法 |
|---|---|
| `TRUNCATE` 清空全部租户（§3.5） | 运行时角色不授予 `TRUNCATE`，清表交给迁移角色 |
| 唯一约束侧信道（§3.5） | 首选让约束带 `tenant_id`；三张做不到的表 `REVOKE ALL FROM app_user` |
| 凭证表被改写 | `tenant_consents` 只 `GRANT SELECT, INSERT`，无 `UPDATE`/`DELETE` |

四个角色，职责不重叠：

```text
tgm_owner     建表与迁移。是表 owner，故必须 FORCE 才受策略约束
app_user      业务运行时。NOSUPERUSER NOBYPASSRLS，非 owner，无 TRUNCATE
auth_lookup   鉴权反查专用（§3.7）。独立连接池，只 SELECT tenant_members
              + 三张会话表的全量 DML（那三张表 app_user 零权限）
platform_ops  运维查 tenant_id IS NULL 的日志行（system_logs / audit_logs）
```

> **`auth_lookup` 的权限面比名字暗示的大** —— 它对
> `bot_console_sessions` / `web_sessions` / `console_login_challenges`
> 有全量 DML，因为这三张表是 `app_user` 完全碰不到的。
> 所以它虽然叫「lookup」，实际是「鉴权域的专属角色」。
> 命名不改（改名会让已写好的 SQL 与文档全部漂移），
> 但**不要**因为名字里有 lookup 就往它身上加更多只读需求 ——
> 需要跨租户只读的场合用 `platform_ops`。

**GRANT 层能被超级用户绕过**（§4.2 的表），所以它是补偿机制而非主机制。
它补的恰好是 RLS 原理上补不了的那部分，两者互补而非重叠。

## 七、凭据隔离：信封加密

```text
KEK（Key Encryption Key）
  存于 AWS KMS / HashiCorp Vault，永不出安全环境
      │
      ├─ 加密 ─> DEK（每租户一个，密文存 credential_keys 表）
                      │
                      └─ AES-256-GCM 加密 ─> identity_secrets.secret_ciphertext
                                             （Bot 是 token 密文，MTProto 是
                                              session 密文，同一列）
                                             identity_secrets.api_hash_ciphertext
```

纪律：内存中的明文凭据用后立即销毁（`zeroize`）。
效果：DBA 仅凭数据库内容无法解密任何租户凭据。

> 对比一种常见的不合格做法：Fernet + 环境变量密钥 ——
> 拿到库和 env 就能全解。单机自用场景下够用，SaaS 不够。

**解密权限收敛**：只有三个组件可以解密凭据 ——
`bot-gateway`、`mtproto-worker`、`delivery-worker`。
`control-plane` 与 `fanout-worker` / `rule-worker` **不具备解密能力**，
**KMS 侧按组件身份授权，不是靠代码自律。**

明文凭据不进 Redis、不进队列消息体、不进日志。
队列里只传 `sender_identity_id`，由消费侧自行解密。

KEK 的两种实现（含本地无 KMS 方案）见 `../eng/01-配置与Secret.md`；
租户凭据的责任边界见 `06-合规与凭据责任.md`。

## 八、权限模型

五级角色：

```text
SUPER_ADMIN     平台运维
TENANT_OWNER    租户所有者
TENANT_ADMIN    租户管理员
MEMBER          成员
VIEWER          只读
```

**关键约束：`SUPER_ADMIN` 默认也看不到明文 Token / Session / 消息正文。**
这条不是客套 —— 它要求平台侧的运维接口在设计时就不提供这些字段，
而非依赖「运维人员不去查」。

```text
所有敏感操作记录：操作人 / 租户 / 对象 / 结果 / 来源 / 时间  → audit_logs
API 查询的 tenant_id 一律从已验证的成员关系推导，
绝不信任请求体或 URL 参数传入的租户标识  ← 越权的头号来源
```

首发阶段 `tenant_members` 实际只有单成员，但角色枚举与鉴权检查点
**现在就按五级写**，避免后续在每个端点补权限判断。

### 8.1 两个入口，一套检查点

控制面有 REST 与 Bot 两条入口（见 `02-总体架构.md` §六），
鉴权必须收敛到同一层，不能各写一遍 —— 两份实现必然漂移，
漂移的那一侧就是越权入口。落地形式：

```text
入口层只负责产出 AuthContext { tenant_id, actor_user_id, role, source }
  REST 入口   ← 会话/Token 解析 → 查 tenant_members
  Bot 入口    ← update.from.id  → 查 tenant_members（经 auth_lookup，§3.7）
业务层只接受 AuthContext，不接受裸 tenant_id
  ← newtype 在此处兑现价值：TenantId 只能从 AuthContext 取出
```

`source` 字段（`web` / `bot`）进 `audit_logs`。Bot 入口没有 IP 可记，
这一列是它唯一的可追溯来源标识，不能省。

### 8.2 限流隔离

按 `sender_identity_id` 分独立队列与令牌桶。理由：Telegram 的限流是
**按身份**计的，若多个租户共用一个发送身份，
一个租户的暴力转发会拖垮所有人。

```text
Redis Stream: delivery:{sender_identity_id}
令牌桶:       ratelimit:{sender_identity_id}
```

## 九、局限

- **审计通过 ≠ 隔离正确。** `USING (true)` 能过全部九条 CI 断言。
  静态检查只能证明「结构上没漏」，证明不了「策略条件写对了」——
  后者只能靠反向测试（`../eng/03-测试策略.md`）。
- 测试环境的超级用户连接会旁路整个 RLS。`sqlx::test` 默认给的就是
  超级用户 pool，用它跑隔离测试会全绿而毫无意义。
  隔离测试必须显式连 `app_user`。
- 本文所有实测都在单机容器上做的，没有覆盖：主从复制下的策略同步、
  逻辑复制订阅端的 RLS 行为、以及托管 PG（RDS / Cloud SQL）
  是否允许 `CREATE ROLE ... NOBYPASSRLS` 与 Event Trigger。
  上云前需要重测。
- `platform_ops` 角色的审计缺一环：它能跨租户读日志，
  但没有机制记录「它读了什么」。当前依赖 PG 自身的 `log_statement`，
  那是运维配置不是应用保证。
- KMS 侧按组件身份授权这件事，文档写了，**但没有验证手段** ——
  没有测试能证明 `control-plane` 真的解不开凭据。
  这一条目前靠部署纪律，是本文最弱的一环。
