## 一、保留期（全表覆盖，30 张）

下表覆盖的表清单与 `03-数据模型.md` 一致。**无遗漏**，
这是刻意的：上一版文档漏登了 `media_archive`，
结果对象存储的账单成了第一个月唯一的意外支出。

| 表 | 保留策略 | 频率 |
|---|---|---|
| `canonical_events` | **未命中（`matched_any = FALSE`）：24h 物理删除**；命中：无 `tenant_events` 引用后才删（见 §1.2） | 每小时 |
| `tenant_events` | free 7 天 / pro 30 天（按 plan）；已处理未命中、无任何任务引用且原始事件完成扇出时，按原始事件的未命中期限提前清理（ADR-0036） | 套餐每日；未命中每小时 |
| `delivery_tasks` | 事件到期后脱钩；DONE/CANCELLED 与有日志 DEAD 在最后日志清理后按 90 天清理，无日志 DEAD 保 30 天 | 每日 |
| `delivery_logs` | 90 天 | 每日 |
| `media_archive` | 记录 180 天；**对象存储文件 3 天**（`object_expires_at`）。实现：fanout 内定时任务，先删对象再置空 key；`staging/` 下超过 1 天的孤儿对象一并删（`crates/app/src/media_cleanup.rs`） | 每小时 |
| `media_relay_jobs` | 不单独清理；随 `canonical_events` 级联删除（`ON DELETE CASCADE`） | — |
| `media_group_members` | 不单独清理；随聚合事件级联删除，成员端以 `NO ACTION` 保护。命中组的成员同步标记 `matched_any`，先确认聚合事件无租户引用并回收，后续批次才回收无引用成员 | — |
| `notify_dedup` | `expires_at` 过期即删 | 每小时 |
| `login_sessions` | `expires_at` 过期即删 | 每 10 分钟 |
| `console_login_challenges` | `expires_at` 过期即删（2 分钟窗口，表常驻近空） | 每 10 分钟 |
| `bot_console_sessions` | 90 天无活动（`updated_at`）即删，下次交互重建 | 每日 |
| `bot_console_updates` | **7 天**（幂等窗口，远大于 Telegram 重投窗口） | 每日 |
| `web_sessions` | `expires_at` 过期即删（滑动续期，绝对上限 30 天） | 每小时 |
| `account_leases` | 不清理（行数 = 身份数） | — |
| `audit_logs` | free 90 天 / 付费 365 天 | 每日 |
| `system_logs` | 90 天 | 每日 |
| `rule_versions` | **与 `audit_logs` 同期**（free 90 天 / 付费 365 天）；当前版本及任何存量任务引用的版本保留，不因到期删除。早于投递记录删会使快照反查失效 | 每日 |
| `tenant_notifications` | SENT / DEAD 自 `terminal_at` 起保留 90 天；PENDING 不主动清理；租户、身份物理删除仍级联清除（ADR-0037） | 每日 |
| `tenant_consents` | **不主动清理**；随 `tenants` 物理删除级联消失（见 §1.3） | — |
| `source_subscriptions` / `target_channels` / `keywords` / `rules` / `rule_replacements` | 永久（逻辑删除 `enabled = FALSE`） | — |
| `tenants` | 永久（生命周期在 `status` 列：`active` / `suspended` / `deleted`，见 `01-产品需求.md` §七） | — |
| `tenant_members` / `rule_conditions` | 永久（**没有逻辑删除，删除即物理删除**；`rule_conditions` 随 `rules` 级联） | — |
| `identities` | 永久（停用走 `status` 列，不是 `enabled`） | — |
| `credential_keys` / `identity_secrets` | 见下方凭据销毁例外 | — |

> **凭据是这张表里唯一的例外，它不「永久」。** `01-产品需求.md` §七 要求
> 租户主动删除身份时**凭据立即销毁**，不等 30 天宽限期 ——
> 也就是 `identity_secrets` 整行物理删除。ADR-0032 起 DEK 跟凭据同行，
> 删行即删 DEK；停写的 `credential_keys` 遗留行仍在该租户再无其他身份时一并删。宽限期保护的是可恢复的业务数据，
> 而把可用的 Telegram 凭据多留 30 天是无法向租户解释的风险敞口。
>
> 代价：宽限期内恢复租户，身份要重新接入一次（重新扫码或重填 Token）。
> 这是有意的 —— 凭据不可恢复，正是「立即销毁」的含义。
>
> 这五张表都没有 `enabled` 列，上一版把它们和另外五张一起写成
> 「逻辑删除 `enabled = FALSE`」是错的。

`enterprise` 档不在保留策略里，因为它不存在 —— 见 `../decisions/ADR-0016-不做私有化部署.md`。

### 1.1 清理纪律

```text
1. 分批删除，每批 ≤ 5000 行，批间 200ms，禁止单条大 DELETE
2. 每次清理写 system_logs（event=cleanup.done，含表名/行数/耗时）
3. canonical_events 增长最快，是首个需要分区的表（RANGE(created_at)）
4. 清理命中过的 canonical_events 必须先确认无引用，见 §1.2
```

第 1 条不是性能考虑，是锁考虑：单条删掉一天的 `canonical_events`
会持有大量行锁并把 WAL 顶起来，采集侧的 `INSERT` 随之变慢 ——
清理任务和采集链路共用同一个库。

媒体对象清理使用独立的 `media_cleanup` 连接写入平台级 `system_logs`，不复用
`app_user`。对象存储删除仍在数据库事务外先行；对象删除成功后，档案 key 清空与
对应的 `cleanup.done` 日志在同一数据库事务提交。档案物理删除与日志也在同一事务；
`staging/` 只有对象存储删除，因此只对成功删除的对象写固定日志。日志写入失败时，
该数据库事务回滚，下一轮按幂等条件重试，不以 tracing 代替完成记录。

鉴权会话首片由独立 `tgm cleanup-auth --category` 命令实现上述三张鉴权表的规则：
`challenges`、`web-sessions`、`bot-sessions`。每批从数据库取 cutoff，按时间和完整键排序，
删除时再次核对到期，避免误删并发续期或刷新的行；恰好 cutoff 算到期。
同类批次用事务级 advisory lock 互斥，重叠执行直接退出；每批删除与固定
`auth_retention/cleanup.done` 日志同事务提交，context 仅含 `table`、`rows`、`elapsed_ms`。
失败回滚，批间不持锁；SIGTERM 取消未提交批次，已提交批次不撤销，后续可重跑。
鉴权日志权限仅覆盖该命令。调度样例与实际部署状态分开验收，
不能因命令可运行就宣称生产周期清理已启用。

租户日志与临时记录由独立 `tgm cleanup-tenant --category` 管理命令处理：
`unmatched-events`、`tenant-events`、`delivery-tasks`、`login-sessions`、`notify-dedup`、`bot-console-updates`、`delivery-logs`、`audit-logs`、`system-logs`、`rule-versions`、`tenant-notifications`。
每类期限与频率沿用 §一；按主键分页枚举全部状态租户，不因 suspended/deleted 而跳过留存。
每批设置事务级租户上下文，使用数据库 cutoff、完整键排序和限批删除；删除时重新检查刷新后的时间字段。
投递日志通过父任务约束租户，不删父任务；审计日志按删除语句快照可见的当前 plan 分档，
不跨批缓存 plan，未知值不按 free 回退。删除语句开始后的套餐变更不追溯恢复已清理记录。
平台级日志不在本命令删除范围；每批删除与当前租户的 `tenant_retention/cleanup.done` 脱敏日志同事务提交。
同租户同类别使用事务锁互斥，批间释放，SIGTERM 取消未提交批次；生产调度状态单独验收。
规则版本须同时满足到期、非当前版本及无任何存量任务引用；停用规则的当前版本也保留。
版本清理持租户、类别排他事务锁，入队共享同键的事务锁，等待后在新语句中复查版本是否存在。
复查与清理要求 READ COMMITTED，不支持的隔离级别直接失败；已有幂等任务不因快照消失重建。
清理先提交造成旧计划失效时，入队整批回滚并重新取规则；当前版本本身缺失属于数据不一致，不能持续重试。
该锁协议覆盖共用入队/清理入口，不约束任意直接 SQL；显式删除规则及其历史的接口语义不变。
本命令不处理共享媒体、租户注销及同意凭证，不能代表全部留存规则已实现。

平台行由独立 `tgm cleanup-platform` 按 `system_logs` 的同一期限回收，
不通过删除租户清理 SQL 的 tenant 条件实现。`platform_cleanup` 仅能读删到期 NULL 租户行的
候选列，不能读取 context、修改日志或接触业务表；固定 `platform_retention/cleanup.done`
日志与每批删除同事务，计数不包含新日志。按数据库 cutoff 与完整键限批并复查，恰好 cutoff 可删；
仅支持 READ COMMITTED，类别事务锁互斥，批间等待，取消或日志失败回滚未提交批次。
CLI 对重叠或中断报告非零退出，不将未执行记为完成。历史清理日志与其他平台日志同样到期回收，
新完成日志不在本批候选中。每日调度样例不代表生产已启用。

通知终态清理只按 `terminal_at`，不按入队时间、重试计划或次数推算；恰好 cutoff 算到期。
SENT 的终态时间等于 `sent_at`，DEAD 用数据库结束时间，PENDING 必须为空。
旧 SENT 沿用成功时间，旧 DEAD 从首次迁移时保守起算，重跑迁移不刷新。
发送入口先锁定 PENDING，再以新语句写终态时间；重复确认不改时间，清理后不重建记录。
通知普通回收期限不阻止租户/身份级联提前删除，也不构成已读或 exactly-once 承诺。

共享原始事件由独立 `tgm cleanup-shared` 命令处理，不复用租户清理角色或业务连接串。
候选必须已经完成扇出、达到 §一/§1.2 的期限、无任何租户投影或存量成员关系，
且没有仍在有效回收期限内的 DOWNLOADING 中转任务；没有回收期限的下载保守保留。
PENDING 和已过回收期限的下载在无引用时可随原始事件回收，不因此修改投递状态或日志。
先删除符合条件的聚合事件并级联释放成员关系，再在后续批次回收成员与 job；媒体档案和对象仍由既有清理处理。
候选按数据库时间和完整键限批，清理按接收身份持排他事务锁，相关写入口持同键共享事务锁，
媒体组另复用原有聚合锁；等待后在新语句中复查，要求 READ COMMITTED。批间释放事务锁。
每批删除与 `shared_retention/cleanup.done` 平台日志同事务，context 仅含表名、原始事件删除数和耗时；
取消回滚未提交批次。引用竞态由非延迟外键阻止，已识别的外键竞争有界重试，其他错误不伪装成清理成功。
命令和调度样例不代表生产已启用。`cleanup-tenant --category unmatched-events` 先清理
已处理未命中且无任何状态任务引用的投影，以原始事件创建时间和 §一未命中期限作为严格年龄门槛，
恰好位于 cutoff 的行保留；投影创建或处理时间不重新起算。未处理、已命中和未完成扇出的投影不走此例外，
其余套餐清理与在途保护不变。清理只影响当前租户，不重置全局 `matched_any`，不脱钩终态任务或缩短日志期限。
投影删除后再由共享命令核对全部引用；媒体组仍先组后成员，有效下载继续保护。
该类别与套餐事件/任务清理共用生命周期排他事务锁，扇出与入队持共享锁。
锁后以新语句复查完成状态：已完成扇出的事件只可返回现存投影，不得重建已删除投影；
已处理事件不接受旧计划新增任务，已有任务重放只返回既有结果。
后台处理区分列表项消失与其他数据库/规则错误，不因并发回收退出或吞掉其他故障。
命令汇总输出 `retained` 表示仍存在的到龄未命中投影，非零须调查未处理、未扇出或任务引用，
不把它当作已回收。重叠未执行和中断时该类别非零退出；日志失败整批回滚。
年龄门槛不是精确时刻硬删除承诺：未完成处理、存量引用、有效下载和失败重跑可延后物理删除。
systemd 小时样例以显式依赖先完成未命中投影清理，再启动独立身份的共享回收；生产周期及告警仍须验收。

### 1.2 命中的 `canonical_events` 不能只按时间删

一条 canonical 可被 N 个租户的 `tenant_events` 同时引用 ——
演示源（`02-总体架构.md` §4.1）就是这个场景。
按单个租户的保留期删 canonical 会误伤其他租户。
原有级联关系已改为 `NO ACTION`，作为阻止误删的数据库防线；应用仍须先检查全部引用：

```sql
DELETE FROM canonical_events ce
WHERE ce.created_at < now() - interval '30 days'
  AND NOT EXISTS (SELECT 1 FROM tenant_events te
                  WHERE te.canonical_event_id = ce.id);
```

时间条件取**最长保留期**（当前 pro 的 30 天）作为兜底上界，
实际删除时机由 `NOT EXISTS` 决定。

媒体组成员还要检查 `media_group_members → 聚合事件 → tenant_events`：
成员自己没有租户投影，不能仅凭成员无直接引用就删除。聚合事件仍被租户引用时，
必须保留成员和其 `media_relay_jobs`，否则会把待投相册裁成残缺组。
成员外键同样为 `NO ACTION`，组端保持级联释放成员关系；成员在关系释放后的下一批回收。

> free 档统一 7 天时这个竞态是潜伏的，**一旦分档保留期不同就会必然发作** ——
> 也就是说，它不会在开发期暴露，会在第一个 pro 租户上线那天暴露。
>
> 前提是 `tenant_events (canonical_event_id)` 上有索引 ——
> `uq_tenant_event` 以 `tenant_id` 为首列，覆盖不了这个查询，需另建：
>
> ```sql
> CREATE INDEX idx_tenant_event_canonical ON tenant_events (canonical_event_id);
> ```

**分级保留的双重收益**：未命中事件 24h 即删，既控制了 `canonical_events`
的体积（这是全库最大的表），又满足数据最小化合规要求。
命中事件保留正文，使 L3 指纹可复算（三级去重见 `03-数据模型.md` §5.3）。

### 1.3 `tenant_consents` 的保留期：不留存（已定案）

**随租户级联删，零 DDL 变更**（ADR-0029，上游是辖区定案 ADR-0028）。
两条 `ON DELETE CASCADE` 都不动（`03-数据模型.md`），
所以租户注销宽限期满、物理删除租户时授权凭证一并消失，
平台对已注销租户没有抗辩材料。**这是认了的代价，不是遗漏。**

支撑这个选择的是 `audit_logs` 的 FK 形状 —— 它的 `tenant_id`
同样是 `ON DELETE CASCADE`。所以归零的是该租户的**全部历史记录**，
审计与凭证同时消失，不存在「能证明他做过什么、
却证明不了他授权过什么」这种更难看的组合。

> **原先记在这里的「留存」方案是错的，不要照着做。**
> 它写的是「FK 改 `ON DELETE SET NULL`，并加 `deleted_tenant_ref` 冗余列」，
> 只覆盖了指向 `tenants` 的那条 FK —— 而 `tenant_consents` 有**两条**
> CASCADE，第二条指向 `tenant_members`，是复合 FK，
> 其 `tenant_id` 参与主键且 `NOT NULL`，按上面那句话改会在
> **第一次真实 DELETE 时**报 not-null violation（`CREATE TABLE` 照样通过）。
> PG 17.11 实测的四种写法与唯一可行的那种（`SET NULL (user_id)`，
> 需同时摘掉 `user_id` 的 `NOT NULL`）记在 ADR-0029 的背景节。

升级路径是**加一张无 FK 的归档表**，不是改现有 FK ——
不动既有 DDL、不动 RLS 策略、不动建表铁律。
触发升级的三个外部信号（首个 DPA 诉求 / 首次已注销租户异议 /
律师明确要求）写在 ADR-0029，本文不复述，以免两处口径漂移。

租户注销流程见 `06-合规与凭据责任.md`。

## 二、按 `sender_id` 的删除请求：走脱敏，不走删行

第三方发言者的内容与 `sender_id` 被存进 `canonical_events`，
但该表五个索引**没有一个覆盖 `sender_id`**，且删行会 `CASCADE`
到其他租户的 `tenant_events`。**定案是两条，都不是「加个索引」**：

```text
1 删除动作 = 脱敏（UPDATE），不是删行（DELETE）
    UPDATE canonical_events
       SET sender_id = NULL, text = NULL, caption = NULL, content_hash = NULL
     WHERE sender_id = $1;
  理由：删行会经 tenant_events.canonical_event_id 的 ON DELETE CASCADE
        连带删掉其他租户仍在保留期内的投递记录（同 §1.2 的竞态）。
        脱敏后行还在、引用链完整，个人数据已不在库里。
  代价：该行的 L3 指纹不可复算（content_hash 一并清空）——
        可接受，指纹只服务于去重，不是业务数据。

2 首发不加 sender_id 索引，接受全表扫描
    稳态 20~30 万行（§三），一次顺序扫描在秒级；
    删除请求是低频人工流程，不在请求路径上。
  触发加索引的条件（任一即加）：
    a canonical_events 触及 §三 的分区阈值（5000 万行 / 20GB）
    b 删除请求变成常规运营动作而非个例
  加的时候是 CREATE INDEX ... (sender_id) WHERE sender_id IS NOT NULL
  —— 部分索引，因为脱敏后的行不需要再被检索到。
```

> **`tenant_events` 与 `delivery_logs` 侧不需要单独处理**：
> 前者不存 `sender_id`（靠 `canonical_event_id` 回连，`idx_tenant_event_canonical`
> 已在 §1.2 建好），后者隔了两层。脱敏只改 `canonical_events` 一张表，这是
> 「一条消息全平台只存一份」的设计**在这件事上的红利** —— 单点脱敏，全平台生效。
>
> **但对外答复仍须诚实**：脱敏不能撤回已经投递到租户频道里的消息。
> 这句话必须进隐私政策，见 `06-合规与凭据责任.md`。

## 三、容量与分区预案

```text
假设：1000 个活跃订阅、日均每订阅 200 条消息
  canonical_events  ≈ 20 万/日（去重后）→ 未命中 24h 删，稳态约 20~30 万行
  tenant_events     ≈ 视订阅重叠度，最坏 = 订阅数 × 消息数
  delivery_tasks    ≈ 命中率 5% → 1 万/日

分区触发阈值：canonical_events 或 tenant_events 超 5000 万行 / 20GB
  → RANGE(created_at) 按月分区，配 pg_partman
  → 清理由 DELETE 改为 DROP PARTITION
```

稳态只有 20~30 万行这件事值得记住：它意味着**首发阶段几乎所有
「性能优化」都是过早优化**。分区、`sender_id` 索引、读写分离，
全部挂在阈值上，不提前做。

### 3.1 分区与 RLS 的冲突（`tenant_events` 分区前必读）

`canonical_events` 不带 RLS，分区无碍。但 **`tenant_events` 带 RLS，
分区会打开一个真实缺口**，已实测（PG 17.11）：

```text
父表 ENABLE + FORCE ROW LEVEL SECURITY，建策略
  pg_class.relrowsecurity:  te(父)=t   te_2026_09=f   te_2026_10=f
                                        ^^^^^^^^^^^^^^^^^^^^^^^^^^
                            分区一律为 f，且在父表启用 RLS 之后新建的分区同样是 f

经父表查询（租户 1）：只返回租户 1 的行          ✓
直接查分区   （租户 1）：租户 1 和租户 2 的行都返回  ✗ 跨租户泄漏
```

这是 PostgreSQL 的**设计行为**，不是 bug：父表策略只在「经父表查询」时应用；
直接指名子表时，父表策略被忽略。文档写在**继承**章节而非 RLS 章节，很容易漏掉。

**三条应对纪律**：

1. **应用代码永远查父表，不直接指名分区。** Repo 层本来就这么做，
   风险来自运维脚本和将来的清理任务。
2. **每个新分区建完必须立刻套策略。** pg_partman 自动建分区时不会带上 RLS，
   所以不能只靠 partman 的模板表 —— 需要 Event Trigger 兜底：

   ```sql
   CREATE OR REPLACE FUNCTION rls_auto_enable() RETURNS event_trigger AS $$
   DECLARE cmd record;
   BEGIN
     FOR cmd IN SELECT * FROM pg_event_trigger_ddl_commands()
                WHERE object_type IN ('table','partitioned table')
     LOOP
       -- 临时表必须跳过，见下方「作用域里的意外成员」
       CONTINUE WHEN (SELECT relpersistence FROM pg_class WHERE oid = cmd.objid) = 't';
       EXECUTE format('ALTER TABLE %s ENABLE ROW LEVEL SECURITY', cmd.object_identity);
       EXECUTE format('ALTER TABLE %s FORCE  ROW LEVEL SECURITY', cmd.object_identity);
     END LOOP;
   END $$ LANGUAGE plpgsql;

   CREATE EVENT TRIGGER ensure_rls ON ddl_command_end
     WHEN TAG IN ('CREATE TABLE','CREATE TABLE AS') EXECUTE FUNCTION rls_auto_enable();
   ```

   > **作用域里的意外成员：临时表。** 上面那句 `CONTINUE WHEN` 是补的 ——
   > 本片段初版没有它，被原样抄进 `migrations/0012_event_trigger.sql`，
   > 结果**任何 `CREATE TEMP TABLE` 之后对它的写入都被 RLS 拒**
   > （临时表不可能有策略：策略含表名，而临时表的名字是运行时才有的；
   > FORCE + 零策略 = 拒绝一切写入）。已修在 `migrations/0013`，
   > 测试 R24（`../eng/03-测试策略.md` §3.4）。
   >
   > **这个缺陷对以超级用户跑的一切检查都是隐形的**（超级用户 bypass RLS），
   > 而迁移与 `tgm audit-rls` 都以 `postgres` 跑 —— 它是被一条无关探针撞出来的。
   > `'u'`（UNLOGGED）不排除：它是持久表，只是不写 WAL，该受 RLS 管。
   >
   > 判据留给下一个写这类兜底的人：**「对所有 X 一律做 Y」的机制，
   > 要先列出 X 这个类型里你没想到的成员** —— 作用域是按类型算的，
   > 而类型里总有那个成员。

   注意 Event Trigger 只能补 `ENABLE`/`FORCE`，**策略本身仍需单独创建**
   （策略含表名，无法泛化）。

   **执行身份：`CREATE EVENT TRIGGER` 要超级用户，`tgm_owner` 不行**（PG 的硬限制）。
   上面这段片段初版没说这件事，而迁移的其余文件全都跑在 `SET ROLE tgm_owner` 之下
   （`../eng/02-本地环境与迁移.md` §3.0：owner 决定 `FORCE` 是真的还是装饰）——
   照字面把这段放进去会失败。落地的写法是建完函数后 `RESET ROLE` 再建触发器，
   见 `migrations/0012_event_trigger.sql`。函数本身归 `tgm_owner` 是对的，
   它以 `SECURITY INVOKER` 跑在触发它的那次 DDL 的身份下。
3. **分区上线前，把「直接查分区」加入隔离测试**（`../eng/03-测试策略.md`）。
   这是分区工作包自带的验收项，不是可选加固。

> **结论**：分区推迟到确实超阈值再做，不提前优化。
> 届时这三条纪律是前置条件。

### 3.2 建表与迁移的两个静默陷阱（已实测）

```text
1. CREATE TABLE cp (LIKE orig INCLUDING ALL)  →  relrowsecurity = f，零策略
   INCLUDING ALL 的清单里没有 RLS 这一项。用 LIKE 造表 = RLS 静默丢失。

2. 策略可以存在于一张 RLS 已关闭的表上，此时策略被完全忽略。
   实测：DISABLE ROW LEVEL SECURITY 后 relrowsecurity=f，但 pg_policy 仍有 1 条记录。
   → 只查 pg_policy 有无记录的审计脚本会漏掉这种表。
```

两条的共同点是**都不报错**。因此 CI 的 RLS 审计必须查
`pg_class.relrowsecurity`，**不能只查 `pg_policy` 是否有记录** ——
审计口径见 `../eng/04-CI门禁.md`。

## 四、局限

- 容量估算基于假设的订阅数与消息量，没有真实流量校准。
  首发后第一件事是把实际 `canonical_events` 日增量记进 `system_logs`，
  用真数替换本文 §三 的假设。
- `tenant_events` 的最坏情况（订阅数 × 消息数）没有给出缓解方案。
  它取决于租户间订阅重叠度，而重叠度只能观测、不能预测。
- 对象存储 3 天的文件保留期没有区分媒体大小。
  一个 2 GB 的视频和一张 20 KB 的图占用同一条规则，成本模型是线性外推的。
- 清理任务的失败重试没有设计。当前假设是「下一轮清理会捡起上一轮漏的」，
  这对时间条件型清理成立，对 §1.2 的 `NOT EXISTS` 型清理也成立，
  但对「对象存储删了、库里记录没删」这种跨系统半成功状态不成立。
