# 范围与非目标

> 这份文档定义边界。判断一个需求该不该做，先看这里。

---

## 一、一句话定位

帮内容运营者把分散在多个 Telegram 频道的信息，按自己的规则筛选、改写、
汇聚到自己的频道或私聊。

多租户 SaaS 形态，不是单人自用工具。

---

## 二、三条边界

| 做 | 不做 |
|---|---|
| 采集租户**有权访问**的频道 | 全网发现、搜全站、爬公开目录 |
| 按关键词/规则筛选与改写 | 历史批量回溯（见 §4.2，是「做不了」不是「不做」） |
| 投递到租户**自己控制**的频道或其成员私聊 | 公开再分发、代客运营公开频道 |

这三条不只是文档承诺，**必须在源订阅与目标端点上做强制校验**。
`source_subscriptions.authorized_by`（拉群授权链路写入）是「有权访问」的
技术凭证，它必须是**准入条件，不只是审计字段** ——
两者的差别是：审计字段允许为空，准入条件不允许。

---

## 三、首发 / 上线 / 商用

这三个词在讨论里经常被混用，混用会导致「首发了为什么不能给客户用」这种争论。
定义如下，`plan/` 与 `ops/` 都按这套口径：

```text
首发   = 可由平台手工开通的种子客户使用的系统
        不是可自助注册的公开 SaaS
        此时的缺口见下方「首发必须对客披露的五条」

上线   = 具备可运营性：备份与一次真实恢复演练、三个核心指标与告警、
        RPO/RTO 已定义并写入对客文档、值班安排已明示

商用   = 三条同时成立：
        至少 1 个种子客户在真实流量下累计运行 ≥ 2 周且无 P1 事故、
        自助注册放开、计费生效
```

**首发不等于上线。** 首发交付的系统自己都说不建议给外部用户用，
这是排期结果不是缺陷 —— 可运营性在上线阶段，自助注册与计费在商用阶段。
对外沟通时必须用「上线」这个词，不要用「首发」。

**「商用」的三条是合取，不是任选。** 只有运行记录没有自助注册，
那是「种子客户在用」而不是商用；只有自助注册没有那 2 周记录，
是把未经真实流量验证的系统对公众放开。两种都不算。

### 3.1 首发必须对客披露的五条

**这是该清单的唯一定义处。** `plan/`、`ops/`、`decisions/` 引用本节，
不各自复述 —— 之前 `ops/01` 与 ADR-0025 各写了「三条」且只有一条重合，
而这份清单会进 G4 交付的对客文档，两个版本同时到客户手里就是信任问题。

```text
1 单实例单点：进程挂了就停服，没有自动接管（ADR-0025）
2 无值班：1 人全职意味着没有人保证在时限内响应
3 无 SLO：因此也无 SLA
4 RPO / RTO 未定义
5 容量未实测：2 vCPU / 4 GB 是估算，超限表现为 OOM 而非降级
```

第 1、5 条都是 ADR-0025 的直接后果，第 2、3、4 条是排期结果。
**五条要一起给，不能挑。** 客户拿这五条判断要不要把关键业务放上来 ——
藏起来会在第一次事故时变成信任问题。

上线（G5）消掉第 3、4 条并给出值班安排（第 2 条可以是「明示无人值班」），
第 1、5 条要到演进期的水平扩展与容量实测才消掉。

## 四、明确不做

### 4.1 不做清单

每条给理由。写在这里是为了不被每隔三个月重新提一次。

| 不做 | 理由 |
|---|---|
| 图片/视频水印 | 同类项目有，但 issue 区无人讨论。需 FFmpeg 依赖，成本与收益不成比例 |
| 图片 OCR | 同上。且 OCR 结果参与关键词匹配会让「为什么命中」无法解释 |
| `ONLY_TOP` 匹配模式 | `stop_processing` 表达力更强且可截断在任意位置 |
| 单规则挂多关键词 | 冲突检查将从 SQL 层搬到应用层，代价大于收益 |
| 邮箱 + 口令登录 | 会引进口令哈希、找回、发信、邮箱验证、撞库防护一整套，且与 Telegram 身份并行两套账号 |
| MTProto 扫码兼作控制台登录 | 那会逼用户为进后台授权整个 Telegram 账号，等于交出全部私聊读取权 |
| 出站 Webhook | 三项连带成本，见 §4.3 |
| 私有化交付 | 见 ADR-0016。企业档已砍，私有化连需求来源都没了 |
| 官方 Bot 托管代持（共享接收身份） | 见 ADR-0014。代之以平台自营演示源，投递侧完全隔离 |

### 4.2 历史消息回溯：不是不做，是做不了

同类项目有 past mode，也确实有人要。但本方案的整个事件模型是**纯流式**的 ——
未命中任何规则的原始事件 24 小时物理删除。要支持回溯需要四件东西：

```text
一条与实时链路并行的批量拉取路径（MTProto 翻页，Bot API 拿不到历史）
回溯任务的进度与断点持久化
回溯产出的事件如何避免与实时链路重复（L1 幂等键能兜住，但需实测）
回溯的限流与实时投递配额如何隔离
```

这是独立立项级别的任务。**不要在首发或上线阶段里顺手加。**

> 顺带确认一条设计的价值：同类项目有 issue 抱怨「没命中关键词的消息也写进数据库，
> 需要频繁清理」。本方案未命中 24h 物理删的设计正好避开了这个坑 ——
> 代价就是回溯做不了。这是一次有意的取舍。

### 4.3 出站 Webhook 不做的三条理由

不是工作量问题（发个 POST 很便宜），是三项连带成本：

```text
1 出站 HTTP 让平台变成 SSRF 代理 —— 租户填内网地址，平台替他探测
  要拦就得做出站白名单 / DNS 重绑定防护，这比投递本身贵
2 重试语义翻倍 —— 现在的 DLQ 与退避是按 Telegram 限流设计的，
  租户端点的超时与 5xx 是另一套模型
3 它把合规面从「Telegram 内搬运」扩大到「把 Telegram 内容导出到任意系统」，
  而条款限制正落在这个方向上
```

投递目标表只有 `tg_chat_id` 一列，**库结构本身就不支持 HTTP 目标**。
若将来要做，前置条件是出站白名单 + 独立重试队列 + 律师确认。
**当前不在任何阶段的范围内，也不出现在定价页。**

## 五、来源标签

`spec/01` 的功能清单每项带一个来源标签：

```text
[继承]  早期单租户方案已有，本方案保留
[补缺]  对照同类项目实测功能表后发现的缺口（见 §六）
[新增]  多租户形态引入，单租户工具不需要
```

`[新增]` 项**没有外部参照** —— 配额、租户隔离、审计这三类功能在被对照的
项目里都找不到先例，只能自己论证。看到 `[新增]` 就意味着这条的依据是内部推理，
比 `[继承]`/`[补缺]` 更值得质疑。

## 六、对照过的项目

`[补缺]` 项来自对以下项目**实际功能表**的对照（2026-09 实查 GitHub API
与源码，非凭记忆）：

| 项目 | ⭐ | 栈 | 最后推送 | 取用了什么 |
|---|---:|---|---|---|
| Heavrnl/TelegramForwarder | 1267 | Python | 2026-02 | 正文改写、批量导入导出、规则复制、扩展名过滤 |
| aahnik/tgcf | 1623 | Python + Streamlit | **2024-05 停更** | Replace 插件的形状、past mode 的定性 |
| Riniba/TelegramMonitor | 315 | ASP.NET Core | 2026-04 | 四种匹配模式、未命中入库的反面教材 |
| dgtlmoon/changedetection.io | 34376 | Python/Jinja2 | 2026-09 | UI 信息架构 |
| miniflux/v2 | 9712 | Go SSR | 2026-09 | 服务端渲染的技术栈先例 |

**判断「高频需求」的依据是命令数量与 issue 评论数，不是 README 的排版。**
Heavrnl 为关键词操作提供了 11 个命令、为替换规则提供了 6 个 ——
这个数量本身就是需求强度的证据。

反过来，tgcf 的水印与 OCR 在 README 里位置显眼，但 issue 区无人讨论，
判定为「看起来有用、实际没人用」，进 §4.1 的不做清单。

> **对照的局限**：以上都是单租户自用工具，没有一个是多租户 SaaS。

## 七、局限

- §六 的星数与推送时间是 2026-09 的快照，会过期
- §三 的「商用」定义里「无 P1 事故」需要先有事故分级，见 `ops/01`
- §4.1 的不做清单不是永久封闭的，但推翻任何一条都要走 `decisions/` 的流程，
  不能在别的文档里悄悄加回来
