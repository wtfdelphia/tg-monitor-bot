# 部署与运行时

本文是**镜像、进程编排、运行时规格与网络边界的唯一定义处**。

`../eng/02-本地环境与迁移.md` 写的是**本地**环境（compose、端口、角色初始化），
本文写的是**生产**形态。两者共用 PgBouncer 那几个参数，
参数的实测理由在 `eng/02`，不在这里重复。

部署形态 A / B 的定义与「未过混沌测试不上多实例」这条约束
在 `../spec/02-总体架构.md` §七 —— 本文只写落地。

## 一、镜像：一个镜像，多个 role

`../eng/00-工程约定.md` §一 已定单二进制 + subcommand，
所以**不构建 7 个镜像，只构建 1 个**，靠 `--role` 与环境变量区分进程。

```dockerfile
# 构建阶段
FROM rust:1.98-bookworm AS builder
WORKDIR /src
COPY . .
# SQLX_OFFLINE 让编译期校验读 .sqlx/ 而不连库（eng/00 §6.1）
ENV SQLX_OFFLINE=true
RUN cargo build --release --locked -p tgm

# 运行阶段
FROM debian:bookworm-slim
RUN apt-get update && apt-get install -y --no-install-recommends \
        ca-certificates && rm -rf /var/lib/apt/lists/*
COPY --from=builder /src/target/release/tgm /usr/local/bin/tgm
USER 10001:10001
ENTRYPOINT ["/usr/local/bin/tgm"]
```

四条选择都有理由，不是模板抄来的：

```text
SQLX_OFFLINE=true    构建时不连数据库。少了它，镜像构建就依赖一个可达的 PG，
                     CI 与生产构建都会变脆（eng/00 §6.1 要求 .sqlx/ 提交，
                     就是为了这一步）
--locked             拒绝在构建时改 Cargo.lock。否则「同一个 commit
                     构建两次得到不同依赖」，出事时无法复现
非 root（10001）     容器里唯一需要写的地方是 /tmp，不需要 root。
                     媒体中转是流式的，不落磁盘（spec/02 §4.2）
debian-slim 而非     grammers / aws-sdk 依赖 OpenSSL 与系统 CA。
alpine               musl 静态链接要额外处理，省下的几十 MB 不值这个麻烦
```

> **不做多阶段缓存优化（`cargo-chef` 之类）**。它省的是 CI 时间，
> 代价是构建脚本多一层间接。单人项目下 CI 慢几分钟不是瓶颈，
> 构建脚本看不懂才是。要加的时机是「CI 时间成为日常阻碍」那天，不是现在。

镜像里**不含** `.env`、不含任何 secret，理由与 `../eng/01-配置与Secret.md` §一 同。

## 二、进程编排（形态 A）

形态 A 是首发锁定的形态。四个逻辑部署单元，不是七个 —— 组件边界是代码边界。

```text
tgm serve --role control-plane      axum + bot-console（控制 Bot Webhook）
tgm serve --role bot-gateway        数据 Bot Webhook
tgm serve --role mtproto-worker     持账号租约，grammers 连接（已接入运行链，未经真机验证）
tgm serve --role fanout             扇出 worker（当前已接入运行链）
tgm serve --role rule               规则 worker（当前已接入运行链）
tgm serve --role delivery           投递 worker，以租户数据 Bot 经 MTProto 发送；独立执行目标只读自检
```

形态 A 的 `pipeline` 是 `fanout + rule + delivery` 的逻辑部署单元，不是合法的
`--role` 值。当前 CLI 已接入 `control-plane`、`bot-gateway`、`mtproto-worker`、
`fanout`、`rule`、`delivery`。`delivery` 用平台 `api_id`（`TGM_PLATFORM_API_ID` /
`TGM_PLATFORM_API_HASH`）以租户 Bot Token 执行 `bot_sign_in`，登录后 session 加密落库、重启先复用，不再重复登录
（`../decisions/ADR-0034-投递Bot的session加密落库.md`），
只接 `kind = 'bot'` 的发送身份（`../decisions/ADR-0033-投递Bot经MTProto登录.md`）。
`mtproto-worker` 只接管已有 session 与 `api_id` 的租户身份；首发形态 A 固定单实例，
多实例前置的混沌清单见 `../spec/08-账号接入.md` §4.5。
真正合并为单进程前，需要补齐生命周期编排、凭据边界与退出传播；在此之前按已接入的
角色分别启动。组件之间只经 PG 与 Redis 交接（`../spec/02-总体架构.md` §1.1），
所以拆开时不需要改交接代码。

目标自检随 delivery 启动，独立于 MTProto 登录和正常投递循环，每次最多一个在途检查。
只访问 Telegram Bot API 的 `getChat` / `getChatMember`，保留默认 HTTPS 地址，不提供生产 URL 覆盖项。
进程退出后未回写的任务待租约到期恢复；发送身份上的执行保留与限流冷却持久化，不用清库解除等待。
部署时先用 `tgm migrate` 应用迁移，再重启 delivery 与 control-plane。缺少 delivery 时页面保持待检查，不得据此宣称可发送。

依赖服务：PostgreSQL 17.11+、PgBouncer 1.25.1+、Redis、对象存储（S3 或 MinIO）。
版本下限的理由分别是 CVE-2026-14666 与 CVE-2025-12819（`../eng/02-本地环境与迁移.md` §一）。

### 2.1 启动顺序

```text
1  tgm migrate            用 TGM_DB_URL_OWNER，跑完即结束，不常驻
2  tgm audit-rls          迁移后立刻跑一次，失败则不启动业务进程
3  四个 serve 进程        任意顺序，它们互不依赖（无 RPC）
```

第 2 步是**部署流水线的一部分，不只是 CI 的一部分**。
CI 验的是「迁移脚本产出的结构合规」，这里验的是「这个环境的库合规」——
两者会不一致，比如有人手工连上生产库做过一次 `ALTER`。

第 3 步的「任意顺序」是无 RPC 换来的：任何进程先起都不会因为别的没起而失败，
最坏情况是队列积压，扫库兜底会补上（`../spec/02-总体架构.md` §1.1）。

租户暂停/恢复不由常驻业务进程执行，使用独立 `tenant_lifecycle` 角色和
`TGM_DB_URL_TENANT_LIFECYCLE` 环境文件运行：

1. 先执行 `tgm migrate` 和 `tgm audit-rls`，确认 `C14`；连接串必须直连 PostgreSQL，
   不得使用 owner、业务或清理角色，也不得与 `DATABASE_URL`、Telegram、KMS 或对象存储凭据同环境。
2. 手工执行 `tgm tenant-lifecycle suspend <tenant_id>`。命令先提交暂停屏障，再按批次取消
   PENDING/FAILED 任务并过期租约；SENDING 不伪造为未发送，排空未完成时返回非零。
3. 只有核对外部结果、在线执行标记和租约均已收敛后，才执行
   `tgm tenant-lifecycle resume <tenant_id>`。恢复不会复活已取消任务，也不能恢复 deleted 租户。
4. 本地命令与隔离测试不代表生产启用；生产还须核对直连、角色属性、环境文件权限、进程退出和
   `pg_stat_activity` 排空证据。逻辑注销、凭据销毁、宽限期和物理删除不在本片范围。

鉴权会话留存使用独立管理进程，不加入持有业务或 KMS 凭据的常驻服务：

1. 先按生产路径迁移、运行 `audit-rls`，确认 `auth_cleanup` 的最小权限通过 `C8`。
   迁移不设置生产口令，由运行环境为该角色单独配置并注入；不要复用 owner 或 `auth_lookup`。
2. 建立无登录、无其他服务组身份的系统用户和组 `tgm-auth-cleanup`；确保
   `/usr/local/bin/tgm` 是已验收的二进制。将 `deploy/systemd/auth-cleanup.env.example`
   配置为 `/etc/tgm/auth-cleanup.env`，替换示例连接串，文件归 root、权限 0600。
   只放该命令的专用配置，不包含 `DATABASE_URL`、业务、KMS、Telegram 或对象存储凭据。
3. 将 `deploy/systemd/tgm-auth-cleanup@.service` 和三个 `.timer` 安装至
   `/etc/systemd/system/`，执行 `systemctl daemon-reload`。先分别手动启动
   `tgm-auth-cleanup@challenges.service`、`tgm-auth-cleanup@web-sessions.service`、
   `tgm-auth-cleanup@bot-sessions.service`，核对退出状态及平台清理日志。
4. 确认后再启用调度：

   ```bash
   systemctl enable --now tgm-auth-cleanup-challenges.timer tgm-auth-cleanup-web-sessions.timer tgm-auth-cleanup-bot-sessions.timer
   ```

   用 `systemctl list-timers 'tgm-auth-cleanup-*'` 检查下次触发时间；周期引用
   `../spec/04-数据生命周期与容量.md` §一。部署前用 `systemd-analyze verify` 检查单位，
   用 `systemd-analyze calendar` 核对日历表达式及服务器时区。
5. 独立环境不从业务服务继承凭据；启动检查要求直接以 `auth_cleanup` 登录。
   同类重叠正常退出、不写本批日志；SQL 或日志写入失败非零退出并整批回滚。
   停止使用 `systemctl stop tgm-auth-cleanup@<category>.service`，
   `KillMode=control-group` 清理本次服务子进程；未提交批次回滚，已提交批次保持。

仓库提供的调度样例与本地临时库调度验证不代表生产启用。生产验收还须在目标机器核对
独立身份、环境文件权限、实际定时触发、失败告警和停止后无残留；未执行时不得记完成。
关闭周期任务先停用三个 timer，再等待或停止对应 service；不删业务库或卷。

租户日志与临时记录清理同样使用独立进程，不能继承鉴权清理或业务环境：

1. 先执行生产迁移和 `audit-rls`，核对 `tenant_cleanup` 的 `C9`；生产口令由 Secret 单独注入。
2. 创建无登录、无业务组成员关系的系统用户/组 `tgm-tenant-cleanup`，配置
   `/etc/tgm/tenant-cleanup.env`（root 所有、0600），内容参考 `deploy/systemd/tenant-cleanup.env.example`。
   只允许专用连接串、profile 和可选日志过滤，不放其他凭据。
3. 将 `deploy/systemd/tgm-tenant-cleanup@.service` 与同前缀的各类别 timer 安装到
   `/etc/systemd/system/`，先 verify 和手动启动各固定类别，核对删除计数、非目标记录保留与日志。
   类别为 tenant-events、delivery-tasks、login-sessions、notify-dedup、bot-console-updates、delivery-logs、audit-logs、system-logs、rule-versions、tenant-notifications；频率见 `spec/04` §一。
   启用 rule-versions 前先部署带共享锁和版本复查的入队实现，停止旧版规则 worker，
   确认没有绕过该协议的生产入队进程；数据库连接使用 READ COMMITTED。
4. 确认后分别启用 `tgm-tenant-cleanup-<category>.timer`，用 `systemctl list-timers 'tgm-tenant-cleanup-*'`
   核对下次触发和机器时区。失败非零并整批回滚；停止先停 timer，再停对应 service。
5. 本地临时 user timer 不证明生产专用身份、文件权限、真实周期及告警已验收；部署时逐项留证。
   平台日志、事件、投递任务和租户注销不在此命令范围；不要因本命令可用而宣布全部生命周期完成。

共享事件留存使用独立 `tgm-shared-cleanup` 系统用户和 `/etc/tgm/shared-cleanup.env`（root 所有、0600），
内容参考 `deploy/systemd/shared-cleanup.env.example`，不得继承业务或其他清理凭据。
先执行迁移及 `audit-rls`，确认 `C10`/`C11`，再部署已包含共享生命周期锁的所有写入进程；
不能在旧 worker 仍运行时先启用清理。安装 `tgm-shared-cleanup.service` 与 `.timer` 后，
先做 `systemd-analyze verify` 和手动执行，核对计数、非目标引用保留及平台日志，再启用每小时 timer。
停止先停 timer，再停止或等待 service，未提交批次回滚。仓库样例与本地测试不代表生产实际调度已通过验收。

ADR-0036 起共享 service 显式 `Requires`/`After` `tgm-tenant-cleanup@unmatched-events.service`：
每次由小时 timer 或手工启动共享 service 时，先以租户清理身份回收无任务的已处理未命中投影。
须一并安装租户清理模板、独立系统用户和各自环境文件；不把两条数据库连接串交给同一进程。
部署前执行追加迁移并确认 `C9`，停止旧版扇出/规则进程，换成带扇出终态及处理终态复查的版本后再启用。
前置失败、重叠未执行或中断非零退出，依赖失败不启动共享 service；排障后重跑共享 service 即可重走顺序。
前置输出 `retained` 非零表示仍有受保护投影，须检查积压或任务引用；共享命令照常保护引用，不强删以补齐计数。
只有两阶段日志、退出状态和受保护记录均核对过，才能登记该轮结果；生产小时触发与告警另行留证。

ADR-0037 的通知留存迁移前，核对存量规模与锁窗口，停止旧版通知发送循环（当前内嵌 control-plane）。
执行追加迁移与保守回填，确认 `C9` 后只启动新版；旧版不写终态时间，会被新 CHECK 拒绝，不能混跑。
再手工执行 `tenant-notifications`，核对到期终态、长期 PENDING 和新终态保留及事务日志后启用对应 timer。
独立系统用户、Secret 权限、实际日周期及告警须另行生产验收；本地样例或临时 user timer 不能替代。

平台系统日志由独立 `tgm-platform-cleanup` 系统用户和 `/etc/tgm/platform-cleanup.env`
处理，文件归 root、权限 0600，参考 `deploy/systemd/platform-cleanup.env.example`，
不得继承业务或其他清理凭据。先走生产迁移并确认 `C13`，再验证
`tgm-platform-cleanup.service` 与 `.timer`；手工执行 `tgm cleanup-platform`，
核对到期平台行、近期平台行、租户哨兵、事务日志和退出状态后，才启用每日 timer。
重叠、中断和失败均非零退出，先停止 timer，再停止 service；重跑不恢复已提交删除。
实际系统用户、Secret 权限、日周期、告警及生产启用须另行验收。

已注销租户的物理清理使用独立 `tgm-tenant-purge` 系统用户和
`/etc/tgm/tenant-purge.env`（root 所有、0600），内容参考
`deploy/systemd/tenant-purge.env.example`，只注入 `TGM_PROFILE`、
`TGM_DB_URL_TENANT_PURGE` 和可选 `RUST_LOG`。该连接必须直接登录
`tenant_purge`，不能使用业务、owner、其他清理角色，也不能经过 PgBouncer。

1. 先完成生产迁移、`audit-rls`、C16/C17 和物理清理专项反向测试；生产环境不得以真实租户作为探针。
2. 创建无登录、无其他服务组身份的 `tgm-tenant-purge` 系统用户，安装
   `deploy/systemd/tgm-tenant-purge.service` 与 `deploy/systemd/tgm-tenant-purge.timer`，先执行
   `systemd-analyze verify` 和 `systemd-analyze calendar daily`。
3. 先手工运行 `tgm purge-deleted-tenants --tenant-id <探针租户>`，核对类别顺序、阻塞时非零退出、
   重跑结果和根行删除日志；确认后再启用 `tgm-tenant-purge.timer`。默认每日调度不改变数据库的 30 天恢复窗口。
4. 失败、锁冲突、共享引用、在途任务、未到期和中断均不得报告成功；停止时先停 timer，再停止 service。
   已提交的短批次不会回滚，下一轮从当前数据库状态继续。生产周期、告警、凭据文件权限和恢复演练仍须单独留证，
   本地样例和临时 timer 不代表生产启用。

## 三、网络边界：控制面不直接见公网

```text
                 公网
                   │  TLS
            ┌──────▼───────┐
            │ 反向代理      │  TLS 终止 / 限流 / 访问日志
            └──────┬───────┘
                   │  HTTP，回环或内网
      ┌────────────┴────────────┐
      ▼                         ▼
control-plane              bot-gateway
(127.0.0.1:8080)           (Webhook 端点)
```

**控制面进程自己不做 TLS 终止。** `../eng/01-配置与Secret.md` §二 的
`TGM_LISTEN_ADDR` 默认绑回环就是这条边界的执行形式。

两个 Webhook 端点必须经反向代理暴露，且**路径不可猜**（含随机段）：

```text
/hook/data/<random>      数据 Bot     → bot-gateway
/hook/console/<random>   控制 Bot     → control-plane
```

路径随机只是降噪，**鉴权仍然完全押在 `secret_token` 上**
（`../spec/02-总体架构.md` §6.4）。这里要明说，
否则容易误以为「路径猜不到」是一道防线 —— 它不是，
Telegram 的请求会带上 `X-Telegram-Bot-Api-Secret-Token`，
校验它是唯一真实的门。反向代理层不要试图替应用做这个校验
（它拿不到每个 Bot 的 token，只会做出一套半对的规则）。

不暴露给公网的：`/metrics`（`../spec/07-接口契约.md`）、PgBouncer、
PostgreSQL、Redis、MinIO。Swagger UI 在生产构建里根本不编译
（`../spec/07-接口契约.md` §2.2）。

## 四、PgBouncer 生产配置

参数与本地一致（`../eng/02-本地环境与迁移.md` §一），但有两处生产才有的考量：

```ini
pool_mode = transaction
server_reset_query_always = 1     ; 安全配置，不是调优
max_prepared_statements = 200
default_pool_size = 20            ; 见下
max_client_conn = 200
```

> **`server_reset_query_always = 1` 在生产比在本地更要紧。**
> 本地 `default_pool_size = 1` 时泄漏几乎必然发生、一测就中；
> 生产池子大，复用路径稀疏 —— 漏配这一项的后果是
> **偶发的跨租户可见性**，而偶发比必然更难发现
> （实测记录见 `../eng/03-测试策略.md` §四）。

`default_pool_size = 20` 是个起点，不是算出来的：
四个进程各自还有应用层连接池，真实值要在压测时按
「PG 的 `max_connections` 减去 owner/备份留的余量」往回调。
**这个数字目前没有实测依据**，写在这里是为了让它有个明确的待验状态。

四个连接串对应四个角色（`../eng/01-配置与Secret.md` §二），
它们**都经 PgBouncer**，除了 `TGM_DB_URL_OWNER` ——
迁移直连 PG，因为迁移里有 DDL 与会话级操作，transaction 模式下不可靠。

## 五、运行时规格

```text
最小可跑（形态 A 全套）     2 vCPU / 4 GB / 40 GB SSD
                            含 PG + Redis + MinIO 同机
数据库                      单实例。稳态数据量 20~30 万行
                            （../spec/04-数据生命周期与容量.md）
对象存储                    媒体只留 3 天，容量按日峰值 × 3 估
```

2 核 4 G 这个数字的来源是「单账号 MTProto 连接的内存占用远低于 Python」
这一判断，**它没有在本项目实测过** —— 真实占用要等
`mtproto-worker` 跑起来才知道。规格不足时的表现是 OOM，
不是性能退化，所以这一项在上线前必须有一次实测（`01-上线就绪与运维.md` §四）。

容量目标（全平台 1000 活跃订阅 / 20 万事件日）与配额数字的倒推
在 `../spec/01-产品需求.md` §6.1，不在这里重复。

## 六、进程重启与优雅退出

**正确性不依赖优雅退出。** 每一级交接都先落库再入队
（`../spec/02-总体架构.md` §1.1），所以任何进程被 `SIGKILL`
都不会丢事件 —— 最坏情况是一条任务被重复处理，由幂等键挡住
（`../spec/03-数据模型.md` §5.2）。

优雅退出要做，但目标只有两个：

```text
SIGTERM → 停止拉取新任务，等在途的 HTTP/MTProto 请求结束，上限 30s
          之后直接退出，不等剩余任务
mtproto-worker 额外一步：主动释放 account_leases 里的租约
          省下的是下一个实例等租约过期的那段时间，不是正确性
```

实现上六个 `serve` 角色同时监听 `SIGTERM` 与 Ctrl-C（`tgm_app::shutdown_signal`），
监听在启动期校验连库之前注册：只监听 Ctrl-C 时 `docker stop` 发出的 `SIGTERM` 走默认处置，
进程以 143 退出、不经过上面的收尾。L3 `worker_processes_exit_cleanly_on_sigterm`
对四个后台角色逐一发 `SIGTERM`，断言 30s 内以 0 退出。

> `mtproto-worker` 的租约释放是**优化，不是要求**。
> 正确性靠 `fencing_token`（`../spec/08-账号接入.md`）——
> 如果它需要靠优雅退出才正确，那说明机制本身有问题。
> 这一点值得写下来，因为「进程退出时清理租约」很容易被实现成必需步骤。

滚动更新在形态 A 下不存在（单实例），部署就是**停旧起新**，
有秒级到分钟级的中断。这与首发「无 SLO」的定位一致
（`../spec/00-范围与非目标.md` §三），不是缺陷，但要对客户明示。

## 七、本文的局限

- **Dockerfile 未构建过。** `rust:1.98-bookworm` 这个 tag 存在性未核实，
  `grammers` 与 `aws-sdk-s3` 的系统依赖是按经验列的，
  第一次构建大概率要补包
- `pipeline` 仍是形态 A 的逻辑部署单元名称，不是 CLI 角色；真正合并为单进程前，
  仍按 `fanout`、`rule`、`delivery` 的已声明角色分别评估启动状态
- §四 的 `default_pool_size = 20` 与 §五 的 2 核 4 G **都没有实测依据**
- 反向代理选型（nginx / caddy / traefik）未定，§三 只写了职责
- 没有 IaC。部署目前是手工 + compose，这在单实例形态下是有意的选择，
  但它意味着**环境漂移无法检测** —— §2.1 第 2 步的 `tgm audit-rls`
  是目前唯一的漂移检测手段，而它只覆盖 RLS 配置
- 日志收集与留存未设计。`../eng/00-工程约定.md` §5.1 已定不做应用内日志轮转、
  交给容器运行时，但「交给谁、保留多久、如何响应租户删除」在生产侧没有下文；
  这些日志不计入主库租户物理删除完成。
