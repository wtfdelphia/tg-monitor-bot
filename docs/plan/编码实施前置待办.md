## 二、正式业务实现前置项

### 1. 统一租约获取、续租和释放语义（已完成）

当前任务卡与规格原先存在直接冲突，现已统一为：

- `acquire` 首次从 1 开始，同 worker 重复获取不改变 token，过期接管递增 token；
- `renew` 必须匹配当前 worker 与 token，过期租约不得复活；
- `release` 只让租约立即过期并保留行，确保 token 不回退。

对应实现和测试已落在 `crates/db/src/repo.rs` 与 `crates/db/tests/lease.rs`，
任务卡 `T-0001` 已归档为 `done`。

验收判据：任务卡、账号接入规格和测试用例使用同一套 token 语义；并发抢占只能成功
一次，正常续租不产生不必要的 token 变化，旧 worker 不能继续续租或写入。

### 5. 完成控制台登录可行性验证（基础设施可用，当前环境尚不可端到端联调）

在编写完整控制台登录前，需要先确定以下实现输入：

- BotFather Allowed URLs 是否接受本地 `localhost` / `http` 回调；
- OIDC 实际流程能否跑通；
- JWKS 缓存 TTL；
- 未知 `kid` 的强制刷新和限速策略；
- 换钥期间新旧 key 是否并存；
- OIDC callback 是否必须使用 HTTPS tunnel / 预发域名；不能把 Mini Apps 测试环境的 HTTP
  例外推导为 OIDC 的 localhost 支持；
- MTProto 账号二维码与控制台登录二维码的页面归属和文案区分。

预核对结果：Telegram 当前官方登录文档已确认 OIDC Authorization Code + PKCE、
BotFather Allowed URLs、Discovery/JWKS 端点和 `RS256` 默认算法；Allowed URLs
需要同时覆盖站点 origin 与 OIDC redirect URI。Telegram 还要求通过 BotFather 提供的
Client ID/Secret 完成 token exchange；当前仓库配置已定义 `TGM_OIDC_BOT_ID`、
`TGM_OIDC_ALG`、`TGM_OIDC_REDIRECT_URL`、`TGM_OIDC_CLIENT_SECRET` 和
`TGM_CONTROL_BOT_TOKEN`。仓库本地 Docker、PostgreSQL、Redis 和 MinIO 已可用，但
`crates/app/` 仍是骨架，`tgm serve --role control-plane` 仍输出
`NOT IMPLEMENTED`，不存在可接收回调的 HTTP endpoint。因此当前环境适合准备配置和
测试材料，不适合做真实 OIDC 端到端联调。

准备步骤、环境变量、HTTPS 回调要求和失败矩阵见
`docs/plan/evidence/P0-外部验证手册-2026-10-08.md` §三。当前可先完成 BotFather
Allowed URLs、站点 origin、OIDC Client ID/Secret 的安全注入，再准备受控 tunnel/预发地址；
待 control-plane callback 实现后再执行真实授权码、PKCE、JWKS 和会话签发验证。

验收判据：形成可复跑的登录验证结果，明确失败时“拒绝登录”的处理方式，并完成两类
二维码不会混淆的页面语义设计。

依据：`docs/design/spec/07-接口契约.md` §1.2、§1.3、§六。

### 14. 明确自动执行权限与发布保护

验收判据：完成一次受控的创建分支、运行卡口、创建 PR、核验 base/head、失败回收和

## 六、建议执行顺序

建议按以下优先级推进未完成事项：

1. **P0：完成外部可行性验证。** 媒体范围已定；完成 grammers 真实 Rust 接入、QR 六项
   真机验证、控制台登录和租户自带 `api_id` 的可行性验证。
2. **P0：冻结 G0/G1/G2 证据链。** 为每个未验证项指定责任人、证据载体和失败处置，
   再进入依赖这些结论的 Telegram 业务编码。
3. **P1：先落地安全与接入基础。** 完成 `grammers-client` 版本锁定、真实账号生命周期、
   session 加密落库、租约心跳与 worker 调用方；`KmsKek` 代码和本地/测试 key 验收
   已完成，目标生产环境验收仍待定。
4. **P1：完成控制面和首发业务链路。** 实现 HTTP 服务、OpenAPI 产物、控制台调用方、
   Bot Gateway、Fanout、Rule、Delivery；媒体按已冻结的首发范围实现或明确延期。
5. **P1：完成驱动发布前核验。** 将当前驱动版本纳入可信远端基线，核对 `gh` 版本兼容性，
   并把 `check-regressions.py` 接入固定自动化入口。
6. **P2：完成上线与扩展关口。** 多实例混沌、容量与恢复演练、值班安排，以及媒体能力
   在首发范围内的完整验收。

已完成的实现期前置代码：租约 repo 与并发测试、QR 纯状态机与 L1 测试。它们不替代
P0 的真实设备和外部依赖验证。
