# 外部关闭证据输入规范（2026-11-18）

任务：`external-closure-evidence-input-20261118`。

本文件定义 G1、WP-8 和 G4 外部关闭证据的脱敏输入边界。它不生成证据、不授权生产操作，
也不把本地测试、维护人确认或公开 provider discovery/JWKS 检查扩大为外部实测。

## 一、校验入口

使用仓库脚本：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 scripts/verify-external-closure-evidence.py \
  --g1 "$HOME/.config/tgm-closure/g1.json" \
  --wp8 "$HOME/.config/tgm-closure/wp8.json" \
  --g4 "$HOME/.config/tgm-closure/g4.json"
```

输入文件必须由当前用户拥有、是普通文件，并使用 `0600` 或更严格权限。脚本只输出状态、
证据引用和缺口，不输出凭据、连接串、token、session、`api_hash` 或用户数据。脚本校验的是
回填结构和记录状态，不验证外部引用的真实性；责任方仍须人工核对引用材料、签署主体和实际
操作记录。

返回码：

- `0`：所提供的每个门都满足关闭条件；
- `2`：JSON 结构合法，但至少一个门仍为 `blocked`；
- `1`：文件、权限或证据结构非法。

## 二、G1 输入

文件根节点固定为：

```json
{
  "schema": "tgm/external-closure-evidence/v1",
  "kind": "g1",
  "baseline_commit": "<40位小写提交哈希>",
  "recorded_at": "YYYY-MM-DD",
  "provider": {
    "rotation": {"status": "pass", "source": "provider-sandbox", "evidence_ref": "ticket-ref", "observed_at": "YYYY-MM-DD", "active_probe": false},
    "unknown_kid": {"status": "pass", "source": "approved-isolation", "evidence_ref": "ticket-ref", "observed_at": "YYYY-MM-DD", "active_probe": false},
    "jwks_failure": {"status": "pass", "source": "provider-sandbox", "evidence_ref": "ticket-ref", "observed_at": "YYYY-MM-DD", "active_probe": false},
    "expired_token": {"status": "pass", "source": "approved-isolation", "evidence_ref": "ticket-ref", "observed_at": "YYYY-MM-DD", "active_probe": false}
  },
  "tenant_api_id_review": {"status": "pass", "evidence_ref": "ticket-ref"},
  "formal_signoff": {"status": "signed", "signer_ref": "role-ref", "signed_at": "YYYY-MM-DD", "evidence_ref": "ticket-ref", "decision": "go"},
  "srs_v1_1": {"status": "frozen", "version": "1.1", "sha256": ["<64位小写 SHA-256>"]}
}
```

`source` 只能是 `provider-sandbox`、`approved-isolation` 或 `natural-observation`。没有 provider
正式沙箱、批准的隔离故障材料或自然观察记录时，相关项必须保持 `not-run`/`blocked`；不能把
未经批准的本地 stub、合成 JWT 或重复真实登录填成外部实测。使用 `approved-isolation` 时，
引用材料必须明确测试对象、结果、哈希和责任方接受范围；其 `pass` 只表示批准的客户端行为
覆盖，应另行记录真实 provider 事件状态。无论记录是 `pass`、`not-run` 还是 `blocked`，
每个 provider 项都必须明确写出 `active_probe=false`；缺少该字段或写成 `true` 都拒绝。

## 三、WP-8 输入

`kind` 为 `wp8`，`production` 下必须逐项提供 `consent`、`reporting`、`backup`、
`cross_replica_retention`、`restore`、`rpo`、`rto`、`alerts`、`oncall`，每项包含
`status=pass` 和脱敏 `evidence_ref`。另需：

```json
"authorization": {
  "restore": "authorized|not-authorized",
  "alerting": "authorized|not-authorized",
  "tenant_purge": "authorized|not-authorized"
}
```

这些字段分别对应真实备份/恢复、跨副本留存、实际 RPO/RTO、告警回执和值班安排。输入文件
不能放生产连接串、密码、Bot token、KMS Secret、用户消息或完整生产日志。授权字段只记录
对应操作是否获批，不会被脚本改写，也不会触发 timer 或真实租户清理；真实租户清理和 timer
仍按独立授权节点处理。

## 四、G4 输入

`kind` 为 `g4`，必须同时提供：

- `fingerprint_recompute.status=pass`、批准授权范围、只读身份、范围引用和脱敏结果引用；
- `flood_wait.status=pass`、观察来源、时间、脱敏证据引用，以及落库、身份冷却、抑制重试、
  等待到期、单次恢复、去重、日志脱敏和清理均为 `pass`。

FloodWait 的来源只能是 provider 正式隔离、自然观察或批准隔离，且 `active_probe` 必须为
`false`，包括 `partial/not-run` 记录。没有自然事件时保持 `partial/not-run`；不能用 mock
429、主动加压、重复探针或重放真实消息替代闭环。
