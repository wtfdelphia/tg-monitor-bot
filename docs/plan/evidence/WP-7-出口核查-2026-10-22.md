没有修改生产代码、API、权限、迁移或卡口，也没有使用真实凭据。

## 二、逐页核对

| 页面类型 | 当前已有内容 | 缺口或验收边界 |
|---|---|---|
| 登录 | OIDC 按钮、控制 Bot 挑战与确认码、串行轮询、错误恢复 | 只展示 `deep_link`，页面没有二维码图像元素或渲染逻辑；历史浏览器用例验证的是未配置 Bot 时的失败恢复，不是扫码成功闭环 |
| 身份 | 列表、状态复位、删除、名称与代理编辑 | 没有 Bot Token 表单，也没有 MTProto 扫码、2FA 或重新授权入口；后端 API 已有，不等于页面已有 |
| 规则列表 | 筛选、分页、批量启停与只读角色限制 | 历史实测已覆盖；本轮只重跑页面脚本，不声称新增完整浏览器验收 |
| 规则编辑 | 新建/编辑、条件与替换编辑、模板、版本历史、确认删除 | 新建与编辑是同一页面类型；本轮不因已有扩展功能而扩大首发范围 |
| 关键词 | 列表、筛选、增改启停删除、导入导出、试跑入口 | 页面脚本有回归；历史浏览器用例覆盖新增、真实错误恢复、持久化及转义，不代表所有入口都已逐项真浏览器验收 |
| 目标频道 | 列表、创建、编辑、启停，发送身份只列 Bot | 缺少自检按钮；创建不触发 Telegram 自检，`/api/v1/targets/{id}/probe` 不在 Router 或生成的 OpenAPI 中 |

后端身份接入的三个入口已在当前 Router 与 OpenAPI 中：
`POST /api/v1/identities/bot`、`POST /api/v1/identities/login/qr`、
`POST /api/v1/identities/login/password`，另有 QR 状态轮询。
`WP-2-qr-login-control.md` 的“不在范围”明确保留了身份页 QR 界面，不能因为 WP-2 已通过就自动关闭。

目标自检不是可自行推迟的附加功能：`ADR-0019-目标频道连通性自检.md` 已将其列入首发，
spec/07 §3.8 仍要求创建即自检，并探测展示权限与内容保护状态。
当前目标记录中的 `can_send`、`checked_at` 不会因字段存在就变成已完成探测。

## 三、已有证据与本轮检查

`WP-7-真实浏览器验收-2026-10-12.md` 记录了真实 Chrome、受限角色 HTTP 请求、
多个视口、键盘焦点、关键词与规则操作、只读角色、会话撤销和退出登录。
对应 Rust fixture 事先创建了身份、目标与成员，再签发临时 Web 会话；
因此该证据不能证明新用户能经页面接入账号，也不能证明目标权限已探测。
默认 workspace 忽略的浏览器用例不算本轮浏览器通过。

本轮提取 `crates/app/src/console.rs` 的实际内嵌脚本，以 Node 执行既有检查，均返回 0：

- `console_login.js`、`console_sessions.js`、`console_writes.js`。
- `console_rule_history.js`、`console_rule_bulk.js`、`console_rule_filters.js`、`console_rule_delete.js`。

同时核对实际页面、Router 和 OpenAPI：身份接入 API 存在但页面未调用；
目标 probe API 不存在；登录页没有二维码图像；控制台页面没有 `tenant_id` 字段。
这些源码检查不代替后续浏览器网络审计，也不证明所有跨租户路径都已验证。

## 四、后续顺序与安全边界

先补身份页接入，让用户不依赖手工 API；再补控制台登录二维码；目标自检单独设计与批准。
本轮提案为 `docs/plan/proposals/WP-7-身份接入页面.md`，只申请第一片，不将后两片一并授权。

身份页将新增凭据输入、二维码 bearer 材料及 2FA 的浏览器处理路径，须在实施前核准。
MTProto 的 `custody-v0` 仍是既有占位授权版本，不能把界面接入写成正式授权文本或合规验收完成。

目标自检还有独立的安全边界：spec/05 §七限制 control-plane 只有 wrap 权限，
不得为了从库里读取 Bot Token 而给它增加 Decrypt。应另行设计在已获解密授权的组件执行探测，
明确租户绑定、超时、结果回写及实际 sender/channel 变更后的失效规则后再提案。
本轮不选定新的队列表或迁移，也不修改 ADR-0019。

本轮结论：保留 WP-7 未通过，已有进展和缺口均已核对；待第一片批准后实施。
