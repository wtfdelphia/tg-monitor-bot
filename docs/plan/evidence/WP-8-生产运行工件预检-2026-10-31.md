## 一、范围与安全边界

- 在从 `cloud/dev` 创建的独立 worktree 中执行。
- 只检查仓库内 `deploy/systemd/` 工件、CLI 帮助和环境变量示例。
- 不连接 PostgreSQL、Redis、对象存储、Telegram、KMS 或任何生产服务。
- 不读取、生成或写入真实凭据，不启用 systemd timer，不执行租户清理。
- unit 语法验证使用临时可执行占位文件替换 `/usr/local/bin/tgm`；该结果只能证明
  unit 结构可解析，不能替代目标机器实际二进制路径验收。

## 二、检查结果

| 检查项 | 结果 | 证据摘要 |
|---|---|---|
| systemd 工件结构 | `pass` | 26 个 `deploy/systemd/` 工件完成结构和关键字段检查，未发现结构错误 |
| 租户清理环境示例 | `pass` | `tenant-purge.env.example` 只声明 `TGM_PROFILE`、`TGM_DB_URL_TENANT_PURGE` 和可选 `RUST_LOG` |
| 租户清理 CLI 入口 | `pass` | `cargo run -q -p tgm -- purge-deleted-tenants --help` 正常返回，支持 `--tenant-id` 和 `--max-tenants` |
| timer 日历表达式 | `pass` | 16 个 `.timer` 的 `OnCalendar` 均由 `systemd-analyze calendar` 返回 0 |
| 隔离 unit 语法 | `pass` | 使用临时可执行占位路径运行 `systemd-analyze verify`，返回码为 0 |
| 目标机器实际 unit 语法 | `blocked` | 当前环境没有 `/usr/local/bin/tgm`，且容器无权读取部分宿主 systemd 单元；不能写成生产通过 |

timer 日历包含 `daily`、`hourly` 和每 10 分钟一次的表达式；本轮只验证表达式可解析，
不验证目标机器时区、timer 是否启用或实际下次触发时间。

当前环境对正式 unit 的原始提示包括：

```text
tgm-tenant-purge.service: Command /usr/local/bin/tgm is not executable: No such file or directory
```

该提示与生产验收模板中的未决项一致：必须在目标机器安装并校验对应发布提交的
`/usr/local/bin/tgm` 后，再运行实际路径的 `systemd-analyze verify`。

## 三、清理与未决项

本轮只使用短生命周期的临时占位文件和进程；没有创建 Docker 容器、卷或网络，
没有启动数据库，也没有生成构建产物以外的持久临时文件。未执行全局 Docker 清理。

以下项目仍保持未完成：

1. 目标机器安装并校验 `cloud/dev` 对应发布提交的 `/usr/local/bin/tgm`。
2. 在目标机器以实际路径再次运行 `systemd-analyze verify`，并核对服务用户、环境文件
   所有权与 `0600` 权限。
3. 提供生产备份、隔离恢复库、探针租户、专用 `tenant_purge` 授权和告警接收信息。
4. 完成真实备份恢复、生产探针租户清理、失败重试和 systemd 停止/重跑验收。
5. 完成跨副本留存策略和 RPO/RTO 的生产证据；WP-8 整体仍未通过。

本记录不授权启用 `tgm-tenant-purge.timer`，不授权删除真实租户，也不构成生产运维验收。

## 四、复跑命令

```bash

systemd-analyze calendar daily
cargo run -q -p tgm -- purge-deleted-tenants --help
```
