## 三、新增通知恢复回归

文件：`crates/app/tests/tenant_notify.rs`，用例
`pending_notification_survives_process_kill_before_response`；子进程入口为
`notification_restart_child`。沿用现有投递重启测试的自启动测试二进制形状，不新增依赖或生产配置。

1. 通过生产 repo 令身份失去授权，通知在同一事务中入队。
2. 子进程清空继承环境，只接收临时数据库的 `app_user` 连接和本地 mock Bot API 地址；
   校验实际角色既不是超级用户，也无 BYPASSRLS，不传 owner 连接或真实 Token。
3. mock 收到包含预期 owner 与身份 id 的请求后等待响应闸门。父进程据实际收到的请求强杀并回收子进程，
   不以固定 sleep 猜测检查点。
4. 以受限租户事务断言通知仍是 `PENDING`、`attempt_count=0`、`sent_at IS NULL`。
5. 新进程运行同一个生产循环，重发的完整请求与前次相同，最终写入
   `SENT`、`attempt_count=1` 和 `sent_at`。

此回归证明持久化通知不会因为进程退出而丢失，不证明私聊恰好一次。
如果 Telegram 已接受发送，但进程没收到响应或没提交 SENT，重启后可能再发一次；
Bot API 私聊路径没有复用 MTProto 的 `random_id`，不能借用投递去重证据。
测试中的两次 HTTP 请求正是这个在途窗口的恢复，不将它们描述成“没有重复请求”。
