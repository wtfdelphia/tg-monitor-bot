## 一、回填真实 OIDC 配置

Telegram 官方文档：<https://core.telegram.org/bots/telegram-login>（2026-11-16 核对）。
在 BotFather mini app 中选专用测试 Bot，进入 Login Widget，取得 Client ID、Client Secret。
这里的 Client Secret 不是 Bot API token；不要替换或重置原来的测试 Bot 凭据。

先确定由操作者控制的 HTTPS 入口和证书。在 BotFather Allowed URLs 中登记网站 origin 和
完整 callback；本项目路径为 `/auth/oidc/callback`。本轮已建立私网 IP 的独立 HTTPS 入口，
BotFather 是否实际接受该地址仍需真实授权验证。不要把示例域名或生产域名登记为测试地址。签名算法选 `RS256` 或 `ES256`；官方文档
明确 `EdDSA` / `ES256K` 当前不能申请本项目所需的 `profile` scope。

在服务器编辑已建立的受控文件，不在聊天回传 Secret：

```bash
nano /home/openclaw/.config/tgm-g1/oidc.env
chmod 600 /home/openclaw/.config/tgm-g1/oidc.env
```

文件按下面的对应关系填写；`login.example.com` 仅为格式示例，必须换成你控制的测试域名：

```dotenv
TGM_OIDC_BOT_ID=替换为BotFather显示的数字ClientID
TGM_OIDC_CLIENT_SECRET='替换为BotFather显示的ClientSecret'
TGM_OIDC_ALG=RS256
TGM_OIDC_REDIRECT_URL=https://login.example.com/auth/oidc/callback
TGM_OIDC_ALLOWED_ORIGIN=https://login.example.com
TGM_OIDC_ALLOWED_CALLBACK=https://login.example.com/auth/oidc/callback
TGM_OIDC_BOTFATHER_CONFIRMED=no
```

例如回调为 `https://受控域名/auth/oidc/callback`，origin 只填 `https://受控域名`，
Allowed callback 与回调逐字一致。实际完成 BotFather 配置后再把 confirmed 改为 `yes`。
该文件供输入检查器读取；不直接作为应用完整运行配置。`TGM_OIDC_BOT_ID` 是 Login Widget
页面上的数字 Client ID，不填 `@bot_username`、Bot API token 或 MTProto `api_id`。
`TGM_OIDC_CLIENT_SECRET` 不填 Bot API token 或 `api_hash`。Allowed URLs 登记完成后才将
`TGM_OIDC_BOTFATHER_CONFIRMED` 改为 `yes`。当前私网测试使用
`https://172.20.66.24/auth/oidc/callback`，浏览器必须能访问该地址并信任测试 CA；服务器已验证
TLS，但这不能证明 Windows 浏览器受信或 BotFather 接受。不得把本机格式检查当成 provider
支持结论。若 provider 拒绝此地址，再改用受控 HTTPS 域名；不得放宽签名、cookie 或 HTTPS 检查。

当前主机为 Ubuntu 22.04.5，地址 `172.20.66.24`，不是此前已完成验收的 Rocky 9.8。

后端使用包含已批准身份修复的本地测试构建，不冒充已签名候选；Bot API 凭据为不可用合成值。

## 二、回填租户自行申请 api_id 的证据

由目标租户本人登录 <https://my.telegram.org/>，进入 API development tools 完成申请。
Telegram 申请说明：<https://core.telegram.org/api/obtaining_api_id>。不要以已有平台 API 凭据
代替，也无需把租户的 `api_hash`、手机号、验证码写进证据或提供给本工具。

```bash

chmod 600 /home/openclaw/.config/tgm-g1/tenant-application.json
```

记录申请操作者和租户的内部代号、申请日期、脱敏截图或受控记录位置、复核人。引用必须为
服务器上实际存在的非空普通文件绝对路径，属主为当前操作者、权限 `0600`；存在性不等于内容已复核。
只有实际申请并复核后才填写 `result: "pass"`、`applicant_is_tenant: true`、
`platform_credentials_reused: false`；没有证据时保留原值。

完成申请后可按下列结构填写；日期、代号和证据路径必须对应实际操作：

```json
{
  "operator_reference": "tenant-test-operator-01",
  "tenant_reference": "tenant-test-01",
  "applied_at": "实际申请日期，如 2026-11-16",
  "result": "pass",
  "applicant_is_tenant": true,
  "platform_credentials_reused": false,
  "evidence_reference": "脱敏申请记录或截图的服务器绝对路径",
  "reviewer": "实际复核人的姓名或内部代号"
}
```

检查输入：

```bash
python3 /tmp/tgm-g1-prestage-20261116/scripts/g1-external-input-check.py \
  --env-file /home/openclaw/.config/tgm-g1/oidc.env \
  --tenant-record /home/openclaw/.config/tgm-g1/tenant-application.json \
```

退出码 `0` 只表示输入字段和证据文件边界齐备，`2` 表示缺输入，`1` 表示权限、格式或公开 provider 检查失败。
工具不执行 env 内容，不提交登录请求，不回显凭据。公开 discovery/JWKS 可读取，不代表真实
登录或真实换钥已通过。用户已于 2026-11-16 批准身份映射修复，实际登录仍需该修复验证完成。

## 三、隔离依赖栈

当前状态目录：`/home/openclaw/.local/state/tgm-prestage-20261116`，权限 `0700`。
其中 `stack.env`、`restore.env`、`state.json` 和备份仅供当前用户读取，不提交仓库。
Compose project：`tgm-prestage-91484a2803`。PostgreSQL、Redis、MinIO 各用专属具名卷，
仅连接本任务的 internal 网络。现场未发布宿主端口；通过 `docker exec` 管理合成数据库。
Redis 已设置随机密码，未使用现有 Telegram 或生产凭据。

日常命令：

```bash
python3 /tmp/tgm-g1-prestage-20261116/scripts/prestage-local.py status
python3 /tmp/tgm-g1-prestage-20261116/scripts/prestage-local.py backup
python3 /tmp/tgm-g1-prestage-20261116/scripts/prestage-local.py restore
```

`backup` 备份此合成 PostgreSQL 库和无密码角色定义；保留最近三份成功备份。
`restore` 从最近成功备份恢复到新的 `template0` 数据库，先恢复角色基线，再恢复对象和权限。
恢复容器使用 `--network none`、tmpfs 和 `--rm`，检查结束后确认容器消失才报告成功。
检查包含 RLS 审计、迁移摘要、全表计数、受限角色双租户隔离和凭据列读取拒绝。

这些备份与原库在同一宿主磁盘，不提供主机损坏保护。Redis/MinIO 的具名卷提供持续存储，
本工具尚未实现它们的备份恢复；生产 WAL、异机副本、加密和完整存储恢复仍未验。

## 四、备份调度、故障与告警

```bash
python3 /tmp/tgm-g1-prestage-20261116/scripts/prestage-local.py schedule
systemctl --user status tgm-prestage-91484a2803-backup.timer --no-pager
python3 /tmp/tgm-g1-prestage-20261116/scripts/prestage-local.py fault-check
```

已建立本任务专用 user backup timer，间隔一小时，未改变 linger。调度器的脚本副本保存在
状态目录 `backup-runner.py`，运行时不依赖 `/tmp` 工作区；源码工具更新后运行
`unschedule`、`schedule` 刷新副本。user manager 没有继承 Docker 附加组时，service 使用
系统 `sg` 激活账号本来已有的 Docker 组；不修改用户、socket 权限或其他 unit。
user manager 停止期间不会备份，不作全天运行承诺。

本工具对同一状态目录使用非阻塞文件锁；手工操作和 timer 重叠时，后到操作失败，稍后重试。
`fault-check` 连续制造两次只针对本合成数据库的备份失败，确认上次成功备份仍在，再停止并
恢复本栈 Redis。它不停止其他 Compose 栈，不触发 Telegram 探针。

事件记录在状态目录 `events.jsonl`。连续备份失败、依赖停止与恢复都有本地事件；目前没有
外部接收渠道或人工回执。不能据此将“生产告警已接通”记为通过。外部告警需先提供接收人、
渠道和一次演练授权，再执行一条带测试标记的消息与人工确认。

停止和清理：

```bash
python3 /tmp/tgm-g1-prestage-20261116/scripts/prestage-local.py unschedule
python3 /tmp/tgm-g1-prestage-20261116/scripts/prestage-local.py stop
python3 /tmp/tgm-g1-prestage-20261116/scripts/prestage-local.py up
```

`stop` 停止本任务容器并关闭备份 timer，保留卷；`up` 恢复容器，需另行 `schedule` 恢复调度。
`down` 移除本任务容器及网络、保留卷；只有操作者明确要丢弃本合成栈数据时才加
`--discard-data`。备份和诊断目录保留，不执行全局 prune。
