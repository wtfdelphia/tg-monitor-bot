## 一、真实源到目标

命令：`TGM_LIVE_E2E_ALLOW=1 bash scripts/g34-live-e2e.sh run`。

同一 `sqlx::test` 临时库和进程内经控制面 QR 登录（含 2FA），登记来源、关键词、规则与
Bot 目标，再运行生产 `run_identity`、fanout、rule 和 delivery。源消息为本次生成的一条
命中与一条未命中文本；第二个 Bot 经 MTProto 只读核对目标消息。

```text
[G34-QR] confirmed worker=shutdown
[G34-E2E] source_messages_sent=2 worker_started=true
[G34-E2E] events_hit=1 events_miss=1 matched=1 tasks=1 task_status=DONE target_message_label_match=true target_message_id_present=true
[G34-E2E] cleanup_message_count=3
test result: ok. 1 passed; 0 failed; 1 ignored
```

命中和未命中各采集一次，命中只产生一条规则命中与一条 `DONE` 投递任务；未命中没有
投递任务。目标标签匹配，任务含 Telegram message id；本用例创建的两条源消息和一条目标
消息均删除成功。没有记录 token、`api_hash`、session、密码或消息正文。

## 二、两时点强杀恢复

命令：

```text
cargo test -p tgm-app --test delivery_live live_delivery_g4_kill_restart -- --ignored --exact --nocapture --test-threads=1
```

`before-send`：子进程在调用真实 transport 前挂起，父进程强杀；恢复子进程使用同一任务和
`random_id` 发出一条消息，任务 `DONE`。`after-send`：真实 transport 已返回 message id 后
挂起并强杀；恢复后返回相同 message id，任务 `DONE`，没有产生第二个 message id。

```text
[V2] phase=before-send first=- restarted=ok task_status=DONE telegram_message_id=present dedupe=single-send
[V2] phase=after-send first=ok restarted=same-message-id task_status=DONE telegram_message_id=present dedupe=same-message-id
test result: ok. 1 passed; 0 failed
```

随后以第二个 Bot 的 MTProto `MediaReader` 按数据库返回的两个 message id 读取目标频道，
各自标签存在且各返回一条；两条消息随后经发送 Bot 删除成功：

```text
[V2-readback] phase=before-send label_present=true readback_count=1
[V2-readback] phase=after-send label_present=true readback_count=1
[V2-readback] cleanup_count=2 cleanup=true
```

## 三、真实限流与未闭环项

既有 V1 探针设置 `TGM_LIVE_LOGIN_REPEAT=5`，前三轮 Bot 登录成功，第四轮返回真实
`FLOOD_WAIT`。旧探针未在首次限流停止，实际第五轮也返回 `FLOOD_WAIT`；本证据不隐去这次
额外请求，也不将该探针记为“安全停止通过”。工具现已改为首次限流即停止并打印服务器
返回的退避秒数，未再为修改后的探针发起登录。

真实限流已出现，但没有完成“记录退避秒数 → 数据库写入 `next_retry_at` → 等待到期 →
恢复后单次投递”的闭环。现有 mock 决策测试和 systemd 重启不能补足这一项，因此限流与
退避仍为 `partial`。

## 四、工具修正与边界

- 登录与端到端改为同库同进程：避免 worker 已更新内存会话后，另一进程使用过时快照。
- 纯文本事件的 `media_type` 为 `NULL`，验收规则不再错误限定 `TEXT`；计数关联本轮
  消息 id，不把 `catch_up` 补采的历史频道消息计入本轮命中。
- V2 子进程显式传入目标和本地 S3 配置，登录与投递有超时；补齐现行领取要求的临时
  canonical/tenant event 关联。`Idle` 不再被当成成功。
- V2 工具现可自动只读核对和清理两条目标消息。子进程正常完成后等待退出，强杀路径由
  `LiveChild` 清理。未改生产消息处理、数据库结构、RLS、GRANT、CI 或运行时依赖。
- QR HTTP 服务、二维码、2FA 文件和一次性 session 已清理。共享
  `tgm-pre008-acceptance` Compose 栈未停止或删除。
- 本分支尚未经过 PR CI；G3、G4、WP-8 均未整体通过。指纹真实历史全量重算、生产留存、
  跨副本删除、探针/告警/值班与其余 WP-8 输入仍按既有矩阵保留未完成。
