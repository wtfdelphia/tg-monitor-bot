# WP-5 规则进程强杀与重启

记录日期：2026-10-12。任务 id：`WP-5-rule-restart`。

判据出处：`docs/design/plan/00-里程碑与工期.md` §4.3 WP-5「后台任务在进程重启后
继续」；受限角色与临时库沿用 `docs/design/eng/03-测试策略.md` §二。基于 PR #7
提交 `c57464f` 的独立工作树补验已有 rule worker，不修改工作包或关口判据。

## 实现

在既有 `bins/tgm/tests/worker_restart.rs` 复用子进程启动、强杀与回收、事件种子和
数据库断连等待。启动辅助函数支持选择 `fanout` 或 `rule`，保留既有 fanout 测试。
子进程提前退出时读取错误输出，避免只见退出码却不知道启动或匹配失败的原因。
子进程环境仍清空后逐项注入开发配置与受限业务连接，没有 owner、真实凭据或外部
平台入口。生产 worker、Repo、迁移、权限、审计、CI 和 backlog 均未修改。

新增测试使用 SQLx 临时库。管理连接仅准备种子与持有暂停锁，业务建规则、生成
事件、扇出和结果检查使用 `app_user`；另验该角色不是超级用户、没有 BYPASSRLS。
规则子进程在数据库活动视图中也必须以 `app_user` 运行。

测试建立可命中同一关键词的两个目标规则，在真实 rule 子进程的入队事务最后一条
`canonical_events` 更新处持有行锁。等待活动查询、锁等待及阻塞连接 pid 同时匹配，
确认它已到提交前位置，不靠固定 sleep 猜进度。该位置之前已执行投递任务写入和
租户事件标记，但另一受限连接只能读到：未处理、未命中、全局未命中、零任务。

随后实际强杀子进程，等待其数据库连接消失，在解锁前后重验相同状态；不把进程
退出当成在途数据库语句已经结束。重启后原事件完整处理并生成两个 PENDING 任务，
核对规则 id、版本和动作。再强杀、重放同一原始消息与租户投影、加入下一条消息，
第三个 rule 子进程继续处理新消息，旧事件仍只有原任务。他租户读不到这些事件
和任务。没有执行投递端或发送 Telegram 消息。

## 验证与反证

首次种子使用 `fuzzy` 时子进程拒绝匹配。补错误输出后确认原因是模糊匹配尚未支持；
`docs/design/spec/01-产品需求.md` §3.1 将它列为演进功能。本轮种子改用首发已有的
`exact`，不扩大匹配器范围，也不把这次失败说成已修好模糊匹配。

定向 rule 回归与包含 fanout 的整文件测试通过，日志分别为发布目录
`rule-restart-exact.log`、`rule-restart-targeted.log`。反证另建一次性 detached
工作树，只在该副本把 `enqueue_delivery_tasks` 的租户事务替换成自动提交连接，
保持 SQL、测试与判据不变；同一真实子进程测试返回 101，目标断言读到
`(true, true, false, 2)`，不是期待的 `(false, false, false, 0)`。这证明它会抓住
任务与处理标记提前落库的半提交状态，而不是只验子进程可以启动。

反证日志 `rule-restart-counterexample.log`、副本 diff
`rule-restart-counterexample.diff` 和复现脚本 `check-rule-restart-counterexample.py`
保留在 `/home/openclaw/wtf_workspace/local/tg-monitor-bot-release/`。反证副本已移除，
发布工作树的生产 Repo 与 pipeline 字节保持原状，破坏代码不进入提交。

反证与正式源码共用过编译目录，首次还原复跑仍执行了破坏版二进制并在同一断言
报红，日志为 `rule-restart-restored.log`。不能把源码恢复当成编译缓存恢复；已清除
`tgm`、`tgm-app`、`tgm-db` 的包缓存并重新构建。首次完整门禁在确认该问题后主动
停止，不计通过；新的定向测试与完整验收结果后续补录。
