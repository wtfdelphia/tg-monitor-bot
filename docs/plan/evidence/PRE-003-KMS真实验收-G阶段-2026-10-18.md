## 一、环境与范围

- 区域 `ap-southeast-2`。key 是 PRE-003 的测试 key；按 ops/02 §一，生产 key 必须另建。
  执行机器是开发主机，出口 IP 为 `103.151.173.90`，不是 OCI 生产出口。
  **所以本记录是机制验收：证明 ops/02 的模板、预检与代码路径在真实 AWS 上按设计工作；
  不是生产验收**，生产 key 与 OCI 主机上要重做一遍。key ARN 不写入证据。
- AWS CLI 2.38.1 从官方地址下载，GPG 签名校验通过：签名者 AWS CLI Team，指纹 `FB5D…475C`。
  本地导入的公钥显示已过期，但签名本身有效。CLI 装在用户目录，SSO 配置放在独立的
  `AWS_CONFIG_FILE`，不写默认 `~/.aws/config`。
- 两套 SSO 角色：`KmsTest`（KMS 往返，无 IAM/CloudTrail 权限），以及临时的 `TgmIamTemp`
  （只能管理 `user/tgm-kms-*` 并查 CloudTrail）。后者的权限集前后改了三次才生效：
  Resource 依次写成了 `<账号ID>` 占位符、`arn:aws:kms:…`，最后才是正确的 `arn:aws:iam::…`。
  每次都是 `ListAccessKeys` 返回 AccessDenied 时发现的。
- 按 ops/02 §2.1 建了 `tgm-kms-acc-encrypt`（只有 `kms:Encrypt`）与 `tgm-kms-acc`
  （`kms:Encrypt` + `kms:Decrypt`），内联策略照模板，带 `aws:SourceIp` 与
  `kms:EncryptionContextKeys` 条件，并打了标签 `purpose=tgm-kms-acceptance-2026-10-18`。
  access key 只存在一个 0700 临时目录里，以 `env -i` 注入进程（`HOME` 指向不存在的目录）；
  命令与日志都没有输出 secret、明文或密文。
- **收尾已删除**：两个 user 的全部 access key、内联策略和 user 本身。`GetUser` 返回
  `NoSuchEntity`，临时目录也已删除。

## 二、`tgm` 二进制对真实 KMS 的启动预检

本地 Compose 库，`TGM_PROFILE=development`，`TGM_KEK_BACKEND=kms`，静态 key 走环境变量：

| 角色 | 凭据 | 结果 |
|---|---|---|
| control-plane | `tgm-kms-acc-encrypt` | 「KEK encrypt-only 自测通过：backend=kms（Decrypt 已被拒）」。之后因 control bot 身份未建，在下一步预检退出，与 KMS 无关 |
| delivery | `tgm-kms-acc` | 「KEK 往返自测通过」。之后因运行链未接入退出 |
| mtproto-worker | `tgm-kms-acc` | 「KEK 往返自测通过」。同上 |
| bot-gateway | `tgm-kms-acc` | 「KEK 往返自测通过」 |
| control-plane | `tgm-kms-acc`（反证） | 拒绝启动：「control-plane 竟然能解开 DEK」 |
| delivery | `tgm-kms-acc-encrypt`（反证） | 拒绝启动：「KEK 往返自测失败」 |

预检的其他反证在 `KmsTest` 会话下做过（同一代码路径）：去掉 `AWS_EC2_METADATA_DISABLED`、
再加 `AWS_CONFIG_FILE`、换成不存在的 key、篡改 session token，四种情况都拒绝启动。

## 三、IAM 策略条件（AWS CLI 直接调用）

32 字节随机测试数据，只在本机比对：

| 操作 | 结果 |
|---|---|
| encrypt 身份 `Encrypt`，上下文 `{tgm:tenant_id=1, tgm:identity_id=2}` | 成功 |
| encrypt 身份 `Decrypt` | `AccessDeniedException` |
| decrypt 身份 `Decrypt`，同一上下文 | 成功，明文逐字节一致 |
| 两个身份 `Encrypt` 都多带一个键 `x=y` | 均为 `AccessDeniedException` |
| encrypt 身份 `Encrypt`，不带上下文 | **成功**（见下） |
| decrypt 身份 `GenerateDataKey`、`DescribeKey`（策略外 API） | 均为 `AccessDeniedException` |
| encrypt 身份的策略把 `aws:SourceIp` 改成 `192.0.2.1/32` 后再 `Encrypt` | `AccessDeniedException`；之后已改回原策略 |

`KmsTest` 会话下还验过：同一份 DEK 密文换 `identity_id`、或者不带上下文去解，KMS 都返回
`InvalidCiphertextException`，即 DEK 密文绑定身份（ADR-0032）。

「不带上下文也能 Encrypt」正是 ops/02 §2.1 已经写明的语义：`ForAllValues` 对空集合也成立，
所以这个条件只能限制「不许多带别的键」，不能保证「必须带」。必须带由代码保证，
CloudTrail 证实了 `tgm` 进程每次都带（第五节）。

出口 IP 反证的做法是改策略，不是换出口：本机代理与直连走的是同一个出口，
所以没有从「另一个 IP」发起调用。它证明的是 `aws:SourceIp` 条件对这把 key 会生效。

## 四、§2.3 轮换（decrypt 身份）

```text
1 创建第二把 key                              → 两把并存
2 新 key 启动 delivery                         → KEK 往返自测通过
3 停用（Inactive）旧 key；旧 key 启动 delivery  → KEK 往返自测失败
                       新 key 再启动            → KEK 往返自测通过
4 删除旧 key                                  → 只剩一把 Active
```

「观察一个完整业务周期」一步没有做：delivery 运行链还没接入，没有业务流量可以观察。

## 五、CloudTrail

`cloudtrail:LookupEvents`，筛选 `userIdentity.arn` 含 `tgm-kms-acc` 的 Encrypt/Decrypt 事件，共 19 条：

- **userIdentity** 分别是 `tgm-kms-acc-encrypt` 与 `tgm-kms-acc`，`sourceIPAddress` 全部是 `103.151.173.90`。
- **`tgm` 进程发起的调用**（启动自测）：`requestParameters.encryptionContext` 全部带
  `tgm:tenant_id` 与 `tgm:identity_id`，值是 `KekContext::SELF_TEST` 的 `0/0`。
  这补上了 PR #13 只有 mock 的那一环：真实请求里确实带了上下文。
- CLI 用 `{1, 2}` 发起的调用，事件里的上下文就是 `{1, 2}`。
- 被拒的调用（`AccessDenied`）在事件中不记录上下文。不带上下文的那次 CLI Encrypt
  显示为 `<none>`，与第三节一致。
