## 一、复现与隔离边界

`scripts/tenant-purge-preflight.py` 增加显式 `--probe-identity-fence`：

```bash
python3 -B scripts/tenant-purge-preflight.py --self-test
python3 -B scripts/tenant-purge-preflight.py \
  --container kms-kek-postgres-1 --probe-identity-fence
```

默认目录仍只读。新探针另外固定连接 `tgm_test_schema`，以 `app_user` 执行，
数据库内再次核实数据库名、当前角色以及 NOSUPERUSER/NOBYPASSRLS。
只在单一事务中插入合成租户、身份和事件，最后 ROLLBACK，不读取、更新或删除既有业务数据，
不创建数据库、角色、持久函数或触发器。异常导致连接退出同样回滚；序列可能留下空洞。
该选项不是在生产库执行的运维工具。

主动检查写入围栏时，若注销租户身份插入成功，输出失败状态并返回 rc=2；
不因“成功复现漏洞”返回总体通过。非预期 SQL 异常也不转成“围栏有效”。
活动租户成功插入是正向锚，避免把所有 INSERT 都不能执行误认为状态保护。

完整结果保留在 `/tmp/tgm-wp8-purge-write-fence-20261028.json`，权限 0600。
这里只包含目录、固定测试结果和角色属性，不含消息正文、凭据、会话或真实租户数据。

## 二、实际结果

- `catalog_contract=pass`：应用迁移版本和 checksum、表/FK/删除触发器及根授权基线一致。
- `role=app_user`、`superuser=false`、`bypassrls=false`。
- 活动租户插入身份成功，证明测试角色具备真实写入能力。
- 合成租户为 `deleted` 且到期，开始时没有身份；设置其租户上下文后，身份 INSERT 仍成功。
- 同一角色继续向该新身份插入 canonical 成功；因此最终清理期间“共享锚点不会再出现”不能作为数据库不变量。
- `terminal_cleanup_precondition=failed`、`all_write_paths_verified=false`、`physical_delete_implemented=false`；命令 rc=2。
- 事务结束后以测试管理连接核查，探针租户记录为零。

这不是“注销后正常产品入口仍可创建身份”的证据。源码显示 `credentials::create_bot_identity` 与
`credentials::create_mtproto_identity` 复用 `tenant_write_tx`，后者先取生命周期共享锁再查 active；
`WorkerGuard` 也限制了正常入口。既有应用围栏仍有作用，不能把直写反证扩大成正常接口已失守。

差别在数据库边界：`identities.tenant_isolation` 的 WITH CHECK 只检查租户上下文，
`app_user` 现有 INSERT 权限能直写绕过应用 helper，SQL 本身没有 lifecycle 取锁或 active 校验。
目录核查表明当前相关非超级运行角色中，`app_user` 是唯一具备 identities INSERT 的角色，
且没有更新 `tenant_id` 的权限；但不能据此忽略这条仍合法的直写路径。

## 三、停止点与下一步

按已批准补充提案 §3.3，写入围栏不成立必须重新升级，不得擅自新增终结状态、列或写入约束。
新增 `../proposals/WP-8-tenant-purge-identity-write-fence.md`，建议以最小 invoker 写入触发器复用
生命周期共享锁和取锁后 active 复查，并与注销/清理排他锁作并发反证；不新增 definer 例外。

在这个补充范围获批并验证前，不实施根删除、成员/同意记录最终清理或 C15/A8 变更。
已批准的终结函数方案仍有效，只是前提尚未成立；不是撤回批准或另换删除策略。
