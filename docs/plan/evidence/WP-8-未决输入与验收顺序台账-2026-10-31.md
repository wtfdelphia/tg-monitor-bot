## 二、必须提供的决策输入

### 2.1 产品与法务：同意文本

每个首发文本版本都必须提供以下字段；实现者不能自行补写正文或把草案升级为正式文本：

| 字段 | 必须提供的内容 | 缺失时的处置 |
|---|---|---|
| 文本标识 | `tos`、`privacy`、`credential_custody` | 保持 `custody-v0` 占位，不进入正式上线判定 |
| 版本 | 稳定版本号及批准记录 | 不生成新的正式版本 |
| 语言 | 文本语言和是否允许回退语言 | 不实现语言回退 |
| 辖区 | 适用司法辖区 | 不自行沿用其他辖区规则 |
| 套餐 | `free`、`pro` 或其他适用范围 | 不自行推断套餐差异 |
| 生效时间 | 明确的生效时间和时区 | 不把提交时间当作生效时间 |
| 撤回语义 | 撤回是否立即停止服务、是否需要重新同意、历史记录如何处理 | 不新增撤回事件或迁移 |
| 同意组合 | 各套餐必须同意的文本集合 | 不改变既有同意校验范围 |

### 2.2 产品、法务与运维：举报受理

首发契约至少需要确认：

| 项目 | 需要确认的规则 | 默认边界（未批准前仍不生效） |
|---|---|---|
| 受理范围 | 可举报对象、受理条件、重复提交和拒绝理由 | 只接受批准的字段和对象 |
| 紧急事件 | session、Bot token、`api_hash` 或账号接管等安全事件的升级路径 | 先隔离凭据和身份，再处理普通案件 |
| 反馈 | 受理回执、补充材料、决定通知和语言 | 不承诺未批准的响应时限 |
| 附件 | 是否收附件、类型、大小、扫描和加密 | 首发不实现上传，不新增媒体表或对象存储策略 |
| 案件留存 | 案件正文、调查日志、决定和附件的删除时间 | 不新增举报表或永久留存 |
| 法律保留 | 触发条件、人工标记、解除人和解除记录 | 未定案前不能声称可冻结或自动解冻 |

### 2.3 运维：跨副本留存

运维需要按存储层提供实际配置或明确批准的策略，不接受只写“已配置”：

| 存储层 | 必须确认的输入 | 验收后才能声明 |
|---|---|---|
| PostgreSQL 备份 | 日备/周备周期、保留窗口、备份区域、访问角色、失败告警 | 备份副本按批准策略处理 |
| WAL | 是否启用、保留窗口、归档位置和清理责任 | WAL 不再是未说明副本 |
| 恢复副本 | 恢复隔离方式、服务阻断方式、删除状态重核对步骤 | 恢复库不会直接重新开放已删除数据 |
| 对象存储 | 版本控制、删除标记、跨区域复制、`staging/` 孤儿和生命周期规则 | 对象、非当前版本和删除标记分别有证据 |
| Redis | AOF/RDB、Stream 裁剪、关联键枚举、备份和副本边界 | Redis 不再被“清空一次”代替全副本证明 |
| 主机日志 | journald、容器、代理和集中式日志位置、期限、访问权限 | 日志中的租户关联信息有明确清理边界 |
| 外部 Telegram | 平台是否具备撤回能力及对客表述 | 只能标记 `external-copy-uncontrolled`，不承诺已删除 |

推荐值只能作为审批输入，不能直接写成已批准事实；任何改变现有规格的期限、删除语义、
权限或迁移都要另行提案。

### 2.4 运维：生产验收环境

开始生产验收前，必须取得以下环境事实：

1. 目标机器已安装并校验对应 `cloud/dev` 发布提交的 `/usr/local/bin/tgm`。
2. 有非生产的隔离恢复库，恢复过程不会覆盖生产库或连接真实 Telegram、KMS、Redis、对象存储。
3. 有专用、无真实业务数据的探针租户；不能把真实租户当破坏性测试对象。
4. 已批准的生产只读审查权限，以及单独的 `tenant_purge` 运行授权。
5. `tenant_purge` 直连 PostgreSQL、非 `BYPASSRLS`、无越权成员关系，环境文件由 root
   所有且权限为 `0600`。
6. 已确认告警接收人、人工升级阈值、值班责任和 timer 停止/重跑步骤。

上述条件缺任何一项，生产验收保持 `blocked-input`；不启用
`deploy/systemd/tgm-tenant-purge.timer`，不删除真实租户。

## 三、批准后的执行顺序

顺序不能倒置；每一步完成后必须留下脱敏证据，失败或阻塞立即停止：

1. **决策输入确认**：产品/法务确认同意与举报规则，运维确认跨副本策略。
2. **规格同步**：仅把已批准的期限、完成等级和对客表述同步到规格、运维文档和验收模板。
3. **实现拆分**：根据批准结果判断是否需要迁移、权限、公开 API、对象存储或告警改动；
   命中升级条件时先提交新提案，不直接写实现。
4. **隔离验证**：在本地或非生产环境验证备份恢复、探针删除、阻塞重试、幂等和跨租户反证。
5. **生产前只读检查**：核对发布包、迁移、角色、连接形态、环境文件和 `audit-rls`。
6. **手工生产演练**：timer 保持停止，先完成恢复演练和探针租户清理，逐项填写生产模板。
7. **启用裁决**：只有维护人对完整证据单独批准后，才可启用生产 timer；启用不等于
   已完成全副本删除，仍需分别填写完成等级。

## 四、禁止提前做的事

- 不把推荐默认值写成产品、法务或运维已批准的规则。
- 不新增举报表、公开举报 API、附件上传、对象存储桶或迁移来绕过缺失的契约输入。
- 不用真实租户做探针，不连接生产，不接收或保存生产凭据。
- 不把主库删除写成备份、快照、Redis、日志、对象版本或 Telegram 内容已删除。
- 不以本地 systemd 样例、占位二进制或 Compose 通过结果替代实际生产验收。
- 不启用 `tgm-tenant-purge.timer`，不执行真实租户物理删除。

## 五、下一次交付边界

在产品/法务/运维输入到位前，下一次代码交付只允许属于以下范围：

- 脱敏验收证据的填写与复核；
- 隔离环境的备份恢复和探针租户演练；
- 既有命令、systemd 工件和模板的本地一致性检查；
- 不改变表结构、权限、审计、公开 API、删除语义或生产部署配置的文档修订。

输入到位后，按批准内容单独拆分实现任务；一个任务一个提交，最终仍以 CI 和实际验收
证据裁决，不以本台账的存在宣布 WP-8 通过。
