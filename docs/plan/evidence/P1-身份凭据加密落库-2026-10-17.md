# P1 身份凭据信封加密落库验证记录（2026-10-17）

## 范围

`编码实施前置待办.md` §8 列出的「session 序列化/加密落库」中的落库部分，也是 KMS 在运行期的第一个调用方。不涉及迁移，`credential_keys` 与 `identity_secrets` 已在 0003 中建好，权限在 0011 中授予。不改 RLS、GRANT 或审计断言。

- `crates/core/src/credential.rs`：生成 DEK，并用 AES-256-GCM 对凭据做 seal/open。AAD 为 `tgm:identity_secrets:secret:v1:` 加上 identity id 的大端字节。每次加密都生成新的 nonce。所有失败只报 `KekError::Crypto`。
- `crates/db/src/credentials.rs`：`store_identity_secret` / `load_identity_secret`。
  - 先确认身份归属，再按需创建租户 DEK（`ON CONFLICT DO NOTHING`，之后以库里那一行为准）。
  - KEK 的 wrap/unwrap 在事务外调用，DEK 不缓存。
  - 读写都经 `identities` 连接，并显式加 `WHERE tenant_id = $1`。
  - `kek_id` 与当前 KEK 不符时报 `KekMismatch`。多 KEK 并存的情况留了 `ponytail:` 注释，等 KEK 轮换落地时处理。

## 验证

- `tgm-core` 单元测试 3 项：往返与 nonce 不重复；AAD 绑定身份；换 DEK、篡改密文、nonce 长度错误三种情况都无法解密。
- `tgm-db` 集成测试 `tests/credentials.rs` 5 项，以 `app_user` 连接，并断言该角色非 BYPASSRLS：
  1. 库中只有密文：nonce 12 字节，DEK 行不是 32 字节明文，`kek_id=local:env:v1`。往返和覆盖写入都正确，覆盖写入不会新建 DEK。
  2. 跨租户：写入报 `IdentityNotFound`，读取返回 `None`，不给对方租户创建 DEK，原值不被覆盖。
  3. 把身份 A 的密文和 nonce 原样搬到同租户的身份 B 后，解密失败。
  4. `kek_id` 被改成别的 KEK 后，读和写都被拒绝。
  5. 同租户两个身份并发首次写入，只产生一个 DEK，且两边都能解开。
- 反证 1：把 AAD 中的 identity id 去掉，第 3 项测试报红。代码已恢复。
- 反证 2：去掉写路径 SQL 中的 `tenant_id` 过滤，5 项仍然全绿。原因是 `identities` 的 RLS 拦住了跨租户写入，说明应用层与 RLS 两道防线中 RLS 一道独立有效。本次没有补「关掉 RLS 后应用层单独有效」的 R5 式断言（需要 owner 连接改表），记为未验。
- 反证 3：去掉读路径 SQL 中的 `tenant_id` 过滤，5 项仍然全绿。读路径经由 `identities` 和 `credential_keys` 连接，这两张表都受 RLS 约束，结论与反证 2 相同。
