## 一、逐条核对

| # | 条款原文 | 出处 | 对 ADR-0033 的含义 |
|---|---|---|---|
| T1 | "In order to log in as a bot, instead of using the standard login code flow, simply provide the bot token generated by @botfather. You must still provide your API ID, as per user logins." | `core.telegram.org/api/bots` Login | 用平台 `api_id` + Bot Token 调 `auth.importBotAuthorization` 是官方写明的用法，不是绕路 |
| T2 | "2.1. You must obtain your own api_id for your application." | API ToS §2.1 | 平台申请、平台程序使用，字面成立。条款的主语是「应用」，不是「被驱动的账号」，没有要求 Bot 的所有者另申 `api_id` |
| T3 | "These credentials are intended solely for the operation of the products and services you offer through Telegram APIs, and, without limiting the foregoing, you are explicitly prohibited from making them available to the public." | Bot 开发者条款 §4.5 | 平台 `api_id` / `api_hash` 只用于平台自己的投递服务，不发给租户、不出现在控制台，与 `eng/01` 的「仅 delivery、只经 Secret 注入」一致 |
| T4 | "You understand and agree that any actions taken by others who authenticate using your credentials will be deemed as taken by you, regardless of how they gained possession of the credentials." | Bot 开发者条款 §4.5 | **连坐有了明文**：任何租户 Bot 经平台 `api_id` 发出的消息，在条款上都算平台的行为。ADR 原文写的「没有找到官方说明」不再成立，风险从推测变为确定 |
| T5 | "your TPA must not operate by proxy (i.e., using Bot API credentials supplied by other users) in an attempt to circumvent bans or content moderation." | Bot 开发者条款 §5.2(f) | 平台使用租户提交的 Bot Token，形态上就是「他人提供的凭据」。禁止的限定语是「意图绕过封禁或审核」，所以约束落在工程上：一个 Bot 被封或被拒后，不得把它的任务换给另一个 Bot 发出 |
| T6 | "(b) Your TPA must not harass or spam users with unsolicited messages;" | Bot 开发者条款 §5.2(b) | 投递目标限于租户自己控制的频道（`spec/06` 既有约束），不向第三方私聊群发 |
| T7 | "If you use the Telegram API for flooding, spamming, faking subscriber and view counters of channels, you will be banned forever." | `obtaining_api_id` Using the api_id | 封禁对象是 `api_id` 背后的账号，印证 T4 的后果是全平台投递停摆 |

## 二、工程约束与现状

| 约束 | 来源 | 现状 |
|---|---|---|
| 平台 `api_hash` 不出平台 | T3 | 只给 delivery 角色，只经 Secret 注入，其他角色配了就报多配（`crates/core/src/config.rs`） |
| 只驱动 Bot，不登录用户账号 | T1、T2 | 候选只取 `kind='bot'`；目标频道的发送身份在应用层限定为 Bot |
| 被封或被拒的 Bot 不换号重发 | T5 | 任务按 `sender_identity_id` 领取。新增 L2 `delivery_tasks_are_not_claimed_by_another_bot_of_same_tenant`：同租户另一 Bot 领不走，原 Bot 能领。反证：领取条件去掉 `sender_identity_id` 后恰好这一条红，已还原 |
| Token 被拒即停用身份 | T4、T5 | 身份标 `unauthorized` 并写审计，不再进入候选（`delivery_runtime` 已有 L2） |
| 目标限于租户自己的频道 | T6 | 既有约束，本次未改 |

## 三、未覆盖与残余风险

- T4 让连坐成为确定的条款后果，不是工程能消除的。缓解只能靠 T5、T6 两行约束，加上发现滥用时停用租户 Bot。
  是否需要「按租户投递量限速」或「滥用举报入口」，属于 WP-8 合规范围，本次不做。
- 控制台允许租户把目标频道的发送身份改成另一个 Bot。由租户主动操作，不属于「绕过封禁」，
  但被封 Bot 的租户可以这样换号。这个场景条款没有逐字覆盖，按 T5 的限定语判断不构成违约，没有加限制。
- Content Licensing and AI Scraping Terms 全文仍未取到（`spec/06` §1.3 的旧登记），与本 ADR 无直接关系。
- 本核对是工程层面的字面解读，不是法律意见。
