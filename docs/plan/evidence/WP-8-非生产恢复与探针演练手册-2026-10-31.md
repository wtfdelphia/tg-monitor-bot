任务：`WP-8-non-production-rehearsal`。

基线：`cloud/dev` 合并提交 `af33ec348882acc7b5fd78120d8e8592c1c96f85`（PR #71）。

本手册只用于本地 Compose 或批准的非生产隔离环境。它不构成生产授权，不连接生产数据库，

`docs/plan/proposals/WP-8-production-ops-acceptance.md` 单独批准。

## 一、执行边界

### 1.1 可以使用的环境

- 本仓库 `compose.yaml` 创建的本地 PostgreSQL、PgBouncer、Redis 和 MinIO；
- 新建、可销毁的非生产 PostgreSQL 恢复库；
- 只包含合成数据的探针租户；
- 与验收提交对应的本地构建产物和脱敏日志。

### 1.2 明确禁止

- 不把生产连接串、备份下载地址、Secret 或完整命令输出写入仓库；
- 不把真实生产备份恢复到本地或共享环境；
- 不把真实租户、真实身份或真实 Telegram 目标当作探针；
- 不启动 `deploy/systemd/tgm-tenant-purge.timer`；
- 不执行真实租户物理删除；
- 不使用 `docker system prune --volumes`；
- 不用“没有发现数据”替代“未执行或未验证”。

## 二、执行前登记

开始前在受控位置建立一份演练编号，不将敏感原始输出复制到 Git：

| 项目 | 记录要求 |
|---|---|
| 演练编号 | 非生产工单或本地唯一编号 |
| 执行窗口 | 开始和结束时间，包含时区 |
| 代码提交 | `git rev-parse HEAD` 的完整值 |
| 构建校验 | 二进制 SHA-256，不上传二进制 |
| 迁移版本 | 恢复库与测试库分别记录已应用版本 |
| 环境边界 | Compose 项目名或隔离恢复库标识 |
| 执行人 | 角色或工单账号，不写个人敏感信息 |
| 原始证据位置 | 受控存储引用，不填 Secret、连接串或消息正文 |

执行前先确认工作树没有把本地凭据、二维码、session、临时 dump 或日志加入 Git：

```bash
git status --short
git diff --check
```

发现敏感文件或无法确认归属的构建/容器残留时，先停止并处理归属，不继续演练。

## 三、恢复演练

### 3.1 创建隔离恢复目标

恢复目标必须是全新、可销毁的数据库或临时 PostgreSQL 实例，不能覆盖现有数据库。
恢复实例不得向业务进程、真实 Telegram、真实 KMS、生产 Redis 或生产对象存储开放网络访问。
恢复目标必须从干净的 `template0` 创建，并在恢复前预置批准的生产角色基线；不能把本地
Compose 的 `tgm_test` 成员关系当作生产角色基线。

执行前记录：

- 空库创建时间；
- PostgreSQL 版本；
- 恢复目标标识；
- 网络隔离和销毁方式；
- 负责执行恢复的角色是否为 owner 或超级用户。

本地 Compose 环境按仓库约定从零创建，不写 down 迁移：

```bash
docker compose up -d --wait
```

如果本地迁移或初始化失败，按 `docs/design/eng/02-本地环境与迁移.md` §3.2 执行：

```bash
docker compose down -v --remove-orphans
docker compose up -d --wait
```

### 3.2 恢复与结构核对

备份文件名、对象地址、密码和连接串只通过受控环境变量或 Secret 注入，不写入命令行、
Shell 历史或证据文件。示例中的变量只表示现场替换项：

```bash
export RESTORE_WORKDIR="$(mktemp -d)"
export RESTORE_DB_URL="<隔离恢复库连接，由受控环境注入>"

pg_restore --exit-on-error --dbname="$RESTORE_DB_URL" "<受控备份文件>"
```

`pg_restore` 由已批准的恢复运维角色执行，不强制 `--role=tgm_owner`，避免恢复到
`tenant_purge_batcher` 等专用对象所有权时触发无权 `SET ROLE`；恢复完成后再以 `tgm_owner`
或等价审计角色执行只读审计。若实际平台必须使用 `--no-owner`，应先证明恢复目标已经由
迁移/角色基线创建了所有对象所有者，并把该差异单独记录，不得静默切换。

恢复后按顺序执行，任何一步失败都停止，不手工修改恢复库制造通过结果：

1. 记录恢复开始与结束时间，计算恢复耗时；
2. 运行 `tgm audit-rls`，必须为零条违规；
3. 核对 `_sqlx_migrations` 成功版本、失败迁移和校验摘要；
4. 核对角色存在、`app_user` 非超级用户且非 `BYPASSRLS`；
5. 使用受限业务角色设置两个合成租户上下文，验证本租户可见、另一租户不可见；
6. 验证 `tenant_purge` 不能直接读取 `identity_secrets` 的凭据列；`app_user` 的凭据读取
   必须走既有信封加密访问链路，不能用表级拒绝替代该链路测试；
7. 核对关键表计数或脱敏摘要与备份记录一致；
8. 确认恢复库未连接真实 Telegram、KMS、Redis 或对象存储；
9. 记录恢复库销毁时间和销毁方式。

不得把 `tgm audit-rls` 全绿单独当作隔离通过；隔离反证必须使用受限角色连接，不能使用
owner、超级用户或测试控制角色替代。

### 3.3 RPO/RTO 记录

- **RPO**：记录备份时间与演练截点的差值；不能用“日备”代替实际时间差。
- **RTO**：记录从恢复开始到完成迁移核对、RLS 审计、角色检查和双租户隔离反证的耗时。
- 只记录实测值、测量窗口、环境规格和是否包含下载时间；不凭估计补写安全系数。
- 对客文档在产品/运维批准前，不把本次非生产演练值写成生产承诺。

## 四、探针租户演练

探针只使用合成租户和合成数据。建议把探针标识写入受控工单，而不是写进公开日志或聊天。

### 4.1 创建前检查

记录：

- 当前迁移版本；
- 探针创建前各相关表的脱敏计数；
- 共享 canonical、共享身份和其他租户的基线计数；
- 受控对象存储、Redis 和日志测试资源的基线计数；
- `tgm-tenant-purge` timer 未安装或保持停止。

本地前置核验只做目录、角色和回滚探针，不执行真实业务数据清理：

```bash
python3 scripts/tenant-purge-preflight.py --self-test
```

若要运行数据库探针，必须使用仓库规定的隔离测试库和受限角色；输出只保留脱敏摘要。

### 4.2 恢复窗口与候选枚举

至少准备以下合成状态：

| 状态 | 目的 | 预期 |
|---|---|---|
| `deleted` 且未满恢复窗口 | 验证年龄门槛 | 不进入候选；指定清理不得绕过 cutoff |
| `deleted` 且已满恢复窗口 | 验证正常候选 | 可以进入候选，等待后续受限清理 |
| `active` 或 `suspended` | 验证状态门槛 | 不进入候选 |
| `deleted` 但 `deleted_at` 缺失 | 验证缺失时间保护 | 不进入候选 |

候选结果必须记录数量、排序和排除原因。不能只记录“扫描完成”。

### 4.3 阻塞、恢复与幂等

按以下顺序执行，每个阶段都要保留退出码、脱敏结果和下一步：

1. 在已满恢复窗口的探针上制造受控在途任务，运行
   `tgm purge-deleted-tenants --tenant-id <探针标识>`；
2. 预期命令非零退出，结果为阻塞，不能写最终完成日志；
3. 确认后续类别没有越过阻塞点继续删除；
4. 清除合成阻塞后重新运行同一命令；
5. 核对各类别按批次推进、固定 `cleanup.done` 日志和根行删除结果；
6. 对已完成探针再次运行，预期结果为安全的幂等失败或空结果，不能误删其他租户；
7. 核对所有项目表无探针残留，并反证共享 canonical、共享身份和其他租户数据仍存在且未改变；
8. 若任意批次失败，保留已提交批次记录，下一次从当前状态重跑，不手工补写成功日志。

阻塞原因只能使用脱敏分类，例如 `not_due`、`blocked_inflight`、`blocked_shared_reference`、
`locked` 或 `failed`；不得输出完整连接串、密文、消息正文或外部平台凭据。

### 4.4 探针残留清理

演练完成后按顺序清理：

1. 停止所有临时 service 或测试进程；
2. 删除探针数据库、对象、Redis 测试键和日志测试记录；
3. 删除临时备份文件和恢复目录；
4. 检查工作树、`/tmp`、临时二维码目录和 session 目录；
5. 运行 `docker ps -a`、`docker volume ls -f dangling=true` 和 `docker network ls`，按名称、标签
   和创建时间确认本轮资源；
6. 只删除能确认属于本轮的容器、匿名卷和网络；无法确认归属的资源列入人工清单；
7. 对本片专属构建目录执行清理前，确认没有其他 worktree 或进程共享；
8. 记录 `df -h`，但不为释放空间删除源码、`.sqlx/`、证据或仍在使用的构建目录。

## 五、证据回填与裁决

把结果回填到 `docs/plan/evidence/WP-8-生产运维验收模板-2026-10-31.md` 的对应章节，
每项只允许使用 `pass`、`fail`、`blocked` 或 `not-run`。以下结果不能互相替代：

| 结果 | 可以声明 | 不能声明 |
|---|---|---|
| 恢复演练通过 | 非生产恢复路径在本次环境中通过 | 生产 RPO/RTO 已承诺 |
| 探针主库清理通过 | 合成租户主库清理链路通过 | 真实租户已删除或全副本已删除 |
| 受控对象/Redis 核对通过 | 本次批准范围内的受控副本已核对 | 备份、恢复副本或 Telegram 内容已删除 |
| 任何阻塞或证据缺失 | 阻塞原因和复查条件 | WP-8 或生产 timer 已通过 |

本手册的非生产演练完成后，仍需满足以下条件才能进入生产验收：

- 产品/法务确认同意文本、举报契约和对客留存边界；
- 运维确认备份、WAL、对象版本、Redis、日志和恢复副本策略；
- 目标机器安装并校验对应 `/usr/local/bin/tgm`；
- 生产只读检查、生产探针、告警接收人和值班升级责任已准备；
- 维护人对生产验收窗口和 timer 启用分别批准。
