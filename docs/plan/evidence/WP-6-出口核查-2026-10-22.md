## 二、同一套会话

`crates/db/src/repo.rs` 的 `issue_web_session_for_user_in_tx` 是共同的签发实现：
OIDC 经 `issue_web_session_for_user` 调用；控制 Bot 扫码经
`consume_confirmed_console_login_challenge` 在消费挑战的同一事务中调用。
租户来自已验证用户唯一的成员关系，不由浏览器参数指定；没有唯一成员关系时不签发。
两条路径都写入 `web_sessions`，分别标记 `oidc` 与 `bot_qr`。

`crates/app/tests/control.rs` 的两个成功用例本轮共用
`assert_issued_session_lifecycle`：使用入口实际签发的 session/CSRF cookie 调用
`/auth/me`，核对用户、租户和角色；再经 `/auth/logout` 注销，原 cookie 必须立即失效。
不使用手工插入会话或注入 `AuthContext` 代替这一段验收。

| 入口 | 实际经过的测试链路 | 验证边界 |
|---|---|---|
| OIDC | `/auth/oidc/start` → 本地 token/JWKS stub → 真实 RS256 验签 → callback → 会话落库与 cookie → 鉴权及注销 | 沿用现有本地 HTTP stub，不是 Telegram OIDC 真联调 |
| 控制 Bot 扫码 | HTTP 创建挑战 → `/bot/webhook` 认领 → 本地 Bot API 收到确认卡 → Webhook 确认 → HTTP 轮询消费 → 会话落库与 cookie → 鉴权及注销 | 不再直接调用 repo 或确认处理函数替代成功用例的 Webhook 链路；Bot API 是本地桩 |

## 三、钓鱼与重放反证

控制 Bot 成功用例在正确确认前，依次验证缺少或错误 Webhook secret、群聊认领、
私聊与操作者不一致、其他账号再次认领、其他账号持正确确认材料、
群聊确认、私聊与操作者不一致的确认。
这些请求不能提前签发 cookie，数据库会话仍为空；合法认领后仅为 `awaiting_confirm`。
本地 Bot API 记录的确认卡必须发给认领者，含浏览器来源 IP、User-Agent、确认码及对应确认按钮。

错误确认码另用独立挑战核对：合法认领者提交错误码后，挑战进入 `rejected`，
随后即使用正确码重试也不能恢复或签发会话。首轮测试错误地预期该状态仍为
`awaiting_confirm`，因实际返回 `rejected` 而失败；核对 repo 的既有终态逻辑后拆分用例，
未为使测试通过而修改生产行为。

正确确认后，签发对象必须是认领并应答的账号；会话 token 与二维码 nonce 不相等。
重复确认及重复轮询不能产生第二条会话，已消费挑战轮询返回 404。
既有多租户成员不猜租户、已确认但过期不签发的用例一并重跑。

OIDC 沿用 PKCE、浏览器绑定、nonce/state 一次性消费、issuer/audience/expiry/subject
校验、固定签名算法、真实 JWT header 篡改拒绝及成功回调重放拒绝。
数据库回归核对 `auth_lookup` 的签发/注销/管理权限边界、受限业务角色不可访问鉴权表、
成员移除失效、并发认领以及 update 重投幂等。
数据 Bot 入口的 Webhook secret、频道消息去重、callback 资源租户绑定与成员反查测试同时执行。
