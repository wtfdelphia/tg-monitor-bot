## 二、Telegram 真机验证

### 2.1 前置条件

由测试环境提供方准备以下材料：

- 可回收的 Telegram 测试账号；
- 已开启 2FA 的测试账号，或同一账号可安全开启并在测试后撤销；
- 可确认扫码的手机；
- 可触发非默认 DC 的账号或测试素材；
- 租户自带 `api_id` 与 `api_hash`，通过本地 Secret 注入；
- 可写的临时 session 加密存储位置。

截至 2026-11-13，WP-2 已有 QR 真机执行入口及 T1、T2–T6 的记录；消息更新、`catch_up`
与硬停恢复另有记录。不得再把“缺完整 harness”作为当前状态，也不重复已完成的真机项目。
现有记录未单独确认同 DC 正常扫码分支；如 G1 裁决要求该项，需单独登记范围后再安排，
不能把包含 DC 迁移的 T1 记作该分支通过。项目内单元测试仍不能替代这些真实账号证据。

### 2.2 六项验证方法（历史判据）

表中步骤说明原验收判据，不构成本轮操作指令。WP-2 已有记录的项目不重跑；同 DC 分支是否
需要单独验收，由 G1 责任方裁决后再安排。

| 编号 | 操作 | 通过判据 | 失败处置 |
|---|---|---|---|
| T1 | 启动登录流程，手机扫描当前二维码 | 同一 DC 完成授权，状态进入 `Authorized` | 保留错误类别和脱敏时间线，不记录 token |
| T2 | 优先使用 Telegram Test DC 的保留测试号码，记录初始 DC 与目标 DC | 收到 `MigrateTo` 后在目标 DC 导入 token，授权成功 | 若无法取得素材，登记 RK-01 未验证，不伪造通过 |
| T3 | 使用开启 2FA 的账号扫码 | 进入密码态；错误密码不推进；正确密码完成授权 | 清除输入，不记录密码；错误次数按 Telegram 结果处置 |
| T4 | 等待二维码过期后刷新 | 旧 token 被拒绝，新 token 可继续登录 | 记录过期时间与刷新代次，不记录 token 明文 |
| T5 | 授权后加密保存 session，停止并重启进程 | 重启后恢复授权，不要求再次扫码 | WP-2 已用临时库与开发 `EnvKek` 验证加密落库和恢复；该结果不等于生产 KEK 后端或目标环境验收，见 `WP-2-qr-login-live-2026-10-21.md` |
| T6 | 手机端撤销该会话，再触发请求或更新 | 识别 `unauthorized`，身份状态变为失效，租约/worker 停止使用 | 记录状态变更和停止动作，不保留旧 session |

### 2.3 消息与断线恢复

原方案在 T1 或 T5 后安排以下步骤。WP-2 消息更新与恢复已有独立记录；此列表不是要求重跑：

1. 从测试频道发送一条带唯一标识的文本消息；
2. 记录 update 到达、消息 ID、接收时间和去重结果；
3. 主动断开网络，再恢复网络；
4. 检查 catch-up 是否补齐、是否重复、是否产生错误状态；
5. 清理测试消息和临时 session。

证据只保留：测试时间、账号脱敏标识、DC、测试版本、结果、错误类别、失败处置和证据
文件路径。不得保留手机号、`api_hash`、session、二维码内容或密码。

原测试方案曾记录 `MigrateTo` 的 Test DC 素材。该记录不是当前操作指引；不得为取得限流或
迁移证据而重复探针、加压或主动制造 FloodWait。若隔离测试账号在正常使用中自然收到
FloodWait，只记录脱敏观察并停止追加请求，按 `G4-真实限流退避闭环.md` 登记证据。

## 三、控制台 OIDC 联调准备

### 3.1 当前环境是否可行

当前 Docker、PostgreSQL、Redis、MinIO 可用于联调依赖；`tgm serve --role control-plane`
已经提供 OIDC 起始、回调和会话签发入口，本地 token/JWKS stub 已有成功与失败路径测试。
应用入口不再是阻塞，但本地测试不证明真实 Authorization Code + PKCE、BotFather
配置或 JWKS 换钥通过。真实执行仍须受控 HTTPS 地址、专用 provider 配置和安全注入，
按下方矩阵逐项保存脱敏结果。

当前实现的回调路由是 `/auth/oidc/callback`。下方 URI 仅是历史示例；执行时必须以
实际路由设置 `TGM_OIDC_REDIRECT_URL`，并与 BotFather 登记值完全一致。

### 3.2 准备步骤

1. 选择一个明确的环境地址：受控 tunnel、预发或正式 HTTPS 域名；不要在不同地址间混用
   callback。当前不要把 `localhost` / 普通 HTTP 当作 OIDC 已支持的联调地址。
2. 在 BotFather 的 Bot Settings > Web Login（Login Widget/OIDC）设置中登记：
   - 页面 origin，例如 `https://console.example.test`；
   - 完整回调 URI，例如 `https://console.example.test/auth/oidc/callback`。
3. 通过 Secret 管理注入以下配置，不写入仓库；Client ID/Secret 是 Telegram OIDC token
   exchange 的必要输入：

   ```text
   TGM_OIDC_BOT_ID
   TGM_OIDC_ALG=RS256
   TGM_OIDC_REDIRECT_URL
   TGM_CONTROL_BOT_TOKEN
   TGM_OIDC_CLIENT_SECRET
   ```

   Telegram 当前文档还会在 BotFather Web Login 设置中提供 Client ID 和 Client Secret；
   它们只能放在受控 Secret 中。仓库配置清单以 `TGM_OIDC_BOT_ID`、`TGM_OIDC_ALG`、
   `TGM_OIDC_REDIRECT_URL`、`TGM_OIDC_CLIENT_SECRET` 和 `TGM_CONTROL_BOT_TOKEN` 为准。
4. 当前回调实现由服务端生成并保存 `state`、`nonce` 和 PKCE verifier；浏览器只拿到
   不可预测的授权请求参数。
5. 服务端将授权码换成 token，按配置固定算法验签，校验 `iss`、`aud`、`exp`、`nonce`，
   并把一次性 `state`/`nonce` 作废。
6. 回调地址不匹配、过期 token、未知 `kid`、JWKS 获取失败和 nonce 重放都必须拒绝登录。

### 3.3 真实联调矩阵

| 场景 | 预期结果 |
|---|---|
| 正常授权码 + PKCE | 回调成功，签发 `web_sessions` |
| redirect URI 不匹配 | 拒绝，不创建会话 |
| state 缺失或不匹配 | 拒绝，不创建会话 |
| nonce 重放 | 拒绝，不创建会话 |
| `alg` 被改写 | 拒绝，不按 token header 选择算法 |
| `kid` 未知 | 只允许一次受限刷新；仍未知则拒绝 |
| JWKS 拉取失败 | 拒绝并返回可重试错误，不跳过验签 |
| 过期 `id_token` | 拒绝，不创建会话 |
| JWKS 换钥，新旧 key 并存 | 新旧有效 token 都按实际 provider 结果验收 |

本地 stub、拒绝路径与 JWT 篡改/重放已有 WP-6 记录；此矩阵剩余的是受控 HTTPS、真实
Telegram provider、BotFather 配置和真实 JWKS 行为联调。没有这些外部条件时，状态为未验，
不是 callback 实现缺失，也不通过重复本地 stub 测试替代真实联调。

Telegram 文档对测试环境中的 HTTP 例外说明属于 Mini Apps 测试路径，不能据此推断 OIDC
callback 可使用本地 HTTP；本项目 OIDC 联调仍按 HTTPS tunnel 或预发域名准备。

## 四、非平台自有目标租户 `api_id` 验证

### 4.1 操作步骤

由目标租户操作员使用自己的 Telegram 账号执行：

1. 登录 `https://my.telegram.org`；
2. 打开 `API development tools`；
3. 按页面要求填写应用名称、短名称和平台信息；
4. 完成申请并确认页面是否返回 application identifier 与 `api_hash`；
5. 退出页面，不向项目群、仓库或聊天回传密钥。

### 4.2 只回填脱敏结果

在 G1 证据中只记录：

- 执行日期；
- 账号是否属于目标租户；
- 是否能进入申请入口；
- 是否成功提交；
- 是否取得 application identifier；
- 是否遇到账号、地区、频率或其他限制；
- 失败类别和下一步处置。

不得记录或提交：`api_hash`、手机号、验证码、2FA 密码、session、完整页面截图或任何
可重放凭据。

通过判据是：目标租户能用自己的账号完成申请，并确认归属模式为“租户自带 `api_id`”。
Telegram 官方说明每个号码当前只能关联一个 `api_id`，并要求发布应用前取得自己的
`api_id`；这些是设计输入，仍需以本次目标租户的实际结果回填 G1。
