## 一、可重跑入口与边界

新增 `scripts/tenant-purge-preflight.py`，仅用 Python 标准库、现有 Docker 和容器内 psql：

```bash
python3 -B scripts/tenant-purge-preflight.py --self-test
python3 -B scripts/tenant-purge-preflight.py \
  --container kms-kek-postgres-1 --probe-safety
```

默认只读核查显式指定的本地 Compose postgres 服务；Docker 固定本地 Unix socket，
不接受数据库 URL、远程 Docker context、任意数据库名或凭据参数。
容器检查只取 id、运行状态和 Compose 服务标签，不读取或输出容器环境凭据。
主库连接用 `BEGIN READ ONLY` 读取目录、迁移版本和 checksum，最后回滚；不读取业务内容。

`--probe-safety` 另以 `tgm_test` 连接 `tgm_test_control`；只创建事务内临时表、运行回滚探针
及短期事务级 advisory lock，不创建新数据库、不改全局角色或持久业务表。
探针连接设置语句、锁等待和空闲事务超时，正常结束时回滚并关闭连接。

完整本地输出为 `/tmp/tgm-wp8-tenant-purge-preflight-20261028.json`，记录目录与结果，
不含数据库连接串、消息正文、session、token、API hash 或对象 key。

## 二、目录核验结果

现有本地 PostgreSQL 迁移版本及 SHA-384 checksum 与工作树一致，包含最近的
`0054_tenant_lifecycle_restricted_deletes.sql`。
目录契约覆盖实际表、外键完整列顺序、部分 SET NULL 列、删除/更新动作、校验和延迟属性，
以及用户定义的删除触发器；发现新表、额外引用或语义变化即失败，不能静默沿用旧清理图。

确认的关键依赖：

- `tenant_events → canonical_events`、媒体成员端指向 canonical 使用 NO ACTION；保护仍被租户或相册引用的事件。
- `delivery_logs → delivery_tasks`、身份上的订阅/目标/投递使用 RESTRICT；需要先清理或报告限制性引用。
- 同意记录同时级联依赖租户和成员；只清空根行的其他子表并不能避免成员删除造成超限级联。
- 身份上的通知、Bot 更新和中转任务使用单列 CASCADE，并非 RESTRICT。不能假设跨租户引用一定由 FK 拒绝保护。
- `media_relay_jobs` 同时引用事件与接收身份，两条外键不要求其身份一致；删除身份可能连带删除属于其他事件的中转记录。
- `media_archive` 是共享对象记录，不进入租户清理范围；`console_login_challenges` 没有租户 FK，继续由鉴权留存处理。

工具的契约只判断目录形状，不校验 RLS 表达式、清理角色权限或租户业务数据。
另外核对根表 owner、RLS 标志、现有相关角色的根表有效 DELETE 权限与非系统 definer 清单，
这些只是当前授权基线，不等于未来角色的完整权限审计。
输出明确保留 `physical_delete_implemented=false`、`permission_audit_verified=false` 和
`all_copies_deleted=false`，不把目录通过升级为删除功能通过。

## 三、隔离 SQL 与锁反证

以非超级用户且无 BYPASSRLS 的 `tgm_test` 在临时表复现：

1. 一行成员关联超过批次上限的同意记录；删成员时父语句只报告一行，但同意记录全部被 CASCADE 删除。
   这证明 `rows_affected <= BATCH_LIMIT` 不足以保证实际删除规模受限。
2. 先限批清理同意记录，再清成员和根行可控制直接子表规模；这只是最终阶段的可行性探针，
   不授权在仍有共享阻塞时提前删除同意记录。
3. 删除与故意失败的日志写入处于同一子事务时，删除一起回滚。
4. NO ACTION/RESTRICT 拒绝身份删除时，已经触发的其他级联操作也不留下部分删除。
5. 解除保护引用后，身份删除会连带删除临时表中另一租户的通知、Bot 更新及身份不一致的 job；
   事件本身仍可存在。显式检查全部身份子项可避免这类误删，不能只检查原始事件或 RESTRICT 引用。

锁探针用两个真实连接验证事务排他锁会拒绝另一连接的共享 try-lock，回滚后可重新获取。
测试只短暂使用现有锁名协议，租户和身份采用随机负值以避免碰到真实对象；全局共享回收键保持原协议。
它证明 PostgreSQL 锁原语和键表达式工作，**不证明现有写入口、全局回收、媒体组与未来 purge 已无死锁**。
输出另标 `production_lock_protocol_verified=false`。

## 四、下一步实现约束

优先复用现有生命周期围栏和事务纪律，候选进入后先取租户生命周期排他锁，再复查 deleted 与数据库时间。
租户事件清理和共享回收阶段的键顺序须与现有写入口一致；跨批不持锁，锁冲突返回待重试，
不在持有低层锁时阻塞取得高层锁。

按实际外键拓扑先清投递日志和任务、租户投影、规则子项和规则、配置与其他私有记录。
共享事件阶段沿用全局回收、身份及媒体组保护，不删其他租户投影、共享身份、档案或对象。
身份删除前须对目录中每条真实入边复查，包含 CASCADE，不允许把隐式级联当作引用已经解除。
成员、同意记录、日志和根行在最终阶段仍须满足限批、失败回滚和日志存证；没有验证有界的残留不得交给根级联。

后续仍须实施独立 `tenant_purge`、受限最终根删除入口、C15 及真实受限角色的并发/回滚/跨租户测试，
以及 app/CLI、调度样例、迁移重入、SQLx prepare 和完整门禁。
当前没有运行真实业务删除，没有创建迁移、权限策略或清理角色，不宣布整个物理删除任务完成。

补充核验确认 `tenants` 当前没有 ENABLE/FORCE RLS，owner 为 `tgm_owner`；
`app_user`、`tenant_lifecycle`、`tenant_cleanup`、`shared_cleanup` 均无根表 DELETE。
目录中没有非系统 definer；实现侧 A8 和 ADR-0004 均全面禁止这类函数。
原提案又禁止给 purge 直通根表 DELETE，普通 invoker 不能解决缺少权限的问题。
因此新增 `../proposals/WP-8-tenant-purge-finalizer-security.md` 请求精确安全例外，
本次前置目录核验不据此修改 A8 或创建函数。
维护人随后已单独批准该例外，但其 §3.3 的身份写入围栏反证触发再次升级，
见 `WP-8-注销租户身份写入围栏反证-2026-10-28.md`；不能把前置目录通过当作这个后续前提成立。
