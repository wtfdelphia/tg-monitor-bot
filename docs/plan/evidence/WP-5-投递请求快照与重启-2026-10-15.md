## 实现与不变量

- 新增 `0018_delivery_random_id.sql`、`0019_delivery_payload_snapshot.sql` 及
  相同字节的测试镜像；已应用迁移没有改动。
- 入队事务同时写入稳定的正整数 `telegram_random_id`、发送身份、目标、动作
  和 `payload_snapshot`。快照保存来源 chat/message、媒体类型、渲染后的 HTML
  文本与解析模式，不复制凭据或传输路径未使用的文件字段。
- 运行时角色只能更新任务状态相关列；触发器阻止改写请求快照、随机 ID、路由、
  关联键和幂等键。owner 仍是受信管理边界，不声称抵御其停用约束或重建任务。
- 投递读取只查询任务行；不再关联可变的事件、来源订阅或规则版本重建请求。
  相同幂等键重复入队保留原请求，不覆盖已固化值。
- Telegram 发送路径显式传递稳定 ID；从匹配该 ID 的更新或当前 RPC 的
  `updateShortSentMessage` 成功响应回填消息 ID。后者没有独立的随机 ID 字段，
  由当前 RPC 绑定请求；最终复查补上该分支回归，避免发送成功后仍反复退避。
  `RANDOM_ID_DUPLICATE` 或缺少消息映射时继续退避，不换 ID，也不猜测 `DONE`。

## 数据库与应用验证

`crates/db/tests/delivery.rs` 使用受限 `app_user` 验证领取、完成、失败退避、
死信、租户隔离、租约回收、随机 ID 约束、快照不可变、非法快照拒绝及历史任务
隔离。合法状态回填仍可完成。对触发器的补验由管理连接执行预期失败的更新，
不以该连接替代运行时角色的权限验证。

`crates/app/tests/pipeline.rs` 在首次尝试后更改事件正文与来源定位、订阅展示
信息、目标配置、规则快照和当前规则，再以相同幂等键提交不同内容；旧任务
构造的完整 `DeliveryPayload` 仍等于初始值，重试复用原 ID 并完成本地回填。

`crates/app/tests/delivery_restart.rs` 清空子进程环境后只传入受限业务连接。
模拟 transport 在请求前、模拟发送后与响应丢失后留下确定检查点；父进程强杀
子进程，再由新进程回收过期租约或领取到期任务。重启前后记录的完整请求按
字节比较，均相同，任务最终 `DONE` 且回填模拟消息 ID。测试 transport 不连接
Telegram，因此没有证明外部平台去重，也不是实际 `tgm worker delivery` 进程
的端到端真机验收。

`C6` 检查运行时角色是否拥有投递不可变列的 UPDATE 权限。双遍反证为
`app_user` 授予 `payload_snapshot` 列级 UPDATE，要求仅 `C6` 报红；显式撤销
列级授权后要求审计恢复，并比较目录快照，不能只看全绿。

## 历史任务与发布边界

2026-10-15 查询本地 Compose 的 `tgm.delivery_tasks`，按状态汇总结果为空。
本地没有可处置的历史任务；这不是生产数据盘点。迁移记录中版本 18、19 均为
成功。

历史任务缺少随机 ID 或快照时，不会被自动领取或回收；迁移不回填。不应从
当前事件或规则推断历史请求内容。对已有部署，发布前仍须暂停旧 worker，按
任务核对外部发送状态，无法证明请求内容和结果的任务继续隔离。

快照不改变已有删除级联和留存策略，也不解决多数据库共享发送账号、随机 ID
全局协调、数据库恢复后的 ID 重用或 `MemorySession` 更新状态恢复问题。
