## 二、OIDC 发现与升级范围

2026-11-16 核对 Telegram 官方文档：
<https://core.telegram.org/bots/telegram-login>，OpenID Connect 的 Available Scopes、
User Data Structure、Signing algorithm；公开 discovery：
<https://oauth.telegram.org/.well-known/openid-configuration>。

文档分别定义 `openid.sub` 与 `profile.id`，示例中两者不同。修复前
`crates/app/src/control.rs::validate_oidc_id_token` 将 subject 交给
`crates/core/src/oidc.rs::validate_id_token_claims` 解析为 Telegram user ID，随后用于
成员反查与会话签发。现有桩把两个值设为同一个用户 ID，无法排除真实 provider 的误绑定。
这是源码与协议文档的差异发现，尚未通过真实 token 验证。

用户已于 2026-11-16 批准具体修复，见
[`G1-OIDC真实身份映射与联调.md`](../proposals/G1-OIDC真实身份映射与联调.md)。
现已把非空 subject 与正整数 `profile.id` 分开，只有后者进入成员反查和会话签发；不回退解析
subject，不改变成员权限。`sub=8002`、`id=7001` 的不同租户成员测试确认只给 `7001` 签发；
移除该成员后拒绝，不借用 subject 对应成员。缺失或非法 id、issuer/audience/azp/expiry/nonce
等拒绝测试通过，RS256/ES256 的 profile 配置约束已同步。
discovery 同时支持 Basic 和 Post 两种客户端认证，未将现有 form secret 擅自判错。

现场主机为 Ubuntu 22.04.5（glibc 2.35），不是此前已验收的 Rocky 9.8。
当前 `https://172.20.66.24` 使用独立代理与现有 IP SAN 开发证书；本机正常 TLS 验证通过。
`/healthz=200`、未登录 `/auth/me=401`、缺 state 的 callback=403、业务 API=404；
登录起点=302，目标为固定 Telegram provider，`scope=openid profile`、PKCE=S256，
state/nonce 存在且 cookie 含 Secure/HttpOnly，redirect_uri 与配置逐字一致。
这些探测没有提交 provider 授权请求，不代表真实登录通过。后端使用本地修复构建，Bot API
配置为不可用合成值；没有发送 Telegram 消息。

操作者随后完成 Telegram 授权，但网站 callback 返回 `OIDC_PROVIDER_UNAVAILABLE`，
所以真实登录仍未通过。使用与应用一致的 reqwest/Rustls、空进程环境访问公共端点时，
discovery 返回正常 JSON，JWKS 返回 `HTTP 200`、`Content-Encoding: gzip`，响应字节为
gzip 数据；原客户端未启用 gzip 解压，`JwkSet::from_bytes` 在 JSON 首字节处失败。
同一探测显式经过本机代理时曾获得未压缩 JSON，可解析出四把公钥；不能用这条不同路径的
成功结果替代应用访问路径验证，也不能据此把问题归为 Client Secret 错误。

现已启用 reqwest 自带的 gzip 解压；token 和 JWKS 共用客户端，解压后的数据继续经过既有
流式大小限制。失败日志只记录固定阶段、固定原因和服务端 request ID，不记录请求 URL、
授权码、token、secret 或响应正文。新增压缩 token/JWKS、解压后超限及日志脱敏回归，
OIDC 定向测试通过；clippy 和依赖检查通过。重建后，相同应用访问路径的 JWKS 解析通过，
返回四把公钥；隔离服务已重启，TLS 验证通过、`/healthz=200`、未登录 `/auth/me=401`。
这证明已修复公共密钥获取的现场故障；历史 callback 没有阶段日志，不能还原其完整执行
过程。旧授权码未重放；后续全新浏览器流程已完成，先记录未邀请拒绝，再在隔离租户中邀请测试用户并核对成功会话归属。

下一次浏览器授权后，callback 返回 `CONDITION_INVALID / OIDC authentication failed`。
当时只为 provider 不可用分支增加了诊断，不能从该错误断定是换码被拒绝、签名问题或
claims 不符。现已为这些拒绝分支补充固定阶段和固定原因；token endpoint 的 OAuth 错误
只记录允许清单内的错误码及 HTTP 状态，未知错误归为 `provider_rejected`，不记录原始
错误描述或正文。换码客户端认证已对齐 Telegram 官方手工流程的 HTTP Basic，secret
