## 二、判据 1：QR 全分支实测

驱动层真机实测（`docs/plan/evidence/WP-2-qr-login-live-2026-10-21.md`，生产 DC，测试用户账号）：

| 分支 | 结果 | 要点 |
|---|---|---|
| T1 扫码授权 | pass | 第 7 代二维码被扫码完成授权 |
| T2 `MigrateTo` | pass | 真机收到 `LoginTokenMigrateTo dc 2 -> 5`，切 DC 后导入成功 |
| T3 2FA | pass | `SESSION_PASSWORD_NEEDED` 后先输错一次，状态停在 `AwaitingPassword`；再输对后授权 |
| T4 过期刷新 | pass | 过期 token 导入返回 `400 AUTH_TOKEN_EXPIRED`，刷新得到新 token |
| T5 加密落库后恢复 | pass | 经 `save_session` 加密落库、`load_session` 恢复，worker 只凭库内 session 上线 |
| T6 撤销会话 | pass（修复后） | 真机暴露「失效 session 仍置 `online`」缺陷，修复后 0.89 秒内转 `unauthorized`，审计一条，租约可接管 |

真机事件序列同时喂给 `tgm_tg::qr::QrLoginState`，T1–T4 运行中没有出现状态机拒绝。
RK-01 已据 T2 标为已验证（`docs/design/plan/01-风险登记.md`）。

控制面接入后的端到端真机验收（`docs/plan/evidence/WP-2-qr-login-control-2026-10-21.md`）：
经 `POST /api/v1/identities/login/qr` → 轮询 → `POST /api/v1/identities/login/password` 完成 8 代二维码、
2FA、加密落库、同意记录与审计各一条，随后 worker 上线并正常退出。

两份证据各自登记的未覆盖项，见 §四。

## 三、判据 2：租约抢占行为可复现

`docs/plan/backlog/T-0001-租约repo层与抢占测试.md`（`status: done`），测试在 `crates/db/tests/lease.rs`，
全部以受限角色 `app_user` 连接：

- `lease_acquire_takeover_and_stale_worker_are_guarded`：有效租约不被别的 worker 抢走，过期后接管 token 递增，旧 worker 续租被拒；
- `lease_renew_keeps_token_and_moves_deadlines`：续租不变 token、推进期限；
- `expired_lease_race_has_exactly_one_winner_and_release_preserves_monotonicity`：两个连接并发抢过期租约，恰好一个成功，释放后 `fencing_token` 保持单调；
- `lease_expiry_is_rechecked_after_row_lock_wait`：行锁等待结束后重新检查过期。

worker 运行链（`docs/plan/evidence/WP-2-mtproto-worker运行链-2026-10-19.md`）在此基础上有 8 条 L2，
并做了反证：把 `lease_is_held` 改成恒真后，恰好依赖 fencing 的三条变红，还原后全绿。
T6 真机修复后，`lease_takeover=ok` 也确认了转 `unauthorized` 时租约立即可接管。

## 四、包内缺口（不属于出口判据）

| 缺口 | 现状 | 影响 |
|---|---|---|
| worker 经更新流 `next_incoming` 实时收消息并写 `canonical_events` | 无真机证据。媒体真机工具走的是 `read_messages` 与 `canonical_event()`，不是实时更新流；落库与去重判据只有 L2 | 包内容「消息接收与落库」的真机部分未验 |
| 断线后 `catch_up` 补齐 | 无真机证据；现有真机工具都用 `without_catch_up()` | 同上 |
| 运行中周期授权校验识别撤销 | 未单独测；T6 识别发生在上线前校验，两条分支共用 `check_authorized` 与 `mark_unauthorized` | 低 |
| 60 秒定时落库后进程重启恢复 | T5 验证了落库后恢复，未验证定时落库路径 | 低 |
| 控制面重新授权（`identity_id`）真机路径、端点上的密码错误分支 | 有 L2；真机未覆盖。密码错误分支在驱动层 T3 已实测 | 低 |
| spec/08 §五 第 2 条「通知租户需要重新授权」 | 未实现，代码中没有对应调用 | 状态机三件事缺一件 |
| spec/08 §4.5 混沌清单 | 一条未跑 | 多实例上线前置；首发形态 A 固定单实例，不阻塞首发 |
| 周期校验的请求量与 `FLOOD_WAIT` | 未评估 | 身份数量大时再评估 |

## 五、建议

1. 由人决定是否宣布 WP-2 通过。如果宣布，建议写明「两条出口判据满足，消息实时接收与 `catch_up` 的真机验证、租户通知另行跟踪」。
2. 下一次真机窗口补实时收消息落库与 `catch_up` 补齐，二者可以在同一次扫码登录中完成。
3. 租户通知依赖通知通道的设计，单独提案。
