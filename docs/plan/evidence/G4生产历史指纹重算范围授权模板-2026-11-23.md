### 2.1 代码核对后的字段与关联范围

以下字段依据 `G4-L3-notify-dedup.md`、`crates/core/src/notification.rs`、`crates/db/tests/notify_dedup.rs` 与 `migrations/0063_g4_notify_dedup.sql` 列出，供申请人按实际生产 schema 核对并填写批准范围。字段清单不代表当前只读角色已经拥有权限。

| 数据来源 | 仅为重算需要的候选字段 | 用途 |
|---|---|---|
| `notify_dedup` | `tenant_id`、`fingerprint`、`target_ref`、`status`、`last_sent_at`、`expires_at` | 选取 `SENT` 记录和已存指纹；按批准租户、时间、留存、行数范围限制 |
| `delivery_tasks` | `tenant_id`、`id`、`tenant_event_id`、`notification_fingerprint`、`notification_target_ref`、`status`、`completed_at` | 关联对应的成功投递任务；候选路径限定 `status='DONE'` 且 `completed_at <= last_sent_at`，按 `completed_at DESC, id DESC` 取一条 |
| `tenant_events` | `tenant_id`、`id`、`canonical_event_id`、`matched_keywords` | 关联租户事件及指纹所需命中词 |
| `canonical_events` | `id`、`sender_id`、`text`、`caption`；`content_hash` 仅在批准后用于识别已清理行 | 前四项是指纹输入；`content_hash` 不参与算法且不得导出。正文只在获批隔离进程内存中用于重算 |

候选关联路径为 `notify_dedup → delivery_tasks → tenant_events → canonical_events`。批准人需核对生产 schema、既有 RLS/列权限及角色成员关系，确认只读身份能够按受限范围关联数据且没有写入、DDL、函数副作用或其他超范围访问。若无法证明权限和访问路径，申请保持待批，不扩大权限或改用 owner 身份执行。

指纹算法按代码版本 `tgm:l3:v1` 复核：SHA-256 输入是 UTF-8 规范串 `tgm:l3:v1\0<sender_id或空串>\0<按 Unicode 字节序排序并去重的命中关键词 JSON>\0<text 优先、否则 caption 的前 300 个 Unicode 标量值>`。正文与命中词不得写入结果。算法版本不一致或源字段已脱敏时归入 `not_recomputable`，只输出计数和经批准的原因类别，不尝试推断原值。

```text
requested_status_filter=SENT
requested_task_status_filter=DONE
requested_task_completion_bound=completed_at <= notify_dedup.last_sent_at
requested_join_path=notify_dedup -> delivery_tasks -> tenant_events -> canonical_events
requested_fingerprint_algorithm=tgm:l3:v1
requested_result_fields=aggregate counts only; message fields and content_hash excluded
requested_tenant_scope=not-provided
requested_business_time_window=not-provided
requested_as_of_timestamp=not-provided
expired_dedup_rows_in_scope=not-approved
requested_row_batch_limit=not-provided
requested_runtime_limit=not-provided
content_fields_read_authorization=not-provided
production_role_and_privileges=not-provided
```

### 2.2 当前角色与列权限复核

按 `cloud/dev@994ab82a2f941ec50bc37146fbfb16d5ff6758c1` 的角色和 GRANT 迁移核对，当前没有可直接用于本扫描的专用只读角色。

| 现有角色 | 已核对边界 | 适用性 |
|---|---|---|
| `tgm_owner` | `NOLOGIN`，承担对象所有权与迁移 | 不能作为扫描登录身份 |
| `app_user` | 有 `canonical_events` 表级 DML。该共享原始事件表没有 `tenant_id` 和 RLS。业务代码规则要求原始事件查询经租户投影，不能把该角色改作跨范围扫描身份 | 不适用 |
| `tenant_cleanup` | 对 `notify_dedup` 等表有清理所需 `DELETE`，读取列也不包含全部重算输入 | 不适用 |
| `shared_cleanup` | 对 `canonical_events` 有 `DELETE`；只能读取有限事件元数据，并可按共享清理策略读取对应的旧 `tenant_events` 投影 | 不适用 |
| `tenant_lifecycle` | 可读取有限 `delivery_tasks` 状态字段并更新任务生命周期字段；不具备指纹重算所需读取范围 | 不适用 |
| `platform_ops`、`auth_lookup` | 分别覆盖平台日志和鉴权查询，不含指纹重算所需事件/投递数据列 | 不适用 |
| `tenant_purge` 系列 | 具有物理清理、函数执行或清理批处理权限 | 不适用 |

这三张租户事件/投递表的业务租户隔离策略面向 `app_user`，另有针对特定维护角色的清理/生命周期策略。那些策略各自服务限定操作，不覆盖本扫描所需的完整读取关联路径。`canonical_events` 是无 `tenant_id` 的共享表，不能仅给扫描角色这些表的 SELECT 列权限后就声称租户范围已由 RLS 限定。不要把 `app_user`、`tgm_owner` 或清理身份填入下方“只读数据库角色”。

## 四、停止条件

任一项触发即停止查询，不扩大范围，不自动重试：

- 连接目标、角色属性、成员关系或权限与批准记录不一致；
- 查询影响生产负载超过批准阈值，出现锁等待、超时或监控告警；
- 返回结果包含消息正文、凭据、可识别个人信息或未批准字段；
- 行数、批次数、时间窗口或执行时长达到批准上限；
- 数据完整性、指纹版本或重算算法版本无法与当前口径对应；
- 停止联系人不可达，或发生其他未预先批准的副作用。
