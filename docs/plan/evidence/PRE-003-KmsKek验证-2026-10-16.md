## 实施范围

- 在 `bins/tgm/src/kms_kek.rs` 实现 `Kek`：`wrap` 调用 KMS `Encrypt`，`unwrap` 调用 `Decrypt`；SDK 错误统一映射为 `KekError::Crypto`。

## 2026-10-17 OCI 方案 B 前提反证

候选方案 B：部署在 OCI VPS 上，由 IAM Roles Anywhere 的 `aws_signing_helper update` 定期改写 shared credentials 文件，应用经 `AWS_SHARED_CREDENTIALS_FILE` 读取，不启用 `credentials-process` feature。

- 源码：`aws-config` 1.12.0 `ProfileFileCredentialsProvider` 的文档注释写明 profile 文件只加载、解析一次，「Parsed file contents will be cached indefinitely」；`ProviderConfig.parsed_profile` 为 `OnceCell`，静态 key 在构建 provider 链时固化为 `BaseProvider::AccessKey`。
- 实测：在 `/tmp` 下用同一固定版本与 feature 组合（`behavior-version-latest`、`default-https-client`、`rt-tokio`）跑了一次性探针。分别对单独的 `ProfileFileCredentialsProvider` 和 `aws_config::defaults(...).load()` 的默认链操作：先读到 `AKIDFIRST`，随后改写文件，第二次调用仍返回 `AKIDFIRST`。
- 结论：进程运行期间不会重读刷新后的文件。Roles Anywhere 会话凭据到期后，KMS 调用将失败，直到进程重启。方案 B 的前提不成立，不予采用；本仓库代码与依赖均未改动。
- 尚可选择的方向：启用 `aws-config` 的 `credentials-process` feature（依赖改动，需批准），或改用 OCI Vault 后端（需提案与 ADR）。若将「定时刷新文件后重启进程」作为过渡方案，需另行评估重启对租约与投递的影响，本轮未验证。
- 探针构建缓存已 `cargo clean`，未删除源码、`.sqlx/` 或测试证据。

## 2026-10-17 OCI 方案 G（过渡）与 A（目标）凭据链探针

背景：OCI VPS 部署先用 G（静态 IAM user key 放在环境变量里）过渡，之后切到 A（IAM Roles Anywhere，SDK 通过 `credential_process` 调用 `aws_signing_helper`）。本节是 `/tmp` 下的一次性探针，固定 `aws-config` 1.12.0、`aws-sdk-kms` 1.123.0，feature 组合与本仓库相同。A 的 feature 用另一个独立 target 打开。KMS 端点是本机 mock，它解析 SigV4 `Authorization` 头里的 AKID 和 `x-amz-security-token`。本仓库代码与依赖均未改动。这里只验证凭据链行为，不访问真实 AWS，也不代表 IAM 策略或 Roles Anywhere trust anchor 已验收。

每次运行都用 `env -i` 起干净环境，设置 `AWS_EC2_METADATA_DISABLED=true`，`AWS_SHARED_CREDENTIALS_FILE` 指向空文件。

| 场景 | 结果 |
|---|---|
| G：环境变量提供静态 key | KMS 请求由该 AKID 签名，不带 session token |
| G：不提供任何凭据 | 失败；凭据链逐个报告 Environment、Profile、WebIdentity、EcsContainer 均未启用，IMDS 因 `AWS_EC2_METADATA_DISABLED` 被禁用，没有回落到 OCI 的 `169.254.169.254` |
| A 对照：profile 配 `credential_process`，未开 feature | 失败，SDK 报错要求开启 `credentials-process` feature，进程不会被执行 |
| A：开启 feature，helper 返回凭据的有效期为 15 秒，每隔 8 秒调用一次，共 5 次 | 每次调用都换了新的 AKID，helper 被调用 5 次；凭据到期前由 SDK 懒缓存自动重取，进程无需重启 |
| A：有效期 3600 秒，间隔 1 秒调用 5 次 | 一直使用同一个 AKID，helper 只被调用 1 次；缓存生效，不会每次请求都起子进程 |
| A：helper 以非零码退出 | KMS 调用失败，报 external process exited；不会回落到其他来源 |
| G 与 A 并存：环境变量里有静态 key，profile 里有 `credential_process` | 静默采用环境变量里的 key，helper 未被调用 |

结论与约束：

- G 与 A 在当前固定版本上的行为符合预期。A 需要在根 `Cargo.toml` 开启 `aws-config` 的 `credentials-process` feature，这项依赖改动需要单独批准。
- 从 G 切到 A 时，必须移除 `AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY`。否则 Environment provider 排在前面，会静默覆盖 Roles Anywhere，切换看上去成功，实际仍在用长期 key。需要预检拒绝两者并存，或在部署检查里显式断言；这一项尚未实现。
- OCI 形态下，`AWS_EC2_METADATA_DISABLED=true` 必须作为必填项。
- 未验证的部分：真实 `aws_signing_helper` 与 trust anchor/profile/role 的配置、G 阶段 IAM user 策略及 `aws:SourceIp` 条件、真实 KMS 往返、长期 key 的轮换流程。
- 探针的构建缓存已经 `cargo clean`。
