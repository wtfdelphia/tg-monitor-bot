## 二、本地复现与源码核对

使用临时 `python:3.6.8-slim` 容器，以只读挂载运行原始
`scripts/verify-native-candidate.py --help`；容器禁用网络、移除 capabilities，结束即删除。
该镜像的拉取摘要为：

```text
sha256:0d095570901e7cf0dac93ba4d0ee75ee2364715338b0396874589c9cc23343b6
```

结果在脚本进入业务验证前失败：

```text
SyntaxError: future feature annotations is not defined
```

根因是 `from __future__ import annotations`。Python 官方文档将该特性列为从 3.7.0b1
开始提供，不支持 Python 3.6。核对来源：
<https://docs.python.org/3/library/__future__.html>。

安装器的候选路径在验证来源后仍调用 `scripts/native-release-preflight.sh`。
该脚本对 cleanup timer 无条件运行 `systemd-analyze calendar`，与目标机回传的命令能力不符。
仅补齐 Python 或 cosign 不能解决该路径。

另用现有 CentOS 7.9 镜像进行只读、无特权探针，其 systemd 同为 219；执行 `verify` 因容器
缺少旧式 cgroup/manager 环境而失败。该结果不能证明 unit 语法通过或失败，也不能替代目标机
验证；本轮未为此启用 privileged 容器或挂载宿主控制接口。

## 三、不能忽略的安全差异

现有 cleanup unit 使用 `ProtectSystem=strict` 和 `RestrictAddressFamilies`。
上游 systemd v219 的 `protect_system_table` 只有 `no`、`yes`、`full`；未启用 SECCOMP 的
构建会把 `RestrictAddressFamilies` 作为编译期禁用项处理。因此不能从 `verify` 返回成功
推导这些约束已经生效，也不能把它们删掉后报告等价安全。

核对来源：

- <https://raw.githubusercontent.com/systemd/systemd/v219/src/core/namespace.c>
- <https://raw.githubusercontent.com/systemd/systemd/v219/src/core/load-fragment-gperf.gperf.m4>
- <https://raw.githubusercontent.com/systemd/systemd/v219/src/core/execute.c>

目标机发行版是否回移了具体指令、如何报告忽略项，仍须采集完整 RPM 版本及本机解析结果。
当前 `-SECCOMP` 输出已经构成必须核对的能力缺口，不是放宽验收的理由。
