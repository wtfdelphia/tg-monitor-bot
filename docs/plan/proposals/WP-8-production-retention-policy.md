# WP-8：生产跨副本留存与删除策略提案

任务 id：`WP-8-production-retention-policy`。

状态：提案阶段，等待维护人、产品/法务与运维确认。当前基线为 `cloud/dev` 合并提交
`28368fccd906823fd07ea11ae43fec1a2c64e564`。本提案只定生产验收所需的策略边界，
不修改代码、迁移、权限、审计断言或部署配置，不连接生产环境，不执行真实租户删除。

## 一、为什么需要单独定案

WP-8 的主库留存、租户注销、到期候选、限批清理、受限根删除和运行入口已经合入
`dev`，本地出口复核也已完成。现有生命周期规格同时明确：

- PostgreSQL 主库清理与全副本删除是两个不同结果；
- 备份、快照、恢复副本、Redis 关联元数据、宿主机日志、对象存储版本和 Telegram
  已投递内容不能被主库删除命令自动覆盖；
- 生产备份副本淘汰、恢复后防止已删除数据重新可用、Redis 生产策略和运行日志留存
  仍未完成定案。

如果没有本提案中的策略，生产验收只能证明“主库命令执行过”，不能回答：

1. 备份里保留多久的已删除数据是否被接受；
2. 恢复一个旧副本后，哪些租户必须被阻止重新上线；
3. 对象存储删除是否同时处理版本、删除标记和 staging 孤儿；
4. Redis、宿主机日志和临时文件是否仍携带租户关联信息；
5. 什么结果可以报告为主库完成、受控副本完成或全副本不可证明。

判据出处：`docs/design/spec/04-数据生命周期与容量.md` 总则及 §1；
`docs/design/ops/00-部署与运行时.md` §二；`docs/design/ops/01-上线就绪与运维.md` §二至§六；
`docs/design/decisions/ADR-0039-恢复窗口与删除完成范围分离.md`；
`docs/plan/proposals/WP-8-production-ops-acceptance.md`。

## 二、术语和完成等级

生产证据必须使用下列等级，禁止用“删除完成”覆盖所有存储层：

| 等级 | 含义 | 可以声明什么 | 不能声明什么 |
|---|---|---|---|
| `main-db-complete` | 批准范围内的租户主库数据、根行和受限清理日志已按流程完成 | 主库租户清理完成 | 备份、Redis、主机日志、对象版本或 Telegram 内容已删除 |
| `controlled-storage-complete` | 平台直接控制的对象存储、临时文件和 Redis 关联数据已按批准策略核对 | 已核对的平台受控副本范围 | 旧备份、快照、恢复副本或外部 Telegram 内容已删除 |
| `operational-copy-complete` | 备份/快照淘汰和恢复隔离流程均按策略完成，并有校验记录 | 本次批准范围内的受控副本已处理 | 平台外部副本已删除 |
| `external-copy-uncontrolled` | 数据已离开平台控制范围，或平台没有删除能力/证据 | 已明确外部控制边界 | 不得对外承诺已撤回或已删除 |
| `blocked` | 共享引用、锁、失败、备份不可恢复、告警缺失或证据缺失 | 阻塞原因和下一次复查条件 | 不得以“已扫描”或“无数据”报告完成 |

租户删除流程至少要分别记录前三个等级；`external-copy-uncontrolled` 不是失败，
但必须在对客隐私文本和案件反馈中明确说明。

## 三、推荐默认策略

以下是可供维护人批准的首发默认值。它们是工程与运营建议，不是法律结论；产品/法务
可以修改，但修改后要同步规格、对客文档和验收命令。

### 3.1 PostgreSQL 主库

- 继续沿用 `docs/design/spec/04-数据生命周期与容量.md` 的表级期限，不在本提案重复定义。
- `tenant_consents` 继续按 ADR-0029 处理：不主动归档，随租户根删除级联消失；共享引用
  阻塞时不得通过先删 `tenant_members` 提前清空同意记录。
- 凭据和 session 不进入 30 天恢复窗口：撤回身份或注销租户时立即销毁；业务数据的恢复
  窗口和主库物理清理分开报告。
- 物理清理返回 `blocked`、`failed` 或非零退出时，不得写主库完成日志；下一次运行必须
  可重试，并保留脱敏原因。
- 租户清理的固定平台日志只能证明清理动作，不保存正文、凭据或完整连接串。

**需要确认：**30 天恢复窗口、同意凭证不归档和“凭据立即销毁”均已有设计依据；若要
改变其中任何一项，应另提生命周期/迁移/安全变更，不在本提案内直接调整。

### 3.2 对象存储和媒体中转

现行规则是对象文件 3 天、`staging/` 孤儿 1 天、`media_archive` 记录 180 天。推荐
生产策略如下：

- 媒体临时 bucket 不保存凭据、举报材料或永久业务附件；只存中转所需对象。
- bucket 生命周期规则必须覆盖正式对象、`staging/` 前缀、非当前版本和删除标记；若
  bucket 开启版本控制，不能把删除当前 key 误报为物理删除完成。
- 首发优先使用不启用版本控制的临时媒体 bucket；若平台/云策略强制启用版本控制，
  非当前版本和删除标记必须有不晚于对象 TTL 的自动淘汰规则，并在验收中实测。
- 应用清理仍遵循“先删对象，成功后在同一数据库事务清空 key 并写固定日志”；对象
  删除失败不能清空引用，也不能计入成功数。
- 清理证据必须分开列出正式对象、staging 孤儿、非当前版本和删除标记；没有列举的
  存储层不能写成已覆盖。

**需要确认：**生产 S3/MinIO 是否启用版本控制、是否存在跨区域复制、生命周期规则由谁
维护，以及对象删除失败的告警接收人。

### 3.3 Redis

架构规则已确定 Redis 不是事实源，只传递唤醒信号和主键关联数据。推荐生产策略如下：

- 禁止写入消息正文、媒体内容、Bot token、`api_hash`、session、KMS Secret、举报正文
  或附件；代码和运维探针都必须以此为反证目标。
- Redis 业务键必须有明确 TTL；唤醒信号丢失时由数据库扫描恢复，不能因为 Redis 清空
  或丢失而报告业务数据删除完成。
- 生产使用的 Stream 必须有明确的最大长度或时间裁剪策略；裁剪不应删除 PostgreSQL
  中仍待处理的事实记录。
- 租户注销后的 Redis 处理分为两步：先停止产生新信号，再按已登记的键前缀/主键关系
  删除关联键；找不到可证明归属的键不得盲删，必须计为待核查。
- 如启用 AOF/RDB，持久化文件和快照按“运行日志/备份副本”同等级管理；不能用
  `FLUSHDB` 代替按租户的删除证明，也不能在生产上执行全库清空。

**需要确认：**生产 Redis 是否启用 AOF/RDB、Stream 名称与裁剪周期、租户键是否可枚举、
以及 Redis 是否有独立备份或跨主机复制。

### 3.4 备份、快照和恢复副本

推荐首发采用“每日完整备份 + 明确副本淘汰 + 恢复隔离”的最小运营方案：

- 每日完整备份至少保留 7 个日备；每周保留 4 个周备。超过期限的副本由生命周期规则
  自动淘汰，并对淘汰失败告警。
- 在未配置 WAL 归档前，对外 RPO 写成“最近一次成功备份到故障发生之间的时间”，不
  得写成零丢失；备份间隔和最近一次成功时间必须可核对。
- 恢复演练使用全新隔离库，不覆盖生产库，不连接生产 Telegram、KMS、Redis 或对象存储。
- 恢复库在开放任何业务前必须执行 `tgm audit-rls`、角色校验、关键计数校验和凭据不可读
  校验；恢复出的已注销租户不得重新开放。
- 恢复流程必须有“删除状态重核对”步骤。当前仓库没有已批准的删除登记表，因此在该
  机制落地前，恢复库只能作为隔离验证环境，不能直接作为生产服务库。
- 每次恢复演练记录备份标识、时间、校验值、恢复耗时、RPO/RTO、租户状态核对结果和
  恢复库销毁结果；证据不得包含连接串、密码或业务正文。

**需要确认：**7 个日备、4 个周备、是否需要 WAL、备份存储位置/地域、是否跨区域复制、
恢复库的人工审批人和恢复后删除状态核对机制。若实际需要长期归档或法定保留，必须另定
法律保留流程，不能把备份无限期保留当作默认方案。

### 3.5 宿主机、容器和代理日志

- `system_logs` 继续按现有 90 天期限清理；`audit_logs` 继续按 free 90 天/付费 365 天
  处理，不因外部副本不确定而无限延长。
- journald、反向代理、容器 stdout/stderr 和备份任务日志单独管理，默认不记录正文、
  token、`api_hash`、session、连接串或完整 URL 查询参数。
- 推荐主机运行日志保留 30 天，安全/审计相关日志最多 90 天；超期自动轮转并告警。
  若法务或事故响应要求更长，应登记具体目的、数据字段、负责人和删除日期。
- 清理日志只保留任务 id、类别、计数、耗时、状态和脱敏错误码；租户标识按最小需要
  记录，禁止把消息正文或凭据写入日志。
- 生产证据引用日志时只保存时间窗、日志类型、结果摘要和哈希/校验值，不复制整段日志。

**需要确认：**主机日志实际收集位置、是否有集中式日志平台、30/90 天是否足够、告警
接收人与日志删除/访问负责人。

### 3.6 临时二维码、2FA 和 session 文件

- 二维码链接、二维码图片/HTML、2FA 密码文件和用户 session 只存在于验收临时目录，
  不进入仓库、镜像、队列、日志、备份或对象存储。
- 登录成功、失败、取消或超时后均执行清理；清理范围包括文件、二维码服务、临时 venv
  和 SSH 转发/浏览器服务。
- session 一旦进入加密数据库，仓库外明文 session 必须删除；无法确认删除时，不得
  报告真机验收完成。
- 证据只记录“已清理/未清理、时间和进程状态”，不记录 QR 内容、2FA 密码或 session。

### 3.7 Telegram 已投递内容和其他平台外副本

- 平台不承诺删除已投递到租户目标频道的历史消息；这不计入平台主库或受控对象存储
  的删除完成等级。
- 举报或数据主体请求涉及已投递内容时，只能记录平台可执行的处置：停止后续采集/投递、
  清理平台受控存储，并向提交者说明 Telegram 外部副本的控制边界。
- 平台不得在没有明确授权和 Telegram 能力验证的情况下自动代表租户删除历史消息。
- 任何对外文本必须同时说明：平台删除主库数据不等于撤回 Telegram 已分发内容。

## 四、法律保留与争议冻结

推荐引入“案件级冻结”规则，但本提案不新增数据库表：

- 只有授权运维/法务人员可以创建、解除或修改冻结；每次操作要有工单号、理由、范围、
  创建人、时间和复核人。
- 冻结只覆盖明确列出的数据类别、租户、对象或案件，不冻结整库，不自动延长所有数据。
- 冻结范围内的清理任务必须安全跳过并报告 `blocked`；其他不相关租户和类别继续按原期限清理。
- 冻结解除后，下一次清理按原始到期时间继续，不重新计算一个新的永久期限。
- 在没有实现可靠冻结载体前，不允许把人工口头通知当作清理豁免依据；可先在生产验收
  中把“无冻结策略”记为阻塞，不启用会误删争议数据的自动任务。

## 五、验收矩阵

批准后，生产验收至少要形成以下证据：

| 类别 | 必验事实 | 失败处置 |
|---|---|---|
| 主库 | `main-db-complete` 与共享阻塞/失败状态可区分；无跨租户残留 | 停止 timer，保留阻塞原因，禁止强删 |
| 对象存储 | TTL、staging、版本/删除标记、失败重试均可证明 | 停止对象清理启用，保留 key 和失败告警 |
| Redis | 无正文/凭据，键 TTL/Stream 裁剪可核对，丢信号可由 PG 恢复 | 不把 Redis 清空当删除完成；修正策略后复验 |
| 备份/恢复 | 副本期限、校验、恢复隔离、RPO/RTO 和删除状态重核对可复现 | 禁止直接开放恢复库，标记 `blocked` |
| 日志 | 无敏感内容，主机日志有期限、轮转和访问控制 | 停止对外报告，先完成脱敏和权限修正 |
| 临时文件 | QR/2FA/session、进程、转发和临时环境均清理 | 删除残留并重新执行真机验收 |
| 外部副本 | 对外明确不可控边界，不伪造删除证明 | 更新隐私文本、举报回复和证据 |

生产验收还必须记录：配置快照的脱敏摘要、实际策略生效时间、失败告警、人工升级人、
停止/恢复步骤和未覆盖范围。不能用“当前没有对象”“当前没有 Redis key”代替策略已验证。

## 六、批准后的实施拆分

本提案获批后仍不直接修改生产环境，按以下顺序拆分：

1. **文档定案**：将批准后的期限、完成等级、外部副本表述同步到 `spec/04`、`ops/00`、
   `ops/01` 和对客文档；如果改变现有 ADR 或留存语义，另行创建 A 类 ADR 提案。
2. **部署核对**：在非生产或隔离环境验证 S3/MinIO 生命周期、Redis TTL/裁剪、日志轮转、
   备份淘汰和恢复库销毁流程。
3. **生产只读验收**：只读核对真实配置、角色、策略、备份和日志，不执行删除、不启用 timer。
4. **探针租户演练**：取得单独批准后，使用无真实数据的探针执行主库删除和受控副本核对。
5. **启用决策**：只有主库、受控存储、告警、停止/恢复步骤和人工升级责任均有证据后，
   才能单独批准生产 timer；本提案不替代该批准。

## 七、当前不做与停止条件

- 不新增“删除登记表”、归档表、举报表或附件表；
- 不新增迁移、角色、RLS、GRANT、审计断言或公开 API；
- 不修改备份、Redis、对象存储或日志配置；
- 不启用生产 systemd timer，不删除真实生产租户，不接收生产凭据；
- 不把推荐期限写成已经批准的法律保留期限；
- 不把主库删除报告成全副本删除，也不承诺撤回 Telegram 已投递内容。

以下任一情况出现时，停止并重新升级：

- 需要新增删除登记表或法律保留字段；
- 需要修改现有留存期限、恢复窗口、外键或 `tenant_purge` 语义；
- 需要对 Redis、对象存储、备份或日志增加新的权限、组件或公开接口；
- 需要接收真实凭据、连接生产数据库或执行真实租户删除；
- 推荐策略与法务批准文本、云平台实际能力或生产备份/恢复事实冲突。

## 八、审核问题

维护人、产品/法务和运维至少需要对以下事项给出明确结论：

1. 是否批准 7 个日备、4 个周备、默认不启用 WAL 的首发基线？
2. 对象 bucket 是否允许版本控制？若允许，非当前版本和删除标记的最长保留多久？
3. Redis 是否启用 AOF/RDB、Stream 裁剪周期和独立备份？
4. 是否接受主库完成与受控副本完成分级，以及 Telegram 外部副本不可控的对客表述？
5. 主机日志推荐 30 天、审计/安全日志最多 90 天是否满足运营和法律需要？
6. 是否需要法律保留/争议冻结？若需要，谁能创建、解除和复核，冻结范围如何记录？
7. 恢复库在删除状态重核对机制完成前，是否禁止直接提供业务服务？

在这些问题未定案前，只能继续做隔离环境的策略验证和证据模板，不能开启生产删除
timer，也不能宣布 WP-8 整体通过。
