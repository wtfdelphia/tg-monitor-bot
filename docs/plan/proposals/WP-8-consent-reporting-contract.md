# WP-8：同意文本与举报受理契约提案

任务 id：`WP-8-consent-reporting-contract`。

状态：提案阶段，等待维护人、产品与法务输入。当前基线为 `cloud/dev` 合并提交
`1d85c72554d9a01566f607c3d91caf15ed0201e8`。本提案不编写法律承诺、不新增接口或表，
也不替代 WP-8 的留存、租户删除和生产验收。

## 一、当前缺口

WP-8 的生命周期代码已经记录和执行 `tenant_consents`，但控制台仍展示占位版本
`custody-v0`，正文明确标记为“内测占位授权版本”，不是可对外使用的法律文本。
现有实现只能证明“提交了某个版本并写入不可变记录”，不能证明该版本文本已经批准、
适用于哪个套餐、何时生效或如何撤回。

仓库当前也没有举报/投诉受理入口的正式契约。没有受理对象、认证方式、证据范围、
反滥用、处理责任和反馈方式，就不能仅增加一个表单或邮箱并宣称举报能力完成。

判据出处：`docs/design/plan/00-里程碑与工期.md` §4.3 WP-8；
`docs/design/spec/06-合规与凭据责任.md` §2.2；
`docs/design/spec/04-数据生命周期与容量.md`；
`docs/plan/proposals/WP-8-auth-retention.md` 的并行准备边界。

## 二、必须先定案的输入

### 2.1 同意文本

产品/法务需要提供或批准以下稳定输入；实现者不得自行补写：

- `tos`、`privacy`、`credential_custody` 三类文本是否都在本片落地；
- 每类文本的稳定版本标识、生效时间、适用套餐和适用地区；
- 凭据代持的明确权限范围：读取哪些 Telegram 数据、允许哪些动作、明确不允许哪些动作；
- 平台、租户管理员和实际授权自然人的责任边界；
- 撤回方式、撤回后的运行边界、凭据销毁时点和重新同意条件；
- 文本变更是否要求现有租户重新同意，以及未重新同意时哪些功能必须停止；
- 是否需要多语言版本、文本摘要、完整文本存档引用或外部法律文档链接。

`tenant_consents` 现有 append-only 形状应继续保持：撤回或重新同意不能 UPDATE/DELETE
既有记录，而是追加新的版本/反向事件；如果现有字段无法表达批准后的语义，必须另写
迁移和安全提案，不能在本任务中偷偷扩展。

### 2.2 举报受理

产品/运维/法务需要明确：

- 受理对象：内容、账号、滥用、版权、隐私请求、凭据风险，还是其中的子集；
- 提交者身份：租户成员、Telegram 权利人、匿名提交者或仅限平台运维；
- 入口位置和认证方式：控制台、公开页面、专用邮箱、工单系统或其他渠道；
- 必填证据：消息链接、频道标识、时间、原因、联系地址和附件范围；
- 平台是否需要向 Telegram 或其他第三方转交，谁负责决定和执行；
- 去重、限流、恶意提交、敏感材料、状态流转和处理时限；
- 是否需要回执、进度查询、最终反馈，以及反馈中允许披露的内容；
- 受理记录、附件、调查日志和最终决定的留存期限及删除边界；
- 紧急安全事件与普通投诉的升级阈值和值班责任。

在这些输入未定案前，不新增 `reports` 表、不新增公开 endpoint、不新增上传能力，
也不把现有 `audit_logs` 当作举报业务台账。

### 2.3 可供审批的同意规则草案

以下是实现前的**审核稿**，不是已经生效的法律文本。每一行都标明了需要谁确认；
没有完成确认的行不得写入正式对客文档，也不得作为代码验收依据。

| 规则 | 推荐默认值 | 必须确认 | 技术影响 |
|---|---|---|---|
| `free` 档同意范围 | `tos` + `privacy`；不代持 MTProto session，不展示 `credential_custody` | 产品、法务 | 继续保持现有 free/pro 准入边界 |
| `pro` 档同意范围 | `tos` + `privacy` + `credential_custody`；代持凭据只服务租户明确启用的采集身份 | 产品、法务 | 继续要求当前版本的代持同意后才能开始 QR 接入 |
| 同意主体 | 当前租户的 `owner` 或被授予身份管理权限的 `admin`；必须由 Web 完成，不接受 Bot 入口代签 | 产品、法务、安全 | 复用现有 `require_identity_write`，不扩大 Bot 权限 |
| 文本版本 | 每类文本使用不可复用的稳定版本号；版本变更必须重新展示并重新同意 | 法务 | 不能继续把 `custody-v0` 当作正式文本版本 |
| 文本证据 | 每个版本登记文本正文、语言、适用辖区、适用套餐、生效时间、批准人、批准时间和内容摘要/哈希 | 法务、运维 | 现有 `tenant_consents` 没有完整字段；若要求落库，必须另提迁移和安全提案 |
| 代持范围 | 仅读取租户明确授权且身份实际有权访问的源频道；不读取私聊、联系人或全局搜索结果，不修改账号设置，不加入/退出频道，不代表用户发送非业务消息 | 产品、法务、安全 | 需与 `08-账号接入.md`、采集调用白名单和对客文本逐条对齐 |
| 凭据提交 | `api_id`/`api_hash` 只允许租户自己提供；平台不得代申请、跨租户复用或转让 `api_id` | 产品、法务 | 与 ADR-0013 和现有身份归属校验保持一致 |
| 撤回代持同意 | 撤回立即停止该身份采集、释放租约并销毁加密 session 和相关凭据；不追溯撤回已投递 Telegram 消息 | 产品、法务 | 需要明确撤回入口、事务顺序、失败重试和可证明的完成状态 |
| 撤回 ToS/Privacy | 推荐按“停止全部业务处理并进入租户注销/关闭流程”处理；不能只删除一条同意记录后继续服务 | 产品、法务 | 需要区分“撤回代持”与“关闭租户”，不能由当前 `latest_custody_consent` 查询自行推导 |
| 重新同意 | 撤回后或文本版本变化后，未重新同意前不得恢复对应功能；重新同意只能追加事件，不能修改旧记录 | 产品、法务、安全 | 当前表只有“同意版本”语义，不能表达撤回事件；需要单独设计事件字段或等价 append-only 方案 |
| 历史业务数据 | 撤回不自动删除既有业务数据；按现有生命周期规则处理；删除请求另走数据主体请求流程 | 产品、法务 | 必须在隐私文本中区分“停止处理”“主库清理”“外部副本不可控” |

**审核结论：**推荐默认值可以作为产品决策草案，但不能直接称为“已批准规则”。
其中“代持范围”“撤回 ToS/Privacy 后的租户状态”“文本证据是否落库”是当前最关键的
三项决策；任一未定，`credential_custody` 都不能从 `custody-v0` 升级为正式文本。

### 2.4 可供审批的举报受理规则草案

首发建议采用“公开说明页 + 专用邮箱或现有工单系统”的人工受理方式，不先做公开
上传接口。这样可以先固定业务边界，避免在受理对象、敏感附件和删除策略未定时新建
`reports` 表或对象存储链路。

| 规则 | 推荐默认值 | 必须确认 | 技术/运维影响 |
|---|---|---|---|
| 受理类型 | 版权/内容权利、隐私/数据主体请求、滥用/未授权转发、凭据或账号安全风险 | 法务、运维 | 其他类型先作为普通支持请求，不进入合规举报台账 |
| 提交者 | 公开入口允许权利人或受影响个人提交；租户成员可从控制台提交；匿名材料可收件但不承诺处理结果 | 法务、产品 | 需要定义身份核验和冒名举报处置，不把“有邮箱”当作权利证明 |
| 第一阶段入口 | 说明页公布专用邮箱/工单入口；不新增公开 API、不上传附件 | 产品、运维 | 复用现有运维受理系统；入口启用前需配置值班和访问权限 |
| 必填信息 | 类型、Telegram 消息链接、源频道/目标频道（如知道）、事实与理由、联系地址；可选消息时间和相关租户标识 | 法务、产品 | 字段白名单应写入接口/表单契约；拒绝任意 JSON 或任意文件 |
| 敏感信息禁止项 | 不要求提交 Bot token、`api_hash`、session、2FA 密码或完整凭据；收到后按凭据事件立即隔离并通知删除 | 安全、运维 | 必须有脱敏、升级和清理流程；不能把敏感材料写入普通工单正文 |
| 附件 | 首发不收附件；如确需附件，另提对象存储、恶意文件扫描、大小限制、加密和留存提案 | 法务、运维、安全 | 未批准前不实现上传、不新增媒体表或 S3 桶策略 |
| 反滥用 | 单来源限频、相同链接和理由去重、超限人工升级；不得因重复提交自动改变已作出的处理决定 | 运维、安全 | 具体阈值、封禁时长和人工解封责任需登记在运维规则 |
| 状态 | `received`、`needs_info`、`triaged`、`actioned`、`closed`、`rejected`、`duplicate` | 产品、运维、法务 | 状态是否需要落库、谁能变更、是否 append-only 要单独定案 |
| 回执与反馈 | 返回案件编号和已收件确认；不披露其他租户、举报人身份或内部风控细节；处理时限先作为内部目标，不写成对客保证 | 法务、运维 | 需要确定模板、发送渠道和泄露审查 |
| 紧急安全风险 | 涉及 session、Bot token、`api_hash`、账号接管或持续未授权发送时，按 P1 安全事件立即隔离凭据和身份，再处理举报材料 | 运维、安全 | 对接现有 P1 事故响应；举报受理不能等待普通队列 |

**审核结论：**第一阶段“不上传、不新增公开 endpoint、不自动向 Telegram 转交”是推荐的
安全边界。若产品要求公开表单、附件或状态查询，必须先补齐认证、限流、敏感数据、
对象存储和删除语义，再提交独立实现提案。

### 2.5 整体留存与删除规则审核稿

现有生命周期规格已经区分主库清理和全副本删除；以下内容是对同意和举报域的补充口径，
不替换 `docs/design/spec/04-数据生命周期与容量.md` 的表级期限，也不凭空增加具体法定
留存年限。欧盟框架下不能用一个统一数字覆盖所有处理目的；留存期应按目的、数据类别、
法律依据和潜在争议分别说明，并由法务批准。

| 数据类别 | 推荐处理规则 | 删除完成口径 | 当前状态 |
|---|---|---|---|
| 同意事件 | 活跃租户期间用于证明当前授权；撤回/重同意只追加事件，不 UPDATE/DELETE 旧事件 | 以主库租户清理完成为准；不承诺备份、日志和外部副本同步消失 | 现有表支持 append-only 同意记录，但不支持明确撤回事件 |
| 举报案件正文 | 仅保存受理、核查、决定所需字段；不得复制完整 Telegram 消息或凭据 | 按案件关闭后的批准期限删除；法律保留或争议冻结须有人工标记和解除责任 | 尚未定案，不新增表 |
| 举报附件 | 首发不收；未来若收取，单独规定对象、版本、扫描失败、删除和备份语义 | 对象、数据库引用、临时文件和备份分别验收 | 尚未实现 |
| 调查/处理日志 | 记录谁在何时做了什么，不复制不必要的举报正文；敏感字段脱敏 | 按平台系统日志规则与案件规则取较严格者，除非法律保留 | 需要运维和法务确认 |
| Redis 关联元数据 | 只允许主键/唤醒信号，不放正文、凭据或举报附件 | 按键 TTL、Stream 裁剪和灾备策略清理；不能以清空 Redis 证明删除完成 | 生产 TTL/裁剪/灾备策略仍待定 |
| 备份、快照、恢复副本 | 源库删除不追溯修改既有副本；必须另定副本淘汰周期、访问限制和恢复后删除重放 | 只能分别报告主库完成与副本处理完成 | 生产运维验收仍未完成 |
| Telegram 已投递内容 | 平台无法控制目标频道历史消息，不承诺撤回；对外隐私文本必须明示 | 不计入平台主库删除完成；由权利人按 Telegram 能力另行处理 | 现有设计已明确不可追删 |
| 临时 QR/2FA/session 文件 | 登录或验收结束即清理；不得进入仓库、日志、队列或备份 | 本机临时文件、服务进程和二维码产物均需单独核对 | 需按部署环境验收 |

**审核结论：**以上矩阵补足了“删什么、何时算完成、哪些不受平台控制”，但没有替法务
决定具体期限。任何人若要把 `tenant_consents` 改成可长期归档、把举报附件放入 S3、或
要求备份内同步删除，都必须另提迁移/权限/对象存储/运维提案。

### 2.6 需要维护人确认的最小决策单

建议维护人按以下顺序给出明确结论；“暂不决定”也必须记录为阻塞，不得默认通过：

1. 批准或修改 free/pro 的同意组合，以及 `credential_custody` 的正式适用范围。
2. 提供三类正式文本的版本号、语言、辖区、适用套餐、生效时间和批准记录；文本正文由法务提供，
   实现者不代写。
3. 确认撤回代持、撤回 ToS/Privacy、文本换版三种情况的功能停止和重新同意语义。
4. 确认举报四类范围、受理入口、提交者核验、敏感字段禁止项、是否收附件和反馈口径。
5. 为案件正文、调查日志、附件、备份和恢复副本分别批准留存/删除规则；明确法律保留的触发、
   解除和负责人。
6. 确认是否接受“已投递 Telegram 内容不由平台撤回”和“主库完成不等于全副本完成”的对客表述。

本清单完成后，才能把输入拆成实现任务。它不等同于批准实现，也不授权连接生产或读取真实凭据。

## 三、批准后的实现拆分

输入定案后再分别提交实现提案：

1. **同意文本落地**：同步规格、显示文本、版本常量/配置、Web 复核、重新同意门槛、
   `tenant_consents` 写入和撤回反向记录；如果涉及迁移、权限或审计，单独升级并走完整门禁。
2. **举报入口契约**：先更新接口规格和 OpenAPI，固定认证、字段白名单、错误语义、限流、
   审计和存储边界；只有契约获批后才实施 handler、持久化和运维接收链路。
3. **留存与删除衔接**：把同意记录、举报记录、附件、调查日志分别接入现有生命周期规则，
   明确租户注销、法定保留、删除请求和跨存储副本的完成语义。
4. **专项验收**：以受限角色验证租户隔离、append-only、未同意/旧版本/撤回/重同意、
   举报越权、敏感材料脱敏、失败重试和留存边界；再运行完整本地门禁和审计双遍。

## 四、当前不做

- 不把 `custody-v0` 改名或标记为正式法律文本；
- 不由实现者起草 ToS、隐私政策、凭据代持授权或举报处理承诺；
- 不新增数据库表、迁移、RLS、GRANT、审计断言或公开 API；
- 不实现举报表单、上传、邮箱转发、工单集成或第三方内容撤回；
- 不连接生产数据库、Telegram、AWS 或任何真实凭据；
- 不宣布 WP-8、G3、G4 或生产上线通过。

## 五、验收与停止条件

本提案只有在产品/法务/运维输入形成可引用的稳定记录后，才可进入实现。实现阶段至少
必须证明：

- 记录中的文本版本与用户实际看到的文本一一对应；
- 未同意、旧版本、撤回和跨租户读取/写入均按定案语义拒绝；
- 既有同意记录不可变，且不会因清理任务绕过权限；
- 举报入口只接受批准的对象和证据，拒绝未知字段、越权租户和敏感信息回显；
- 留存和删除结果能区分主库、日志、附件、备份、对象存储和外部 Telegram 副本。

以下情况必须停止并重新升级：

- 需要改变 `tenant_consents` 结构或现有撤回语义；
- 产品/法务无法提供稳定文本或责任边界；
- 举报受理需要新增角色、第三方存储、文件上传、外部回调或新的敏感数据类别；
- 删除/留存要求与 ADR-0029、ADR-0039 或现有生命周期实现冲突。

## 六、审核发现

本轮对照 `cloud/dev@1d85c72554d9a01566f607c3d91caf15ed0201e8`、现有迁移、控制面代码、
生命周期规格和运维规格完成文档审核，结论如下：

| 编号 | 发现 | 严重度 | 处理结论 |
|---|---|---|---|
| F-01 | 提案原文要求“撤回追加反向记录”，但当前 `tenant_consents` 只有 `consent_type`、`text_version` 等同意字段，代码的 `latest_custody_consent` 也只按版本判断，不能表达撤回 | 高 | 保留为实现前阻塞；不得宣称当前已支持撤回 |
| F-02 | `custody-v0` 仍是内测占位版本，不能升级为正式法律文本 | 高 | 等产品/法务提供稳定文本和批准记录 |
| F-03 | 现有规格已决定同意凭证随租户物理清理消失；共享引用可能使实际删除晚于恢复窗口 | 高 | 对客文档必须区分撤回、到期候选、主库完成和全副本完成 |
