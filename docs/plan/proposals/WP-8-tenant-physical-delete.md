## 一、为什么单独提案

PR #60 已实现 `suspended → deleted`、`deleted_at`、凭据及会话销毁。产品规格规定
租户在 `deleted_at` 起算 30 天宽限期内可恢复；宽限期满后物理删除。但当前没有执行物理删除的
受限入口，而且不能把 `DELETE FROM tenants` 当作足够的实现：

- `tenants` 的级联会沿身份删除其 `canonical_events`；事件若仍被其他租户的 `tenant_events`
  引用，现有 `NO ACTION` 外键会拒绝删除。这是保护跨租户数据的预期行为，不能绕过。
- `canonical_events` 还可能参与 `media_group_members` 和 `media_relay_jobs`；媒体组成员及中转任务
  必须遵守共享事件清理已建立的引用保护与写入锁。
- 多张表对 `identities` 使用单列外键；数据库允许其他租户的配置或任务引用租户私有身份。
  即使正常应用入口禁止这种关联，删除路径也必须检查实际 FK 引用，不能假设脏数据不存在。
- `media_archive` 按内容哈希全局复用，不属于单一租户；租户清理不得据其关联任务删除共享档案或对象。
- `audit_logs`、`system_logs`、`tenant_consents` 随租户级联删除是 ADR-0029 接受的结果；本提案不擅自改为留存。
- 现有 `tenant_lifecycle` 能暂停、注销及删凭据/会话。直接扩大它的 `tenants DELETE` 权限会把两种运维职责
  混在一个凭据边界内。

因此先核定跨租户共享事件仍存活时的处理规则，再实施限批、可重跑的物理删除命令。

## 二、必须先裁决的共享事件边界

物理删除租户自己的 `tenant_events` 后，若其身份关联的 `canonical_events` 仍被其他租户引用，
`canonical_events.receiver_identity_id` 的外键会阻止删除该身份；身份又属于被删除租户。
直接级联会撞上 `NO ACTION`，而将事件删掉或改写会影响仍在保留期内的其他租户。

维护人已批准以下语义，并批准按 ADR-0039 补齐留存衔接：

1. **延迟根租户最终删除。** 分批清理该租户自己的配置、投影、任务、通知、会话和凭据残留；
   只删除无其他租户投影、无媒体组引用、无有效中转任务的 canonical 事件。若仍有共享引用，
   保留完成 FK 所需的租户 tombstone、被引用身份、canonical 事件及其必要媒体关系；不恢复访问、不保留凭据。
   其他租户引用该身份时同样保留身份与其租户根行，不删除引用方数据。
   `tenant_consents` 按既有 FK 随最终清理消失；不能在共享阻塞期间先删成员绕过此边界。
   租户审计/日志继续按既有期限清理，根行删除时剩余记录按 FK 清除。后续批次在共享引用消失后再删除 tombstone。
   窗口结束只表示进入到期候选，不保证根行已删除；tombstone 不延长恢复窗口，也不恢复凭据和访问。
   待清 tombstone 必须报告未完成，不能计作该租户跨表无残留；不能保证受保护残留只会短期存在。
2. 不采用“为完成删除而强行删除共享 canonical”或“将仍被引用的事件改挂平台共享身份”的做法；
   这两种操作都会改变其他租户可见数据或身份归属。

实现阶段不得自行选择破坏共享引用的方案。共享配置等没有自动到期条件的引用需报告人工核查阻塞，
不假定定时重试最终一定成功。

## 三、拟实施范围

### 3.1 独立最小权限边界

- 新增专用 `tenant_purge` 数据库角色与独立运行配置，不复用 `tenant_lifecycle`、`tenant_cleanup`、
  `shared_cleanup` 或 owner 连接。
- 角色仅能枚举到期 `deleted_at`、读取固定候选键和必要归属关系、分批删除批准范围内的租户数据，
  并写固定脱敏日志；不得读取凭据密文、API hash、session 内容、消息正文、对象 key，
  不得删除其他租户/平台共享身份或共享 canonical。
- 不授予 `tenants DELETE` 直通权限。最终根行删除路径须在锁内检查宽限期、所有残留类别和共享引用，
  并由 C15 与真实受限角色测试证明只能删除合格租户；不得以宽泛 `SECURITY DEFINER` 或恒真 RLS 策略绕过检查。
  具体 SQL 与权限形状在批准后依据外键图验证。
- 追加幂等迁移和测试迁移；不修改已应用迁移。若外键形状必须调整，重新提交提案说明原因与反证，
  不在本提案的默认范围内偷偷改变级联语义。

### 3.2 到期、并发与批次

- 候选只包括 `status='deleted'` 且 `deleted_at <= 数据库当前时间 - 30 天` 的租户；命令不提供任意 tenant id、
  cutoff 或表名参数，不接受提前清理。
- 按租户主键稳定分页。每个批次在短事务中取得与注销、恢复、事件扇出、投递及共享事件回收兼容的锁，
  再以新语句复查状态、`deleted_at` 和共享引用；不得跨批次或等待持有事务锁。若现有锁协议无法保护该删除阶段，
  先扩展并测试协议，不能直接执行。
- 每个删除语句最多 5000 行，批间等待 200ms；事务不跨批次、不跨等待持锁。锁冲突安全跳过并留下非成功结果，
  SIGTERM 回滚当前批次，已提交批次可幂等重跑。
- 每批删除与固定 `system_logs` 记录同事务提交；日志失败整批回滚。日志只含租户键、固定表类别、行数、耗时和结果码，
  不含消息、身份凭据或用户提供文本。
- 根租户 DELETE 只能在所有可批量清理的子表均已按限批清空后执行；不得把大量行留给级联一次删除。
  根删除前检查所有 FK 子项计数，只有明确列出的、已证明有界的残留可随最终事务级联。
- 共享 canonical、媒体组、job 的候选与删除必须复用共享事件清理的 advisory lock 协议；如不能在同一协议下证明竞态安全，
  本批保留并重试，不把外键异常记录为成功。
- 每次执行重新检查到期候选，不因上一轮阻塞永久跳过。固定结果区分共享事件引用、身份引用、锁冲突、
  在途未排空和执行失败，只记录待清租户键、固定原因与计数，不输出引用方租户信息。
  自动重试周期、长期阻塞告警及人工升级阈值待生产策略定案，不引入未经批准的时限。

### 3.3 删除依赖与保留边界

实施前按实际迁移生成并测试完整外键图，预计覆盖：

- 先清理投递日志/任务、租户投影、规则版本及配置、通知、去重记录和会话，再处理租户私有身份与其凭据残留，
  最后删除 `tenants` 根行；顺序需由实测外键拓扑确认，不能只依据本清单执行。
- `audit_logs`、`system_logs` 继续由既有分项清理按期限回收；共享阻塞不续期、不冻结日志。
  `tenant_consents` 没有独立 TTL，根行阻塞可能延长其实际存活；两条 CASCADE 与 ADR-0029 的不归档决定不变。
  `tenant_members` 删除会连带同意记录，阻塞阶段不得提前删成员；最终阶段须实测成员、同意记录和根行清理的批次边界，
  不以级联绕过限批约束。如果现有外键与受限路径无法同时满足，另行升级，不临时改外键或放宽判据。
  最终删除日志不能依赖已删除租户行，需在同一事务中写固定平台级脱敏记录；它沿用既有平台日志期限，不是永久删除登记。
- `canonical_events` 仅在无任何 `tenant_events` 引用、无 `media_group_members` 保护关系、无有效 `media_relay_jobs` 下载/重试时删除；
  若其他租户仍引用，按第二节批准的语义延迟最终根删除。
- 对 `identities` 的最终删除前，枚举目录中所有引用它的外键并核对实际行；任何其他租户配置或任务仍引用时，
  保留被引用身份及其租户 tombstone，不能删除或改写引用方记录。
- 身份引用检查不能只看 RESTRICT：`tenant_notifications.identity_id`、`bot_console_updates.bot_id` 及
  `media_relay_jobs.receiver_identity_id` 使用单列 CASCADE。其他租户通知/更新或接收身份与事件不一致的中转任务
  也可能被身份删除连带清除；必须纳入阻塞检查，不能依赖外键拒绝自动保护。
- `media_archive` 和对象存储对象是全局去重资源，不由租户物理删除命令直接删除；继续由既有全局媒体留存清理负责。
- 租户注销时已经删除的 `identity_secrets`、`credential_keys`、Web/Bot/Login sessions 仍须在最终删除前复查为零；
  不将残留凭据交给级联“顺便删除”而跳过审计。

### 3.4 审计与部署

- 扩展权限审计为独立 `C15`（编号实施前核对是否已被占用），逐项验证角色属性、表/列/序列授权、RLS 策略、策略所用函数，
  并禁止成员继承、owner 身份、TRUNCATE、任意表删除和敏感列读取。
- 为每一条新授权、RLS 策略和固定删除路径添加受限角色反向测试；双遍破坏必须只让预期断言报红，撤销后目录快照一致。
- 提供 `tgm purge-deleted-tenants` 与独立 systemd timer 样例；样例不等于生产启用，生产凭据、周期、告警和恢复演练另行验收。
- 不新增通用清理框架或第三方依赖；不运行于生产数据库，不执行真实租户删除。

### 3.5 跨存储留存与完成语义

- 全项目存储范围与结果语义以 `spec/04` 总则为准，不在本提案复制期限表。
- 本命令只处理主 PostgreSQL 数据库内批准的租户清理，不清备份、Redis、运行日志或 Telegram 已投递内容。
  不直接删全局 `media_archive` 或共享对象，也不把这些例外隐去后报告“全部数据已删除”。
- 备份副本的淘汰、恢复后维持删除状态、Redis 持久化与键清理、运行日志留存及阻塞治理时限分别待定。
  生产启用与全副本删除承诺前必须完成对应策略和验收，本次不选型、不新增归档或永久删除登记表。

## 四、验收判据

实现后至少验证：

1. `deleted_at` 前不足 30 天、边界时刻及刚过 30 天的租户分别保留/入选行为；应用主机时钟偏差不影响数据库 cutoff。
2. `active`、`suspended`、不存在的租户不能被清理；注销/恢复/清理并发时仅有一个合法状态结果，重复执行无副作用。
3. 无共享阻塞时，每一租户表的删除结果逐类归零；存在共享引用时，命令明确报告待清 tombstone，不报告物理删除完成。
   每个批次不超过 5000 行；中断、日志失败、锁冲突和重跑不产生虚假完成。
   阻塞消失后重跑可完成；阻塞持续时原因与计数保持可核查，不恢复租户权限，也不停止既有到期日志清理。
4. 引用其他租户 canonical 的投影，以及其他租户指向待清租户身份的配置/任务仍完整；先删、后删及并发清理顺序
   均不误删引用方数据，行为与第二节批准语义一致。
5. 媒体组聚合/成员、`media_relay_jobs` 的下载/完成竞态受现有共享锁与外键保护；`media_archive` 和共享对象不被租户清理误删。
6. `tenant_consents`、租户审计与日志按 ADR-0029 的既定级联结果处理，失败回滚；完成记录不因根行删除而丢失或泄露内容。
   覆盖成员端 CASCADE 与大量成员/同意记录的限批反证，不能只检查租户端外键。
7. 使用 `tenant_purge` 受限连接验证不能读密文、会话内容、消息正文和对象 key，不能访问/删除其他租户或共享身份，不能 TRUNCATE、建对象或提升角色。
8. 迁移重入、实际删除级联（不是仅检查建表成功）、批次上限、并发反证、C15、审计双遍、SQLx prepare 与完整本地门禁通过；ignored 项不计作通过。
9. 结束后检查磁盘与本片专属构建目录，核对本任务新增 Docker 容器/匿名卷/网络；不清具名卷、不运行 `docker system prune --volumes`。

## 五、批准与停止点

本提案命中 `AGENTS.md` §五第 1、3、4 条：涉及迁移、数据库授权/RLS/审计及 WP-8 基线语义。
方案已获批准；实现阶段仍不得连接生产、执行真实租户删除或把未定的跨存储期限写成已定策略。

维护人已批准第二节的共享引用/tombstone 语义及整体留存衔接方案。按 A 类变更登记 ADR-0039，
不改写 ADR-0029、不把主库完成扩大成全副本完成。新增期限、改变级联或扩展权限边界仍须按仓库纪律升级。

前置核验确认 A8 全面禁止未经批准的 definer；本片按已批准的 ADR-0040 精确例外实现终结入口，
不授予 `tenant_purge` 根表直通 DELETE。
维护人已单独批准 `WP-8-tenant-purge-finalizer-security.md` 的精确例外；
随后按该提案 §3.3 验证发现注销租户可通过受限角色直写重建身份与 canonical，触发再次升级。
写入围栏补充提案 `WP-8-tenant-purge-identity-write-fence.md` 随后已批准，追加身份围栏迁移与专项测试；
限批清理、共享阻塞后的后续处理、CLI/调度和生产验收仍未完成，不把终结入口片的通过扩大为整个物理删除任务完成。

后续在本隔离工作树实施；完整本地门禁通过后再申请单提交、推送并开向 `dev` 的 PR。PR CI 与合入仍分别裁决，
本提案及其实现均不自动宣布 WP-8、G3/G4 或生产部署通过。
