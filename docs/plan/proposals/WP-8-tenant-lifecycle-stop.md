## 一、下一步为何先做停止执行

判据出处：`docs/design/plan/00-里程碑与工期.md` §4.3 WP-8，
`docs/design/spec/01-产品需求.md` §七，`docs/design/spec/04-数据生命周期与容量.md` §1.2、§1.3，
以及 `docs/design/eng/03-测试策略.md` §二、§三。

现有到期清理已覆盖多类会话、租户记录、事件、通知、媒体和平台系统日志，
下一条明确未完成的出口是租户删除。不能从一条 `DELETE FROM tenants` 开始：
先要让租户停下来，防止后台执行或稍后完成的登录把数据、会话和凭据写回来。

复用核查：

- `tenants` 有 active/suspended/deleted 状态，但只有通用 `updated_at`，没有可靠的暂停或删除起算时间。
  不能用最后一次普通更新推算生命周期宽限期。
- `list_all_active_tenants` 供后台发现使用；`mtproto_worker::spawn_candidates` 和
  `delivery_runtime::spawn_senders` 只启动新任务，未因租户退出 active 而关闭已运行的任务。
- `repo::claim_due_delivery_task` 已有事件留存共享锁，但未检查租户仍为 active。
  `acquire_lease`、`renew_lease` 也未以租户状态阻止继续获取或续租。
- `load_web_session` 每次查成员关系，但未查租户状态；Web 和 Bot 写操作目前主要按成员角色判断。
  不能把停掉后台发现误写成 Web 已只读。
- QR 登录登记簿、凭据写入、Bot session 回写各有既有实现；这些完成路径也需参与状态复查，
  不能只在发起登录时检查一次。
- `tenants` 仍允许 `app_user` 表级 UPDATE；生命周期状态若交给独立角色，必须同时收窄原授权。
  `platform_ops` 当前只用于平台查询，不应顺手扩大成可销毁数据的角色。
- 租户行、身份、投递、授权凭证存在级联及 RESTRICT/NO ACTION 关系；
  共享身份和 canonical 的保护已由既有回收流程处理，不应在注销时撤掉防线。

复用现有受限角色预检、独立命令配置、租户事务、租约 fencing、关闭信号、事务日志和测试设施。
不新增依赖，不建通用生命周期框架，不把管理 HTTP API 或新控制台页面混入本片。

## 二、租户删除的分片顺序

本次只申请第 1 片实施权限，后两片须分别核查、提案和批准：

1. **暂停/恢复与执行围栏（本片）**：可靠暂停时间、独立运维命令、非 active 禁写、后台停止及排空。
2. **逻辑注销与凭据销毁**：可靠删除时间、立即销毁租户自有凭据及遗留密钥，关闭会话和未完成登录，
   宽限期恢复不复活凭据。明确存量 deleted 行的保守起算和 suspended 超期转 deleted。
3. **宽限期满物理删除**：按真实依赖顺序限批清理，处理与共享 canonical 的引用关系，
   最后删除租户根行；受限角色实测跨表无残留、其他租户及共享对象不受损。

不在第 1 片自动把 suspended 转为 deleted，不提前授予物理 DELETE 租户根行或删除凭据的权限。
一般服务条款、隐私文本、正式代持文本和举报入口仍需各自范围与批准；不把现有 custody-v0 当正式法律文本。

## 三、本片拟实施范围

### 3.1 可靠状态时间与最小权限

追加幂等迁移，为 `tenants` 增加 `suspended_at` 及对应状态一致性约束；不修改旧迁移。
active/deleted 行该字段为空，suspended 行必须有起算时间。
存量 suspended 行从首次迁移时保守起算，重复迁移不刷新；不根据 `updated_at` 猜历史。
该字段本片只记录暂停，不据此自动删除。

新增独立 `tenant_lifecycle` 登录角色及 `TGM_DB_URL_TENANT_LIFECYCLE`：

- 只供独立命令持有，拒绝业务、owner、其他清理、Telegram、KMS、对象存储凭据及 `DATABASE_URL` 混入。
  普通服务和既有清理命令拒绝持有新连接串。
- 无超级用户、BYPASSRLS、建库/建角色、复制、成员关系、对象所有权或转授权。
- 精确授予状态读写、租户自有身份与租约的必要键列、任务取消所需列，以及固定脱敏日志权限。
  不读消息正文、投递 payload、凭据密文、API hash、session id 或对象 key；不解密凭据。
- 对含 tenant_id 的表新增策略时保留 ENABLE/FORCE，限定当前目标租户及固定操作形状。
  不授 UPDATE/DELETE `tenant_consents`，也不授根租户或身份的 DELETE。
- 撤销 `app_user` 的租户表级 UPDATE，按实际调用方保留普通业务确需的列权限，
  不允许业务角色自行修改 status 或 suspended_at；新增精确权限审计 C14 和对应双遍反证。

### 3.2 独立暂停与恢复命令

建议入口为 `tgm tenant-lifecycle suspend --tenant-id <id>` 与 `resume --tenant-id <id>`。
运维命令的显式租户 id 不进入租户 Web/Bot API；不伪造租户成员或 SUPER_ADMIN 的身份上下文。

- suspend 仅允许 active → suspended，幂等重跑不刷新原起算时间，并继续未完成的排空。
- resume 仅允许 suspended → active，清空暂停时间；不处理 deleted，不复活 CANCELLED 任务，
  不擅自启用原来被用户关闭的来源、规则或身份。
- 不存在、错误状态、错角色、配置混入和数据库失败使用固定脱敏错误，不泄漏连接串或对象内容。
- 初始状态变更与固定 `source=system` 审计同事务；命令不接受任意伪造的自然人 actor。
  批次取消与清理完成日志同事务，context 只含固定类别和数量等必要字段。
- 暂停的准入屏障提交与任务排空分别报告；失败或中断不冒充整轮排空完成，重跑可接续。
  取消等待仅回滚未提交批次，不悄悄把已暂停租户改回 active。

### 3.3 状态复查与并发边界

按租户使用独立生命周期锁；状态变更取排他锁，生产写入和执行准入取共享锁并在同一事务复查状态。
先取生命周期锁，再进入既有事件/规则/共享回收锁及行锁；实现前列清各路径顺序，避免反向锁序。
不在 Telegram 或 KMS 网络等待期间持有数据库锁，不只依赖进程内标志或候选扫描。

应沿共享调用点覆盖：

- Web 和 Bot 的业务写操作、规则入队、任务 claim/retry/recovery 和通知出队；
  suspended 仍可只读查看、注销当前会话或撤销自己的其他会话，不得修改业务数据。
  既有 deleted 行不能继续业务读写；不把恢复 deleted 的入口混入本片。
- Bot webhook 的租户自有身份采集、MTProto 采集/续租/持租约写入、媒体中转和目标自检。
  平台共享身份不因一个租户暂停被停掉，其他 active 租户的订阅继续工作。
- Bot 接入、MTProto QR/2FA 完成、凭据及 Bot session 写回。
  发起后才暂停的登录在完成落库前再次复查，关闭未落库连接，不得借旧 AuthContext 写入。
- 已运行 worker 收到或观察到暂停后停止，不再续租、启动新发送/下载或重启。
  租户自有租约即时失效但保留 fencing 历史，恢复后新租约不能让旧 token 再次有效。
- 未开始发送的 PENDING/FAILED 任务按现行批次纪律转 CANCELLED；每批重新确认仍为 suspended。
  与 resume 并发时不能在恢复后继续取消新任务。

**在途外部请求必须单独记账。** 状态提交前已获得执行许可的请求视为在途，
包括底层传输在状态提交后才开始的竞争窗口；不能声称数据库提交能原子阻止 Telegram 收包。
建议边界为：暂停后不再批准新的外部执行，
已获成功回执的请求保留真实成功结果；失败或取消不再安排重试，收敛为取消终态，
结果不确定时明确记录不确定，不伪造“未发送”。多步媒体发送也必须在下一步前复查，不能续发剩余片段。
已有在途任务的回写必须与取消分批竞争核对影响行数，不覆盖另一方终态。
租约过期只证明旧 worker 不再有合法写入权，不等于其网络连接已经关闭；
无法确认 worker 退出或仍有在途结果时，报告未排空，不以超时或租约过期冒充完成。
本片追加 ADR 明确该边界并同步相关规格，不把 Telegram 发送与 PG 提交描述成一个原子事务。

## 四、验收判据

批准后至少覆盖：

- active/suspended/deleted、不存在租户、非法状态转换、幂等暂停/恢复及存量时间保守回填；
  重复迁移和重复命令不推迟原起算时间。
- 真实 Web cookie 与 Bot 成员入口：暂停前已有会话在暂停后仍可只读、可注销/撤销会话，
  不可进行任意业务写入；恢复后旧的取消任务不复活，其他 active 租户不受影响。
- 真实受限连接验证状态字段不能被 `app_user` 修改，新角色不能访问凭据、消息详情或 session id，
  含 tenant_id 的操作受当前事务目标租户约束。运维角色本就允许指定不同租户，GUC 不是身份凭证；
  固定日志不能伪造任意内容，多授/漏授/可转授由 C14 报红。
- 持有旧 AuthContext 或已取得 QR/KMS 结果后再暂停，实际完成入口不得重新写入凭据、session 或业务对象。
  使用本地桩和 EnvKek，不要求真实 Telegram/AWS 凭据，不把桩写成真机验收。
- 已有 worker 的停止、旧租约续租失败、恢复后 fencing 递增；暂停一个租户不停止平台演示身份或其他租户。
- claim/暂停、入队/暂停、凭据落库/暂停、发送回执/取消、批间 resume 均验证两个真实并发提交顺序。
  不能用单连接顺序操作或固定 sleep 冒充竞争；移除锁或状态复查后，对应检查必须按预期报红。
- 分批上限、批间等待、事务日志失败回滚、中断重跑、排空仍在途和外部结果不确定的诚实报告。
- 隔离空库走生产迁移路径，在线 SQLx prepare/check、迁移幂等、定向测试、完整本地门禁和审计双遍通过；
  ignored 和未验的生产行为单独记录，PR CI 仍为最终裁决。
- 门禁后检查磁盘和进程引用，及时清理本片专属 target 与临时 Docker 残留，不销毁已有 Compose 数据。

本片通过只说明租户注销的停止执行前置条件已建立，不等于租户已注销、跨表已归零或 WP-8 通过。
