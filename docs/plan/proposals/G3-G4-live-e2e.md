## 一、现有证据与缺口

当前 `dev` 已有三类可复用材料：

- `mtproto_live` 证明测试用户实时收消息、正常退出和硬停后的 `catch_up`；
- `delivery_live` 的 V2 使用真实 MTProto transport，在发送前和发送后挂起子进程，
  由父进程强杀并用同一请求快照恢复，核对 Telegram message id 和任务状态；
- `delivery_soak` 和规则/扇出子进程测试覆盖重启、幂等和本地链路。

这些结果不能拼成一次完整的“真实源消息 → 规则命中 → 目标频道收到”。现有 V2 直接创建
`delivery_tasks`，没有经过 MTProto 收消息、扇出、规则命中和正式入队；旧的真机结果也早于
当前 `dev`。因此不能用历史分项结果替代当前端到端验收。

本机 `~/.config/tgm-live.env` 含平台 API、测试 Bot 和目标频道的非空配置，但没有用户 session
文件。配置存在不等于凭据有效；实施时只做必要的存在性检查，不打印 secret、session、
消息正文或个人标识。实施中发现的 session 快照交接、测试夹具与清理问题只修正验收工具，
未改生产消息处理、数据库结构、角色、RLS、GRANT、CI 或运行时依赖。

## 二、片一：真实源到规则命中的端到端

新增一个 `#[ignore]` 的数据库隔离验收用例，放在现有 live 测试目录，不进入默认 CI：

1. 经现有控制面 QR 登录路径接入专用测试用户，含 2FA；用户只加入专用测试源频道。
   登录、身份接入和端到端在同一数据库与进程内完成，避免 worker 更新内存会话后仍把旧快照
   交给另一进程。二维码按仓库统一终端或 SSH 隧道方式交付，不在对话中贴二维码图片。
2. 在同一临时数据库中登记测试用户来源订阅、Bot 发送身份、唯一关键词和测试目标，
   使用生产 `run_identity`、fanout、rule 和 delivery 代码路径，不直接插入 `delivery_tasks`。
3. 测试 Bot 向源频道发送带随机标签的合成消息；断言只生成对应规范事件、规则命中和一条
   投递任务，最终任务为 `DONE`，使用第二个专用 Bot 的 MTProto 只读会话核对返回消息的标签；
   不使用收不到频道更新的 Bot API `getUpdates` 伪造自动计数，由维护人核对频道无重复。
4. 再发送一条不含关键词的消息，断言被采集但不产生新投递任务。消息使用专用测试标签，
   不读取或记录其他频道内容。
5. 核对完成后删除本用例创建且可安全删除的源消息和目标消息；若 Telegram 拒绝删除，
   在证据中保留标签与人工清理清单，不删除非本用例消息。临时数据库随 `sqlx::test` 销毁，
   session、二维码、2FA 和临时服务在结束后清理。

实现只允许新增验收测试、脱敏运行脚本和证据，不改生产消息处理、数据库结构、角色、RLS、
GRANT、CI 或依赖。若现有生产接口无法串联而必须改业务代码，停止并另报具体原因。

片一通过只更新 G3 的“真实源到目标”判据，不自动宣布 G3、G4 或 WP-8 通过。

## 三、片二：强杀、在途响应与真实限流

片一通过后复用当前基线执行；V2 使用独立随机标签并自动核对、清理其消息：

1. 运行 `delivery_live` V2 的 `before-send` 与 `after-send` 两时点，核对相同 `random_id`
   恢复、message id、任务 `DONE` 和频道只出现一次；历史通过记录不代替本次结果。
2. 复用当前 fanout/rule 子进程强杀测试作为内部恢复证据，并在端到端场景选择一个可重复的
   进程恢复窗口。不得把 systemd 自动重启单独记为“不丢事件、不重复投递”。
3. 限流优先复用测试中自然出现的 Telegram `FLOOD_WAIT`/`retry_after`，记录脱敏错误码、
   请求退避时间和恢复后的单次投递结果。若没有自然限流，先运行既有短间隔 Bot 登录探针；
   一旦出现限流立即停止加压，不循环轰击 Telegram，也不通过向真实用户/公开频道刷消息触发。
4. 若测试账号/频道无法安全触发限流，保留 `not-run`，说明已尝试的受控探针与停止原因；
   不把 mock 429 或本地分类测试写成真实限流通过。

真实限流不是可随意放大的性能测试。每次外呼前确认目标和 Bot 均为专用测试对象；测试失败时
先停止 worker 与外呼，再读取脱敏日志。真实 `RANDOM_ID_DUPLICATE` 若不能可靠关联原消息，
按现有语义保留恢复缺口，不通过猜测 message id 判绿。

## 四、验证与证据

- 新增测试先跑编译、静态门禁和相关非生产回归；ignored 真机用例单独执行，不能计入普通
  `cargo test --workspace` 的通过数。
- 真机证据记录基线 commit、执行命令、用例阶段、计数、message id 是否存在及一致性、任务状态、
  脱敏平台错误码、清理结果和未运行项；不记录 token、`api_hash`、session、密码、二维码、
  手机号或消息正文。
- 外部验收完成后再跑必要的静态/数据库门禁并提交 PR，由 CI 对代码与文档变更作最终裁决。
- 即使两片结果全部通过，仍需逐项核对 WP-8、对客文档、生产留存与其余 G3/G4 判据，
  不在本提案内宣布首发、稳定发布或生产上线。
