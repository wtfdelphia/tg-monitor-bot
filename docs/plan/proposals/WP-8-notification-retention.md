## 一、现状与复用

基线为 PR #55 合入后的 `dev`：`a8cb84c227aadbe9aa151096ec3eec1a9c11575b`。
前片已覆盖已处理未命中投影与共享原始事件的顺序回收，不包含通知终态期限。

本片需要存在：`spec/04` §一明确将 `tenant_notifications` 的 SENT/DEAD 保留期留给 WP-8，
当前只能随租户或身份物理删除级联消失。继续跳过会留下独立增长的终态记录。
现有 `tenant_cleanup`、db/app 清理分层、CLI 固定类别、租户枚举、批量日志和 systemd 模板可复用，
不需要新任务表、角色、凭据来源、依赖或调度框架。

真实链路已核查：

- `migrations/0024_tenant_notifications.sql` 定义 PENDING/SENT/DEAD，只有 `created_at`、
  `next_retry_at` 和仅 SENT 非空的 `sent_at`，没有 DEAD 的可靠结束时间。
- 身份转入 unauthorized/banned 的同一事务负责入队；control-plane 的
  `crates/app/src/tenant_notify.rs` 读取到期 PENDING 后发送，再由共用
  `crates/db/src/repo.rs::record_tenant_notification` 记录结果。
- 共用写入只推进仍为 PENDING 的行。Retry 更新下次尝试时间；Sent 写 `sent_at`；
  Dead 不写结束时间。`next_retry_at` 不是终态发生时间，不能拿它替代。
- `app_user` 没有该表 DELETE；`tenant_cleanup` 尚未获该表权限，`C9` 也未将它纳入清理白名单。
  `system_logs` 的租户清理 INSERT 策略目前不接受该表名。

因此不能只加一条按 `created_at` 删除的 SQL。长期等待后刚送达或刚失败的通知，
若按入队时间起算，会在刚进入终态时立即被清理。

## 二、请求定案的留存语义

建议 SENT 与 DEAD **均从进入终态起保留 90 天，每日清理**，不按套餐区分。
这是本次请求批准的新规则，不是既有规格或法律要求；只在获批后写入规格与新 ADR。

- 新增可空 `terminal_at`。PENDING 必须为空；SENT/DEAD 必须非空；SENT 的值与 `sent_at` 一致。
  成功与永久失败都以数据库时间记录，Retry 不启动终态计时，不通过失败次数推算时间。
- 清理仅选当前租户、SENT/DEAD 且 `terminal_at <= 数据库 cutoff - 保留期限` 的记录。
  恰好边界可删，后一微秒保留；任意年龄的 PENDING 都不得由本类别删除。
- 旧 SENT 用已有 `sent_at` 回填；旧 DEAD 没有可证明的结束时间，以本次迁移的数据库时间保守回填，
  从迁移起重新保留一个完整窗口。不编造历史失败时间，也不使用 `created_at` 或 `next_retry_at` 冒充。
  重跑迁移不得刷新已回填值或让期限无限顺延。
- 同一通知进入终态后，现有记录入口的重复确认返回未推进，不改写终态时间。
  不新增 DEAD 人工重发或终态恢复入口，也不把本片当作通知投递 exactly-once 的证明。
- 既有租户/身份物理删除级联仍可提前删除通知。本期限是通常回收规则，不是必须独立保存的合规凭证；
  同意凭证与租户注销另行处理。

两种状态采用同一期限，减少分支并保留一段可排障的终态历史；这不保证通知已经被用户阅读，
也不改变现有重试上限、错误分类、收件人选择或身份失权入队事务。

## 三、获批后的最小实现

### 3.1 迁移与最小权限

仅追加幂等迁移及测试迁移链接，不改已应用文件，不新建表或角色。
迁移增加 `terminal_at`、终态形状 CHECK、一次性存量回填和候选 partial index
`(tenant_id, terminal_at, id) WHERE status IN ('SENT', 'DEAD')`。
实施前核对存量规模与迁移锁窗口；若无法在可接受窗口完成回填，停止并升级，不把大规模回填混同限批清理。

复用 `tenant_cleanup`，仅增加该表的 `tenant_id`、`id`、`status`、`terminal_at` 列 SELECT 与 DELETE。
限定该角色的 SELECT/DELETE 策略同时核对租户、终态和到期，不授通知类型、身份、错误详情、
收件人或凭据读取，不授 INSERT/UPDATE/TRUNCATE、序列或转授权限。
现有业务角色保留发送状态写入能力，不增加删除权限。

新列的业务写权限须逐项核对：当前该表有表级 SELECT/INSERT/UPDATE，新增列会自动落入既有授权，
不能把这种继承误写成“业务角色不可写”。CHECK 保证终态形状，
完成时间由受信的共用应用写入入口记录；不声称能阻止该角色绕过入口执行任意 SQL。

`C9` 增加精确白名单，租户清理固定日志策略只追加该表名，继续限制 context 的表名、行数和耗时。
审计实现与 `eng/04` 同步，保留正文超授双遍反证，另用该表漏授、多授及转授作定向反证。
不修改 CI 判绿规则，不削弱其他断言或租户隔离。

### 3.2 写入、清理与调度

在 `record_tenant_notification` 共用入口记录终态时间，搜查并回归全部调用方。
Sent 同一条 UPDATE 写相同数据库时间到 `sent_at`/`terminal_at`；Dead 同事务写结束时间；
Retry 仍只推进 PENDING，清理后的重复确认不重建记录、不改变身份状态或再入队通知。

在现有 db/app/CLI 增加固定类别 `tenant-notifications`，复用全部状态租户分页、事务级 GUC、
同租户同类别互斥、数据库 cutoff、完整键排序、限批及批间等待。
删除时重新核对状态和时间，删除与 `tenant_retention/cleanup.done` 日志同事务，
日志失败或 SIGTERM 回滚未提交批次，不把旧候选当作删除授权。
租户 GUC 只是受信清理进程的上下文，不声称能阻止该角色主动切换到另一租户。

复用 `tgm-tenant-cleanup@.service` 与独立租户清理凭据，追加每日 timer 样例，
不向 control-plane 下发清理连接串，不让通知发送进程兼任清理身份。
不引入 Telegram/AWS 真凭据，也不改变现有未命中投影与共享清理依赖。

### 3.3 文档与部署

本片定案后新增 ADR，编号按实施时索引顺延；不改旧 ADR。
同步 `spec/03`、`spec/04`、`spec/05`、测试策略、工程门禁、部署说明和实施证据。
`spec/04` 继续是期限的唯一事实源，部署文档引用规则，不另设默认值。

迁移会使旧版发送入口缺少终态时间而违反新 CHECK。部署须先停止旧版通知发送循环
（当前内嵌 control-plane），执行迁移与保守回填后再启动新版，确认写入和清理均正常后启用 timer。
不声称新旧发送进程混跑安全；需要无停机滚动发布时，须另行升级兼容性方案。
生产角色、Secret 文件、真实日周期与告警验收分别记录，本地临时调度不替代生产验收。

## 四、验收与批准边界

- 固定 cutoff 验证边界前、恰好相等、后一微秒；分别覆盖 SENT、DEAD、旧入队但新终态和长期 PENDING。
- 验证存量 SENT 保留原时间，旧 DEAD 从迁移时间保守起算，PENDING 不回填；从空库迁移和重复执行结果一致。
- Retry、首次 Sent/Dead、重复确认和清理后确认覆盖共用入口；非法终态形状被 CHECK 拒绝，
  既有失权同事务入队、退避、永久失败与进程重启通知回归不变。
- 多租户、free/pro 和全部租户状态都覆盖；使用受限 `tenant_cleanup` 验证错租户、无 GUC、
  活跃记录保护与详情不可读写，不能用测试控制角色证明隔离。
- 两个真实连接观察锁等待，覆盖长时间 PENDING 刚变终态与清理交错、终态重复确认与删除竞争、
  同类别重叠；不靠固定 sleep 推定并发已发生，不把列表或候选快照当作最终状态。
- 删除条件放宽到 PENDING、去掉终态时间更新、权限漏授/多授和日志失败均须有会变红的检查；
  审计双遍撤销破坏后目录快照一致。
- 限批、多批、批间释放锁、日志回滚、锁等待中 SIGTERM 和恢复重跑可复跑；
  隔离空库及临时调度验证独立环境、非零失败和停止无残留。
- 在线 SQLx prepare/check、生产路径迁移、迁移重入、完整 `scripts/ai-driver/ai-gates.sh` 通过；
  ignored/skipped 不计通过，最终由本片 PR CI 裁决。

构建完成检查磁盘与本片独占 target，结束后定向清理缓存、临时 Docker 和 systemd 资源，
保留源码、`.sqlx/`、证据、失败日志、运行中的 Compose 栈和具名卷。

不处理媒体清理平台日志债务、租户注销与凭据销毁、同意文本、举报入口或第三方删除请求。

不能由实现者编造文本或承诺。
