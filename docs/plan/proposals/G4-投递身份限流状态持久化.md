状态：产品语义已批准（2026-11-08）；迁移、权限与审计实施已批准（2026-11-09）并已落地；

## 一、发现

在已批准的 G4 真实限流退避闭环验收实现中复核当时的 `dev`：

- `crates/app/src/delivery.rs` 在真实投递返回 `FLOOD_WAIT` 后，将任务写为可重试并持久化
  `delivery_tasks.next_retry_at`；
- `crates/db/src/repo.rs` 的 dashboard 也从这类任务计算 `flood_wait_until`；
- 但发送 Bot 身份没有被写成 `identities.status = 'flood_wait'`，且发送身份候选查询不会因
  某条任务的等待时间排除该身份；
- 因此仅以任务级 `next_retry_at` 可以保护已失败任务，却不能证明“发送身份上的限流冷却持久化”。

这不是验收脚本能够修复的问题。把脚本中的身份检查删除或改成无条件通过，会把未实现的
状态机写成验收已通过，违反 fail-closed 约束。

## 二、建议范围

1. 定义发送 Bot 收到投递 `FLOOD_WAIT` 时的原子状态变更：任务错误码、`next_retry_at`、
   Bot 身份的 `flood_wait` 状态以及可恢复时间必须具有一致的事务边界。
2. 为发送身份建立可判定的冷却截止时间来源。不得修改已应用迁移；新增列、索引或权限变更
   按 `G4-投递身份限流状态持久化实施.md` 单独审批。
3. 调整发送身份候选查询与运行循环，使冷却未到期的 Bot 不重新领取或重新建立发送循环，
   到期后按定义恢复，不依赖人工清库、手动篡改时间或重启碰运气。
4. 明确与既有 `unauthorized`、`banned`、手动 `reset-status`、session 复用、任务级
   `next_retry_at` 和 dashboard `flood_wait_until` 的优先级，避免把身份恢复成可发送而未到期任务
   仍被绕过，或让终态身份被错误复位。
5. 新增 L1/L2 反证：去掉身份状态写入、提前候选、提前恢复或跨租户读写时，对应测试必须失败。
   真实 Telegram 测试只用于验证外部响应已正确进入这条状态机，不替代 DB/受限角色验证。

## 三、验收判据

在隔离数据库中，受限运行时角色触发或模拟 `FLOOD_WAIT` 后，必须同时验证：

- 任务保留为可重试，`last_error_code = 'FLOOD_WAIT'`，`next_retry_at` 不早于服务端等待；
- 对应发送 Bot 状态为 `flood_wait`，且存在可读的冷却截止时间；
- 冷却期间同一 Bot 不能领取任何新的发送任务，既有任务也不能绕过等待；
- 到期后恰好恢复一次可发送能力；恢复前后不产生重复投递；
- 其他 Bot 和其他租户不受影响；
- `unauthorized`、`banned` 不得被限流恢复路径降级为可发送；
- 控制面 dashboard 与身份列表反映一致的脱敏状态，不暴露 token、session 或 Telegram 原始错误正文；
- 完整 `ai-gates.sh` 与真实限流闭环均通过后，才可把 G4 的该子项从 `partial` 改为 `pass`。

## 四、已确认的产品语义

维护人已批准以下行为（2026-11-08）：

1. `flood_wait` 是发送 Bot 的正式运行状态。
2. 同一 Bot 的所有待发送任务在冷却期内暂停，不切换到其他 Bot 代发。
3. 冷却到期后自动恢复为可调度状态；恢复时复用已保存的 Bot session，不通过重新登录绕过等待。
4. `unauthorized` 与 `banned` 不得被冷却恢复路径降级或覆盖；手动复位不得缩短仍有效的冷却。
