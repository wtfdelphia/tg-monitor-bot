# WP-8：生产运维验收与删除运行启用提案

任务 id：`WP-8-production-ops-acceptance`。

状态：提案阶段，等待维护人批准。当前 `dev` 基线为 PR #66 合并提交
`078238458bc83ee30bb323a610f11a429ec2ebb6`。本提案不把本地门禁、systemd 样例或
隔离 Compose 测试写成生产验收。

## 一、为什么现在做这片

WP-8 的留存、租户生命周期、到期候选、限批清理、受限根删除和独立运行入口已经合入
`dev`，出口复核证据见 `docs/plan/evidence/WP-8-出口复核-2026-10-31.md`。
但生产侧仍没有以下事实证据：

- 真实生产备份已经配置并可恢复；
- 真实机器上的 `tgm-tenant-purge` 用户、Secret、service 和 timer 权限边界正确；
- 探针租户经历过注销、宽限期、阻塞、恢复和最终清理；
- 清理失败、锁冲突、共享引用和进程中断能够告警并安全重试；
- 主库删除与备份、快照、Redis、运行日志、对象存储及 Telegram 外部副本的完成范围已被明确区分。

判据出处：`docs/design/plan/00-里程碑与工期.md` §4.3 WP-8、G5；
`docs/design/ops/00-部署与运行时.md` §二；`docs/design/ops/01-上线就绪与运维.md` §二至§六；
`docs/design/spec/04-数据生命周期与容量.md`；`docs/design/decisions/ADR-0039-恢复窗口与删除完成范围分离.md`。

## 二、批准后执行范围

### 2.1 生产前检查

在任何删除动作前，使用生产只读审查和受控运维窗口核对：

1. `cloud/dev` 对应构建的版本、迁移版本和发布包校验值；
2. 生产库迁移状态、`tgm audit-rls`、C16/C17 和物理清理专项反向测试；
3. `tenant_purge` 登录角色、非 `BYPASSRLS`、无其他业务/清理角色成员关系，以及
   `TGM_DB_URL_TENANT_PURGE` 直连 PostgreSQL（不经过 PgBouncer）；
4. 生产库中没有把真实租户直接当作破坏性探针使用；探针必须是专门创建、无真实业务数据的租户；
5. root 所有、`0600` 的 `/etc/tgm/tenant-purge.env`，不把连接串、密码或其他 Secret 写入 Git、日志或命令行历史。

若任一项不满足，停止，不启用 timer，不运行物理清理。

### 2.2 真实备份与恢复演练

按 `docs/design/ops/01-上线就绪与运维.md` §2.1–§2.2 执行一次真实恢复演练：

1. 选取一份已完成且非刚刚生成的生产备份；记录备份时间、覆盖范围和校验值；
2. 恢复到隔离的全新空库，不覆盖生产库，不连接生产业务进程；
3. 在恢复库运行 `tgm audit-rls`，结果必须为 0 条违规；
4. 使用受限 `app_user` 设置两个测试租户上下文，验证本租户可见、其他租户不可见；
5. 运行迁移一致性、关键数据计数和凭据不可读检查；
6. 记录从恢复开始到可验证服务状态的耗时，作为实测 RTO；备份间隔作为 RPO，不能凭估计填写；
7. 记录恢复库销毁方式，避免把生产凭据、会话或真实 Telegram 连接带入演练环境。

恢复失败、RLS 不一致、角色缺失、数据计数异常或凭据泄漏时，停止后续生产启用；不得手工
修改恢复库来制造“通过”。

### 2.3 探针租户删除演练

只使用专用探针租户，不使用真实客户租户。探针至少包含可安全造出的租户私有数据，且不包含
真实身份、真实 Token、真实 API hash、真实消息正文或真实外部目标。

执行顺序固定为：

1. 创建探针租户和最小测试数据，保存创建前的对象计数与迁移版本；
2. 验证未到 30 天宽限期时，候选枚举不返回、指定清理不能绕过 cutoff；
3. 将探针置为 `deleted`，验证身份、会话和凭据写入围栏；
4. 制造一个受控共享引用或锁冲突，验证命令返回非成功结果、日志原因脱敏且可重试；
5. 清除受控阻塞后手工运行 `tgm purge-deleted-tenants --tenant-id <probe>`，核对七类清理顺序、
   每类批次边界、固定 `cleanup.done` 日志和根行删除；
6. 对已删除探针重复运行，验证幂等结果；
7. 核对所有项目表无探针残留，同时核对共享 canonical、共享身份和其他租户数据未被误删；
8. 删除探针的数据库、对象和日志测试残留，不把探针数据留在生产留存范围内。

该演练只证明主库受限清理链路。它不证明既有备份、快照、Redis、宿主机日志、对象存储版本或
Telegram 已投递内容已经被追溯删除；这些副本必须在证据中单独标记为“未覆盖”或按批准的策略验证。

### 2.4 systemd 与告警启用

仅在 2.2 和 2.3 的证据通过后：

1. 以实际安装路径运行 `systemd-analyze verify` 和 `systemd-analyze calendar daily`；
2. 创建无登录、无额外服务组身份的 `tgm-tenant-purge` 系统用户；
3. 先保持 timer 停止，手工执行一次并核对退出码、日志和数据库结果；
4. 配置生产告警：连续两次备份失败、清理非零退出、锁/共享引用阻塞、清理持续超时；
5. 记录告警接收渠道、人工升级阈值、值班事实和停用步骤；
6. 维护人明确批准后才执行 `systemctl enable --now tgm-tenant-purge.timer`，并记录首次触发结果。

timer 启用后仍必须保留“停止 timer、停止 service、检查已提交批次、从当前状态重跑”的恢复步骤。
默认每日周期不得缩短 30 天恢复窗口。

## 三、验收证据

新增一份生产证据文件，至少包含：

- 发布提交、二进制校验值、迁移版本和执行时间；
- 备份来源、校验值、恢复库隔离方式、RPO/RTO 实测值；
- systemd unit 校验、用户/文件权限和连接角色校验；
- 探针租户每个阶段的命令结果、固定日志、残留盘点和跨租户反证；
- timer 启用前后的状态、告警测试、失败重试和停用演练；
- 主库、备份/快照、Redis、运行日志、对象存储和 Telegram 外部内容各自的删除完成范围；
- 所有未执行项、失败项和人工升级项，不以“无数据”代替未验证。

证据不得包含数据库密码、Bot token、API hash、session、KMS Secret、完整连接串或用户消息正文。

## 四、明确不包含

- 不新增表、迁移、角色、RLS 策略、GRANT、审计断言或 CI 门禁；
- 不修改 30 天恢复窗口、留存期限、外键语义或 `tenant_purge` 代码；
- 不在未批准前启用生产 timer；
- 不删除任何真实生产租户；
- 不把主库删除表述成备份、快照、Redis、日志、对象存储或 Telegram 副本的删除；
- 不在仓库或聊天记录中接收、保存或回显生产凭据。

若实际验收发现需要改代码、迁移、权限、告警接口或删除语义，立即停止并按
`AGENTS.md` §五针对新增范围另写提案。

## 五、批准与停止条件

本提案需要维护人明确批准后才能进入生产验收。批准不等于授权真实租户删除；真实租户删除、
timer 启用和跨副本删除仍需在对应证据节点分别确认。

以下任一情况都标记 `blocked` 或 `escalated`，不以重试掩盖：

- 无法取得非生产探针和隔离恢复环境；
- 生产备份无法恢复或恢复后 RLS/角色/计数不一致；
- `tenant_purge` 连接经过 PgBouncer、拥有超出白名单的权限或能读取敏感数据；
- 共享引用、锁冲突、失败日志或跨租户反证不符合预期；
- 告警接收人与人工升级阈值未明确；
- 需要新增 DDL、权限、审计、运行代码或改变留存完成语义。
