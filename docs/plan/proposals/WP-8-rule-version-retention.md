本片只扩展 `rule-versions` 类别，沿用 `tenant_cleanup` 与 `TGM_DB_URL_TENANT_CLEANUP`，
不另建角色、业务表、调度框架或依赖。调度复用 `tgm-tenant-cleanup@.service`，增加对应 timer 样例。

只读核查依据为 `migrations/0004_tables_rule.sql`、`0006_tables_delivery.sql`、

`crates/app/src/delivery.rs` 和现有租户留存模块。

核查发现：

- 规则执行先读取当前规则，再读取版本快照，最后另开事务入队；当前版本可能长期不变。
  只按快照创建时间清理，会删掉仍被规则执行使用的版本，停用规则重新启用时也会遇到该问题。
- 任务以 `rule_id`、`rule_version` 反查快照，但没有指向版本表的外键。
  列表与详情仍使用版本数据；不能只保留在途任务引用的版本。
- 发送使用已冻结的 `payload_snapshot`；显式删除规则会级联删掉版本历史，已入队任务不因此取消。
  本片不改这项既有语义，也不增加会级联删除任务的外键。
- 入队前的快照读取与入队不在同一事务。单条 DELETE 中的 `NOT EXISTS` 不能独自解决并发入队，
  必须同时改共享入队入口，并覆盖快照已经消失时的恢复路径。

## 二、本片范围与暂缓项

期限与频率沿用 `spec/04` §一的 `rule_versions` 规则，不新设保留期。
建议清理必须同时满足：

1. 属于本批租户，且按删除语句可见的已提交 plan 判断已到期；未知 plan 不回退 free。
2. 不是 `rules.version` 指向的当前版本；规则是否启用不影响该保护。
3. 没有该租户任何存量 `delivery_tasks` 引用同一 `(rule_id, rule_version)`。
   不按任务状态缩小引用范围，DONE、DEAD 等终态也算引用。

当前版本与任务引用是超过期限仍需保留的正确性例外，已在 `spec/04` 原有条目和清理说明中写明。
版本历史列表允许到期的无引用旧版本消失，不伪造空快照。

本片不删除或改写规则、任务、事件、凭据、授权凭证或平台日志。
`tenant_events` 的任务级联、共享 `canonical_events` 与媒体组回收、无关联 DEAD 任务、
通知终态留存、媒体清理日志缺口、同意文本、举报入口和租户注销另行处理。
尤其不以“任务已经终态”为由提前回收其规则版本。

## 三、实施方案与批准边界

### 3.1 清理入口、迁移与最小权限

扩展既有类别枚举、CLI 参数、批次查询和固定清理日志白名单；仍按全部状态租户分页执行。
每批使用数据库时间，按时间及完整复合键稳定排序，限批及批间等待沿用 `spec/04` §1.1。
删除与 `tenant_retention/cleanup.done` 日志同事务提交，重叠、错误及 SIGTERM 沿用前片纪律。
套餐按每次删除语句的快照判断，不跨批缓存；套餐变更不追溯恢复已提交的删除。

只追加幂等迁移，不改已应用的迁移。建议仅扩展下列权限：

- `rules`：SELECT `tenant_id`、`id`、`version`，用于当前版本保护。
- `rule_versions`：SELECT `tenant_id`、`rule_id`、`version`、`created_at` 及 DELETE，
  不授予 `snapshot` 读取、INSERT、UPDATE 或 TRUNCATE。
- `delivery_tasks`：在已有键列 SELECT 上增加 `rule_id`、`rule_version`，不读取 payload 或消息内容。
- 为上述访问补限定角色的租户策略；版本 DELETE 策略同时限制到期、非当前版本及无任务引用。
  不使用 `SECURITY DEFINER` 绕权限，不向清理角色授予业务表 UPDATE 来换取行锁能力。
- 固定日志的类别白名单增加 `rule_versions`，不扩大 context 或平台行写入范围。

核对现有索引后，只为实际查询追加所需索引，重点检查任务侧的租户、规则及版本反查。
不把“新增索引”写成已经获得性能提升。核对 RLS 子查询依赖，不能引入策略递归。

### 3.2 清理与入队的事务边界

复用租户留存模块既有的租户、类别锁键，清理继续持排他事务级 advisory lock。
共享 `enqueue_delivery_tasks` 在入队事务中先获取同键的共享事务级 advisory lock，
再锁租户事件、判断幂等结果并写任务；锁一直持有到任务与事件处理标记一起提交或回滚。
锁键计算共用一处，不在两个模块分别拼写。

入队等待锁后，必须用独立的后续语句重新核对将新增任务引用的版本。
不能把取锁与存在性检查塞进同一语句，使用等待前的旧快照；本方案以 READ COMMITTED 为前提，
实施时核实连接实际隔离级别，不在更高隔离级别下默认该前提成立。
先排除已有幂等任务，维持重复入队返回既有任务与 `random_id` 的语义，不能借检查版本重新生成任务。

两种先后顺序应有明确结果：

- 入队先持锁并提交：后续清理语句看到存量引用，保留该版本。
- 清理先删除并提交：后续入队发现版本不存在，不写入新悬空引用；整批新写入及事件处理标记回滚。
  重新读取规则并生成计划，不能把旧快照重新插回版本表，也不能只丢掉受影响任务后提交其他任务。

在入队之前加载版本时遇到同类消失，也要进入重新取规则的路径。
使用内部可区分的计划失效结果接入 worker 的退避与停止处理，不增加对外错误码，
不把所有 NotFound 或其他业务错误都改成无限重试。
若重新读取后确认当前版本本身缺失，应作为数据不一致失败，不能持续空转或把事件标为已处理。

核查规则语义更新、替换复制和显式删除的调用链：语义更新及复制推进版本后，旧计划必须能恢复；
显式删除规则的接口及已入队任务继续发送的语义不变。
多规则任务在同一租户锁下处理，锁顺序统一，不在持锁时发 Telegram、S3 或其他外部请求。

advisory lock 约束的是这些共用入口，不约束任意直接 SQL。
RLS 负责直接 SQL 的租户、到期与引用可见性限制，但不能把它声称为任意 SQL 并发下的完整引用约束。
验收须搜索所有生产入队和留存入口确认没有绕行；未来新增入口必须复用该协议。
若需要把任意 SQL 的并发保护也纳入保证，须另提数据库约束方案，不能凭本片宣称已覆盖。
