## 一、为什么再次升级

原提案要求不给 `tenant_purge` 直接删除 `tenants` 的权限，改由锁内检查所有条件的固定入口完成根删除。
实测当前根表没有 RLS，owner 为 `tgm_owner`；现有业务和清理角色均没有根表 DELETE。
普通 `SECURITY INVOKER` 函数不能弥补调用者缺少的表权限。

另一方面，ADR-0004 全面禁止 `SECURITY DEFINER`。实现侧 A8 对所有非系统 schema 的此类函数报红，
没有“函数只处理根表”或“owner 不是超级用户”的例外。原提案没有批准修改这条基线。
不能把终结函数加进去后再调弱断言，也不能临时使用 owner 连接完成删除。

## 二、方案比较与建议

| 方案 | 可满足的边界 | 代价与结论 |
|---|---|---|
| 继续使用 invoker，且不授根表 DELETE | 保持现有 A8 和原提案的权限禁令 | 没有可执行的根删除入口，不作为实现方案 |
| 给 `tenant_purge` 根表 DELETE，以 invoker 触发器强制检查 | 不必引入 definer | 改变原提案的授权边界；根表没有 RLS，安全承重集中到触发器；可另行批准，不默认采用 |
| 为 `tenants` 引入 RLS | 可以另行设计根行删除策略 | 改变全部租户查询与生命周期入口的授权模型，本片不扩为全局权限重构 |
| **只为一个固定终结函数增加精确 definer 例外** | purge 登录凭据仍没有根表 DELETE，检查在数据库中完成 | 必须新 ADR、A8 精确例外和 C15；建议采用，但批准前不实施 |

建议选择最后一项。它不是“保留全面禁用但悄悄例外”，而是明确变更 ADR-0004 的这一项决定。
批准后追加新 ADR，保留旧 ADR 正文；FORCE、invoker 视图、其他函数的禁令均保持。
同步 `spec/05`、`eng/00`、`eng/04` 和测试策略，不只改审计 SQL。

## 三、拟批准的精确范围

### 3.1 角色与入口

- 只允许 `public.tenant_purge_finalize(bigint)` 这一完整函数标识成为新增 definer 例外。
  bigint 仅为 worker 从数据库候选中取得的定位键，不是删除授权；数据库须把它视为不可信输入并重验全部条件。
  CLI 仍不开放任意租户、cutoff、表名或 SQL 参数，不接受用户提供的提前清理时间。
- 函数由独立 `tenant_purge_finalizer` NOLOGIN 角色持有；该角色不是表或 schema owner，
  没有 SUPERUSER、BYPASSRLS、CREATEROLE、CREATEDB、REPLICATION，也不加入其他角色。
  运行身份不得成为其成员，不得通过 SET ROLE 取得其表权限。
- finalizer 只获根表 DELETE、候选与残留存在性检查所需的最小列权限，以及固定完成日志的写权限。
  不给子表 DELETE/UPDATE、TRUNCATE、建对象、凭据密文、会话标识、消息正文或对象 key 的读取权限。
  `tenant_purge` 自身仍无根表 DELETE；业务及其他清理角色的既有权限不扩大。
- 撤销 PUBLIC EXECUTE，只给 `tenant_purge` 执行权限且不可转授。
  登录角色不可在函数所在 schema 建对象，也不可替换函数或其依赖。
  函数创建、owner 设置、撤销默认权限和精确授权必须在同一迁移事务中完成，不留下 PUBLIC 可执行窗口。
- 函数使用固定 SQL、显式 schema 限定对象，固定 `search_path=pg_catalog,pg_temp`，
  不执行动态 SQL，不采用调用者可写对象、可改函数体或用户文本作为判断依据。
  固定语言、返回类型、VOLATILE 与并行属性；这些均进入审计，不靠文件名或函数名约定。

### 3.2 根删除与完成日志

- 复用生命周期锁，按 READ COMMITTED 下“取锁后新语句复查”的协议执行；锁不可得则返回非成功结果，
  不在持锁事务内跨批次等待。锁序必须与注销、扇出、投递及共享回收一并测试。
- 数据库重新验证租户状态、数据库时间计算的到期条件、在途排空和所有真实 FK 子项。
  不相信调用者已经检查过，也不把调用者设置的 `app.tenant_id` 当成授权凭证。
- **根删除要求所有可清子项为零**，不依赖根级联扫尾。不先删根再用 FK 报错代替残留检查，
  也不能因 finalizer 的 RLS 看不到某类残留而误判为空。
  存在性检查须在最小列授权和专用非恒真策略下实际看见需要阻止删除的行；看不见不算通过。
- 根行删除与固定平台级完成日志同事务。完成日志 `tenant_id IS NULL`，只记录已批准的租户键、
  固定类别、计数及结果，不在根行删除时随租户级联消失，也不含引用方租户或业务内容。
  日志失败回滚删除；零行、缺失租户或阻塞不得输出物理删除成功。

### 3.3 成员与同意记录的最终限批

成员端 CASCADE 已实测会突破父语句计数，不能把根入口受限当作限批已经解决。
建议按以下依赖顺序实现，不新增同意记录 TTL，不在共享阻塞阶段提前清除同意记录：

1. 共享阻塞期间保留成员和同意记录；先按原提案限批处理其他获准的数据。
2. 必须先安全清空该租户的**全部私有身份及依赖它们的 canonical、媒体关系与 job**，
   不以“当前没查到外部引用”替代这一步。有任一共享阻塞或尚存身份就不能开始成员/同意记录阶段。
   旧身份和事件行删除后，外键本身拒绝继续引用那些已不存在的锚点。
3. 每一最终批次重新取得生命周期锁并复查锚点为空、到期和排空条件，再显式限批删除同意记录；
   只有同意记录及会话等子项为零的成员才允许删除，不依赖成员 CASCADE 扫尾。
   每批日志同事务，跨批次释放锁；成员或同意记录仍在时，终结函数拒绝根删除。
4. 必须测试已注销租户不能在批间被现有写入口重新创建私有身份或其他共享锚点。
   外键只能保护已经消失的锚点，不能阻止重新建身份；因此“身份清空后不会再出现共享阻塞”仍是
   需要受限角色、全部相关写入口和并发测试证明的性质，不记作当前已验证事实。

如果现有生命周期围栏不能证明最后一项，继续升级明确持久围栏或写入约束；
不擅加终结状态/列、不改级联、不改成单个长事务，也不为了继续实施先删同意记录。

### 3.4 A8、C15 与反证

- A8 仍跨所有非系统 schema 检查 definer，只排除完整 schema、名称和输入类型一致的这一函数。
  不按函数名前缀、schema 整体或角色名放行；新增重载和换 schema 同名函数仍必须被 A8 捕获。
- C15 必须要求该函数存在，精确检查签名、语言、返回类型、owner、ACL、配置、函数体与已审查版本一致，
  以及 finalizer/purge 的角色属性、成员关系、所有表/列/序列/函数有效权限及 RLS 表达式。
  覆盖根表全部真实 FK 入边与级联依赖、用户删除触发器，新增清理对象必须重新核定，不能沿用旧函数静默级联。
  没函数、被替换、失去 definer 属性或新增可写依赖都不得假绿；期望定义不能来自运行角色可改写的对象。
- A8 负责“还有没有别的 definer”，C15 负责“唯一例外是否仍精确受限”，不把例外仅写成名称白名单就结束。
  审计源码与 `eng/04` 同步；新增和改动的断言按双遍纪律逐项破坏、仅预期断言报红、撤销后目录一致。
- 受限角色测试覆盖直接根 DELETE、SET ROLE、任意 tenant 参数、错误上下文/隔离级别、search_path/临时对象、
  提前或非 deleted 删除、残留遮蔽、其他租户/共享数据、超限级联、日志失败与并发新引用。
  静态目录检查不能替代这些执行测试。
- 沿用原提案的迁移重入、SQLx prepare 与完整门禁，不新增依赖、不改已应用迁移，
  不将 ignored 用例当作验收通过，不连接生产或执行真实业务删除。

## 四、当前验证与交付边界

`scripts/tenant-purge-preflight.py` 自测与本地隔离 SQL/锁探针通过；只验证前置目录和探针性质。
新增根表授权基线与现存 definer 对象检查，使上述冲突可以从目录复核，而不是只靠散文说明。
工具不代替 A8/C15，也不证明终结入口、限批清理或完整生产锁协议已实现。

平台机制复核以 PostgreSQL 17 官方说明为准：
`https://www.postgresql.org/docs/17/sql-createfunction.html` 的安全 definer 章节，及
`https://www.postgresql.org/docs/17/ddl-rowsecurity.html` 的默认拒绝、策略权限和外键检查边界。
官方说明不能替代本仓原语禁令的批准，也不能替代受限角色测试。

身份围栏已追加迁移 `0055` 并通过专项、SQLx prepare/check、迁移重入及完整本地门禁，
包括 A8、当前身份围栏范围的 C15 与审计双遍；证据见
`../evidence/WP-8-注销租户身份写入围栏实施-2026-10-28.md`。
本提案的 purge/finalizer 安全面、根删除入口和 C16 已实施并通过本片证据；限批清理、CLI/调度、
生产验收和完整 WP-8 出口仍未完成，不宣布 WP-8 通过。
