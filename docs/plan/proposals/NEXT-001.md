## 任务与 PR 拆分顺序

1. 先收口 `PRE-001` 的远端基础环境与驱动校验；在无预置镜像缓存的 runner 上验收，
   查询或引用核验失败必须阻断发布。
2. 单独验收 WP-3/WP-4 已有事件、规则、投递与后台 worker 链路；连同对应受限角色
   测试及必要 SQLx 缓存收口，不把后续会话迁移和控制台 UI 一起混入。
3. 收口 WP-5 控制面及双 OpenAPI 产物，再接入 `PRE-004` 卡口。真实进程重启回归只
   覆盖 fanout 路径，不据此宣称所有 worker 或投递恰好一次已经验收。
4. 按 `0015`、`0016`、`0017` 的依赖顺序收口已批准会话签发、登出和会话管理；每批
   同步生产/测试迁移、SQLx 缓存、契约及反向测试，不改已应用迁移。
5. 最后按现有切片证据整理 WP-7 控制台改动。切片本地通过不等于六页整体可用，仍须
   真实浏览器验收，不能用脚本结构检查替代布局、焦点与兼容性。

这是待批准的分批方案，不是声称当前文件已能机械分割；共享 `repo.rs`、配置、错误
类型、依赖和 HTTP 路由需逐批核对编译与接口依赖。每批在前置提交基线上重跑门禁，
不能拿最终大工作树的绿灯给某个拆分提交背书。WP-2 未过出口的偏离需维护人明确
处理，任务卡不得把它隐去。

## 外部补验与冻结

执行入口与逐项判据沿用 `docs/plan/evidence/P0-外部验证手册-2026-10-08.md`，归档责任
如下：

- 实现人与测试环境提供方：QR、session 恢复、授权撤销、消息及断线恢复。
- 控制台/运维负责人：受控 HTTPS、BotFather、真实 OIDC 回调与换钥失败路径。
- 目标租户/产品负责人：脱敏申请记录与 `api_id` 归属结论。
- 产品负责人/实现人：媒体范围同步和真实媒体中转可行性；范围已定不等于验证通过。
- 维护人：核对证据后记录 G0/G1/G2 冻结结论；未验证保留未通过，例外按原判据处理。

责任角色沿用 P0 收口记录，实际执行人员和环境仍须指定。缺真实证据时不自动冻结，
也不把未知外部条件降级为本地 stub 检查。
