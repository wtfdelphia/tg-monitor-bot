## 需要完成的工作

### 1. 首发媒体范围同步（早期任务，决策与设计同步已完成）

产品负责人已选择“首发包含媒体”。受控同步必须写明：

- 首发能力与明确不做的能力；
- 套餐和容量口径是否变化；
- `spec/01`、`spec/02`、`eng/02`、任务卡和首发验收如何同步；
- 媒体失败时的处置，不再默认降级成“首发只转文本”。

决策和设计同步已经完成；媒体实现及限定场景验收见 WP-5 记录。MinIO 容器存在本身不构成
媒体能力证据，WP-5 局部通过也不能替代 G4 的生产存储、容量和未覆盖场景判据。触及需求
基线或 `plan/00` 的变更仍按 A 类变更控制执行。

### 2. grammers 与 QR 真机验证

沿用 `T-0002` 与 `docs/plan/proposals/T-0002.md`，使用测试账号和可撤销凭据完成：

- 同 DC 扫码；
- `MigrateTo` / 非默认 DC；
- 2FA；
- token 过期刷新并拒绝旧 token；
- session 落库后重启恢复；
- 手机端取消授权后识别为 `unauthorized`。

每项记录时间、账号素材标识、结果、失败处置和证据位置；不把手机号、二维码 token、
`api_hash`、session 或密码写入仓库。

此列表是早期验收计划。后续 WP-2 已记录 T1 与 T2–T6、消息更新、catch-up 和 session 恢复；
T1 同 DC 分支未单独确认。按 G1 责任方裁决处理该窄项，不重复已有验收，具体边界见
`docs/plan/evidence/G0-G2基线缺口盘点-2026-11-13.md` 与外部验证手册 §二。

### 3. 控制台登录可行性

本地 `control-plane` OIDC 起始、`/auth/oidc/callback`、PKCE、JWKS 验证和会话签发已经实现，
stub 成功/失败路径已有测试。真实联调仍需专用 BotFather 配置、Client ID/Secret 和可访问
的 HTTPS 地址；不得把真实 provider、Allowed URLs 或 JWKS 换钥描述为已验证。按外部验证手册
准备受控配置后，再由责任方安排真实流程：

- 登记实际站点 origin 与回调 URI；
- 验证本地开发地址、预发地址和正式地址的可用性边界；
- 完成 Authorization Code + PKCE 回调与会话签发；
- 验证未知 `kid`、JWKS 拉取失败、换钥期间新旧 key 并存和过期 token；
- 确认控制台二维码与 MTProto 账号二维码的页面标题、说明和错误态不混淆。

失败时统一拒绝登录，不把未知 key、回调不匹配或过期 token 降级为未验证用户。

### 4. 租户自带 `api_id` 验证

使用已具备的非平台自有目标租户账号，按官方申请入口完成一次申请记录，并只保存：

- 申请步骤是否可完成；
- 需要的账号条件与限制；
- 失败页面或失败类别；
- 是否支持租户自带归属模式；
- 不保存 `api_hash`、手机号、验证码或任何 session 材料。

Telegram 官方资料确认申请入口是 `my.telegram.org` → `API development tools`，
并要求应用使用自己的 `api_id`；这只能作为设计输入，不能替代本项目目标租户的实际
申请记录。
