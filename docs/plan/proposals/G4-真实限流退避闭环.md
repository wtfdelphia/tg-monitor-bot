## 一、目标与边界

本片只补 G4 的真实限流退避证据，不扩大生产功能范围，不宣布 G3、G4、WP-8 或稳定版
发布通过。验收必须使用专用、隔离的 Telegram 测试账号、测试 Bot、测试源和测试目标，
不得使用生产 Bot token、`api_id`、`api_hash`、session、频道或租户。

本片不通过反复刷消息、并发轰击或公开频道制造限流。优先复用既有真机测试自然产生的
`FLOOD_WAIT`；只有在维护人确认测试对象、调用上限和停止条件后，才允许执行一次短时、
低频、可中止的受控探针。无法安全获得真实限流时，结果记为 `not-run`，不得用 mock
429、单元测试或 Bot API 的本地错误替代真实 Telegram 证据。

不修改已应用迁移、数据库结构、RLS、GRANT、CI 或生产调度。若为完成闭环必须改动生产
投递逻辑、凭据处理、迁移或安全门禁，立即停止并另立提案。

## 二、实施前检查

1. 维护人确认专用测试账号只加入测试源和测试目标，确认目标消息可删除，并提供外部平台
   风险边界、最大调用次数和人工停止联系人。
2. 只读检查测试配置存在性；不打印 token、`api_hash`、session、手机号、密码、二维码、
   消息正文或个人标识。需要扫码时，遵循仓库根 `AGENTS.md` 的终端二维码或 SSH 隧道
   交付方式，不在聊天中贴二维码。
3. 使用当前 `dev` 对齐的候选或已批准的真机验收基线；记录 commit、候选版本和测试材料
   摘要，不把历史候选的结果移植到当前基线。
4. 先确认临时 PostgreSQL、Redis 和 MinIO 的 project 名称；不连接生产数据库、不启用
   生产 timer、不安装生产 unit。验收失败时先停止外呼和 worker，再保留脱敏诊断。

## 三、验收步骤与判据

### 3.1 触发并记录真实限流

1. 运行现有真实投递路径，使用唯一随机标签生成一条仅属于本次验收的测试任务。
2. 观察 Telegram 返回的真实 `FLOOD_WAIT` 或等价的限流响应；只记录脱敏错误码和服务端
   返回的等待秒数，不记录原始错误正文或凭据。
3. 收到限流后立即停止新增外呼和加压，不重试轰击，不改变等待秒数，不把本次错误扩大到
   其他测试账号。

若未观察到真实限流，输出已执行的受控探针、调用次数范围和停止原因，判定
`flood_wait_observed=not-run`，继续保留非生产分类测试，但不得写成通过。

### 3.2 核对数据库退避状态

在受限的验收查询路径中核对：

- 任务仍属于本次随机标签，未被标记为 `DONE` 或永久失败；
- `error_code` 为脱敏后的 `FLOOD_WAIT` 分类；
- `next_retry_at` 已写入，且不早于服务端要求的等待截止时间；
- 关联身份进入 `flood_wait` 状态或等价的当前实现状态；
- 限流期间 worker 不重复发起同一外呼，不生成第二条等价任务。

判据输出为 `retry_at_persisted`、`identity_state` 和 `retry_suppressed`，每项必须有明确
的 `pass` 或 `fail`；只看到日志而没有数据库状态不算通过。

### 3.3 等待到期并恢复

1. 等待 `next_retry_at` 到期，不手工提前修改数据库时间，不删除失败记录，不清空身份状态
   来制造恢复。
2. 恢复 worker 后核对同一任务最终只完成一次，Telegram 目标只出现一条本次随机标签消息。
3. 重复运行恢复检查，核对不会生成第二条投递，也不会重复消费已经完成的任务。
4. 若服务端再次延长等待，按新的真实响应重新进入等待；连续第二次触发时立即停止本片，
   记录为未完成，不循环尝试。

判据输出为 `wait_expiry`、`single_delivery_after_recovery` 和 `duplicate_delivery`。
消息 id、任务 id 和随机标签只写入脱敏的本地证据；不写入 token、session 或消息正文。

### 3.4 日志、凭据与清理

- journal、错误响应和验收报告不得包含 token、`api_hash`、session、密码、手机号或完整
  的 Telegram 错误正文；`journal_redaction` 必须通过。
- 测试结束后停止 worker、清理临时 Compose project、临时数据库、Redis、MinIO、二维码
  和 session 快照。
- 仅删除本片创建且可安全确认的测试源/目标消息；平台拒绝删除时，保留脱敏标签和人工
  清理清单，不删除任何非本片消息。
- 验收报告必须明确 `production_services=untouched`、`production_credentials=not-used`
  和清理结果。任何无法确认归属的资源交给维护人，不执行全局清理。

## 四、验收报告格式

报告至少包含以下字段，未达到的字段写 `not-run` 或 `fail`，不得省略：

```text
source_message: pass|not-run
flood_wait_observed: pass|not-run|fail
retry_at_persisted: pass|fail|not-run
identity_state: pass|fail|not-run
retry_suppressed: pass|fail|not-run
wait_expiry: pass|fail|not-run
single_delivery_after_recovery: pass|fail|not-run
duplicate_delivery: pass|fail|not-run
journal_redaction: pass|fail|not-run
production_credentials: not-used
production_services: untouched
cleanup: pass|partial|fail
```

本片通过的最低条件是：真实限流已观察、退避状态已落库、等待到期后同一任务单次完成、
重复运行不重复投递、日志脱敏和清理均通过。若真实限流未安全发生，整体只能记录为
`partial`/`not-run`，不得更新 G4 为通过。

## 五、停止条件与审批请求

命中以下任一情况立即停止：调用速率或对象边界不再可控；出现生产凭据或生产资源；
出现非本片消息；Telegram 返回连续延长的限流；数据库状态与任务标签无法一一对应；
需要修改生产代码、迁移、RLS、GRANT、凭据处理或 CI 门禁。
