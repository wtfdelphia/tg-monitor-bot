# PRE-007：生产二进制发布与原生安装工件

任务 id：`PRE-007-binary-release`。

状态：已批准，进入实现。基线为 `cloud/dev` 当前合并提交
`cbbff4c`（PR #77）。本提案新增独立的原生二进制发布路径，与 GHCR Docker 镜像发布并行；
不修改现有 `ci.yml`，不直接安装或启用目标机服务。

## 一、背景与目标

当前仓库已经有以下基础：

- `Dockerfile` 可以构建单一 `tgm` 运行镜像；Docker 镜像由独立 workflow 推送到 GHCR。
- `tgm` 是单二进制、多 subcommand 形态，迁移文件编译期嵌入二进制。
- `deploy/systemd/` 已有租户清理、平台清理、共享清理和身份清理的 unit/timer 工件。
- WP-8 曾完成过 release 二进制的本地构建与 unit 语法预检，但那不是可下载、可验证、可签名、
  可回滚的正式发布工件。

生产需要同时支持两种交付形态：

1. Docker：从 GHCR 拉取已标记和已证明的镜像；
2. 原生二进制：从 GitHub Release 下载与提交绑定的压缩包，在目标机校验后安装。

两条路径必须来自同一稳定版本提交，但不能互相替代。GHCR 推送成功不代表原生二进制已经
通过目标机验收；二进制签名通过也不代表生产数据库、备份、告警或清理 timer 已经验收。

判据出处：`docs/design/ops/00-部署与运行时.md` §一至§二、§六；
`docs/design/ops/01-上线就绪与运维.md` §二至§六；
`docs/plan/evidence/WP-8-release运行工件预检-2026-10-31.md`；
`docs/plan/proposals/WP-8-production-ops-acceptance.md`。

## 二、批准后交付范围

### 2.1 独立二进制发布 workflow

新增独立 `.github/workflows/binary-release.yml`，不修改现有 `.github/workflows/ci.yml`，
也不把二进制发布步骤塞进 Docker 发布 workflow。

默认只对正式版本 tag 发布，例如 `v0.1.0`；不对普通 `dev` push、PR 或每次 `main` push
自动生成生产二进制。手工 `workflow_dispatch` 只允许重跑一个已经存在且指向 `main` 历史的
版本 tag，不允许从任意分支选择源码发布。

发布前必须核对：

- tag 对应提交在 `main` 历史中；
- 版本号与 Cargo workspace 版本、发布 tag 的规则一致；
- 当前提交的现有 `static` 与 `database` CI 已通过，或由 `main` 分支保护保证合入前通过；
- 工作区不含未提交文件，构建使用提交中的 `Cargo.lock`、`rust-toolchain.toml` 和 `.sqlx/`。

workflow 使用固定的 Rust 工具链和 `SQLX_OFFLINE=true cargo build --release --locked -p tgm`，
不连接生产数据库，不读取生产 Secret，不把 `.env`、Telegram session、二维码、KMS 值或
对象存储凭据放入工件。

### 2.2 发布工件内容

每个目标平台发布一个压缩包。首发强制支持目标机 CentOS 7 / glibc 2.17，目标平台固定为 Linux x86-64 glibc：

```text
tgm-<version>-linux-x86_64-gnu.tar.gz
```

压缩包包含：

- `bin/tgm`：release 二进制；
- `SHA256SUMS`：包内文件校验值；
- `BUILDINFO.json`：版本、提交、目标 triple、Rust 工具链、构建器镜像摘要、构建时间和
  依赖锁定信息；
- `sbom.cdx.json`：该二进制构建输入的 SBOM；
- `deploy/systemd/`：当前已批准的 systemd unit/timer 和环境变量示例；
- `scripts/install-native.sh`：只在批准后实现，默认只校验和安装，不自动启动或启用服务；
- `README.md`：目标机前置条件、安装、迁移、验证、回滚和清理步骤。

GitHub Release 另外发布：

- 压缩包；
- `SHA256SUMS`；
- `SHA256SUMS` 的签名或等价签名工件；
- provenance/attestation 文件；
- SBOM 文件。

工件不包含数据库密码、生产环境文件、Bot token、`api_hash`、Telegram session、QR 文件、
KMS Secret、Redis/S3 凭据或生产数据。

### 2.3 签名、来源和不可变标识

采用 Sigstore/cosign keyless 签名：workflow 通过 GitHub OIDC 取得短期签名身份，签名
`SHA256SUMS`，并发布可验证的 provenance。仓库不保存长期私钥；workflow 需要显式声明
`id-token: write`，同时只保留发布所需的 contents 权限。实施 PR 必须单独检查 OIDC subject、
签名身份约束、透明日志记录和日志脱敏。

每个工件必须同时绑定：

```text
版本 tag → Git 提交 SHA → 构建目标 triple → 压缩包 SHA-256 → 签名/证明 → GitHub Release
```

版本 tag 和文件名是人类入口，SHA-256、签名和提交 SHA 才是安装前的裁决依据。

## 三、目标机兼容性与平台边界

此前目标机已确认 Linux 3.10 系列内核、Docker Engine 26.1.4 和 Compose v2.27.1；本提案
进一步要求原生二进制必须兼容 CentOS 7 / glibc 2.17。架构、OpenSSL 运行库和 systemd
版本仍需在目标机采集；在这些事实获得前，不能宣称原生二进制可安装。

批准后必须先采集并留证：

```bash
uname -m
ldd --version
openssl version -a
systemd --version
cat /etc/os-release
```

初始平台矩阵建议为：

| 平台 | 规划状态 | 放行条件 |
|---|---|---|
| Linux x86-64 glibc 2.17 | 首发强制目标 | 使用 glibc 2.17 兼容 builder 构建，并在目标机运行帮助、动态依赖和 unit 预检通过 |
| Linux x86-64 musl | 不默认承诺 | 只有确认 grammers、AWS SDK、TLS 和系统 CA 形态后另行验收 |
| ARM64 | 不在首发 | 需要独立构建、依赖和目标机验收证据 |
| macOS/Windows | 不在生产范围 | 不生成生产工件 |

目标机必须兼容 CentOS 7 / glibc 2.17，因此必须使用 glibc 2.17 兼容的专用构建环境，
不能直接用现代 Ubuntu runner 编译后上传。实现必须记录 builder 镜像/环境摘要、glibc
符号版本和动态库清单；不能用“内核版本相同”替代 libc 兼容性证据。

如果无法在目标机满足动态链接条件，必须在提案实现阶段停止，重新评估：升级目标机、改用
兼容 builder、提供静态/准静态目标，或将该目标机限定为 Docker-only。不得通过 `setcap`、
`seccomp=unconfined` 或关闭系统安全策略绕过兼容性失败。

## 四、原生安装、迁移和运行边界

### 4.1 安装布局

建议采用版本目录和原子切换，而不是覆盖正在运行的文件：

```text
/opt/tgm/releases/<version>/tgm
/opt/tgm/releases/<version>/SHA256SUMS
/usr/local/bin/tgm -> /opt/tgm/releases/<version>/tgm
```

安装脚本必须：

1. 在 root 模式要求 root；在非 root 模式安装到用户目录，禁止尝试写 `/usr/local/bin` 或系统 unit；两种模式都检查目标架构、glibc/OpenSSL/systemd 前置条件；
2. 先验证签名和 SHA-256，再复制到临时目录；
3. root 模式以 root:root、`0755` 安装二进制，以 root:root、`0644` 安装 systemd unit；非 root 模式以当前用户安装到 `$HOME/.local/opt/tgm/releases/<version>`，不修改系统 unit；
4. 原子更新 `/usr/local/bin/tgm`，保留上一版本以便回滚；
5. 默认不执行 `tgm migrate`、不启动服务、不启用 timer；
6. 失败时不切换当前 symlink，不删除旧版本；
7. 不从网络下载额外脚本或依赖，不执行 `curl | sh` 形态。

### 4.1.1 root 与非 root 模式

两种模式必须是明确的独立入口，不能通过自动探测当前用户静默改变安装位置：

| 模式 | 安装位置 | 可执行内容 | systemd 能力 |
|---|---|---|---|
| root 安装 | `/opt/tgm/releases/<version>` 和 `/usr/local/bin/tgm` | 安装二进制、cleanup unit/timer、root 所有的环境文件模板 | 可安装 unit，但默认不 enable/start；启用需另行批准 |
| 非 root 安装 | `$HOME/.local/opt/tgm/releases/<version>` 和 `$HOME/.local/bin/tgm` | 安装二进制和用户级配置模板 | 只能使用 `systemd --user` 的后续方案；本首片不自动注册用户 unit |

root 模式的 cleanup unit 仍按仓库既有 `User=` / `Group=` 运行，不允许直接以 root 执行租户
清理。非 root 模式不得伪装成生产 cleanup 调度：它只能用于开发、验证或维护人明确执行的
手工命令，不能访问 root-only 的 `/etc/tgm` 环境文件。

安装脚本必须提供 `--root` 与 `--user`（或等价的显式模式），拒绝同时使用；在非 root 模式
发现目标路径属于 root 或无法写入时立即失败。二进制本身不需要 root 权限，权限提升只用于
系统级安装和 systemd 工件管理。

### 4.2 启动和迁移顺序

生产发布必须遵守现有前滚迁移纪律：

1. 停止或隔离旧运行进程；
2. 在隔离恢复库上验证新二进制与历史数据、迁移和 RLS 审计；
3. 在生产维护窗口执行 `tgm migrate`；
4. 执行 `tgm audit-rls`，必须为零报红；
5. 按批准顺序启动进程；
6. 最后才考虑启用已批准的 systemd timer。

安装脚本不得自动把迁移和服务启动绑在一起。迁移是数据库变更，服务启动是运行时变更，
必须分别记录结果。

### 4.3 回滚语义

二进制可以回滚，数据库迁移不能依赖 down migration 回滚。若新版本已应用迁移，旧二进制
不一定兼容；回滚只能选择：

- 前向修复并继续使用新 schema；或
- 按批准的恢复流程恢复数据库，再切回旧二进制。

安装工具必须明确输出这一边界，不能提供“恢复旧二进制即可恢复生产”的误导性按钮。

## 五、systemd 范围

本提案首片只打包和校验仓库已有的 cleanup unit/timer，包括 `tenant_purge`、租户留存、共享
事件、平台日志和身份清理。安装包不自动启用任何 timer；生产启用仍需独立批准和真实告警
接收人、停止/重跑步骤证据。

root 和非 root 安装都必须支持二进制本身的签名/校验和帮助命令；只有 root 模式可以安装
系统级 cleanup unit。非 root 模式不安装系统 unit，也不改变系统服务状态。

当前仓库没有完整的 control-plane、bot-gateway、mtproto-worker、fanout、rule、delivery
原生 systemd service 集合。应用角色原生 systemd service 明确另立提案，补齐：服务用户、
root/非 root 运行模式、环境文件、依赖顺序、监听端口、重启策略、日志、健康检查、停止传播
和单实例约束。本提案不把缺失的服务定义伪装成已完成。

## 六、验收判据

1. 独立二进制发布 workflow 不修改 `ci.yml`，只对合入 `main` 的正式版本 tag 发布。
2. workflow 构建使用锁定 Rust 工具链、`Cargo.lock`、提交 `.sqlx/` 和无生产凭据的环境。
3. GitHub Release 同时提供版本、提交 SHA、目标 triple、SHA-256、签名、SBOM 和 provenance。
4. 目标机能够验证签名和校验值；不验证就拒绝安装。
5. root 安装和非 root 安装均可完成签名/校验、帮助命令和失败回滚；cleanup 二进制以非特权服务用户运行，安装目录、symlink、unit、环境文件权限符合文档。
6. `tgm --help`、相关 cleanup help、`systemd-analyze verify` 和动态依赖检查通过。
7. 目标机实际 `ldd`、OpenSSL、systemd 和架构兼容性有脱敏证据；不能用构建机结果替代。
8. 隔离恢复库上执行 `tgm migrate`、`tgm audit-rls` 和适用测试；不连接生产 Telegram、KMS、
   Redis、S3 或真实租户。
9. 安装失败不切换当前版本；回滚演练确认旧版本保留且数据库前滚边界已记录。
10. 构建、签名、压缩包、临时 target、Buildx builder 和临时容器结束后按仓库纪律清理，
    不使用全局 `docker system prune --volumes`。

## 七、明确不在本提案范围

- 不修改数据库迁移、RLS、GRANT、删除语义或公开 API。
- 不自动安装到生产目标机，不启用生产 timer，不删除真实租户。
- 不把 GitHub Release 二进制当作 Docker 镜像，也不把 GHCR tag 当作二进制版本签名。
- 不支持 ARM64、musl、macOS 或 Windows 首发工件。
- 不补齐应用角色 systemd service；该事项另立原生运行时提案。
- 在没有目标机 libc、OpenSSL、systemd 和架构证据时，不执行发布或安装。

## 八、已确认决策与后续前置条件

1. 正式版本只允许 `vMAJOR.MINOR.PATCH` tag，不对每次 `main` push 发布二进制。
2. 首发必须兼容目标机 CentOS 7 / glibc 2.17，目标平台为 Linux x86-64 glibc 2.17。
3. 签名采用 Sigstore/cosign keyless；workflow 使用 GitHub OIDC 短期身份，不保存长期私钥。
4. GitHub Release 暂作为二进制唯一分发渠道；目标机不直接从源码或 registry 拉取二进制。
5. 首片只打包仓库已有 cleanup systemd unit/timer；应用角色原生 systemd service 另立提案。
6. root 与非 root 安装都要支持，但非 root 只提供用户目录安装和验证，不伪装成系统级生产调度。
7. `main` 分支保护尚未配置；首次稳定版从 `dev` 合入 `main` 前，必须配置并验证 `static`、
   `database` 和发布 tag 权限，避免合并后自动发布绕过门禁。

## 九、批准后交付顺序

1. 采集并审核目标机架构、glibc、OpenSSL、systemd 和安装权限事实；
2. 固定首发 target triple、builder 基线和版本/tag 规则；
3. 实现独立二进制发布 workflow、CentOS 7/glibc 2.17 兼容 builder、打包脚本、cosign keyless 签名/证明和校验工具；
4. 在隔离恢复库和非生产目标机验证安装、迁移、审计、unit 解析、启动检查和回滚；
5. 生成脱敏证据并提交目标机生产安装验收提案；
6. 维护人单独批准后，才在稳定版本 tag 上发布第一份生产二进制。

本提案批准不等于授权生产安装、数据库迁移、timer 启用或真实租户物理删除。
