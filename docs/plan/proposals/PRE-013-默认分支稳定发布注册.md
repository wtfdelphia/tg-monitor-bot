# PRE-013：默认分支稳定发布注册

任务 id：`PRE-013-default-branch-stable-release-registration`。

状态：提案阶段，等待维护人批准。

## 一、背景

当前仓库的默认分支是 `main`，但实际开发和验收基线是 `dev`。截至
2026-11-05：

- `cloud/dev` 已包含 CI、候选二进制、Docker 无推送构建、Docker GHCR 发布和正式二进制发布
  workflow；
- `cloud/main` 仍是早期手工创建的最小分支，只包含候选 workflow 及其前置提交；
- GitHub Actions 只注册默认分支可见的 workflow，因此 `docker-publish.yml` 和
  `binary-release.yml` 当前没有实际 job 记录；
- 直接把 `dev` 推到 `main` 会同时改变稳定代码基线，并可能触发 GHCR 发布，不能用普通同步动作
  代替稳定发布评审。

判据出处：`docs/design/plan/00-里程碑与工期.md` §三 G4、§三 G5；
`docs/design/ops/00-部署与运行时.md`；
`docs/design/ops/01-上线就绪与运维.md`；
`docs/plan/proposals/PRE-006-GHCR-main镜像发布.md`；
`docs/plan/proposals/PRE-007-原生二进制发布.md`。

## 二、目标

建立一条可审计的稳定发布路径：

1. `dev` 继续作为开发、非生产验收和候选包来源；
2. `main` 只接收经过稳定发布评审的 PR，不接受直接 push；
3. 合并稳定代码后，Docker workflow 才允许为 `main` 构建并推送 GHCR 镜像；
4. 正式二进制只从 `main` 历史中的符合格式 tag 发布；
5. 默认分支 workflow 注册不会被误报为 G4、G5 或生产上线通过。

## 三、批准后实施顺序

### 3.1 先配置仓库保护

由维护人在 GitHub 仓库设置中完成并留存截图或 API 输出：

- `main` 仅允许 PR 合并，禁止直接 push；
- 合并前要求 `CI / static` 和 `CI / database` 成功；
- 要求分支及时更新，禁止绕过保护规则；
- 发布权限仅授予维护人或受控 release 角色；
- `dev` 继续作为开发分支，不把 `main` 改为开发默认分支。

在保护规则没有证据前，不执行稳定发布 PR。

### 3.2 准备稳定晋级 PR

从已通过 G4 的 `dev` 提交创建以 `main` 为 base 的稳定晋级 PR。该 PR 必须包含：

- 完整源代码和迁移，而不是只复制 workflow 文件；
- `ci.yml`、`docker-publish.yml`、`binary-release.yml` 及其依赖脚本；
- 稳定版本号、来源提交和发布说明；
- 对客文档 v1.0 与首发缺口明示；
- PRE-009/PRE-012 的候选验收边界，不把 CentOS 7 `-SECCOMP` 原生拒绝改写成通过。

稳定晋级 PR 不得包含生产 Secret、真实 Telegram session、KMS 凭据或用户消息正文。

### 3.3 合并后的发布顺序

1. 先观察 `main` push 触发的 CI；失败时不处理为发布成功。
2. 确认 Docker workflow 仅构建当前 `main` 提交，检查镜像 digest、provenance、SBOM 和
   GHCR 标签；不执行目标机生产部署。
3. 单独创建符合 `vMAJOR.MINOR.PATCH` 的稳定 tag。
4. 等待正式二进制 workflow 验证 tag 位于 `main` 历史、`static`/`database` check 成功、
   glibc 2.17 兼容检查通过，再创建 GitHub Release。
5. 发布后分别登记 Docker digest、二进制归档摘要、Sigstore bundle、provenance 和 SBOM。

### 3.4 发布后生产边界

稳定包产生不等于生产上线。G5 仍必须单独完成：备份恢复、RPO/RTO、指标和告警、值班、
容量实测、单实例租约防误双开。WP-8 的生产 timer、探针租户和真实租户删除仍按
`docs/plan/proposals/WP-8-production-ops-acceptance.md` 单独批准，不因本提案自动启用。

## 四、验收判据

1. GitHub 仓库保护规则已留证，`main` 无直接 push 路径。
2. 稳定晋级 PR 的 base 为 `main`，head 来自已通过 G4 的 `dev` 提交。
3. 合并后 `CI`、Docker GHCR 发布 job 和相应 provenance/SBOM 产物均有成功记录。
4. 正式二进制只由 `main` 历史中的稳定 tag 触发，候选 workflow 仍只接受 `dev` 手工运行。
5. 发布结果未触发生产迁移、systemd timer、真实租户删除或外部 Telegram 操作。
6. 发布证据明确区分“已生成稳定工件”和“已完成 G5 生产上线验收”。

## 五、不在范围

- 不把 `dev` 改为默认分支；
- 不直接复制 `dev` 到 `main`；
- 不在批准前配置或启用 GHCR 发布；
- 不创建稳定 tag、GitHub Release 或稳定 Docker 镜像；
- 不修改 G4/G5 判据，不跳过真实恢复、告警和值班验收；
- 不处理 CentOS 7 `-SECCOMP` 的原生安全缺口；该问题仍保持拒绝，另选 EL9 或另立补偿方案。

## 六、停止条件

出现以下任一情况，停止稳定晋级并回到提案评审：

- `main` 保护规则未配置或无法证明生效；
- 稳定提交没有 G4 证据或仍有关键系统测试未完成；
- Docker 发布将使用非 `main` 提交、错误标签或未启用 provenance/SBOM；
- 正式二进制 tag 不在 `main` 历史或缺少成功的 `static`/`database` 检查；
- 需要修改发布权限、生产配置、迁移、RLS 或删除语义；
- 需要绕过 CentOS 7 原生安全预检。
