# 动工前置（pre-do）

本目录回答一个问题：**设计文档已经写完了，还差什么才能敲第一行代码。**

它**不是文档集的第六层**。`../design/README.md` 的五层轴不变，本目录是一次性清单，
第一行业务代码提交之后即作废 —— 那时它列的每一项要么已完成，要么已转入
`../design/plan/00-里程碑与工期.md` 的工作包。

| | |
|---|---|
| 回答什么 | 动工前还缺什么 |
| 稳定性 | **最低。用完即弃** |
| 谁读 | 准备动工的人，只读一次 |
| 失效条件 | 命令流水线首次全绿（清单见 `../design/eng/04-CI门禁.md`） |

---

## 三条使用纪律

```text
1 本目录不定义任何数字与结论。表数、工期、版本号一律只引用 spec/ 与 eng/
  —— 违反这条就等于开了第二个事实源，而 ../design/README.md 硬规则 1 不允许
2 每一条「缺什么」必须带可复跑的验证判据。没有判据的条目不写进来
3 判定与设计文档冲突时，以设计文档为准，冲突本身记进 03-文档待更正.md
```

第 1 条最容易破。写清单时天然想把表数、断言条数、流水线命令数抄一遍方便阅读，
但那些数字在 `../design/spec/03-数据模型.md` 与 `../design/eng/04-CI门禁.md` 里各有唯一出处，
抄进来就会在它们变更时静默过期。本目录一律写「见某文件某节」，
引用断言时用它们的编号（`A1`~`A9`）而不是「九条」—— 编号不随数量变动。

## 进度

八步全部走完（`02-动工顺序.md`），三项环境阻塞全部解除（`00-环境前置.md`），
待建清单两类全部落地（`01-待建清单.md`）。**但本目录尚未作废**，两个理由：

```text
失效条件未真正满足   表头写的是「命令流水线首次全绿」。流水线现在是全绿的，
                     但其中 tgm openapi --check 仍是 not_implemented、
                     openapi.json 不存在，且没有 CI 配置文件 ——
                     八条卡口目前都是人在本地跑。这是「绿」不是「卡口在跑」
第一行业务代码未提交  作废条件是第一行业务代码提交（见上文）。当前只有骨架、
                     迁移与审计，没有一行业务逻辑，也没有一行 query! 宏
```

> 这两条本身就是本目录反复记下的那类事：**判据满足了，不等于它想保证的性质成立。**
> 所以不按「都做完了」作废，按表头那条失效条件作废。

## 一句话结论

**设计层没有一项阻塞动工**，这条结论经动工验证成立 —— 八步里没有一步因设计缺失而卡住。

但**工程层落地过程改掉了设计文档里的一批结论**（逐条登记在 `03-文档待更正.md`，
条数看那份文件，这里不抄 —— 纪律 1）。
其中相当一部分不是笔误，是「文档写的判据能被一个坏实现满足」。
最值得记住的一条形状是：**验证手段自己失效时，表现出来的是「通过」。**

原结论里两个写错的环境事实（`psql` 在非交互 shell 里不存在、`docker compose` 没装）
均已修复。后者当时推出的那条「`eng/02` §一 的 compose 编排从未真正跑过」**已作废** ——
现在全部迁移与审计都是在这套编排起的库上跑的。

核查日期 2026-09-21，动工与复测 2026-09-22，方式均为逐条实测，不是读文档推断。
