# 动工前置（pre-do）

本目录回答一个问题：**设计文档已经写完了，还差什么才能敲第一行代码。**

它**不是文档集的第六层**。`../design/README.md` 的五层轴不变，本目录是一次性清单，
第一行业务代码提交之后即作废 —— 那时它列的每一项要么已完成，要么已转入
`../design/plan/00-里程碑与工期.md` 的工作包。

| | |
|---|---|
| 回答什么 | 动工前还缺什么 |
| 稳定性 | **最低。用完即弃** |
| 谁读 | 准备动工的人，只读一次 |
| 失效条件 | 命令流水线首次全绿（清单见 `../design/eng/04-CI门禁.md`） |

---

## 三条使用纪律

```text
1 本目录不定义任何数字与结论。表数、工期、版本号一律只引用 spec/ 与 eng/
  —— 违反这条就等于开了第二个事实源，而 ../design/README.md 硬规则 1 不允许
2 每一条「缺什么」必须带可复跑的验证判据。没有判据的条目不写进来
3 判定与设计文档冲突时，以设计文档为准，冲突本身记进 03-文档待更正.md
```

第 1 条最容易破。写清单时天然想把表数、断言条数、流水线命令数抄一遍方便阅读，
但那些数字在 `../design/spec/03-数据模型.md` 与 `../design/eng/04-CI门禁.md` 里各有唯一出处，
抄进来就会在它们变更时静默过期。本目录一律写「见某文件某节」，
引用断言时用它们的编号（`A1`~`A9`）而不是「九条」—— 编号不随数量变动。

## 一句话结论

**设计层没有一项阻塞动工。** 阻塞的是工程层为零，加上两个环境事实文档写错了：
`psql` 在非交互 shell 里不存在，`docker compose` 插件根本没装 ——
后者意味着 `../design/eng/02-本地环境与迁移.md` §一 那份 compose 编排从未真正跑过。

核查日期 2026-09-21，方式是逐条实测，不是读文档推断。
