## 一、`spec/03` §4.2：`rule_versions` 的主键漏了 `tenant_id`（跨租户侧信道）

本文唯一一条已经改了代码的项 —— `migrations/0004_tables_rule.sql` 没有照抄，
偏离处写在该表的注释里。设计文档本身仍未改。

```text
现状   PRIMARY KEY (rule_id, version)
问题   破了铁律 1，且 eng/04 A4 会报红。实测确认不是误报 ——
       攻击者 tenant 1，受害 rule_id 1 属 tenant 2，以 app_user 带 app.tenant_id=1 插入：
         (1, 1,   tenant_id=1) → duplicate key ... "rule_versions_pkey"
         (1, 999, tenant_id=1) → FK violation "Key is not present in table rules"
         (999, 1, tenant_id=1) → 同上，与前一条不可分
         (2, 1,   tenant_id=1) → INSERT 0 1（自己的规则）
       前两种报错可分 = 一个可枚举的 oracle：探出他租户有哪些规则、各改了几版
影响   同表那道 FOREIGN KEY (tenant_id, rule_id) 拦不住它。
       唯一索引在堆插入期检查，外键是 AFTER 触发器 —— 唯一约束永远先报，
       复合外键这一层根本轮不到执行
改法   PRIMARY KEY (tenant_id, rule_id, version)
```

**为什么是漏列而不是破例**：同胞表 `rule_replacements` 与它同形（同样挂在 `rules`
下、同样的复合外键），PK 本来就是 `(tenant_id, rule_id, seq)`。而 spec/03 §7.1 说
`bot_console_sessions` 是全套设计里唯一允许违反铁律 1 的表，并明确
`不要为新表扩那个白名单` —— 两处一起看，只能是这里漏了一列。

补列不削弱唯一性：复合外键已把 `tenant_id` 钉死为 `rule_id` 对应的那一个值，
`(tenant_id, rule_id, version)` 与 `(rule_id, version)` 唯一性等价。
无下游影响 —— 全仓库无 `REFERENCES rule_versions`，`pg_constraint` 查引用为 0 条。
`delivery_tasks.rule_version` 是软引用，不是外键。

**已销账。** `spec/03` §4.2 的建表语句已改成 `PRIMARY KEY (tenant_id,
rule_id, version)`，并把「复合外键补不上这一列」那条理由写在了 PK 上方 ——
这是最容易再犯一次的地方，光改形状不写理由会被下一个人"优化"回去。

顺带撞上一件事：改完 spec 之后，`0004` 里那句「偏离 spec/03 §4.2」的注释
就过期了（分歧已不存在），于是我去改它 —— **迁移文件改不得**。
详见 `eng/02` §3.2 新增的那段：sqlx 的校验和不区分注释与 DDL，
已应用的文件改一个字节就 rc=1，而 CI 从零建库永远绿。已回退。

        Makefile、迁移脚本、cargo sqlx prepare、tgm audit-rls
建议   把「✓ 已装」限定为交互式 shell，并把「对 CI 的含义」扩成
        「对一切非交互执行的含义」

详见 `00-环境前置.md` §二。

**已销账（2026-09-22），但改法比上面的建议强一档 —— 原建议不够。**
「限定为交互式 shell」只描述了当时的状态；动工第 1 步已经把
`source env.sh` 挪到早退**之上**，所以现在登录 shell 也有了。
本来该到此为止，复查时多跑了一组对照：

```text
env -i HOME=$HOME bash -lc 'psql -V'   → 17.11        （挪动生效）
env -i HOME=$HOME bash -c  'psql -V'   → command not found
```

**不带 `-l` 的非交互 bash 既不读 `~/.profile` 也不读 `~/.bashrc`**
（`BASH_ENV` 未设），所以「挪到早退之上」治不了它 —— 而脚本默认就是这一种。
于是判据不能写成「`.bashrc` 里那行在第几行」，`eng/00` §零 的注解落成：
**凡是要 `psql` 的脚本自己 `source "$HOME/opt/pgdg17/env.sh"`。**

写下这条纪律之后立刻反查了现有脚本，**`scripts/audit-double-pass.sh` 是个反例**
（用 `psql` 但不 source，只有 `migrate-idempotent.sh` 有那一段），已补上。
验的方式是把 pgdg 路径从 `PATH` 里剔掉再跑整个脚本：16 条断言逐条打红、
收尾快照 554 行逐字节相同。
**一条只写在文档里的纪律，和一条不存在的纪律，在仓库里长得一样。**

连带把 `eng/00` §八 那条局限也划掉了：它说「RLS 审计命令一次都没在真实库上跑过」，
库已建、`audit-rls` 已接活库、双遍已逐条验过。

## 八、`cargo sqlx prepare --check` 目前是一条空的绿灯

                             另外它需要 DATABASE_URL —— 不设时报 error 但

## 十、`spec/03` §5.2 与 `eng/04` §二 A4 白名单：`uq_task_idem` 的破例论证不成立

与第一条同类，也已改了代码 —— `migrations/0006_tables_delivery.sql` 改了索引形状，
偏离处写在该索引的注释里。设计文档本身仍未改。

```text
现状   CREATE UNIQUE INDEX uq_task_idem ON delivery_tasks (idem_key)
       两处文档给的理由一致：「不含 tenant_id 是有意的，
       idem_key 本身是含 tenant 的五元组哈希」
问题   哈希把 tenant 藏进了值里，但**唯一约束泄漏的是存在性，与值是否可读无关**。
       攻击者不需要读出 idem_key，只需要能构造候选 ——
       而构造材料是公开的：spec/03 §5.2 自己给了公式
         idem_key = sha256("tenant|rule_id|rule_version|event_id|target")
         target           公开频道 id，自己订阅同一频道即得知，不是秘密
         其余四项          全是小整数，枚举空间很小
影响   实测（攻击者 tenant 5，受害 tenant 6 有一条 rule 7 / v3 / 事件 42 的任务）：
         以 ON CONFLICT (idem_key) DO NOTHING 批量插入 5000 个候选，
         一条语句 0.583 秒，返回「INSERT 0 4999」。
         差值 1 就是 oracle，指出哪个五元组真实存在。
       不报错、不留行（回滚即可）、不逐个往返 —— 所以按请求计的速率限制也拦不住
改法   CREATE UNIQUE INDEX uq_task_idem ON delivery_tasks (tenant_id, idem_key)
```

**为什么只能改形状，不能像另两项那样用 GRANT 补偿**：A4 白名单原有三项，
另两项（`bot_console_sessions_pkey` / `uq_web_session_id`）都对 `app_user` 零权限，
探测请求在权限层就被拒（实测 `permission denied for table web_sessions`），
这是 A7 在校验的那道补偿。而 `delivery_tasks` 是业务主表，`app_user` 的
`SELECT/INSERT/UPDATE/DELETE` 四项实测全为 t，**收不回来** —— 没有补偿可用。

补列不削弱幂等：`tenant_id` 本来就在哈希输入里，把它加进索引键不改变任何一对
`(tenant, key)` 的唯一性判定，只是不再把不同租户的键放进同一个命名空间比较。

**已销账。** `eng/04` §二 的白名单此前那轮已从三项减到两项；本轮补上
`spec/03` 两处：§5.2 的建表语句改成 `(tenant_id, idem_key)`，
以及那张幂等表里「`uq_task_idem`（哈希入 `idem_key`）」一格 ——
后者不改会留下"哈希就够了"的暗示，而那正是原论证的出处。

同第一条：`0006` 的开头注释也过期了，也同样改不得，已回退。
实测改后同一批探测返回 5000（无信息），而同租户内重复 `idem_key` 仍报 duplicate key。

配套：该项已从 `eng/04` A4 的白名单里移除，由 A4 正常覆盖；A7 的白名单相应为两项。

> 本条与第一条合起来是一个形状：**「唯一约束含 tenant_id」这条铁律的每一次破例，
> 都要单独论证「攻击者能不能构造这个值」，而不是论证「这个值好不好猜」。**
> 哈希、随机 id、自然键，三种破例理由里只有第二种（值由库随机分配）真的站得住。

## 十一、`eng/02` §二 的权限矩阵：`identities` 那一格按字面照写会让断言报红

```text
现状   矩阵里甲类 19 张一律「SELECT/INSERT/UPDATE/DELETE」，identities 在其中
问题   eng/04 §三-2 的补充断言查的正是
         has_column_privilege(..., 'identities', 'tenant_id', 'UPDATE')
       表级 GRANT UPDATE 会让每一列都为 t —— 照矩阵写，这条断言第一遍就报红。
       实测确认：已发布的迁移上它本来就是红的，第 7 步才发现
依据   spec/06 §2.5「不提供把身份转给别的租户的端点」
改法   identities 的 UPDATE 收窄到列级，不含 tenant_id（见 migrations/0011）
```

**写法上有个实测过的陷阱，比这条更正本身更值得记住**：

```text
GRANT UPDATE ON identities TO app_user           → 每一列 has_column_privilege = t
再 GRANT UPDATE (kind, ...) ON identities        → 仍然是 t（列级加不减）
再 REVOKE UPDATE (tenant_id) ON identities       → 仍然是 t（实测）
```

**列级 REVOKE 减不掉表级 GRANT。** 必须先 `REVOKE UPDATE ON identities`（表级），
再逐列 `GRANT UPDATE (...)`。顺序反了不报错、权限照旧 —— 这正是这条断言存在的理由。

逐列列举而非「除 tenant_id 之外全部」：PG 没有后者的语法，且逐列列举会在将来加列时
暴露出来（新列默认不可写），这是想要的方向。

> 断言弱于它想保证的性质：列级 GRANT 拦得住改这一列，拦不住「先删后建」这种
> 等效操作。真正的保证靠 §2.5 的「写入路径只有一条」。断言只是让配置层不反悔。

**已销账（2026-09-22）。** `eng/02` §二 的矩阵加了一行
`└ 例外 identities`，并把那个「列级 REVOKE 减不掉表级 GRANT」的三行实测
搬进了 §二 下方 —— 原先它只在 `migrations/0011_grants.sql` 的注释里，
而**写 GRANT 的人读的是矩阵，不是上一版迁移的注释**。

矩阵里写成甲类底下的缩进例外行而不是单列一行，是为了让「甲类一律四项」
那句话与它的例外挨着 —— 分开写的话，照矩阵抄的人仍会先读到那句全称。

## 十二、`ADR-0022` 的双遍：判据要写成「每条断言各自可被打红」

不是文档错误，是判据可以更强，记下来供 ADR 的下一次修订参考。

`02-动工顺序.md` 第 7 步的判据是「DISABLE RLS 之后第二遍必须红」。照字面做一次

落地成 `scripts/audit-double-pass.sh`：每条断言各配一处针对性破坏，逐条验证

```text
1  被针对的那条必须红
2  报红的必须恰好是它一条（预期的连带登记在脚本的 ALSO 表里）
```

## 十三、写这个脚本时踩的两个「验证本身是假的」

两条都不是文档问题，是核查方法的问题，形状与「静默全绿」那一类同类。
登记在这里因为它们会重复发生。

```text
一  「审计重回全绿」证不了库回到了原状
    第一版脚本用「破坏全部撤销后 audit-rls 仍返回 0」作收尾检查，它通过了。
    但实测发现 ALTER TABLE keywords OWNER TO app_user 会把 app_user 的受赠 ACL
    条目并进 owner 条目，改回 tgm_owner 时**不还原** ——
    app_user 在 keywords 上的四项权限就此消失，而审计照样全绿。
    根因：这套断言只查「不该有的权限」，没有一条查「该有的权限还在不在」。
    一个 app_user 什么都碰不到的库，在 A0~C2 下完全合规。
    改法：收尾比对目录快照，不比对退出码。并且逐条撤销后就比一次 ——
    末尾比只能告诉你「有残留」，逐条比能指出是哪个用例的撤销不完整

二  快照脚本自己报错，而报错落进了快照文件
    快照里 POL/CON/ETR 三段都拼接了 "char" 类型列（polcmd/contype/evtenabled），
    `text || "char"` 报「operator is not unique」；CON 那段还有个 oid 歧义。
    因为快照是用 `> file 2>&1` 生成的，前后两份带着同样的报错，diff 干净 ——
    于是「目录快照逐字节相同，460 行」这句话里既不含策略也不含约束。
    改法：三道检查并用 —— 查 psql 退出码、grep 输出里的 ERROR、查行数下限。
    第三道是为「整段静默消失」设的，前两道拦不住段落被 WHERE 过滤成空
```

> 共同形状：**验证手段自己失效时，表现出来的是「通过」。**
> 所以每写一个检查，要同时问「它坏掉的时候会红还是会绿」——
> 会绿的那些，必须再加一层专门检查它没坏（A0 之于派生，行数下限之于快照）。

## 十四、`eng/04` §二：五条断言认领的性质，换一种 PG 写法就漏报

十三那套双遍通过之后复核断言本身，发现的。**双遍全绿证不了覆盖完整** ——
破坏用例是照着每条断言的 `WHERE` 写出来的，所以必然落在它已经看得见的形状里。
换个问法「这个性质在 PG 里还有哪些实现方式」，五条全部漏。
都已在本地库实测，都已改掉，改在 `crates/db/src/audit/queries.sql`。

```text
一  A4 拿整个 indkey 做成员测试，INCLUDE 列混在里面
    CREATE UNIQUE INDEX ... ON keywords (word) INCLUDE (tenant_id)
    → indkey = "3 2"、indnatts = 2、indnkeyatts = 1
    tenant_id 在 indkey 里，旧断言判定合规放过；而 INCLUDE 列不参与唯一性，
    换租户插同一个 word 照样 duplicate key —— 侧信道原样开着（实测报错文本
    DETAIL: Key (word)=(secret-word) already exists）。
    改法：只取前 indnkeyatts 个键列。int2vector 转数组下界是 0（实测
    [0:1]={3,2}），所以切片是 [0:indnkeyatts-1]。
    顺带 indnatts→indnkeyatts 改了 identity 列那处判断
    已知误报（方向保守，接受）：表达式索引的 indkey 里是 0，没有列的 attnum 是 0，
    所以含 tenant_id 的表达式唯一索引会被报红

二  A6 只查 polroles = '{0}'，限定了角色的恒真策略不算
    CREATE POLICY probe_role_true ON tenant_members FOR SELECT TO app_user
    USING (true) —— polroles 是 {16386} 不是 {0}，旧断言不看。
    危害等同：attacker 租户读 tenant_members 的行数实测 0 → 1。
    改法：判据改成「PUBLIC 或 qual/withcheck 恒真」，并且逐策略报而不是逐表报
    覆盖边界（已知，不补）：PG 不规范化恒真表达式 —— 实测 USING (1=1) 存下来是
    (1 = 1)、USING (x IS NOT NULL OR x IS NULL) 原样保留。字面匹配只抓直白写法

三  A7 全用 has_table_privilege，看不见列级 GRANT
    GRANT SELECT (id) ON web_sessions TO app_user
    → has_table_privilege = false、has_any_column_privilege = true，
    而 app_user 的 SELECT id FROM web_sessions 真的执行成功（不是权限拒绝）。
    A4 白名单是靠 GRANT 换 RLS 的，补偿被列级授权掏空了旧断言察觉不到。
    改法：拆两支。SELECT/INSERT/UPDATE/REFERENCES 用 has_any_column_privilege
    （表级授权也让它为真，一支覆盖两种写法）；DELETE/TRUNCATE 没有列级形式，
    实测传进去直接报 ERROR: unrecognized privilege type: "DELETE"，只能问表级

四  物化视图两处 relkind 都不含 'm'，整类对象在断言视野外
    MAIN 查 ('r','p')、A8 查 'v'。实测：victim 租户写 keywords 一行，
    以 owner 建物化视图固化其内容，attacker 从基表读 0 行、从物化视图读 1 行。
    而物化视图**根本不支持 RLS**：ALTER TABLE probe_mv ENABLE ROW LEVEL SECURITY
    → ERROR: ... This operation is not supported for materialized views.
    所以没有「配齐三件套就合规」这条出路，判据只能是禁建 ——
    这是新断言 C4 与 A8 的性质差别，不是 A8 加个 relkind 就能合并的
    C4 不在 `eng/04` §二的编号里，同步时按新增处理（`queries.sql` 头部要求
    「改这里必须同步改那里」，mod.rs 的条数测试已从 14 改到 15）

五  A0 的派生只查 relacl 与 pg_policy，漏了 attacl
    CREATE ROLE probe_col LOGIN + GRANT UPDATE (tenant_id) ON identities
    → relacl 命中 0、pg_policy 命中 0、attacl 命中 1。整个角色从派生里落选，
    A1/A2a/A2b/C2 一条都不查它，而它 has_column_privilege(...tenant_id, UPDATE)
    = true —— 正是 C2 要拦的那件事。
    A0 也拦不住这种失效：它只管「派生为空」，管不了「不为空却缺人」。
    改法：派生查三处。后者没有第二道哨兵，是已知的覆盖边界
```

> 方法上的结论：**造破坏用例时不要照着断言的 `WHERE` 写。**
> 要先问「这个性质在 PG 里还有哪些实现方式」，逐个试。
> 上面五条全是同一个性质的另一种实现：INCLUDE 列、表达式索引、物化视图、
> 列级授权、限定角色的恒真策略。
> 相应地，`scripts/audit-double-pass.sh` 的破坏用例已改成打新形状 ——
> 旧的直白形状是新形状的子集，改后的断言对两者都报（逐条实测过）。

## 十六、`eng/04` §二：六处断言的形状在「换个 schema」「列序错位」下失效

动工前复核这套断言实现时发现的六处，已全部改完并在双遍里配了破坏用例。
共性是断言把「判据」和「它当时见过的那一种写法」写成了同一件事。

```text
A7  白名单反查索引→基表，把 relname 喂给 has_*_privilege
    裸名字走 search_path 解析。实测 has_any_column_privilege('app_user',
    'probe_nonexistent_t','SELECT') → ERROR: relation ... does not exist。
    别的 schema 里出现同名索引时，反查拿到它的基表名，而该表不在搜索路径里 →
    A7 整条崩掉。改法：反查限定 nspname='public' AND relkind='i'，
    且往下传 oid（regclass 重载）而不是 relname

A8  视图侧与函数侧都写死 nspname='public'
    等于「换个 schema 就绕过」。别的 schema 里的视图照样能读 public 的表，
    SECURITY DEFINER 更是与所在 schema 无关。
    改法：只有基表侧限定 public，另两侧改成排除 pg_*/information_schema。
    C4（物化视图）同一处病、同一处改法

A9  判据是「conkey 里含不含 tenant_id」
    conkey[i] 与 confkey[i] 按下标对应，只问「含不含」放得过错位写法：
    FOREIGN KEY (tenant_id, keyword_id) REFERENCES keywords (id, tenant_id)
    形式合规、实质仍可建跨租户边。
    改法：generate_subscripts 找同一个 i 上两侧都是 tenant_id。
    实测现有 10 条复合 FK 在新判据下全部对齐 —— 补覆盖缺口，不是修现存违规。
    顺带一条 PG 行为：被引用列按集合匹配不按顺序，所以上面那个错位 FK
    直接复用了现有的 uq_keywords_tenant_id (tenant_id, id)，不需要另建索引

C1  从目录出发查两个布尔标志
    三处漏报：表被删或改名 → `WHERE relname IN (...)` 零行即通过；
    策略数为 0 → FORCE + 零策略是默认拒绝，业务一行都读不到，
    而 MAIN 按「有 tenant_id 列」筛表，这两张表的特征恰恰是没有 tenant_id，
    所以谁都没在看它们的策略数；没有 nspname 过滤。
    改法：白名单断言必须从白名单一侧出发（VALUES LEFT JOIN），
    否则「要查的东西不存在」和「查过了没问题」在结果里长得一样

C5  runtime_role 派生只认直授（新增断言）
    五处同一份 CTE 都是 `a.grantee = r.oid`。权限经组角色继承时被授的是组的
    oid，登录角色本人在 relacl/attacl/polroles 三处都查不到 → 整个角色从派生
    落选，A1/A2a/A2b/C2 一条都不查它，而 A0 照样绿（派生非空，只是缺人）。
    直觉修法（把等值换成 pg_has_role）实测会把 postgres 拉进派生集 ——
    它经 GRANT tgm_owner TO postgres 继承，而它 rolsuper + rolbypassrls
    → A2a 在健康库上当场报红。再加 NOT rolsuper 排掉更坏：A2a 的全部职责
    就是抓「运行时角色被提成超级用户」，把超级用户排掉它就永远不会触发，
    从误报换成绿得毫无意义。
    改法换方向：不追认继承，而是禁掉「登录角色持有组成员身份」本身，
    让派生的前提由断言维持。豁免写成 postgres → tgm_owner 这**一对**
    而不是豁免 postgres 整个角色，这样以后给它加第二个组时会报红
```

一并修掉的一处执行器缺陷（`crates/db/src/audit/mod.rs`）：断言 SQL 自己报错那一支
原先是 `?` 直接抛出去，第一条报错会让它后面的断言一条都不执行，而进程退出码
仍是 1 —— 读者看到「红了」，看不到「另外 5 条根本没跑」。改成第三种状态
（`Outcome::error`）继续往下跑，`tgm audit-rls` 用 `ERR` 而不是 `FAIL` 打它，
并在汇总里单独计数。注入一条坏断言实测过：16 条全部执行，`ERR` 那条带出错文本，
退出码 1。

> 方法上的结论与十四那条同源，但补了一个新侧面：**断言的覆盖范围改了，
> 快照的覆盖范围要跟着改。** 这一轮为 A8 的新撤销（`DROP SCHEMA probe_ns CASCADE`）
> 补了 `NSP` 段并把 `FUN`/`MV` 两段的 `public` 限定去掉，为 C5 的新撤销补了
> `MBR` 段并把 `ROL` 段从「`rolcanlogin OR tgm%`」放宽成「非 `pg_` 开头」——
> 旧筛法漏掉的正是 C5 那个 NOLOGIN 组角色。
> 快照看不见的对象类型，针对它的撤销就无从验证，而 diff 会干净得很有说服力。

填存在的他租户 id 成功、填不存在的报 FK violation（两者可区分 = 枚举 oracle）；
建边之后 tenant 20 删自己的身份 900 报 `still referenced`（攻击者单方面钉住他租户的数据）。

的演示身份建源 → 403」—— 它覆盖的是**共享**身份，不覆盖**他租户私有**身份。

```text

```

所以准确状态是：要求写了、测试没有。

## 二十、我把「42 条」登记成过期数字，而它是对的

**已销账（2026-09-22），销的是我自己前一小时制造的错。**

写 `ADR-0022` 落地追记时，我在「代价一节被推翻的数字」里列了第四处：
「`eng/03` 的 42 条 → 实际 23 条」。依据是 grep `^| R` 数出 23 行。

```text
真相   42 = R1~R22(22) + A1~A9(9) + Q1~Q6(6) + X1~X5(5)
       R23 与 §3.1 分区那条，原文各写了一句「这条不进上面的 42」
错处   把编号的最大值当成了清单的长度，且漏掉 A/Q/X 三族
```

三处已回改：`ADR-0022` 追记节那一行改成「这一处没被推翻」并留下返工记录、
`decisions/README.md` 规则 6 的说明从「四处数字全不对」改成三处、
`eng/03` §八 那句「42 条里…16 条审计断言」改掉 —— **16 不是 42 的子集**，
是 A 族 9 席拆开后的条数，原文把两个数放进了同一个分母。

三件事值得记下来：

**一、这个错的形状是「看起来仍然合理」。** 数得出来、有依据，方向还符合
「文档里的数字通常偏旧」这个先验。本文件第四条早记过这个形状
（改坏的方式是日期看起来仍然合理，不会有任何检查报警），第十九条甚至
明写了「42 这个数字被七份文档硬编码引用」—— **我写下第十九条，然后照样
在第十二条的销账里把它当成过期数字。** 同一个文件里的前车之鉴防不住我。

**二、唯一的纠错手段是读被引用的原文。** `eng/03` §三 标题下第二行就是
「**不要在别处硬编码 42 这个数字** —— 它随设计变动，引用时说『§三 的清单』」。
那句话在场，我数编号时没读它。grep 出行数只能回答「有多少行」，
回答不了「这个数字指的是什么」。

**三、如果我按原判断动手，七处会一起变错。** 我当时的下一步正是
「分类处理那批 42 条残留：`docs/design/README.md` 与 `plan/00` 四处不受
规则 2 保护，直接改」—— 直接改就是把五处对的改成错的，且两处受保护的
ADR 反而因为改不动而保持正确。**保护规则在这一轮的作用是拦住了我，
而它拦住的是一次错误的批量修正，不是一次正确的。**

> 这条与 [[verification-fails-green]] 反向同形：那条说的是验证手段坏掉时
> 表现为「通过」；这条是**修正动作自己坏掉时表现为「改齐了」** ——
> 七处数字终于一致，而一致的是错的那个值。
> 判据：改任何一个跨文档引用的数字之前，先读它的定义处那一句，
> 不是数它的条目。

## 二十一、CI 首跑：注释里那句「所以不需要改 PATH」是错的

**已销账（2026-09-23）。** `ci.yml` 第一次在 GitHub 上跑
（`ci/verify-wp1` 开 PR 触发，`push` 只监听 `main`/`dev`）。
两次跑完：首跑 `static` 绿、`database` 红；修完第二次两个 job 全绿。

```text
首跑红处   R7 反证 —— pg_dump: server version: 17.11; pg_dump version: 16.15
真因       apt 装 postgresql-client-17 成功（17.11），但 runner 镜像自带
           client-16 占住 /usr/bin/pg_dump；装 17 只往
           /usr/lib/postgresql/17/bin/ 放文件，不动 /usr/bin
被推翻的   ci.yml 原注释：「/usr/bin/pg_dump 是 pg_wrapper，它选已装的
           最高版本，所以装完不需要改 PATH」
```

**这条注释的写法本身有问题：它是一句关于运行环境的断言，被写成了理由。**
写的时候没有 runner 可验，于是它既是设计依据又是未验假设，而读的人
（包括我）会把它当成前者。`eng/04` §八 那条局限已按实测改写。

修法两处，第二处才是重点：

```text
ci.yml       17 的 bin 写进 $GITHUB_PATH；版本从「打印」改成「断言」
             —— 只 pg_dump --version 的话版本不对也绿到下一步，
             真正的失败推迟到测试里，报错指向 backup.rs 而不是装机那步

backup.rs    pg_dump() 从「能起就用」改成「必须 17.x」
```

**后一处是防误绿。** 版本不匹配时 `pg_dump` 也会失败，而 R7 正向那条的判据
是「退出码非 0 且 stdout 没有业务数据」—— 版本不匹配恰好同时满足。
首跑只红了反证那条，**正向那条当时是绿的，而它的绿是假的**。
ci.yml 的注释预见到了这个形状（「若只有 R7 正向那条，版本不匹配会让它因为
错误的原因变绿」），但防线只写在注释里，没写进代码 ——
参照本文件第二条那句：一条只写在文档里的纪律，和一条不存在的纪律，
在仓库里长得一样。

验法：造一个只报 `16.15` 的假 `pg_dump` 放 PATH 最前、`HOME` 指向不存在的
目录（让 `env.sh` 那条兜底也失效），改后两条都红并列出三个候选各自的版本；
改前正向那条绿。

> **反证那条是这一轮唯一的报警器。** 它在 `eng/03` §三 的优先级清单里
> 属于「同批成本近零」那类，很容易被当成冗余删掉 ——
> 而如果没有它，这次 CI 会全绿，R7 会以「pg_dump 对谁都失败」的形态
> 一直绿着。**判据不是「测试通过」，是「测试失败时失败的原因是对的」。**

## 二十二、一条真缺陷，被无关探针撞出来（`ensure_rls` 与临时表）

**已修（2026-09-23），迁移 `0013`。** 记在这里不是为了销账 ——
它没登记过，从来不在任何清单里 —— 而是为了记下**它是怎么被发现的**。

```text
在做什么   想验 R11（同 update_id 重投三次 → 一次副作用）能不能纯 SQL 测。
           探针里写了一句 CREATE TEMP TABLE p(t bigint, b bigint) 存两个 id
撞到什么   ERROR: new row violates row-level security policy for table "p"
           —— p 是我刚建的临时表，它凭什么有 RLS 策略
真因       0012 的 ensure_rls 对 object_type='table' 一律 ENABLE + FORCE，
           临时表也在内。而临时表不可能有策略（0010 的策略含表名，
           临时表的名字是运行时才有的）。FORCE + 零策略 = 拒绝一切写入
实测       relrowsecurity=t、relforcerowsecurity=t、pg_policy 零行
影响面     tgm_owner 与 app_user 都中招；当前无代码用临时表（已 grep），
           所以是潜伏缺陷不是现行故障
```

**最值得记的不是这个 bug，是它为什么一直隐形。**

超级用户 bypass RLS，而迁移、`tgm audit-rls`、`audit-double-pass.sh`
**全都以 `postgres` 身份跑**。决定性的一步实测：把函数体回退成 0012 的形态，
临时表确实被打上 `forced=t`，而超级用户照样 `INSERT 0 1` 成功。
于是 12 个迁移全绿、16 条断言全绿、59 条测试全绿，**一条都碰不到它**。

> 这与 [[static-audit-passes-isolation-still-broken]] 里「`sqlx::test` 的
> 超级用户 pool 会旁路整个 RLS」是同一个根：**验证身份的权限高于被验证的
> 机制时，那个机制就不在验证范围内。**
> 那条记的是 pool 的层面，这条是**整套审计工具链**的层面 ——
> `tgm audit-rls` 查的是配置（`relrowsecurity` 等于什么），
> 而它查不到「这个配置在非超级用户身上意味着什么」。

R24 因此必须用 `app_user` 的池；用 `admin` 写这条测试会永远绿。
反向那半条（普通表仍须被开 FORCE）与它同在一条测试里，理由是
只验「临时表能写」的话，把 0013 放宽成「全部跳过」同样会绿 ——
而那恰好是 0012 要防的形状。两个方向各自验过能单独打红，报错指向不同真因。

登记在 `../design/eng/03-测试策略.md` §3.4，并明说**不进那 42 条**。
理由不是「清单漏了一条」，而是：

> **那份清单的推导方式覆盖不到这个形状。** 它从设计文档反推「哪些不变量要验」，
> 而这条缺陷不在任何设计里 —— 它是一条兜底机制的副作用。
> 同类的下一条只会以同样方式出现：被别的活动撞到，而不是被清单想到。
> 判据：**兜底机制（`ensure_rls` 这类「对所有 X 一律做 Y」的东西）要单独列出
> 它作用域里的意外成员**，因为它的作用域是按类型算的，而类型里总有你没想到的那个。
