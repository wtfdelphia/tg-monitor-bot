## 一、`spec/03` §4.2：`rule_versions` 的主键漏了 `tenant_id`（跨租户侧信道）

本文唯一一条已经改了代码的项 —— `migrations/0004_tables_rule.sql` 没有照抄，
偏离处写在该表的注释里。设计文档本身仍未改。

```text
现状   PRIMARY KEY (rule_id, version)
问题   破了铁律 1，且 eng/04 A4 会报红。实测确认不是误报 ——
       攻击者 tenant 1，受害 rule_id 1 属 tenant 2，以 app_user 带 app.tenant_id=1 插入：
         (1, 1,   tenant_id=1) → duplicate key ... "rule_versions_pkey"
         (1, 999, tenant_id=1) → FK violation "Key is not present in table rules"
         (999, 1, tenant_id=1) → 同上，与前一条不可分
         (2, 1,   tenant_id=1) → INSERT 0 1（自己的规则）
       前两种报错可分 = 一个可枚举的 oracle：探出他租户有哪些规则、各改了几版
影响   同表那道 FOREIGN KEY (tenant_id, rule_id) 拦不住它。
       唯一索引在堆插入期检查，外键是 AFTER 触发器 —— 唯一约束永远先报，
       复合外键这一层根本轮不到执行
改法   PRIMARY KEY (tenant_id, rule_id, version)
```

**为什么是漏列而不是破例**：同胞表 `rule_replacements` 与它同形（同样挂在 `rules`
下、同样的复合外键），PK 本来就是 `(tenant_id, rule_id, seq)`。而 spec/03 §7.1 说
`bot_console_sessions` 是全套设计里唯一允许违反铁律 1 的表，并明确
`不要为新表扩那个白名单` —— 两处一起看，只能是这里漏了一列。

补列不削弱唯一性：复合外键已把 `tenant_id` 钉死为 `rule_id` 对应的那一个值，
`(tenant_id, rule_id, version)` 与 `(rule_id, version)` 唯一性等价。
无下游影响 —— 全仓库无 `REFERENCES rule_versions`，`pg_constraint` 查引用为 0 条。
`delivery_tasks.rule_version` 是软引用，不是外键。

## 六、`eng/02` §三 与 §二、`spec/04` §3.1：迁移落地时补的三处

动工第 5 步写迁移时发现的，都不是错误，是文档没写到的必要细节：

```text
eng/02 §三   没提执行身份。迁移以 postgres 连库，不 SET ROLE tgm_owner 则 27 张表
             全归超级用户所有 —— 而超级用户不受 RLS 约束，FORCE 形同虚设。
             实测：owner=postgres 时 owner 自己 SELECT 看见 2 行；owner=tgm_owner 时
             看见 0 行且 INSERT 被拒。A2 只查 app_user，查不出这一种失效。
             配套代价：SET ROLE 持续到事务末尾，而 sqlx 记版本号的 INSERT 在同一事务里，
             每个文件必须以 RESET ROLE 收尾，否则报 permission denied for _sqlx_migrations
eng/02 §二   GRANT 矩阵完全没有序列。16 张表用 GENERATED ALWAYS AS IDENTITY，
             隐式序列不给 USAGE 则 INSERT 报 permission denied for sequence
spec/04 §3.1 给的 rls_auto_enable 片段没说执行身份。CREATE EVENT TRIGGER 要超级用户，
             tgm_owner 不行 —— 该文件必须在建函数后 RESET ROLE 再建触发器
```

第一条的形状值得单独记住：**owner 决定 FORCE 是真的还是装饰**，而静态断言看不见。

## 七、`eng/00` §二 没有 CLI 解析库，而 `eng/04` §四 要求 `tgm` 有子命令

动工第 6 步建骨架时发现的缺口。`eng/00` §二 自称是版本号的唯一定义处，
但清单里没有任何 CLI 解析库 —— 而 `eng/00` §一 列了 8 条 `tgm <subcommand>`，

```text

建议   eng/00 §二 补一条 CLI 段，否则「版本号唯一落点」这句话已经不成立
```

同批还有三个文档完全未提及的文件（`01-待建清单.md` §2.1 已预告），
它们的取值是决定，记在此处：

```text
rust-toolchain.toml  channel = "1.98.1"，不用 "stable"
                     理由：流水线是 clippy -- -D warnings，lint 集合随工具链变动，
                     不钉版本等于把卡口的严格程度交给工具链更新决定
rustfmt.toml         只有 edition = "2024"。实测 wrap_comments / comment_width 在
                     稳定版 rustfmt 1.9.0 上是 nightly-only，写了只会每次打
                     "unstable features are only available in nightly channel"
                     然后忽略 —— 在 fmt --check 输出里变成常驻噪音。
                     后果是长注释不受 max_width 约束，只能靠评审
clippy.toml          只放阈值（too-many-arguments-threshold = 8，因为 eng/00 §4.1
                     要求 TenantId 是每个 Repo 方法的第一个参数）。
                     lint 开关不在这个文件里 —— 走 Cargo.toml 的
                     [workspace.lints.clippy]，这个分工不明显
deny.toml            licenses 白名单从真实依赖图反推（194 个包全枚举），不抄模板。
                     刻意排除 LGPL-2.1-or-later（r-efi 的三选一之一）与
                     GPL/AGPL/SSPL/BUSL，理由写在文件里
```

`deny.toml` 有两处是实测才知道的：`unmaintained` 在 cargo-deny 0.20 不是 lint
级别而是取值范围 `["all","workspace","transitive","none"]`（选查哪一圈依赖，
不是查到了怎么办）；`cargo deny check licenses` 对本仓自己的 crate 与第三方
一视同仁，五个 crate 不写 `license` 就报五条 `error[unlicensed]` ——
用 `[workspace.package] license = "MIT"` 补真实值，没用 `private.ignore` 跳过。

## 八、`cargo sqlx prepare --check` 目前是一条空的绿灯

第 6 步的判据是「命令流水线在空项目上全绿」，五条都绿了。但其中两条的绿
不携带信息，写在这里免得被当成已验：

```text
cargo sqlx prepare --check   零个 query! 宏，.sqlx/ 目录根本没生成。
                             它在「没有任何编译期 SQL」时也返回 0。
                             另外它需要 DATABASE_URL —— 不设则退出码 1，
                             所以 CI 里这条必须在起库之后
tgm audit-rls / openapi      骨架实现，打 NOT IMPLEMENTED 到 stderr 后退出 0。
                             这是 02-动工顺序.md 第 6 步判据明确允许的
                             （「命令存在且退出 0，不是断言真验过了东西」），
                             但它正是 eng/04 §五 说的 false sense of security
```

**所以「流水线全绿」这个状态在第 7 步之前不携带信息。** 这与 `eng/04` §五
那条结论同源：审计通过 ≠ 隔离正确。第 7 步落地 `audit-rls` 之后，
`bins/tgm/src/main.rs` 里 `not_implemented()` 的调用点要同步减少。
