## 二、决定类：设计文档没有约定，动工时必须现做

### 2.1 三个工具链配置文件（全仓库与全文档均无提及）

```text
rustfmt.toml         未约定
clippy.toml          未约定
deny.toml            未约定
rust-toolchain.toml  未约定
```

前两个不写也能跑（用默认值），但 `../design/eng/04-CI门禁.md` 的流水线里有
`cargo clippy -- -D warnings`，默认 lint 集合等于把选择权交给 clippy 的版本变动 ——
升一次工具链就可能多出一批 error。

`deny.toml` 是真的必须写：`cargo deny check` 没有配置文件跑不出有意义的结论。
要定的是 licenses 白名单与 advisories 的处置级别，这是个决定，不是抄写。
考虑到 `../design/eng/00-工程约定.md` §二 已经钉死了全部依赖版本，
licenses 清单可以从现有依赖图反推，但**允许/拒绝哪些协议**仍要人定。

`rust-toolchain.toml` 缺失的后果是工具链版本不固定。本机是 1.98.1，
但没有任何文件声明这个下限，换机器或 CI 里可能拿到别的版本。

**已落地：四个文件都写了**（标题说「三个」，实际是四个 —— 上面代码块里就列了四行）。
四处决定，连同实现时才发现的约束：

```text
rustfmt.toml         只写偏离默认值的项，即 edition = "2024"。
                     wrap_comments / comment_width 刻意不加：实测在稳定版
                     rustfmt 1.9.0 上是 nightly-only，只会每次打一行
                     "unstable features are only available in nightly channel"
                     然后忽略 —— 在 cargo fmt --check 输出里变成常驻噪音。
                     代价写在文件里：长注释不受 max_width 约束，只能靠评审看
clippy.toml          only 放阈值参数。lint 的开关不在这里，在 workspace root 的
                     [workspace.lints.clippy] —— 这个分工不明显，写在文件里了。
                     唯一放宽项：too-many-arguments-threshold 7 → 8，
                     因为 eng/00 §4.1 要求 TenantId 是每个 Repo 方法的第一个参数，
                     按默认值会让那个纪律要求的形状被普遍误判成坏味道
deny.toml            licenses 白名单从真实依赖图反推（194 个包 cargo metadata 全枚举），
                     不抄通用模板 —— 模板的宽松清单等于预先批准还没进来的协议。
                     刻意不列入的四类（LGPL / GPL-AGPL / SSPL-BUSL-Elastic）
                     在文件里写了各自的理由，防止下次有人「顺手加上」。
                     bans 用 warn 而非 deny：194 个包里重复版本是常态，
                     一律 deny 会让卡口变成噪音源
rust-toolchain.toml  钉 1.98.1 而非 "stable"。理由正是本节开头那句 ——
                     不钉等于把卡口的严格程度交给工具链更新决定
```

> 一处与本节判断不同的事实：`clippy.toml` **不配 `msrv`**。
> 版本已经钉在 `rust-toolchain.toml`，两处写版本必然漂。

### 2.2 `0002_tables.sql` 的切分（G2 三处空白之一）

`../design/eng/02-本地环境与迁移.md` §三 把全部表放进 `0002_tables.sql` 一个文件，
而 ADR-0021 的结论是「每个迁移文件尽量只做一件事」，理由是
sqlx 的迁移器**按文件**记录版本，一个文件里多条语句时部分成功的状态是真实存在的。

所以要做的不是从零列清单，是**把 0002 拆开**。拆的依据是表之间的外键依赖顺序，
而 `../design/spec/03-数据模型.md` 的 DDL 是最终态视图，没有给这个顺序。

`../design/plan/00-里程碑与工期.md` G2 把它列为三处空白之一，另两处是
`AppError` → HTTP 状态映射表、tracing span 字段清单。

**已落地：拆成了 `0002`~`0007` 六个文件**，分组依据是本节说的外键依赖顺序
（租户 → 身份 → 规则 → 事件 → 投递 → 审计），每个文件内部也按依赖排。
表数与 `../design/spec/03-数据模型.md` 的声明一致 —— 数目在那份文档里，不抄进本目录（纪律 1）。

另两处空白（`AppError` 映射表、span 字段清单）**仍是空白**，它们在 G2 而不在动工第 0~7 步里。

### 2.3 RLS 语句：甲类没有一张写过

`../design/spec/03-数据模型.md` 的 RLS 部分给的是**模板加一个乙类样例**，不是逐表语句：

```text
带具体表名的 ENABLE / FORCE / POLICY    只有 rule_conditions 一张（乙类样例）
另一处 ENABLE / FORCE                   是 <表名> 占位模板
```

分类本身是齐的、自洽的（用该文档自带的 awk 复核过，甲乙丙三类数目对得上 §结尾声明的总表数），
但**甲类每一张的实际语句要动工时逐条写**，并且有若干处 GRANT 层差别要分别处理
（见 `../design/spec/03-数据模型.md` 的差别表：三张表要加 `TO auth_lookup` 的 SELECT 策略、
`identities` 要加共享身份策略、两张日志表要 `platform_ops`、
`tenant_consents` 只给 SELECT/INSERT、两张会话表要 `REVOKE ALL FROM app_user`）。

写的时候有一条纪律容易漏：**任何附加的 PERMISSIVE 策略必须限定 `TO <role>`**，
否则 PERMISSIVE 之间的 OR 语义直接作废租户策略。这条在
`../design/spec/03-数据模型.md` 里已写明，但它是那种「写错了测试照样过」的错误。

乙类两张（`rule_conditions` / `delivery_logs`）用 EXISTS 策略，
性能已实测不成问题（PG 17 优化成 hashed SubPlan 只执行一次），
**前提是父表 `tenant_id` 上有索引** —— 建索引时不要漏掉这个前提。

**已落地：`0009` ENABLE+FORCE、`0010` 策略、`0011` GRANT，三个文件。**
`0009` 与 `0010` 分开是安全要求，不是风格：实测**策略能存在于一张 RLS 已关闭的表上
并被完全忽略**（`DISABLE` 后 `relrowsecurity=f`，而 `pg_policy` 仍有记录）。
分开之后审计才能分别验证「开了」和「有策略」两件事。

本节那条容易漏的纪律（附加 PERMISSIVE 策略必须限定 `TO <role>`）在实现时**升级成了断言**：
`A6` 现在逐条查恒真或未限定角色的 PERMISSIVE 策略。原来的写法漏报 ——
它按 `polroles = '{0}'` 判 PUBLIC，而限定了角色的策略 `polroles` 是 `{16386}`，
恒真 qual 一声不响就过了（`03-文档待更正.md` 十六）。

> 一处与本节「差别表」不同的实测结果：`identities` 那一格按 `eng/02` §二 字面照写会让断言报红。
> **列级 `REVOKE` 减不掉表级 `GRANT`** —— 顺序必须是先 `REVOKE` 表级再逐列 `GRANT`。
> 这正是断言 `C2` 存在的理由：写反了不报错，权限照旧（`03-文档待更正.md` 十一）。

### 2.4 `audit-rls` 的两处已认领欠账

`../design/eng/04-CI门禁.md` §局限 自己记了断言覆盖不全：

```text
A2 只查 app_user 一个角色     四个角色里 auth_lookup 与 platform_ops 没覆盖
A7 只查 bot_console_sessions  而 A4 白名单还有别的项
```

A1~A9 全部是查 `pg_class` / `pg_policy` / `pg_constraint` 的目录查询，
**全部需要一个已迁移的活库** —— 没有一条能在空项目上跑。
所以「流水线在空项目上全绿」这个 G2 判据里，`audit-rls` 那条的含义是
命令存在且退出码为 0，不是断言真的验过了东西。

实现时 ADR-0022 的双遍要求照旧：CI 跑两遍，第二遍在
`ALTER TABLE ... DISABLE ROW LEVEL SECURITY` 之后，**第二遍必须是红的**。
理由是 `USING (true)` 能通过 A1~A9 全部断言 —— 静态审计全绿不证明隔离成立。

**已落地：两处欠账都还清了，而且改的是形状不是范围。**

```text
A2  不再写角色名。改成从目录派生「运行时角色集合」：登录角色，且在 public 的表上
    持有任何直授权限或被任何策略点名。换来的性质是将来加第四个运行时角色断言自动覆盖。
    代价是多了两条元断言 —— A0 管派生算成空集，C5 管派生「不为空却缺人」
A7  不再写表名。白名单写成索引名的 VALUES 列表，表名由索引名反查 pg_index 得到。
    换来的性质是 A4 的排除项与 A7 的补偿检查不可能各自漂移
```

上面那个代码块里「A4 白名单还有别的项」原本写的是具体项数 —— 改掉了，它违反纪律 1。
而且那个数已经变了：实现时实测确认其中一项的破例论证不成立，白名单减了一项
（`03-文档待更正.md` 十）。**「已论证」也可能是错的论证**，所以白名单只能减不能加。

`audit-rls` 现已在真实的 27 张表上跑过，全绿 —— 也就是说上面那句
「不是断言真的验过了东西」对当前状态不再成立。但 G2 判据本身没变。

双遍要求的**判据被换成了更严的形式**，理由是原判据有漏洞：
「第二遍至少有一条红」和「第二遍每条断言各自可被打红」在 CI 日志里长得一样，
而后者才是 ADR-0022 要的东西。现在的实现是 `scripts/audit-double-pass.sh`：
逐条破坏后恰好那一条红，且撤销后一份库状态快照必须逐字节相同
（见 `03-文档待更正.md` 十二、十三 —— 十三记的是写这个脚本时两次「验证本身是假的」）。
