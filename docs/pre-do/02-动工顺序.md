# 动工顺序

八步。每步一个判据，判据不满足就不进下一步。

前四步（0~3）互不依赖，都是分钟级，可以一次做完。
第 4 步起有严格顺序依赖。

> **八步已全部走完**（2026-09-22），每步的判据结果附在该步末尾。
> 有两步的**判据本身在执行中被换掉了**，都是因为原判据能被一个坏实现满足：
> 第 5 步（可重入）与第 7 步（双遍）。换判据的理由写在各步里 ——
> 这两处比「做完了」更值得读。

## 4 · 写 compose.yaml 与角色初始化脚本，起库

```text
做什么   照抄 ../design/eng/02-本地环境与迁移.md §一 与 §二
判据     以 app_user 连上后，current_setting('app.tenant_id') 报错
         —— 必须是报错（fail-loud），不是返回空串
```

判据为什么是「报错」而不是「连上就算成功」：空串会让 RLS 策略静默匹配零行，
把一个配置错误伪装成「查不到数据」。要的是启动就炸。

这一步同时验两条硬要求：PgBouncer 的 `pool_mode = transaction` 与
`server_reset_query_always = 1`。后者是安全配置不是调优 ——
不开会导致会话变量跨请求泄漏到别的租户。

**已完成** —— `compose.yaml` 与 `scripts/init/01-roles.sql` 已提交，库起得来，
`app_user` 连上后 `current_setting('app.tenant_id')` 报错（fail-loud）。

> 一处抄写时才发现的约束：`scripts/init/01-roles.sql` 建的 `tgm_owner` 是 **NOLOGIN**，
> 所以 `eng/01` §一 的 `TGM_DB_URL_OWNER` 不能按字面写成 `tgm_owner`，
> 要用 `postgres` 连（它经 `GRANT tgm_owner TO postgres` 继承 owner 身份）。
> `03-文档待更正.md` 十五 登记了这条。

## 5 · 切开 0002，写完全部迁移文件

```text
做什么   先定 0002 的切分（见 01-待建清单.md §2.2），其余各文件按
         ../design/eng/02-本地环境与迁移.md §三 照写
判据     迁移连跑两遍等价 —— 即可重入
```

顺序上有三条不能动，全是安全要求：

```text
0003 seed 必须在 0004 FORCE 之前     否则 owner 执行 seed 也被策略拦
0004 与 0005 必须分开                 策略能存在于 RLS 已关闭的表上并被完全忽略
不写 down 迁移                        代价就是迁移必须可重入
```

第一条已实测，报错是 `new row violates row-level security policy`，
执行者是 owner、策略写的是 `TO app_user`，照样被拦 —— 报错文本里没有任何线索指向执行顺序。

可重入的具体要求：DDL 用 `CREATE TABLE IF NOT EXISTS`，seed 用 `ON CONFLICT DO NOTHING`。

**已完成** —— `0002`~`0007` 六个文件（切分依据见 `01-待建清单.md` §2.2），
`0008` seed、`0009` ENABLE+FORCE、`0010` 策略、`0011` GRANT、`0012` 事件触发器。
上面那三条顺序要求全部满足（文件号变了，约束没变：seed `0008` 在 FORCE `0009` 之前，
ENABLE/FORCE 与策略分成 `0009`/`0010` 两个文件）。

**判据被换掉了。** 「连跑两遍等价」这个说法拦不住一类坏实现：
第二遍**因为报错而没改变任何东西**，也满足「等价」。所以实际用的判据是
连跑两遍且第二遍**退出码为 0**，再加一次目录状态比对。
实现里三处非平凡的可重入写法：

```text
CREATE POLICY   PG 没有 IF NOT EXISTS，故用 DROP POLICY IF EXISTS + CREATE
每个 DDL 文件   要 SET ROLE tgm_owner 起头、RESET ROLE 收尾。少了前者，
                表的 owner 是 postgres，而 owner 决定 FORCE 是真的还是装饰；
                少了后者，sqlx 记版本号那条 INSERT 会
                permission denied for table _sqlx_migrations（已实测）
0008 seed       当前**没有任何 INSERT**。不是漏写 —— 全套设计文档里没有定义种子行，
                唯一候选（演示身份）需要一份 Bot token，而 token 是凭据不能进仓库。
                文件保留是为了占住这个序号位置，将来有种子行必须落在 FORCE 之前
```

## 7 · 补齐 audit-rls 覆盖并跑双遍

```text
做什么   补 A2 的另两个角色、A7 的另两张白名单表（见 01-待建清单.md §2.4）
         按 ADR-0022 跑双遍
判据     DISABLE RLS 之后第二遍必须红
```

第二遍不红说明断言本身是坏的。`USING (true)` 能通过 A1~A9 全部断言 ——
所以「全绿」这个状态本身不携带信息，双遍的差值才携带信息。

**已完成，但做法与「补覆盖」不同：两处都改成了从目录派生，不再写角色名与表名**
（见 `01-待建清单.md` §2.4 —— 换来的性质是将来加角色/加白名单项时断言自动跟上）。
实现落在 `crates/db/src/audit/`（`queries.sql` 是断言全文，`mod.rs` 切分并执行）。

**判据被换成更严的形式，原判据有漏洞：**

```text
原判据  「DISABLE RLS 之后第二遍必须红」
        漏洞是「至少有一条红」和「每条断言各自可被打红」在 CI 日志里长得一样,
        而后者才是 ADR-0022「断言替代第二人复核」要排除的情形 ——
        一条断言写成永不触发，靠别人的红色掩护着,不会被发现
现判据  逐条破坏后**恰好那一条**红，撤销后一份库状态快照**逐字节相同**
        实现是 scripts/audit-double-pass.sh
```

第二个条件（快照）是因为第一版脚本的收尾检查本身是假的：它用「破坏全部撤销后
`audit-rls` 仍返回 0」收尾，而实测 `ALTER TABLE ... OWNER TO app_user` 会把
`app_user` 的受赠 ACL 条目并进 owner 条目、改回时**不还原** ——
`app_user` 在那张表上的权限就此消失，而审计照样全绿。
根因是这套断言只查「不该有的权限」，没有一条查「该有的权限还在不在」：
**一个 `app_user` 什么都碰不到的库，在全部断言下完全合规。**
`03-文档待更正.md` 十三 记了这个和另一个同类失效。

覆盖也在这一步补了几条原文没有的断言（`A0` 派生非空、`C4` 禁物化视图、
`C5` 禁登录角色的组成员身份），并改掉了六处「换个 schema / 列序错位就漏报」的形状。
逐条记在 `03-文档待更正.md` 十四、十六，`../design/eng/04-CI门禁.md` 已按实现更新。

```text
  测试规格本身是待验证物，G2 的要求是逐条标注实测状态，不是先全跑通

MigrateTo 账号素材未确认
  非默认 DC 的账号从 W1 开始准备，G1 时若仍无 → 记为 RK-01 未验证，
  不阻塞 G1，但须在 G4 前补验

数据出境口径
  已转入 ../design/plan/01-风险登记.md 的 RK-18，监控关口 G6，不阻塞首发

司法辖区
  已定案（ADR-0028 欧盟），其唯一技术下游定为不留存（ADR-0029），零 DDL 变更
  —— 所以它不再卡在 27 表迁移之前
```

有一条是真的硬前置，不在上面的清单里：**第一行业务代码之前必须有一个连得上、
且已配好 RLS 的库**。因为 `cargo sqlx prepare --check` 要求它。
这就是 `../design/plan/00-里程碑与工期.md` 把「骨架」和「数据层」合并成一个工作包的原因 ——
这两件事不能串行。也就是上面第 4、5 步必须在第 6 步的业务代码之前。
