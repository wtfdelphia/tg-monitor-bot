# 动工顺序

八步。每步一个判据，判据不满足就不进下一步。

前四步（0~3）互不依赖，都是分钟级，可以一次做完。
第 4 步起有严格顺序依赖。

---

## 0 · 装 docker compose 插件

```text
做什么   apt 安装 docker-compose-v2（不是 docker-compose，那是已停维护的 v1）
判据     docker compose version 有输出
为什么在第一步  第 4 步之后全部依赖它，且它是迁移失败时的唯一恢复方式
```

详见 `00-环境前置.md` §一。

## 3 · 换 .gitignore 为 Rust 模板

```text
做什么   当前是 Python 模板，换成 ../design/eng/00-工程约定.md §6.2 列的条目
判据     git check-ignore -v Cargo.lock .sqlx/ 均无命中
为什么要单独验  这两样都必须入库：Cargo.lock 因为 eng/00 §二 钉死了版本，
         .sqlx/ 因为 cargo sqlx prepare --check 靠它做离线校验。
         通用 Rust 模板不会替你留意这两条，而 §6.2 已经写成注释提醒过
顺带     §6.2 提到 target/ 当前是被 Python 模板里 PyBuilder 那节巧合覆盖的，
         换模板时要显式写 /target，不要继续依赖巧合
```

这一步也是 `../design/plan/00-里程碑与工期.md` G2 的一条判据。

## 4 · 写 compose.yaml 与角色初始化脚本，起库

```text
做什么   照抄 ../design/eng/02-本地环境与迁移.md §一 与 §二
判据     以 app_user 连上后，current_setting('app.tenant_id') 报错
         —— 必须是报错（fail-loud），不是返回空串
```

判据为什么是「报错」而不是「连上就算成功」：空串会让 RLS 策略静默匹配零行，
把一个配置错误伪装成「查不到数据」。要的是启动就炸。

这一步同时验两条硬要求：PgBouncer 的 `pool_mode = transaction` 与
`server_reset_query_always = 1`。后者是安全配置不是调优 ——
不开会导致会话变量跨请求泄漏到别的租户。

## 5 · 切开 0002，写完全部迁移文件

```text
做什么   先定 0002 的切分（见 01-待建清单.md §2.2），其余各文件按
         ../design/eng/02-本地环境与迁移.md §三 照写
判据     迁移连跑两遍等价 —— 即可重入
```

顺序上有三条不能动，全是安全要求：

```text
0003 seed 必须在 0004 FORCE 之前     否则 owner 执行 seed 也被策略拦
0004 与 0005 必须分开                 策略能存在于 RLS 已关闭的表上并被完全忽略
不写 down 迁移                        代价就是迁移必须可重入
```

第一条已实测，报错是 `new row violates row-level security policy`，
执行者是 owner、策略写的是 `TO app_user`，照样被拦 —— 报错文本里没有任何线索指向执行顺序。

可重入的具体要求：DDL 用 `CREATE TABLE IF NOT EXISTS`，seed 用 `ON CONFLICT DO NOTHING`。

## 6 · 建 workspace 骨架与三个工具链配置

```text
做什么   照 ../design/eng/00-工程约定.md §一 的树建 crate 与 bins/tgm
         同时写 rustfmt.toml / clippy.toml / deny.toml
判据     命令流水线在空项目上全绿（清单见 ../design/eng/04-CI门禁.md）
```

三个配置文件必须和骨架同批做，否则流水线里的 clippy 与 deny 两条跑不起来 ——
`deny.toml` 的 licenses 白名单是个决定，见 `01-待建清单.md` §2.1。

注意「空项目全绿」里 `audit-rls` 那条的含义是命令存在且退出 0，
不是断言真验过了东西 —— A1~A9 全部需要活库。

## 7 · 补齐 audit-rls 覆盖并跑双遍

```text
做什么   补 A2 的另两个角色、A7 的另两张白名单表（见 01-待建清单.md §2.4）
         按 ADR-0022 跑双遍
判据     DISABLE RLS 之后第二遍必须红
```

第二遍不红说明断言本身是坏的。`USING (true)` 能通过 A1~A9 全部断言 ——
所以「全绿」这个状态本身不携带信息，双遍的差值才携带信息。

## 不阻塞动工的那些事

容易被误当成前置，实际不卡第一行代码：

```text
四项 spike（grammers 连通 / QR 全分支 / 租约原型 / 媒体中转）
  卡 ../design/plan/00-里程碑与工期.md 的 G1 与 WP-2，不卡 WP-1。
  骨架与数据层可以立刻开始

反向测试清单里只有少部分实测过（比例见 ../design/eng/03-测试策略.md §八）
  测试规格本身是待验证物，G2 的要求是逐条标注实测状态，不是先全跑通

MigrateTo 账号素材未确认
  非默认 DC 的账号从 W1 开始准备，G1 时若仍无 → 记为 RK-01 未验证，
  不阻塞 G1，但须在 G4 前补验

数据出境口径
  已转入 ../design/plan/01-风险登记.md 的 RK-18，监控关口 G6，不阻塞首发

司法辖区
  已定案（ADR-0028 欧盟），其唯一技术下游定为不留存（ADR-0029），零 DDL 变更
  —— 所以它不再卡在 27 表迁移之前
```

有一条是真的硬前置，不在上面的清单里：**第一行业务代码之前必须有一个连得上、
且已配好 RLS 的库**。因为 `cargo sqlx prepare --check` 要求它。
这就是 `../design/plan/00-里程碑与工期.md` 把「骨架」和「数据层」合并成一个工作包的原因 ——
这两件事不能串行。也就是上面第 4、5 步必须在第 6 步的业务代码之前。
